DARS 33 · MODUL D — FOYDALANUVCHI VA HUQUQLAR

Gate va Policy: «bu yozuv kimniki?»

32-darsda middleware «kirganmi?» degan savolga javob berdi. Lekin hozir kirgan har qanday odam istalgan vakansiyani o'chira oladi. Bugun vakansiyaga egasi qo'shamiz va Laravel'ning huquq tekshirish mexanizmini o'rganamiz — 403 javobi bilan birga.

📱 O'qish ≈ 16 daqiqa 💻 Amaliyot ≈ 26 daqiqa Kerak: Dars 32

Bu darsda nimalar bor
  1. Nega middleware yetmaydi Middleware route darajasida ishlaydi; savol esa aniq yozuv haqida: «shu vakansiya shu odamnikimi?»
  2. Vakansiyaga egasi Migration bilan user_id ustuni va egasi() bog'lanishi. ⚠️ 26-darsdagi tuzoq qaytadi.
  3. make:policy --model= Yasalgan skelet: viewAny · view · create · update · delete. Hammasi false qaytaradi.
  4. Policy avtomatik topiladi Models\Vakansiya → Policies\VakansiyaPolicy. O'zbekcha nomda ham ishlaydi — ko'plik yasalmaydi.
  5. ⚠️ AuthorizesRequests trait'i Laravel 11+ da bazaviy Controller bo'sh — $this->authorize() ishlamaydi. Aniq xato va bir qatorli yechim.
  6. authorize() → 403 Ruxsat bo'lmasa 403 Forbidden. Egasi uchun esa oddiy 302. O'lchandi.
  7. @can Blade direktivasi Tugmani faqat huquqi borga ko'rsatish. 🔒 Lekin yashirish himoya emas — uchinchi marta.
  8. can: middleware Controllerda kod yozmasdan route darajasida tekshirish: 'can:delete,vakansiya'.
  9. Gate::define va Gate::before Modelsiz oddiy qoidalar va «hamma narsaga ruxsat» beruvchi ustun qoida (superuser).
  10. Har xil holatlar (7 ta) Metod yo'qligi · mehmon holati · Response::deny bilan sabab · inspect() · can va cannot · policy'ni qo'lda bog'lash · 403 sahifasini o'zgartirish.
Nega middleware yetmaydi

middleware('auth') bitta savolga javob beradi: «kirganmi?» Bu route darajasidagi savol — u hamma so'rov uchun bir xil.

Lekin haqiqiy savol boshqacha: «shu vakansiyani shu odam o'chira oladimi?» Javob aniq yozuvga bog'liq — birida «ha», boshqasida «yo'q».

middleware: «kirganmi?» → route darajasida policy: «bu yozuv seniki-mi?» → yozuv darajasida

Bu farqni bilmaslik jiddiy zaiflik keltiradi: hozirgi IshTop'da kirgan har qanday odam boshqa odamning e'lonini o'chira oladi. Real saytda bu bir kunda seziladi.

Avval — vakansiyaga egasi kerak

«Kimniki?» degan savolga javob berish uchun jadvalda egasi bo'lishi kerak. 23-darsdagi migration mexanizmi bilan qo'shamiz:

database/migrations/…_add_user_id_to_vakansiyalar_table.php
public function up(): void { Schema::table('vakansiyalar', function (Blueprint $table) { $table->foreignId('user_id')->nullable()->constrained()->nullOnDelete(); }); } public function down(): void { Schema::table('vakansiyalar', function (Blueprint $table) { $table->dropForeign(['user_id']); $table->dropColumn('user_id'); }); }
QismNima uchun
foreignId('user_id')->constrained()Tashqi kalit (23-dars). Jadval nomi users deb taxmin qilinadi — inglizcha nom, shuning uchun to'g'ri chiqadi
->nullable()Eski vakansiyalarda egasi yo'q — NULL ruxsat
->nullOnDelete()🆕 Foydalanuvchi o'chsa, vakansiya qolsin, faqat egasi NULL bo'lsin (27-darsdagi cascadeOnDelete ning yumshoq varianti)
🔍 SQLite'da ALTER TABLE qanday bajariladi

migrate --pretend qiziq narsa ko'rsatadi:

⇂ drop table "vakansiyalar" ⇂ alter table "__temp__vakansiyalar" rename to "vakansiyalar"

SQLite tashqi kalit qo'shishni bilmaydi, shuning uchun Laravel vaqtinchalik jadval yasab, ma'lumotni ko'chirib, eskisini o'chiradi va yangisini o'sha nom bilan qayta nomlaydi. MySQL'da bu oddiy ALTER TABLE bo'lardi.

Amaliy xulosa: migration bir xil kod, lekin baza uni o'zicha bajaradi — 23-darsdagi «bir xil kod turli bazalarda ishlaydi» va'dasining ichki tomoni.

app/Models/Vakansiya.php
protected $fillable = ['nom', 'maosh', 'shahar', 'faol', 'kompaniya_id', 'user_id']; public function egasi(): BelongsTo { return $this->belongsTo(User::class, 'user_id'); }
⚠️ Ikkinchi argument — 26-darsdagi tuzoq qaytdi

Metod nomi egasi(), ustun esa user_id. Laravel tashqi kalitni metod nomidan taxmin qiladi (26-dars):

belongsTo(User::class) ikkinchi argumentsiz: taxmin qilingan ustun: egasi_id natija: NULL ← jimgina, xatosiz

Shuning uchun 'user_id' ni aniq yozamiz. Bu — 26-darsdagi HOLAT 2 ning amaliy takrori, va u aynan shunday joyda uchraydi: metodga ma'noli o'zbekcha nom berganingizda.

Policy — bitta model uchun qoidalar to'plami

terminal
php artisan make:policy VakansiyaPolicy --model=Vakansiya

Yasalgan fayl beshta metod bilan keladi va hammasi false qaytaradi:

public function viewAny(User $user): bool { return false; } public function view(User $user, Vakansiya $v): bool { return false; } public function create(User $user): bool { return false; } public function update(User $user, Vakansiya $v): bool { return false; } public function delete(User $user, Vakansiya $v): bool { return false; }

Diqqat qiling: metodlarning ikki xil shakli bor:

ShaklQachon
update(User $user, Vakansiya $v)Aniq yozuv haqida: «shu vakansiyani?»
create(User $user)Yozuv hali yo'q: «umuman yaratishi mumkinmi?»

Bizga hozir ikkitasi yetadi:

app/Policies/VakansiyaPolicy.php
class VakansiyaPolicy { public function update(User $user, Vakansiya $vakansiya): bool { return $vakansiya->user_id === $user->id; } public function delete(User $user, Vakansiya $vakansiya): bool { return $vakansiya->user_id === $user->id; } }

Butun qoida shu bitta solishtirishda. Va === ishlatilgani ham bejiz emas — 3-darsdagi qat'iy solishtirish.

Policy avtomatik topiladi

Hech qayerda ro'yxatdan o'tkazmadik, lekin Laravel uni topadi:

Gate::getPolicyFor(Vakansiya::class) → App\Policies\VakansiyaPolicy

Qoida: App\Models\X → App\Policies\XPolicy. 🎯 Va bu safar o'zbekcha nom muammo bermaydi — chunki bu yerda ko'plik yasalmaydi, shunchaki Policy qo'shiladi.

Kerak bo'lsa qo'lda ham bog'lash mumkin (pastda HOLAT 6).

Controllerda: authorize()

app/Http/Controllers/VakansiyaController.php
public function ochirish(Vakansiya $vakansiya): RedirectResponse { $this->authorize('delete', $vakansiya); $vakansiya->delete(); return redirect()->route('vakansiyalar.index') ->with('xabar', 'Vakansiya o\'chirildi.'); }

Bitta qator. Ruxsat bo'lsa — kod davom etadi; bo'lmasa — 403 otiladi va keyingi qatorlar umuman ishlamaydi (20-darsdagi validate() bilan bir xil naqsh).

⚠️ Birinchi to'siq: AuthorizesRequests trait'i

Laravel 11 dan beri bazaviy controller bo'sh:

// app/Http/Controllers/Controller.php abstract class Controller { // }

Shuning uchun $this->authorize() yozsangiz:

BadMethodCallException Call to undefined method App\Http\Controllers\VakansiyaController::authorize()

✅ Yechim — bazaviy controllerga bitta trait (10-dars):

use Illuminate\Foundation\Auth\Access\AuthorizesRequests; abstract class Controller { use AuthorizesRequests; }

Bu 28-darsdagi HasFactory bilan bir xil holat: hujjatlardagi misollar «ishlaydi», chunki ular eski Laravel'ga yoki starter kit'ga mo'ljallangan.

Natija — o'lchangan

Vali (begona) o'chirmoqchi: 403 Ali (egasi) o'chiradi: 302 → /vakansiyalar xabar: Vakansiya o'chirildi.

403 Forbidden — «kimligingni bilaman, lekin bunga huquqing yo'q». Buni 404 yoki 302 bilan aralashtirmaslik kerak:

StatusMa'nosi
401 / 302 → login«Kim ekaningni bilmayman» — auth middleware
403 Forbidden«Bilaman, lekin huquqing yo'q» — policy
404 Not Found«Bunday yozuv yo'q» — 24-dars

Blade'da: @can

resources/views/vakansiyalar/show.blade.php
@can('delete', $v) <form method="POST" action="{{ route('vakansiyalar.ochirish', $v->id) }}"> @csrf @method('DELETE') <button type="submit">Vakansiyani o'chirish</button> </form> @endcan
Ali (egasi): tugma ko'rinadi ✅ Vali (begona): tugma YO'Q ✅

@method('DELETE') — 19-darsdagi method spoofing: HTML forma faqat GET va POST ni biladi.

🔒 Uchinchi marta: yashirish — himoya emas

Bu qoidani 30-darsda (@auth) va 32-darsda (middleware) ham aytgandik. Endi uchinchi shaklda:

@can → tugmani YASHIRADI (ko'rinish) $this->authorize() → so'rovni TO'XTATADI (himoya)

Tugma ko'rinmasa ham, so'rovni qo'lda yuborish mumkin — biz buni sinab ko'rdik va 403 oldik. Ya'ni ikkalasi ham kerak: biri foydalanuvchi uchun, ikkinchisi xavfsizlik uchun.

Muqobil: can: middleware

Controllerda kod yozmasdan ham bo'ladi — 32-darsdagi middleware shaklida:

routes/web.php
Route::delete('/vakansiyalar/{vakansiya}', [VakansiyaController::class, 'ochirish']) ->name('vakansiyalar.ochirish') ->middleware(['auth', 'can:delete,vakansiya']);
Begona odam o'chirmoqchi → 403 (controllerda hech qanday kod yo'q)

Ikkinchi qism — vakansiya — route parametrining nomi (24-dars). Laravel undan modelni topadi va policy'ga uzatadi.

Qaysi birini tanlash? authorize() — controllerda, chunki u ko'rinadi: kodni o'qigan odam tekshiruv borligini darhol biladi. can: middleware — route fayli o'qilganda ko'rinadi. Kursda authorize() ni ishlatamiz.

Gate::define — modelsiz qoidalar

Ba'zi qoidalar hech qanday modelga bog'liq emas: «hisobotni ko'rish», «sozlamalarni o'zgartirish». Ular uchun policy og'irlik qiladi — Gate::define yetadi:

app/Providers/AppServiceProvider.php — boot()
Gate::define('hisobot-korish', function (User $user) { return str_ends_with($user->email, '@example.uz'); });
Gate::forUser($ali)->allows('hisobot-korish') → true Gate::forUser($begona)->allows('hisobot-korish') → false Blade'da: @can('hisobot-korish') ... @endcan

Ishlatilishi bir xil: @can, authorize(), can: — hammasi ham gate, ham policy bilan ishlaydi.

Gate::before — ustun qoida

AppServiceProvider — boot()
Gate::before(function (User $user, string $qobiliyat) { return $user->email === 'admin@example.uz' ? true : null; });

U har tekshiruvdan oldin ishlaydi:

QaytarganiNatija
trueRuxsat — policy umuman so'ralmaydi
falseTaqiq — policy so'ralmaydi
null«Menda gap yo'q» — policy o'z ishini qiladi

O'lchandi: Gate::before yoqilganda begona odam ham boshqaning vakansiyasini o'zgartira oldi — chunki true policy'ni chetlab o'tdi.

⚠️ Shuning uchun null qaytarish muhim: false yozib qo'ysangiz, hech kim hech narsa qila olmaydi.

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Policy'da metod yo'q bo'lsa

// VakansiyaPolicy da faqat update va delete bor Gate::forUser($ali)->allows('view', $v) → false

Xato otilmaydi — shunchaki taqiq. Bu xavfsiz standart («ruxsat berilmagan narsa taqiqlangan»), lekin chalkashtirishi mumkin: «nega tugma ko'rinmayapti?» degan savolning javobi ba'zan «policy'da o'sha metod yo'q».

✅ Tekshirish: policy faylini ochib, metod nomi aynan to'g'ri yozilganini ko'ring (delete, o'chirish emas).

HOLAT 2

Mehmon (kirmagan odam)

Policy metodi User $user talab qiladi. Mehmon uchun null keladi va Laravel tekshiruvni taqiq deb hisoblaydi — policy chaqirilmaydi ham.

Agar mehmonga ham ruxsat kerak bo'lsa (masalan ochiq yozuvni ko'rish), tipni ixtiyoriy qiling:

public function view(?User $user, Vakansiya $vakansiya): bool { return $vakansiya->faol || $vakansiya->user_id === $user?->id; }

?User va $user?->id — 26-darsdagi nullsafe operator shu yerda ish beradi.

HOLAT 3

Taqiq sababini aytish — Response::deny

use Illuminate\Auth\Access\Response; public function delete(User $user, Vakansiya $vakansiya): Response { return $vakansiya->user_id === $user->id ? Response::allow() : Response::deny('Faqat e\'lon egasi o\'chira oladi.'); }

bool o'rniga Response qaytarsangiz, 403 sahifasida sizning xabaringiz ko'rinadi. Foydalanuvchi uchun ancha tushunarli.

⚠️ Lekin ehtiyot bo'ling: sabab ba'zan ma'lumot sizdiradi (30-darsdagi «umumiy xabar» qoidasi). «Bu yozuv boshqa foydalanuvchiniki» deyish odatda xavfsiz; «Ali Valiyevniki» deyish — yo'q.

HOLAT 4

Tekshirishning barcha shakllari

// Controllerda $this->authorize('delete', $vakansiya); // ruxsat bo'lmasa 403 // Shart sifatida if ($request->user()->can('delete', $vakansiya)) { ... } if ($request->user()->cannot('delete', $vakansiya)) { ... } // Gate fasadi orqali (skriptda, testda) Gate::allows('delete', $vakansiya); Gate::denies('delete', $vakansiya); Gate::forUser($boshqaOdam)->allows('delete', $vakansiya); // Blade'da @can('delete', $v) ... @endcan @cannot('delete', $v) ... @endcannot

Gate::forUser(...) — boshqa foydalanuvchi nomidan tekshirish. Skriptlarda va Modul E dagi testlarda juda qulay.

HOLAT 5

inspect() — «nega?» degan savolga javob

$natija = Gate::inspect('delete', $vakansiya); $natija->allowed() → true / false $natija->message() → Response::deny(...) dagi matn (yoki NULL)

Tekshiruv nima uchun yiqilganini bilish kerak bo'lganda — masalan xatoni topayotganda yoki API javobida sababni qaytarmoqchi bo'lganda.

HOLAT 6

Policy'ni qo'lda bog'lash

Avtomatik topilish qoidasi buzilgan bo'lsa (nom boshqacha, papka boshqacha), qo'lda bog'lash mumkin:

// AppServiceProvider::boot() Gate::policy(Vakansiya::class, VakansiyaPolicy::class); // yoki modelga atribut bilan (Laravel 12+) #[UsePolicy(VakansiyaPolicy::class)] class Vakansiya extends Model { ... }

Bizda kerak emas — Models\Vakansiya → Policies\VakansiyaPolicy qoidasi o'zbekcha nomda ham ishlaydi. Tekshirish: Gate::getPolicyFor(Vakansiya::class).

HOLAT 7

403 sahifasini o'zgartirish

php artisan vendor:publish --tag=laravel-errors → resources/views/errors/403.blade.php

Shundan keyin fayl sizniki — dizaynini va matnini o'zgartirasiz. Xuddi shunday 404.blade.php, 500.blade.php ham.

Bu 29-darsdagi pagination ko'rinishlari bilan bir xil naqsh: Laravel'ning ko'rinishlari — oddiy Blade fayllari, ularni chiqarib olib o'zgartirish mumkin.

💻 Amaliy qism kompyuterda

Amaliyotda vakansiyaga egasi qo'shasiz, policy yozasiz va ikkita foydalanuvchi bilan sinab ko'rasiz: biri o'chira oladi, ikkinchisi 403 oladi. Yo'lda AuthorizesRequests trait'i yo'qligidagi xatoni ham ko'rasiz.

  7. ⚠️ authorize() ni sinang — avval xato bilan

    Xatoni oldin ko'rish — keyin tanib olish uchun.

    Controllerga ochirish metodini qo'shing:

    Va route qo'shing:

    Route::delete('/vakansiyalar/{vakansiya}', [VakansiyaController::class, 'ochirish']) ->name('vakansiyalar.ochirish') ->middleware('auth');

    Kutilgan natija: hozircha sinaganda 500 chiqadi:

    Call to undefined method App\Http\Controllers\VakansiyaController::authorize()

    Sababi: Laravel 11+ da bazaviy Controller bo'sh — cat app/Http/Controllers/Controller.php bilan ko'ring.

Sinab ko'ramiz

Natijani taxmin qiling

Policy shunday — faqat ikkita metod bor:

app/Policies/VakansiyaPolicy.php
class VakansiyaPolicy { public function update(User $user, Vakansiya $vakansiya): bool { return $vakansiya->user_id === $user->id; } public function delete(User $user, Vakansiya $vakansiya): bool { return $vakansiya->user_id === $user->id; } }

Endi view'da @can('view', $v) yozildi — vakansiyaning egasi sahifani ochdi. Ichidagi kod ko'rinadimi? Va xato bo'ladimi?

Javobni ko'rish
Ko'rinmaydi. @can bloki ichidagi kod chiqmaydi. Xato: YO'Q. Hech qanday ogohlantirish ham yo'q. Gate::forUser($egasi)->allows('view', $v) → false

Policy'da view metodi yo'q, va Laravel buni taqiq deb hisoblaydi. Mantiq to'g'ri: «ruxsat berilmagan narsa taqiqlangan» — xavfsizlik uchun eng to'g'ri standart.

⚠️ Lekin chalkashtiradi. Siz «egasiman-ku, nega ko'rinmayapti?» deb policy mantig'ini qidirasiz — aslida metodning o'zi yo'q.

Xuddi shu xato yana bir shaklda uchraydi — nom xato yozilganda:

public function ochirish(User $user, Vakansiya $v) ← o'zbekcha nom @can('delete', $v) ← inglizcha so'raldi natija: false (chunki 'delete' nomli metod yo'q)

🔑 Qoida: policy metodlari nomi — Laravel kutadigan nom (view, create, update, delete, viewAny, restore, forceDelete). Ular kelishuv, shuning uchun o'zbekchaga o'girilmaydi.

Tashxis: Gate::inspect(...) yoki policy faylini ochib, metod nomini harfma-harf solishtirish.

SAVOL 1 Policy'da metod yozilmagan bo'lsa nima bo'ladi?

«Ruxsat berilmagan narsa taqiqlangan» — xavfsiz standart. Lekin chalkashtiradi: «nega ishlamayapti?» degan savolning javobi ba'zan «metodning o'zi yo'q».

SAVOL 2 authorize() ruxsat bermasa qaysi status qaytadi?

403 — «kimligingni bilaman, lekin huquqing yo'q». Kirmagan odam uchun esa auth middleware 302 bilan kirish sahifasiga yuboradi (30-dars).

SAVOL 3 @can bilan tugmani yashirish yetarlimi?

So'rovni qo'lda yuborish mumkin — biz sinab ko'rdik. @can ko'rinish uchun, authorize() yoki can: middleware himoya uchun. Ikkalasi ham kerak.

Eslab ayting

Avval o'zingiz javob bering, keyin ochib tekshiring. Oxirgi ikkitasi — 32-darsni takrorlash.

Middleware va policy farqi nimada?

Middleware — route darajasida («kirganmi?»), policy — yozuv darajasida («bu yozuv seniki-mi?»).

Policy qanday topiladi?

Nom bo'yicha: App\Models\X → App\Policies\XPolicy. Ro'yxatdan o'tkazish shart emas. Tekshirish — Gate::getPolicyFor(...).

Gate::before null qaytarsa nima bo'ladi?

«Menda gap yo'q» — tekshiruv policy'ga o'tadi. true qaytarsa policy umuman so'ralmaydi.

↩︎ Takrorlash: middleware'da $next chaqirilmasa?

Controller umuman ishlamaydi — so'rov to'xtaydi. auth shunday ishlaydi.

↩︎ Takrorlash: middleware qayerda ro'yxatdan o'tkaziladi?

bootstrap/app.php dagi withMiddleware da. app/Http/Kernel.php Laravel 11+ da yo'q.

Cho'ntak xulosasi
  • Middleware — route darajasida («kirganmi?»), policy — yozuv darajasida («bu yozuv kimniki?»).
  • Egalik uchun jadvalda user_id kerak: foreignId('user_id')->nullable()->constrained()->nullOnDelete().
  • ⚠️ egasi() metodida ikkinchi argument majburiy — aks holda egasi_id deb taxmin qilib jimgina NULL qaytaradi (26-dars).
  • make:policy VakansiyaPolicy --model=Vakansiya — beshta metodli skelet, hammasi false.
  • Policy avtomatik topiladi: Models\X → Policies\XPolicy. O'zbekcha nomda ham ishlaydi.
  • ⚠️ Laravel 11+ da bazaviy Controller bo'sh — use AuthorizesRequests; qo'shmasangiz Call to undefined method ...::authorize().
  • $this->authorize('delete', $v) → ruxsat bo'lmasa 403, keyingi kod ishlamaydi.
  • Statuslar: 302→login «kim ekaningni bilmayman» · 403 «huquqing yo'q» · 404 «yozuv yo'q».
  • Blade: @can / @cannot. Kodda: $user->can(...), Gate::allows(...), Gate::forUser($x)->allows(...).
  • 🔒 Yashirish — himoya emas (uchinchi marta): @can ko'rinish uchun, authorize() himoya uchun.
  • Muqobil: 'can:delete,vakansiya' middleware — controllerda kod yozmasdan.
  • Gate::define — modelsiz qoidalar. Gate::before — ustun qoida; null qaytarish muhim, aks holda policy hech qachon so'ralmaydi.
  • ⚠️ Policy metodlari nomi — kelishuv (view, update, delete…), o'zbekchaga o'girilmaydi.
🌱 Keyingi dars

Endi «bu yozuv kimniki?» degan savolga javob bor. Lekin IshTop'da ikki xil odam bo'lishi kerak: ish beruvchi (vakansiya joylaydi) va nomzod (ariza beradi). Hozir esa hamma bir xil.

34-darsda rollar qo'shamiz: users jadvaliga rol ustuni, policy'da roldan foydalanish («faqat ish beruvchi vakansiya yarata oladi»), va ro'yxatdan o'tishda rol tanlash.

O'shanda bugungi create(User $user) metodi — yozuvsiz shakl — ish beradi.
