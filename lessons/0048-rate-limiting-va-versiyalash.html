DARS 48 · MODUL F — API QATLAMI

Rate limiting va versiyalash

API to'liq, himoyalangan, qidiriladigan va xatolari tartibli. Lekin hozir istalgan kishi /api/token ga soniyasiga ming marta so'rov yubora oladi — parolni taxmin qilish uchun ham, serverni band qilish uchun ham. Bugun 429 bilan tanishamiz — va yo'lda ikkita jimgina yolg'onni tutamiz.

📱 O'qish ≈ 18 daqiqa 💻 Amaliyot ≈ 30 daqiqa Kerak: Dars 47

Bu darsda nimalar bor
  1. ⚠️ Laravel 13'da cheklov YO'Q 🔍 O'lchandi: api middleware guruhida atigi bitta narsa bor — SubstituteBindings. Rate limiting o'zi kelmaydi.
  2. throttle:3,1 va 429 Uchta 200, keyin 429. Javob shakli va X-RateLimit-* sarlavhalari bittalab o'lchandi.
  3. Retry-After — mijozga ko'rsatma 429 «yo'q» degani emas, «hozircha yo'q» degani. Mijoz qachon qayta urinishini bilishi kerak.
  4. ⚠️ Birinchi jimgina yolg'on: umumiy hisob throttle:2,1 ikki xil marshrutda — ular bitta hisobni bo'lishadi. Sabab framework manbasida topildi. A/B o'lchandi.
  5. Uchinchi argument — prefiks throttle:2,1,kalit — hisoblarni ajratadigan bir so'z.
  6. RateLimiter::for() — nomlangan cheklov Cheklovni bir joyda ta'riflash: Limit::perMinute(), by(), response().
  7. throttleApi() Butun api guruhiga bir qatorda. O'lchandi: aynan 60 ta 200, keyin 429.
  8. ⚠️ Ikkinchi jimgina yolg'on: $request->user() Rasmiy hujjatdagi shakl token API'da null qaytaradi va cheklov jimgina IP bo'yicha ishlab qoladi. Sabab — config/auth.php.
  9. ⚠️ Uchinchi tuzoq: yolg'on sarlavhalar O'z 429 javobingiz standart sarlavhalarni yo'qotadi — va qo'shnisinikini ko'rsatib qo'yadi: «54 ta so'rov qoldi» deb yozib turib rad etadi.
  10. Versiyalash: /api/v1 🔍 O'lchandi: prefiks qo'shilishi bilan 15 testdan 11 tasi qizardi. Nega buni hozir qilish kerak.
  11. Cheklov testlari 429 ni testda tekshirish, va nega har bir test toza hisob bilan boshlanadi.
  12. Har xil holatlar (7 ta) Eski manzillarni tirik qoldirish (Deprecation/Sunset) · kesh drayveri · bir nechta server · 429 va 503 farqi.
Ochiq eshik

44-darsda /api/token ni yozgandik. U email va parolni oladi, to'g'ri bo'lsa token beradi, xato bo'lsa 422. Endi hujumchi nuqtai nazaridan qaraymiz:

while (true) { POST /api/token { email: "ali@example.uz", parol: keyingi_taxmin() } if (status === 201) break; }

Hech narsa uni to'xtatmaydi. Sekundiga yuzlab urinish — va ko'p ishlatiladigan parollar ro'yxati unchalik uzun emas.

Ikkinchi tomoni — pul. Har bir so'rov bazaga boradi, PHP jarayonini band qiladi. Bitta skript butun serveringizni sekinlashtira oladi. Bu hatto hujum ham bo'lmasligi mumkin: mijoz dasturchisi tsiklda xato qilsa ham natija bir xil.

Yechim — rate limiting: «bir daqiqada shuncha, ko'pi yo'q». Va u uchun alohida status kodi bor — 429 Too Many Requests.1

Avval: bizda cheklov bormi?

Ko'p qo'llanmada «Laravel API'ni o'zi cheklaydi» deyiladi. Tekshiramiz — api guruhida nima borligini ko'ramiz:

web: Illuminate\Cookie\Middleware\EncryptCookies Illuminate\Session\Middleware\StartSession Illuminate\Foundation\Http\Middleware\PreventRequestForgery ... api: Illuminate\Routing\Middleware\SubstituteBindings ← BITTA

Cheklov yo'q. Laravel 10'gacha api guruhida throttle:api bor edi; Laravel 11'dan boshlab skelet soddalashtirildi va u olib tashlandi.

⚠️ «Standart holda xavfsiz» degan taxmin

Bu darsning birinchi saboqi: framework nimani o'zi qilishini taxmin qilmang — qarab tekshiring.

SubstituteBindings — bu 45-darsdagi route model binding. Ya'ni api guruhida faqat qulaylik bor, himoya yo'q.

🔍 Tashxis: php artisan route:list guruh nomini ko'rsatadi (api), ichidagini emas. Ichini ko'rish uchun tinker kerak — amaliyotda yozamiz.

throttle va 429

Eng oddiy shakl — marshrutga to'g'ridan-to'g'ri:

routes/api.php
Route::get('/x/tez', fn () => ['ok' => true])->middleware('throttle:3,1');

«Daqiqasiga 3 ta». Beshta so'rov yuboramiz:

urinish 1: 200 X-RateLimit-Limit: 3 X-RateLimit-Remaining: 2 urinish 2: 200 X-RateLimit-Limit: 3 X-RateLimit-Remaining: 1 urinish 3: 200 X-RateLimit-Limit: 3 X-RateLimit-Remaining: 0 urinish 4: 429 X-RateLimit-Limit: 3 X-RateLimit-Remaining: 0 Retry-After: 60 X-RateLimit-Reset: 1787644549 urinish 5: 429 ...

Javob tanasi:

{ "message": "Too Many Attempts." }

Uchta sarlavhaga alohida e'tibor bering — ular mijoz uchun yozilgan:

X-RateLimit-Limit → jami nechta mumkin X-RateLimit-Remaining → yana nechta qoldi Retry-After → necha soniyadan keyin qayta urinish mumkin X-RateLimit-Reset → hisob qachon nolga tushadi (unix vaqti)
🔑 429 — «yo'q» emas, «hozircha yo'q»

403 «senga ruxsat yo'q» degani va qayta urinish befoyda. 429 esa vaqtinchalik — shuning uchun unda Retry-After bor.

Yaxshi mijoz buni o'qiydi va kutadi. Yomon mijoz darrov qayta uradi va cheklovni yanada uzaytiradi. Shuning uchun siz mijoz bo'lganingizda ham Retry-After ni hurmat qiling.

Birinchi jimgina yolg'on: umumiy hisob

Ikkita marshrutga alohida cheklov qo'yamiz — mantiqan ikkalasi ham o'zining 2 tasiga ega bo'lishi kerak:

routes/api.php
Route::get('/x/c', fn () => ['ok' => 'c'])->middleware('throttle:2,1'); Route::get('/x/d', fn () => ['ok' => 'd'])->middleware('throttle:2,1');
/x/c: 200 /x/c: 200 /x/d: 429 ⚠️ /x/d ga BIRINCHI marta murojaat qilyapmiz /x/d: 429

/x/d ga hech qachon bormagan edik — lekin u darrov rad etdi. Sababi framework kodida:

// ThrottleRequests::resolveRequestSignature() if ($user = $request->user()) { return $this->formatIdentifier($user->getAuthIdentifier()); ← foydalanuvchi id } elseif ($route = $request->route()) { return $this->formatIdentifier($route->getDomain().'|'.$request->ip()); ← domen|IP }

Kalitda marshrut yo'q. Faqat foydalanuvchi (yoki IP). Ya'ni throttle:2,1 qaysi marshrutda bo'lmasin, bitta hisobga yozadi.

✅ Yechim — uchinchi argument, prefiks:

routes/api.php
Route::get('/x/a', fn () => ['ok' => 'a'])->middleware('throttle:2,1,aaa'); Route::get('/x/b', fn () => ['ok' => 'b'])->middleware('throttle:2,1,bbb');
/x/a: 200 /x/a: 200 /x/a: 429 ✅ o'z hisobi /x/b: 200 /x/b: 200 /x/b: 429 ✅ o'z hisobi
⚠️ Nega bu «yolg'on»?

Chunki kod o'qiganda to'g'ri ko'rinadi: har marshrutda o'z cheklovi yozilgan. Xato ham chiqmaydi. Faqat xatti-harakat boshqacha.

Amalda bu shunday ko'rinadi: qidiruvni ko'p ishlatgan foydalanuvchi login qila olmay qoladi — chunki ikkala marshrut bitta hisobni yeb bo'lgan.

🔑 Naqsh tanish: 46-darsdagi ?sort=moash, 47-darsdagi o'lik handler — xato chiqmaydi, natija noto'g'ri.

Nomlangan cheklov: RateLimiter::for()

Marshrutlarga raqam yozib yurish tez chalkashadi. Yaxshiroq yo'l — cheklovni bir joyda ta'riflab, unga nom berish:

app/Providers/AppServiceProvider.php
use Illuminate\Cache\RateLimiting\Limit; use Illuminate\Http\Request; use Illuminate\Support\Facades\RateLimiter; public function boot(): void { RateLimiter::for('api', fn (Request $request) => Limit::perMinute(60) ->by($request->user('sanctum')?->id ?: $request->ip())); RateLimiter::for('kirish', fn (Request $request) => Limit::perMinute(5) ->by($request->ip()) ->response(fn (Request $request, array $sarlavhalar) => response()->json([ 'message' => 'Juda ko\'p urinish. Bir daqiqadan keyin qayta urinib ko\'ring.', 'kod' => 'juda_kop_urinish', ], 429, $sarlavhalar))); }

Uchta qism bor:

Limit::perMinute(60) → qancha ->by(...) → KIM uchun hisoblanadi ← kalit shu yerda ->response(...) → rad etilganda nima qaytadi

by() — bu avvalgi bo'limdagi «kalit» muammosining to'g'ri yechimi: siz uni o'zingiz tanlaysiz, taxmin qilmaysiz.

api nomini butun guruhga ulash bir qator:

bootstrap/app.php
->withMiddleware(function (Middleware $middleware): void { $middleware->throttleApi(); $middleware->alias([...]); })
// endi api guruhi: throttle:api ← qo'shildi Illuminate\Routing\Middleware\SubstituteBindings // 62 ta so'rov yubordik: 200: 60 429: 2 ✅ aniq 60 tada to'xtadi

kirish ni esa faqat token marshrutiga ulaymiz:

routes/api.php
Route::post('/token', [TokenController::class, 'yarat']) ->middleware('throttle:kirish');
urinish 1..5: 422 { "message": "Email yoki parol xato." } urinish 6: 429 { "message": "Juda ko'p urinish...", "kod": "juda_kop_urinish" }

Endi parolni taxmin qilish daqiqasiga 5 ta urinishga tushdi. Va javob 47-darsdagi shaklda — o'z kod maydonimiz bilan.

Ikkinchi jimgina yolg'on: $request->user()

Yuqoridagi kodda $request->user('sanctum') deb yozilgan. Rasmiy hujjatlarda esa odatda shunday:

❌ token API'da ishlamaydi
->by($request->user()?->id ?: $request->ip())

Sinaymiz. Cheklovni vaqtincha 3 ga tushiramiz, avval mehmon sifatida hisobni tugatamiz, keyin token bilan murojaat qilamiz — token egasining o'z hisobi bo'lishi kerak:

mehmon: 200 200 200 429 ← kutilgan token bilan: 429 429 429 429 ⚠️ birinchi so'rovdan!

Token egasi mehmonning hisobiga tushib qoldi. Sabab config/auth.php da:

'defaults' => [ 'guard' => env('AUTH_GUARD', 'web'), ← standart guard: web ],

$request->user() — standart guard'ni so'raydi, ya'ni web, ya'ni sessiya. Bizda esa sessiya yo'q — bizda token bor. Shuning uchun u null qaytaradi va ?: bizni IP'ga tushirib yuboradi.

✅ Guard'ni aniq aytish kerak:

->by($request->user('sanctum')?->id ?: $request->ip()) mehmon: 200 200 200 429 token bilan: 200 200 200 429 ✅ alohida hisob
⚠️ Bu qanday zarar keltiradi

Cheklov ishlaydi — shuning uchun hech kim shubha qilmaydi. Lekin u IP bo'yicha ishlaydi.

Bitta ofisdagi 50 ta xodim bitta tashqi IP orqali chiqadi. Mobil operator NAT'i ostida esa minglab foydalanuvchi bitta IP'da bo'lishi mumkin. Ular sizning API'ingizda bitta odam bo'lib ko'rinadi va bir-birining cheklovini yeb qo'yadi.

🔍 Tashxis: cheklovni vaqtincha kichik qiling (perMinute(3)) va ikki xil token bilan sinang. Agar ikkinchisi darrov 429 olsa — guard muammosi.

🔑 44-darsga bog'lanish

44-darsda auth:sanctum deb yozgan edik — u yerda ham guard aniq ko'rsatilgan. auth deb yozganimizda ham xuddi shunday bo'lardi: web guard, sessiya, va token e'tiborsiz.

Qoida: token API'da guard nomini har doim yozing.

Uchinchi tuzoq: yolg'on sarlavhalar

->response(...) yozganimizda birinchi variantim shunday edi — argumentsiz:

❌ sarlavhalarni yo'qotadi
->response(fn () => response()->json([ 'message' => 'Juda ko\'p urinish...', 'kod' => 'juda_kop_urinish', ], 429))

Javob to'g'ri keldi — 429 va bizning matn. Lekin sarlavhalarga qarasak:

status: 429 x-ratelimit-limit: 60 ⚠️ bizniki 5 edi x-ratelimit-remaining: 54 ⚠️ «54 ta qoldi» deb turib RAD ETDI (retry-after yo'q) ⚠️ mijoz qachon urinishini bilmaydi

Ikkita muammo birdan. Retry-After yo'qoldi — mijoz endi ko'r-ko'rona qayta uradi. Va qolgan sarlavhalar qo'shnisiniki: ular tashqi api cheklovidan qolgan, ya'ni javob yolg'on gapiryapti.

Sabab: response() callback'i sarlavhalarni ikkinchi argument sifatida oladi, biz esa uni olmagan edik:

// ThrottleRequests::buildException() $responseCallback($request, $headers) ← ikkinchi argument

✅ Uni qabul qilib, javobga uzatamiz:

->response(fn (Request $request, array $sarlavhalar) => response()->json([ ... ], 429, $sarlavhalar)) // natija: x-ratelimit-limit: 5 ✅ x-ratelimit-remaining: 0 ✅ retry-after: 60 ✅ x-ratelimit-reset: 1787644916 ✅

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Eski manzillarni tirik qoldirish

Mijozlaringiz allaqachon bor bo'lsa, versiyani birdaniga qo'yib bo'lmaydi. Eski manzillarni bir muddat saqlab, ularni belgilab qo'yish kerak:

// app/Http/Middleware/EskiVersiya.php $javob->headers->set('Deprecation', 'true'); $javob->headers->set('Sunset', 'Wed, 31 Dec 2026 23:59:59 GMT'); $javob->headers->set('Link', '</api/v1/vakansiyalar>; rel="successor-version"'); // routes/api.php Route::name('api.eski.') ->middleware(\App\Http\Middleware\EskiVersiya::class) ->group(function () { ... });

Deprecation — «bu manzil eskirgan». Sunset — «shu sanadan keyin o'chadi». Link — «o'rniga buni ishlating». Uchalasi ham standart.2

⚠️ Nomlar boshqacha bo'lishi shart (api.eski.) — aks holda 45-darsdagi to'qnashuv qaytadi.

⚠️ Bu guruhga ->middleware(function (...) {...}) deb closure berib bo'lmaydi: Object of class Closure could not be converted to string. Marshrut guruhida middleware klass nomi bo'lishi kerak — 32-darsdagidek.

HOLAT 2

Kesh drayveri va bir nechta server

CACHE_STORE=file → hisob HAR BIR serverda alohida ⚠️ CACHE_STORE=database → umumiy (bizda shunday) CACHE_STORE=redis → umumiy va tez ✅

Cheklov hisoblari keshda yashaydi. Ikkita server orqasida file keshi bo'lsa, cheklov amalda ikki barobar bo'ladi — har bir server o'zicha sanaydi.

🔍 Bizning bazamizda ko'rish mumkin: DB::table('cache')->get() — ichida laravel-cache-<hash> va ...:timer juftliklari turadi.

✅ Ko'p serverli ilovada redis va $middleware->throttleWithRedis().

HOLAT 3

Har xil foydalanuvchiga har xil cheklov

RateLimiter::for('api', function (Request $request) { $user = $request->user('sanctum'); return $user?->rol === Rol::Admin ? Limit::none() : Limit::perMinute($user ? 60 : 20)->by($user?->id ?: $request->ip()); });

Limit::none() — cheklovsiz. Mehmonga kamroq, ro'yxatdan o'tganga ko'proq — bu keng tarqalgan naqsh.

🔑 34-darsdagi Rol enum shu yerda ham ishlatiladi — bitta manba, ko'p joyda.

HOLAT 4

Bir vaqtda ikkita cheklov

RateLimiter::for('api', fn (Request $request) => [ Limit::perMinute(60)->by($request->ip()), Limit::perDay(1000)->by($request->ip()), ]);

Massiv qaytarsangiz, hammasi tekshiriladi — birinchi oshgani rad etadi. «Daqiqasiga 60, kuniga 1000» kabi qoidalar shunday yoziladi.

⚠️ Sarlavhalar oxirgi cheklovniki bo'lib qoladi — mijozga qaysi biri ishlaganini aytish uchun response() yozing.

HOLAT 5

429 va 503 farqi

429 → SIZ juda ko'p so'radingiz (mijozning aybi, 4xx) 503 → SERVER hozir xizmat qila olmaydi (bizning holat, 5xx)

Ikkalasida ham Retry-After bo'lishi mumkin, lekin ma'nosi boshqa. php artisan down — 503 beradi.

🔑 47-darsdagi chegara shu yerda ham: 4xx — mijozniki, 5xx — sizniki.

HOLAT 6

Cheklov proksi orqasida

$request->ip() → proksi/CDN manzili ⚠️ HAMMA uchun bir xil

Nginx, Cloudflare yoki load balancer orqasida ishlasangiz, ip() haqiqiy mijozni emas, proksini ko'rsatishi mumkin. U holda butun dunyo bitta hisobga tushadi.

✅ bootstrap/app.php da $middleware->trustProxies(at: '*') (yoki aniq IP ro'yxati) — shundan keyin Laravel X-Forwarded-For ni o'qiydi.

⚠️ at: '*' ni faqat proksi haqiqatan ham oldinda bo'lganda yozing — aks holda mijoz sarlavhani o'zi yasab, IP'sini o'zgartirib yuboradi.

HOLAT 7

Versiyani boshqa joyga qo'yish

/api/v1/vakansiyalar ← manzilda (biz shuni tanladik) Accept: application/vnd.ishtop.v1+json ← sarlavhada ?version=1 ← query parametrda

Uchalasi ham amalda uchraydi. Manzildagi variant eng ko'rinadigan: brauzerda ochib ko'rish mumkin, logda ko'rinadi, curl da yozish oson.

Sarlavhali variant «toza» hisoblanadi (manzil resursni ko'rsatadi, versiya esa shakl haqida), lekin tekshirish qiyin va keshlash bilan muammo tug'diradi.

🔑 Tanlov texnik emas, amaliy: qaysi birini mijozlaringiz osonroq ishlatadi.

💻 Quyida amaliyot bor. Hozir o'qish rejimidasiz — kompyuter yoningizda bo'lganda 💻 Amaliyot rejimiga o'ting va shu bo'limdan davom eting.

Sinab ko'ramiz

Natijani taxmin qiling

Dasturchi rasmiy hujjatdan ko'chirib, cheklov yozdi:

app/Providers/AppServiceProvider.php
RateLimiter::for('api', fn (Request $request) => Limit::perMinute(60) ->by($request->user()?->id ?: $request->ip()));

Sinab ko'rdi: 60 ta so'rov o'tdi, 61-si 429. Sarlavhalar joyida. Testlar yashil. Ishga tushirdi.

Bir oydan keyin bitta korxona shikoyat qildi: «bizning xodimlarimiz API'dan foydalana olmayapti, ba'zilari ishlaydi, ba'zilari yo'q». Boshqa mijozlarda muammo yo'q. Nima bo'lyapti?

Javobni ko'rish

$request->user() standart guard'ni so'raydi. config/auth.php da esa:

'guard' => env('AUTH_GUARD', 'web'), ← web = sessiya

⚠️ Token bilan kelgan so'rovda sessiya yo'q → user() null → ?: ishlaydi → cheklov IP bo'yicha.

Korxonaning 50 ta xodimi bitta tashqi IP orqali chiqadi. Ular sizning API'ingizda bitta odam bo'lib ko'rinadi va daqiqasiga 60 tani bo'lishib oladi. Kim birinchi ulgursa — o'shanikiga ishlaydi.

🔑 Nega dasturchining sinovi buni ko'rsatmadi? Chunki u bitta token bilan sinadi. Muammo faqat ikkita har xil token bir IP'dan kelganda ko'rinadi.

bitta token bilan sinov → 60 ta o'tdi, 61-si 429 ✅ «ishlayapti» ikkita token bir IP'dan → ikkalasi 60 tani BO'LISHADI ⚠️

✅ Yechim bir so'z:

->by($request->user('sanctum')?->id ?: $request->ip())

🔍 Umumiy saboq: token API'da guard nomini har doim yozing — auth:sanctum da ham, user() da ham. «Standart» degani «siznikiga mos» degani emas.

SAVOL 1 Laravel 13 API'ni standart holda cheklaydimi?

🔍 O'lchandi: api guruhida atigi SubstituteBindings bor. Laravel 10'gacha throttle:api bor edi, 11'dan boshlab olib tashlandi. ✅ $middleware->throttleApi() bilan qaytariladi.

SAVOL 2 Ikki marshrutda throttle:2,1 yozilsa nima bo'ladi?

Kalit — foydalanuvchi id yoki domen|IP. Marshrut kalitda yo'q. O'lchandi: /x/c ikkitani yegach, /x/d birinchi murojaatdayoq 429. ✅ Uchinchi argument — prefiks: throttle:2,1,kalit.

SAVOL 3 Cheklov ichida $request->user() nima qaytaradi?

config/auth.php da standart guard — web, ya'ni sessiya. Token bilan sessiya yo'q → null → cheklov jimgina IP bo'yicha ishlab qoladi. ⚠️ Bitta IP ostidagi barcha foydalanuvchilar hisobni bo'lishadi. ✅ $request->user('sanctum').

Eslab ayting

Javobni ovoz chiqarib ayting, keyin ochib solishtiring.

429 javobidagi to'rtta sarlavha qaysilar va qaysi biri eng muhim?
X-RateLimit-Limit (jami nechta mumkin), X-RateLimit-Remaining (yana nechta qoldi), Retry-After (necha soniyadan keyin), X-RateLimit-Reset (hisob qachon nolga tushadi, unix vaqti). Eng muhimi — Retry-After: 429 «yo'q» emas, «hozircha yo'q» degani, va mijoz qachon qayta urinishini bilishi kerak.
Ikki marshrutdagi throttle:2,1 nega bitta hisobni bo'lishadi?
Chunki cheklov kaliti resolveRequestSignature() dan keladi: autentifikatsiya qilingan bo'lsa foydalanuvchi id, bo'lmasa domen|IP. Marshrut kalitda yo'q. ✅ Yechim — uchinchi argument (prefiks): throttle:2,1,kalit, yoki nomlangan cheklov yozib by() ni o'zingiz belgilash.
Token API'da $request->user() nega xavfli?
U standart guard'ni so'raydi — config/auth.php bo'yicha web, ya'ni sessiya. Token so'rovida sessiya yo'q, demak null. Natijada ?: $request->ip() ishlaydi va cheklov jimgina IP bo'yicha bo'lib qoladi — bitta NAT ortidagi minglab foydalanuvchi bitta hisobga tushadi. ✅ $request->user('sanctum').
O'z response() ingizni yozganda nimani unutmaslik kerak?
Callback ikkinchi argument sifatida sarlavhalarni oladi — uni javobga uzatish kerak: fn ($request, array $sarlavhalar) => response()->json([...], 429, $sarlavhalar). ⚠️ Aks holda Retry-After yo'qoladi, va javobda tashqi cheklovning sarlavhalari qolib ketadi — o'lchandi: «54 ta qoldi» deb turib rad etdi.
Versiyani qachon qo'shish kerak va nega?
Mijoz paydo bo'lishidan oldin. O'lchandi: /v1 prefiksi qo'shilishi bilan 15 testdan 11 tasi qizardi — ya'ni har bir mavjud mijoz buziladi. Hozir «mijozimiz» faqat testlar va ularni tuzatish bitta sed; mobil ilova chiqqandan keyin esa bu imkonsiz. Mijozlar allaqachon bo'lsa — eski manzillarni Deprecation, Sunset va Link sarlavhalari bilan bir muddat tirik qoldiring.

  • ⚠️ Laravel 13'da api guruhida cheklov yo'q — faqat SubstituteBindings. Framework nimani o'zi qilishini tekshiring.

  • ⚠️ throttle:2,1 ikki marshrutda — bitta hisob. Kalitda marshrut yo'q. Uchinchi argument prefiks beradi.
