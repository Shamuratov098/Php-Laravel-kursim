Controller nima qilishi kerak?

Controllerning bitta vazifasi bor: HTTP so'rovini javobga aylantirish. Ya'ni:

so'rovni qabul qil → kerakli ishni CHAQIR → javob qaytar

O'rtadagi «ishni» o'zi bajarish — uning vazifasi emas. Lekin biz aynan shuni qilib kelgan edik.

Hozirgi index() ga qarang — u to'rtta ish qilyapti:

1) tekshirish qoidalari (5 qator) 2) tartib xaritasi (7 qator) 3) so'rov qurish (9 qator) 4) resursga o'rash (1 qator)

Bu xato emas — kod ishlaydi, testlar yashil. Lekin uchta savolga javob bering:

1) Tartib mantiqini konsol buyrug'ida ham ishlatmoqchisiz. Qanday? 2) Faqat saralashni testlamoqchisiz. HTTP so'rovisiz qanday? 3) Yangi dasturchi "vakansiya yaratilganda nima bo'ladi?" deb so'radi. Qaysi faylni ochib ko'rsatasiz?

Uchalasiga ham javob bir xil: hozircha hech qanday. Chunki mantiq controllerga yopishib qolgan.

Uchta sinf — uchta rol

Bu nomlar Laravel'da majburiy emas — jamoalar kelishuvi. Lekin ma'nolari farqlanadi:

ACTION → BITTA ish bajaradi. Fe'l bilan nomlanadi. VakansiyaYarat · ParolniTikla · HisobniYop SERVICE → Bir mavzu atrofidagi bir necha ish. Ot bilan. StatistikaXizmati · TolovXizmati QUERY → So'rov QURADI, bajarmaydi. Filtr va saralash. VakansiyaQidiruvi

Oddiy savol: sinfning ichida nechta ommaviy metod bo'ladi?

bitta → Action bir nechtasi → Service so'rov quradi → Query

⚠️ Nomni haddan tashqari o'ylab o'tirmang. Eng muhimi — mantiq controllerdan chiqishi. Nomni keyin ham o'zgartirasiz.

Action — bitta ish

Hozirgi store():

public function store(VakansiyaRequest $request) { $vakansiya = Vakansiya::create( $request->validated() + ['user_id' => $request->user()->id] ); VakansiyaYaratildi::dispatch($vakansiya); return VakansiyaResource::make($vakansiya->fresh()) ->response()->setStatusCode(201); }

Ikkita ish aralashgan: yaratish qoidasi (egasini biriktirish, hodisa yuborish) va HTTP javob (201, resurs).

app/Actions/VakansiyaYarat.php
<?php namespace App\Actions; use App\Events\VakansiyaYaratildi; use App\Models\User; use App\Models\Vakansiya; class VakansiyaYarat { public function bajar(array $malumot, User $egasi): Vakansiya { $vakansiya = Vakansiya::create($malumot + ['user_id' => $egasi->id]); VakansiyaYaratildi::dispatch($vakansiya); return $vakansiya->fresh(); } }

Controller endi:

public function store(VakansiyaRequest $request, VakansiyaYarat $yarat) { $vakansiya = $yarat->bajar($request->validated(), $request->user()); return VakansiyaResource::make($vakansiya) ->response()->setStatusCode(201); }
🔑 VakansiyaYarat $yarat — bu qayerdan keldi?

Hech qayerdan «kelmadi». 49-darsdagi konteyner uni o'zi yasab berdi.

Laravel controller metodini chaqirishdan oldin parametr tiplariga qaraydi: VakansiyaYarat — sinf. Konstruktori bo'sh. Demak new VakansiyaYarat qilib uzatadi.

🔍 O'lchandi — konteyner har chaqiruvda yangi nusxa beradi:

expect(app(VakansiyaYarat::class)) ->not->toBe(app(VakansiyaYarat::class)); ✅ o'tdi

Bu «metod orqali inyeksiya» (method injection). Ro'yxatdan o'tkazish shart emas.

'yangi']; return Vakansiya::query() ->with('kompaniya') ->when(filled($filtr['q'] ?? null), fn (Builder $s) => $s->whereLike('nom', '%'.$filtr['q'].'%')) ->when(filled($filtr['shahar'] ?? null), fn (Builder $s) => $s->where('shahar', $filtr['shahar'])) ->when($filtr['faqat_faol'] ?? false, fn (Builder $s) => $s->faol()) ->orderBy(...$tartib); } }

⭐ Singleton + holat = jim xato

Endi darsning eng qimmatli qismi. Xizmat sinflari bilan ishlashda eng ko'p uchraydigan jim xato.

Tabiiy ko'rinadigan naqsh — «zanjirli» qidiruv:

class YomonQidiruv { private array $shartlar = []; public function filtr(string $k, $v): static { $this->shartlar[$k] = $v; // ← HOLAT saqlanyapti return $this; } }

Chiroyli ko'rinadi. Endi uni 50-darsdagi provayderda ro'yxatdan o'tkazamiz. Ikki variant:

app()->bind(YomonQidiruv::class, ...) → har chaqiruvda YANGI app()->singleton(YomonQidiruv::class, ...) → HAR DOIM bitta

Ikkalasini ham sinab ko'rdik. Ikki so'rovni taqlid qilamiz: birinchisi shahar bo'yicha, ikkinchisi matn bo'yicha filtrlaydi.

1) bind() — har chaqiruvda YANGI nusxa: 1-so'rov shartlari: {"shahar":"Toshkent"} 2-so'rov shartlari: {"q":"php"} bir xil obyektmi? YO'Q ✅ 2) singleton() — HAR DOIM bitta nusxa: 1-so'rov shartlari: {"shahar":"Toshkent","q":"php"} 2-so'rov shartlari: {"shahar":"Toshkent","q":"php"} bir xil obyektmi? HA ⚠️
⚠️ Nima bo'ldi?

singleton holatida ikkinchi so'rov birinchisining filtrini meros qilib oldi.

Foydalanuvchi «php» deb qidirdi — natijada faqat Toshkentdagi php vakansiyalari chiqdi. U buni hech qachon so'ramagan.

Xato yo'q. Ogohlantirish yo'q. Log toza. 200 OK. Faqat natija — NOTO'G'RI.

⚠️ Va bu mahalliy ishda ko'rinmaydi: artisan serve har so'rovda PHP jarayonini qayta boshlaydi, ya'ni singleton ham yangilanadi.

Ishlab chiqarishda esa (Octane, Swoole, uzoq yashaydigan worker) — jarayon saqlanadi. Va xato o'sha yerda boshlanadi.

✅ Nega bizning sinfimiz xavfsiz?

$bir = app(VakansiyaQidiruvi::class); $bir->soRov(['shahar' => 'Toshkent'])->toSql() → select * from "vakansiyalar" where "shahar" = ? order by "created_at" desc $bir->soRov(['q' => 'php'])->toSql() → select * from "vakansiyalar" where "nom" like ? order by "created_at" desc ✅ ikkinchisida "shahar" YO'Q

Chunki VakansiyaQidiruvi da hech qanday private $holat yo'q. Har chaqiruv o'z argumentidan o'z natijasini quradi.

🔑 Oltin qoida
Xizmat sinflari HOLATSIZ bo'lsin. Kirish → argument orqali Chiqish → qaytariladigan qiymat orqali Orasida → $this ga HECH NARSA yozilmasin

Shunda bind yoki singleton — farqi yo'q. Kod ikkalasida ham to'g'ri ishlaydi.

✅ Konstruktorda saqlanadigan bog'liqliklar (boshqa xizmatlar, sozlamalar) — bu holat emas. Ular o'zgarmaydi. Muammo — so'rovga oid ma'lumotni saqlash.

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Action ichida tranzaksiya

public function bajar(array $malumot, User $egasi): Vakansiya { return DB::transaction(function () use ($malumot, $egasi) { $vakansiya = Vakansiya::create($malumot + ['user_id' => $egasi->id]); $vakansiya->konikmalar()->sync($malumot['konikmalar'] ?? []); VakansiyaYaratildi::dispatch($vakansiya); return $vakansiya->fresh(); }); }

✅ Bir necha jadvalga yozilsa — tranzaksiya Action ichida bo'lsin, controllerda emas.

🔑 Sabab: «bu amal bo'linmas» — bu biznes qoidasi, HTTP qoidasi emas. Demak u Action bilan birga ko'chishi kerak.

⚠️ 61-darsdan eslang: MySQL'da DDL tranzaksiyaga bo'ysunmaydi. Oddiy insert/update esa — bo'ysunadi.

HOLAT 2

__invoke bilan yozish

class VakansiyaYarat { public function __invoke(array $malumot, User $egasi): Vakansiya { ... } } // chaqirish: $vakansiya = $yarat($malumot, $egasi); // metod nomi YO'Q

Ba'zi jamoalar buni afzal ko'radi: sinfning bitta ishi borligi kodda ko'rinadi.

⚠️ Kamchiligi: $yarat(...) deb yozilganda nima bo'layotgani noaniq — $yarat->bajar(...) o'qishga osonroq.

🔑 Ikkalasi ham to'g'ri. Muhimi — jamoada bir xil bo'lsin.

HOLAT 3

Action ichida HTTP narsalari

❌ public function bajar(Request $request): JsonResponse { $v = Vakansiya::create($request->validated()); return response()->json($v, 201); }

Bu Action emas — bu ko'chirilgan controller. Endi uni konsol buyrug'idan yoki navbatdan chaqira olmaysiz.

✅ Action Request ni ham, Response ni ham bilmasin:

kirish → array, model, oddiy tiplar chiqish → model, array, oddiy tiplar

🔑 Sinov: «bu sinfni artisan buyrug'idan chaqira olamanmi?» Javob «yo'q» bo'lsa — u hali controller.

HOLAT 4

Xizmatni ro'yxatdan o'tkazish kerakmi?

class VakansiyaYarat { } → kerak EMAS, konteyner o'zi yasaydi class TolovXizmati { public function __construct(private string $kalit) { } } → KERAK — konteyner $kalit ni bilmaydi

50-darsdagi provayderda:

$this->app->bind(TolovXizmati::class, fn () => new TolovXizmati(config('services.tolov.kalit')));

✅ Qoida: konstruktor faqat sinflardan iborat bo'lsa — hech narsa yozmang. Oddiy qiymat (matn, son, massiv) bo'lsa — bog'lang.

HOLAT 5

Haddan oshirish

❌ class VakansiyaOchir { public function bajar(Vakansiya $v): void { $v->delete(); } }

Bitta qatorli amal uchun alohida sinf — foyda emas, shovqin. Endi o'quvchi bitta delete() ni ko'rish uchun ikki fayl ochadi.

✅ Chegara qayerda? Mantiq quyidagilardan kamida bittasini qilsa, ajratishga arziydi:

1) bir nechta qadam bor (yaratish + hodisa + sinxronlash) 2) boshqa joydan ham chaqiriladi (konsol, navbat, boshqa controller) 3) alohida testlash kerak (murakkab shart yoki hisob)

🔑 destroy() bizda controllerda qoldi — va bu to'g'ri qaror.

HOLAT 6

Repository kerakmi?

class VakansiyaRepository { public function topId(int $id): ?Vakansiya { return Vakansiya::find($id); } public function saqla(Vakansiya $v): void { $v->save(); } }

Repository naqshining maqsadi — bazani almashtirish mumkin qilish. Lekin Eloquent o'zi allaqachon shu: 61-darsda SQLite'dan MySQL'ga bitta qator o'zgartirib o'tdik.

⚠️ Shunday Repository — Eloquent ustiga yopishtirilgan ikkinchi qatlam. U with(), paginate(), when() larni ham qayta yozishga majbur qiladi.

✅ Laravel'da odatiy yo'l — Query sinfi (biz qilgandek): so'rovni quradi, Eloquent'ni yashirmaydi.

Sinab ko'ramiz

Natijani taxmin qiling

Jamoa NarxXizmati yozdi — u vakansiya e'lonining narxini hisoblaydi:

class NarxXizmati { private float $chegirma = 0; public function chegirmaBer(float $foiz): static { $this->chegirma = $foiz; return $this; } public function hisobla(int $kun): int { return (int) round($kun * 1000 * (1 - $this->chegirma)); } }

Provayderda:

$this->app->singleton(NarxXizmati::class);

Controller:

public function narx(Request $request, NarxXizmati $narx) { if ($request->user()->rol === 'admin') { $narx->chegirmaBer(0.5); } return ['narx' => $narx->hisobla($request->integer('kun'))]; }

Testlar yashil. Mahalliy ishda ham to'g'ri ishlaydi. Serverga chiqarildi.

Bir hafta o'tib buxgalter shikoyat qildi: ba'zi oddiy foydalanuvchilar ham 50% chegirma olibdi. Lekin hammasi emas — taxminan o'ndan biri. Nima bo'lyapti?

Javobni ko'rish

singleton + holat ($chegirma).

Admin bir marta so'rov yuborsa, $chegirma 0.5 bo'lib o'sha nusxada qoladi. Undan keyingi har bir so'rov — kim yuborishidan qat'i nazar — 50% chegirma oladi.

1-so'rov admin → chegirma = 0.5 → narx to'g'ri 2-so'rov oddiy → chegirma HALI HAM 0.5 → narx NOTO'G'RI ⚠️ 3-so'rov oddiy → chegirma HALI HAM 0.5 → narx NOTO'G'RI ⚠️

🔑 Va «taxminan o'ndan biri» ham tushunarli: server bir necha jarayonda ishlaydi. Faqat admin so'rovi tushgan jarayon «zaharlanadi», boshqalari toza qoladi.

⚠️ Nega testlar tutmadi? Chunki har test toza ilova bilan boshlanadi — singleton har testda yangi. Muammo faqat ketma-ket kelgan so'rovlarda ko'rinadi.

✅ To'g'ri yechim — holatni yo'qotish:

class NarxXizmati { public function hisobla(int $kun, float $chegirma = 0): int { return (int) round($kun * 1000 * (1 - $chegirma)); } } // controller: $chegirma = $request->user()->rol === 'admin' ? 0.5 : 0; return ['narx' => $narx->hisobla($request->integer('kun'), $chegirma)];

Endi singleton bo'lsa ham farqi yo'q.

Eslab ayting

Javobni ovoz chiqarib ayting, keyin ochib solishtiring.

Action, Service va Query — farqi nima?
Action — bitta ish, fe'l bilan nomlanadi (VakansiyaYarat). Service — bir mavzu atrofidagi bir necha ish, ot bilan (StatistikaXizmati). Query — so'rov quradi, bajarmaydi (VakansiyaQidiruvi). 🔑 Tanlash oson: ommaviy metod bitta → Action, bir nechta → Service. ⚠️ Nomlar Laravel'da majburiy emas — bu jamoa kelishuvi. Muhimi mantiq controllerdan chiqishi.
Refaktoring muvaffaqiyatli bo'lganini qanday bilasiz?
Testlar o'zgarmadi va yashil qoldi. Refaktoring — ichki tuzilishni o'zgartirib, tashqi xulqni saqlash. 🔍 O'lchandi: index() 28 → 6, controller 77 → 58, statistika 42 → 14 — va 85 ta test hech o'zgarmasdan yashil qoldi. 🔑 Bir bo'lakni ko'chiring → test → commit → keyingisi. Hammasini birdan emas.
Ajratishning asosiy foydasi nima?
Mantiqni alohida testlash mumkin bo'ladi. 🔍 O'lchandi: beshta tartibni tekshirish — HTTP orqali 0.13s, to'g'ridan (toSql()) 0.01s — 13 barobar. Va boshqa foydalar: mantiqni konsol buyrug'idan ham chaqirish, «bu yerda nima bo'ladi?» degan savolga bitta fayl ko'rsatish. 🔑 soRov() va bajar() ni ajratish shuning uchun — Builder ni bajarmasdan tekshirish mumkin.
⭐ Singleton bilan qanday jim xato bo'ladi?
Xizmat holat saqlasa (private $shartlar) va singleton bo'lsa — keyingi so'rovlar oldingisining holatini meros oladi. 🔍 O'lchandi: ikkala so'rov ham {"shahar":"Toshkent","q":"php"} ko'rdi. ⚠️ Xato yo'q, log toza, 200 OK. ⚠️ Mahalliy ishda ko'rinmaydi (artisan serve har so'rovda qayta boshlanadi) va testda ham tutilmaydi (har test toza ilova bilan boshlanadi). ✅ Yechim: holatni yo'qotish — ma'lumot argumentda kelsin, javobda ketsin.
Qachon ajratmaslik kerak?
Mantiq quyidagilardan hech birini qilmasa: 1) bir nechta qadamdan iborat emas, 2) boshqa joydan chaqirilmaydi, 3) alohida testlash kerak emas. Masalan bizdagi destroy() — bitta delete(), controllerda qoldi. ⚠️ Bitta qatorli amal uchun alohida sinf — foyda emas, shovqin. 🔑 Va Repository ham odatda shunday: Eloquent allaqachon abstraksiya — 61-darsda bazani bitta qator bilan almashtirdik.
