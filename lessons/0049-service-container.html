DARS 49 · MODUL G — LARAVEL ICHKI MEXANIZMI

Service Container

Modul F davomida ko'p marta «Laravel buni o'zi qiladi» dedik. Request $request deb yozdingiz — u keldi. Vakansiya $vakansiya deb yozdingiz — model topildi. Bugun o'sha «o'zi» ning ichini ochamiz. Va siz uni allaqachon yozgansiz — 15-darsda, 35 qatorda.

📱 O'qish ≈ 18 daqiqa 💻 Amaliyot ≈ 30 daqiqa Kerak: Dars 15 · Dars 48

Bu darsda nimalar bor
  1. app() nima ekani 🔍 O'lchandi: Illuminate\Foundation\Application, u esa Illuminate\Container\Container dan meros oladi. Ya'ni app() — container.
  2. Avtomatik yasash (autowiring) Hech qanday bind qilmasdan app(LogXabar::class) ishlaydi. Nega — manbadan ko'rsatamiz.
  3. 🔑 Yonma-yon: bizniki va Laravelniki 15-darsdagi 35 qatorli Container va Laravelning build() metodi — bir xil to'rt qadam.
  4. Ikkita xato — ikkita throw Laravelning ikkala xato xabari bizning container'imizdagi ikkita throw ga aynan mos keladi. O'lchandi.
  5. bind — interfeysni ulash «XabarYuboruvchi so'ralsa LogXabar ber» — bu Reflection hal qila olmaydigan yagona narsa.
  6. bind va singleton farqi 🔍 spl_object_id bilan o'lchandi: bind har safar yangi, singleton bitta.
  7. ⚠️ «Singleton» qancha yashaydi? Eng ko'p yanglishiladigan joy. Javob bitta so'rov. O'lchash usuli ham muhim — o'lchovning o'zi meni bir marta aldadi.
  8. instance, scoped, bound bound() false bo'lsa ham klass yasaladi — «bog'langan» va «yasalishi mumkin» boshqa narsa.
  9. Kontekstli bog'lash Bitta interfeys, ikki xil amalga oshiruvchi — qaysi klass so'rayotganiga qarab.
  10. Laravelning o'z ro'yxati 🔍 O'lchandi: 217 bog'lanish, 159 instance, 81 alias. Shu sababdan app('router') ishlaydi.
  11. Metod argumentlari qayerdan keladi Manbada topildi: 45-darsdagi route model binding bilan bir joyda hal qilinadi.
  12. Har xil holatlar (7 ta) Singletonda holat saqlash tuzog'i · app() ni hamma joyda ishlatish · new qachon to'g'ri · testda almashtirish.
Javobsiz qolgan savol

17-darsda so'rovning yo'lini kuzatgandik. 45-darsda esa shunday yozdik:

public function show(Vakansiya $vakansiya) { return VakansiyaResource::make($vakansiya->load('kompaniya')); }

Bu metodni hech kim chaqirmaydi — hech bo'lmaganda siz chaqirmaysiz. Va unga $vakansiya qayerdandir keladi. 35-darsda esa VakansiyaRequest $request deb yozdik — u ham keldi, hatto validatsiyani bajarib bo'lgan holda.

Yaxshi xabar: to'lash uchun yangi tushuncha kerak emas. Siz buni yozgansiz. 15-darsda, 35 qatorli Container klassida. Bugun uni Laravelning kodi bilan yonma-yon qo'yamiz.

app() — bu container

Avval app() nima qaytarishini ko'ramiz:

get_class(app()) → Illuminate\Foundation\Application class_parents(app()) → Illuminate\Container\Container ← mana Container::getInstance() === app() → ha App::getFacadeRoot() === app() → ha

Ya'ni app(), App fasadi va Container::getInstance() — bitta obyekt. Va u Container dan meros oladi.

Endi eng qiziq qismi. Hech qanday sozlama yozmasdan:

$a = app(App\Xizmatlar\LogXabar::class); → App\Xizmatlar\LogXabar ✅ yasaldi

Biz hech qayerda «LogXabar ni shunday yasa» demadik. Container uni o'zi yasadi. Bu — autowiring, va siz uni 15-darsda yozgansiz.

Yonma-yon: bizniki va Laravelniki

Chap tomonda — 15-darsda o'z qo'lingiz bilan yozgan kod. O'ng tomonda — Laravelning Container::build() metodi.

15-dars — bizning Container::make()
$reflector = new \ReflectionClass($klass); if (! $reflector->isInstantiable()) { throw new \Exception("Container yasay olmadi: {$klass}"); } $konstruktor = $reflector->getConstructor(); if ($konstruktor === null) { return new $klass(); } $argumentlar = []; foreach ($konstruktor->getParameters() as $parametr) { $tip = $parametr->getType(); if ($tip === null || $tip->isBuiltin()) { throw new \Exception("... {$parametr->getName()} parametri klass emas"); } $argumentlar[] = $this->make($tip->getName()); } return $reflector->newInstanceArgs($argumentlar);
Laravel — Illuminate\Container\Container::build()
$reflector = new ReflectionClass($concrete); if (! $reflector->isInstantiable()) { return $this->notInstantiable($concrete); } $constructor = $reflector->getConstructor(); if (is_null($constructor)) { return $instance = new $concrete; } $dependencies = $constructor->getParameters(); $instances = $this->resolveDependencies($dependencies); return $instance = new $concrete(...$instances);

To'rt qadam, bir xil tartibda:

1) ReflectionClass bilan klassni "so'roq qilish" 2) Yasab bo'ladimi? (interfeys/abstract bo'lsa — yo'q) 3) Konstruktor bormi? Yo'q bo'lsa — darrov new 4) Bor bo'lsa — har bir parametrni rekursiv yasab, new ga uzatish
🔑 «Sehr» ning haqiqiy nomi — Reflection

PHP klassdan «senga nima kerak?» deb so'ray oladi. ReflectionClass — shu savolni beradigan vosita.

Laravelning container'i sizning 35 qatoringizdan ancha uzun (1000+ qator) — lekin uzunlik qo'shimcha imkoniyatlar uchun: kontekstli bog'lash, event'lar, atributlar, xatolarni chiroyli qilish. Asosiy g'oya — o'sha to'rt qadam.

🔑 Modul G ning maqsadi shu: har safar «sehr» degan joyni ochib, ichida oddiy kod borligini ko'rsatish.

Ikkita xato — ikkita throw

Bizning container'da ikkita throw bor edi. Laravelda ham ikkita xato bor — va ular aynan o'sha joylarda chiqadi.

Birinchisi — interfeys so'ralsa, lekin uni qaysi klass amalga oshirishi aytilmagan bo'lsa:

app(App\Xizmatlar\XabarYuboruvchi::class); Illuminate\Contracts\Container\BindingResolutionException Target [App\Xizmatlar\XabarYuboruvchi] is not instantiable while building [Laravel\Tinker\Console\TinkerCommand].

«is not instantiable» — bu bizning if (! $reflector->isInstantiable()) shoxi. Interfeysdan obyekt yasab bo'lmaydi: unda tana yo'q.

while building [...] qismi qo'shimcha — Laravel qurilish zanjirini saqlaydi va xatoni qaysi klassni yasayotganda uchratganini aytadi. Chuqur zanjirlarda bu juda foydali.

Ikkinchisi — konstruktorda klass emas, oddiy tip (satr, son) bo'lsa:

class SmsXabar { public function __construct(private string $kalit) {} } app(App\Xizmatlar\SmsXabar::class); BindingResolutionException Unresolvable dependency resolving [Parameter #0 [ <required> string $kalit ]] in class App\Xizmatlar\SmsXabar

Bu bizning if ($tip === null || $tip->isBuiltin()) shoxi. Container string ni yasay olmaydi — «qaysi satr?» degan savolga javob yo'q.

🔍 Laravel bizdan ko'ra bir oz ko'proq qiladi

Biz oddiy tipni ko'rsak darrov throw qilgandik. Laravel avval to'rtta imkoniyatni sinab ko'radi (resolvePrimitive):

1) kontekstli bog'lash bormi? when(...)->needs('$kalit')->give(...) 2) standart qiymat bormi? string $nom = 'standart' ✅ o'lchandi 3) variadic (...$args) mi? → [] 4) nullable mi? ?string $nom → null ✅ o'lchandi 5) yo'q bo'lsa — xato

Ya'ni string $nom = 'standart' deb yozsangiz, container hech narsa so'ramasdan yasaydi.

bind — Reflection hal qila olmaydigan narsa

Endi haqiqiy misol qilamiz. IshTop'da xabar yuborish kerak: hozir logga, keyinchalik SMS yoki emailga. Buni interfeys bilan yozamiz:

app/Xizmatlar/XabarYuboruvchi.php
<?php namespace App\Xizmatlar; interface XabarYuboruvchi { public function yubor(string $kimga, string $matn): string; }
app/Xizmatlar/LogXabar.php

Reflection bu yerda ojiz: XabarYuboruvchi dan obyekt yasab bo'lmaydi, va qaysi klass uni amalga oshirishini faqat siz bilasiz. Shuning uchun aytamiz:

Endi controllerda shunchaki so'raymiz:

Uch sabab bor, va uchalasi ham amaliy:

1) Ertaga SmsXabar yozsangiz — controller O'ZGARMAYDI 2) Testda soxta obyekt qo'yish mumkin (haqiqiy SMS ketmaydi) 3) Controller "log"ni emas, "xabar yuborish"ni biladi

Uchinchisi eng muhimi: controller nima qilish kerakligini biladi, qanday qilishni emas.

bind va singleton

Ikkalasi ham «shu so'ralsa — buni ber» deydi. Farq — nechta obyekt yasalishida. O'lchaymiz:

$c->bind(XabarYuboruvchi::class, LogXabar::class); $a = $c->make(XabarYuboruvchi::class); $b = $c->make(XabarYuboruvchi::class); → id 6438 va 6440 bir xilmi: YO'Q ← har safar yangi $c->singleton('sinov', fn () => new LogXabar()); $x = $c->make('sinov'); $y = $c->make('sinov'); → id 6442 va 6442 bir xilmi: HA ← bitta obyekt

Yana ikkita usul bor:

instance('nom', $tayyorObyekt) → tayyor obyektni container'ga berish scoped('nom', fn () => ...) → singleton, lekin "doira" tugaganda unutiladi

scoped ni singleton dan ajratib ko'rish uchun forgetScopedInstances() chaqiramiz:

forgetScopedInstances() dan keyin: singleton → bir xil obyekt HA scoped → yangi obyekt YO'Q

Oddiy PHP ilovada farq sezilmaydi. U Octane yoki navbat ishchilarida muhim bo'ladi — u yerda bitta jarayon ko'p so'rovga xizmat qiladi va «doira» har so'rovda tozalanadi.

bound() — ishonchli emas

$c->bound(XabarYuboruvchi::class) → true (bind qilingan) $c->bound(LogXabar::class) → false ⚠️ lekin YASALADI

«Bog'langan» va «yasalishi mumkin» — boshqa narsa. Autowiring bilan yasaladigan klasslar ro'yxatda yo'q. Shuning uchun if ($c->bound(X::class)) deb tekshirish ko'pincha noto'g'ri javob beradi.

⚠️ «Singleton» qancha yashaydi?

Bu eng ko'p yanglishiladigan joy. «Singleton» so'zi «bittagina» degani — lekin nima doirasida?

Sinov marshruti yozamiz:

routes/api.php (vaqtinchalik)
Route::get('/x/idlar', function (XabarYuboruvchi $x1) { $x2 = app(XabarYuboruvchi::class); return [ 'metodga_kelgan' => spl_object_id($x1), 'app_dan_olingan' => spl_object_id($x2), 'bir_xilmi' => $x1 === $x2, ]; });
1-so'rov: {"metodga_kelgan":302,"app_dan_olingan":302,"bir_xilmi":true} 2-so'rov: {"metodga_kelgan":302,"app_dan_olingan":302,"bir_xilmi":true} 3-so'rov: {"metodga_kelgan":302,"app_dan_olingan":302,"bir_xilmi":true}

Xulosa aniqdek: id uchala so'rovda ham 302, demak obyekt so'rovlar orasida yashaydi.

Bu xulosa noto'g'ri.

⚠️ spl_object_id global emas

spl_object_id — joriy jarayondagi raqam, va u qayta ishlatiladi. Har bir HTTP so'rov yangi PHP jarayoni; o'sha jarayonda o'sha navbatdagi obyekt yana 302 raqamini oladi.

🔑 Ya'ni o'lchov «bir xil» deb ko'rsatdi, aslida esa ikki xil obyekt edi. O'lchov usulining o'zi aldadi.

To'g'ri o'lchash uchun obyektga tug'ilganda belgi qo'yamiz:

class LogXabar implements XabarYuboruvchi { public string $tugilgan; public function __construct() { $this->tugilgan = uniqid('', true); } }
1-so'rov: bir_xilmi: true | tugilgan: 6a8d59b19ac923.37491193 2-so'rov: bir_xilmi: true | tugilgan: 6a8d59b19ea3e7.48516056 ← boshqa 3-so'rov: bir_xilmi: true | tugilgan: 6a8d59b1a269d1.17584153 ← boshqa

Endi rasm aniq:

bir so'rov ICHIDA → bitta obyekt (bir_xilmi: true) so'rovlar ORASIDA → har safar yangi (tugilgan boshqa)

Sabab oddiy: PHP ilovasi har so'rovda noldan ishga tushadi. Container ham yangi, singleton ham yangi. singleton — «shu so'rov davomida bittagina» degani.

Bu darsdagi eng qimmatli saboq kod haqida emas: o'lchov nimani o'lchayotganini tekshiring.

«Raqam bir xil» — «obyekt bir xil» degani emas. Bu 46-darsdagi ?sort=moash (200, lekin saralanmagan) va 47-darsdagi o'lik handler (test yashil, lekin kod ishlamagan) bilan bir oiladan.

Kontekstli bog'lash

Ba'zan bitta interfeysga ikki xil javob kerak bo'ladi: web tomon logga yozsin, mobil tomon SMS yuborsin.

Metod argumentlari qayerdan keladi?

Konstruktor tushunarli bo'ldi. Lekin show(Vakansiya $vakansiya) — bu metod, konstruktor emas. U qanday to'ldiriladi?

Javob Illuminate\Routing\ResolvesRouteDependencies da:

$className = Reflector::getParameterClassName($parameter); // If the parameter has a type-hinted class, we will check to see if it is // already in the list of parameters. If it is we will just skip it as it is // probably a model binding and we do not want to mess with those... if ($className && ! $this->alreadyInParameters($className, $parameters)) { return $parameter->isDefaultValueAvailable() ? ... : $this->container->make($className); ← o'sha container }

Ikkita yo'l bir joyda ko'rinadi:

Request $request → alreadyInParameters: YO'Q → container->make() Vakansiya $vakansiya → alreadyInParameters: HA → tegilmaydi

$vakansiya ro'yxatda allaqachon bor, chunki uni route model binding qo'ygan — 45-darsdagi SubstituteBindings middleware'i. Container esa «bunga tegmayman, bu binding'niki» deydi.

🔑 45-dars bilan bog'lanish

45-darsda parametr nomi {vakansiyalar} bo'lib qolganda binding jimgina buzilgandi. Endi sabab to'liq ko'rinadi: binding modelni nomi bo'yicha parametrlar ro'yxatiga qo'yadi. Nom mos kelmasa — ro'yxatga tushmaydi — alreadyInParameters false qaytaradi — va container Vakansiya ni bo'sh qilib yasab beradi.

Shuning uchun show 200 qaytargan, lekin ma'lumot null bo'lgan edi.

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Singletonda so'rovga tegishli holat saqlash

class Savat { private array $mahsulotlar = []; ⚠️ singletonda XAVFLI }

Oddiy PHP-FPM da bu ko'rinmaydi: har so'rov yangi jarayon, singleton ham yangi. Lekin Octane yoki navbat ishchisida bitta jarayon ko'p so'rovga xizmat qiladi — va bir foydalanuvchining ma'lumoti ikkinchisiga oqib o'tadi.

✅ Qoida: singleton ga faqat holatsiz xizmatlarni qo'ying (ulanish, sozlama, klient). So'rovga tegishli narsalar uchun bind yoki scoped.

🔍 Bizning LogXabar holatsiz — shuning uchun singleton to'g'ri tanlov.

HOLAT 2

app() ni hamma joyda ishlatish

❌ public function store(...) { $xabar = app(XabarYuboruvchi::class); // yashirin bog'liqlik } ✅ public function __construct(private XabarYuboruvchi $xabar) {}

Ikkalasi ham ishlaydi. Farq — ko'rinishida. Konstruktorda yozilgan bog'liqlik klassning e'loni: «menga shu kerak». app() esa metod ichida yashiringan.

⚠️ Yashirin bog'liqlikni testda almashtirish qiyinroq va klassni o'qiganda nima kerakligini bilib bo'lmaydi.

✅ app() ni marshrut closure'larida, komandalarda va migratsiyalarda ishlating — konstruktor yo'q joylarda.

HOLAT 3

new qachon to'g'ri

✅ new Vakansiya() — model, ma'lumot ✅ new DateTime('now') — oddiy qiymat obyekti ✅ new SmsXabar('kalit') — give() ichida ⚠️ new LogXabar() — xizmat, container'dan olinsin

Container hamma narsa uchun emas. U xizmatlar uchun: bog'liqliklari bor, almashtirilishi mumkin bo'lgan obyektlar.

🔑 Oddiy qoida: obyektning bog'liqligi bo'lsa yoki uni almashtirishingiz mumkin bo'lsa — container. Aks holda new ancha soddaroq.

HOLAT 4

Testda almashtirishning uch yo'li

app()->instance(X::class, $soxta); // o'z obyektingiz $this->mock(X::class, fn ($m) => ...); // Mockery $this->swap(X::class, $soxta); // instance() ning qisqasi

Biz birinchisini ishlatdik — anonim klass bilan. U eng ko'rinadigan: soxta obyekt nima qilishini o'zingiz yozasiz.

⚠️ Muhim shart: almashtirish controller yasalishidan oldin bo'lsin. Test ichida $this->postJson(...) dan oldin yozing.

HOLAT 5

register() va boot() farqi

register() → faqat container'ga bog'lash. Boshqa xizmatlarga TEGMANG. boot() → hamma provider register bo'lgandan keyin ishlaydi

Biz singleton ni register() ga, RateLimiter::for() ni (48-dars) boot() ga yozdik — va bu tasodif emas.

⚠️ register() ichida boshqa xizmatni ishlatsangiz, u hali ro'yxatdan o'tmagan bo'lishi mumkin.

HOLAT 6

Qurilish zanjiri xato xabarida

Target [App\Xizmatlar\XabarYuboruvchi] is not instantiable while building [App\Http\Controllers\Api\VakansiyaController].

while building [...] — xato qayerda boshlanganini aytadi. Chuqur zanjirlarda bu bir necha klassni sanaydi.

🔍 Tashxis: oxirgi nomdan boshlang — «bu klass nimani so'radi?» deb orqaga yuring. Odatda javob bitta: bind yozilmagan.

HOLAT 7

Interfeysni qachon yozish kerak emas

⚠️ Bitta amalga oshiruvchi + almashtirish rejasi yo'q → interfeys ortiqcha qatlam

Har bir klassga interfeys yozish — keng tarqalgan ortiqchalik. Container konkret klassni ham bemalol yasaydi va testda uni ham almashtirsa bo'ladi.

✅ Interfeys yozing, agar: ikkinchi amalga oshiruvchi bor (yoki aniq rejada), yoki tashqi xizmat bilan ishlaydi (SMS, to'lov, email) va testda uni uzish kerak.

🔑 Bizning XabarYuboruvchi ikkala shartga ham mos: SMS rejada bor va testda uzish kerak.

💻 Quyida amaliyot bor. Hozir o'qish rejimidasiz — kompyuter yoningizda bo'lganda 💻 Amaliyot rejimiga o'ting va shu bo'limdan davom eting.

Sinab ko'ramiz

Natijani taxmin qiling

Dasturchi «singleton so'rovlar orasida yashaydimi?» degan savolga javob izlab, shunday o'lchov qildi:

routes/api.php
Route::get('/x/idlar', function (XabarYuboruvchi $x) { return ['id' => spl_object_id($x)]; });
1-so'rov: {"id":302} 2-so'rov: {"id":302} 3-so'rov: {"id":302}

U xulosa qildi: «id bir xil — demak obyekt saqlanib qolyapti, singleton butun ilova umri davomida yashaydi». Va singletonga foydalanuvchi ma'lumotini keshlay boshladi.

Xulosa qayerda noto'g'ri?

Javobni ko'rish

spl_object_id — global emas. U joriy PHP jarayonidagi ichki raqam, va obyekt o'chgandan keyin raqam qayta ishlatiladi.

⚠️ Har bir HTTP so'rov — yangi PHP jarayoni. O'sha jarayonda o'sha navbatdagi obyekt yana 302 raqamini oladi. Raqam bir xil, obyekt boshqa.

To'g'ri o'lchash — obyektga tug'ilganda belgi qo'yish:

public function __construct() { $this->tugilgan = uniqid('', true); } 1-so'rov: 6a8d59b19ac923.37491193 2-so'rov: 6a8d59b19ea3e7.48516056 ← boshqa 3-so'rov: 6a8d59b1a269d1.17584153 ← boshqa

Ya'ni singleton — «bitta so'rov davomida bittagina». So'rov tugadi — ilova butunlay o'chadi.

🔑 Nega bu xavfli xulosa edi? Chunki dasturchi singletonga holat saqlay boshladi. Oddiy PHP-FPM da bu shunchaki ishlamaydi (kesh har so'rovda bo'sh). Octane'ga o'tsa esa ishlaydi — lekin bir foydalanuvchining ma'lumoti ikkinchisiga ko'rinadi.

🔍 Umumiy saboq: o'lchov nimani o'lchayotganini tekshiring. «Raqam bir xil» — «obyekt bir xil» degani emas.

SAVOL 1 app(LogXabar::class) nega bindsiz ishlaydi?

Bu — autowiring, siz uni 15-darsda yozgansiz: ReflectionClass → isInstantiable → getConstructor → parametrlarni rekursiv yasash. 🔍 O'lchandi: bound(LogXabar::class) false, lekin klass baribir yasaladi. ⚠️ Interfeys uchun esa bind shart.

SAVOL 2 bind va singleton farqi nimada?

🔍 O'lchandi: bind → id 6438 va 6440 (boshqa), singleton → id 6442 va 6442 (bir xil). Yana ikkitasi bor: instance() — tayyor obyektni berish, scoped() — «doira» tugaganda unutiladigan singleton.

SAVOL 3 singleton qancha vaqt yashaydi?

PHP ilovasi har so'rovda noldan ishga tushadi — container ham, singleton ham yangi. 🔍 O'lchandi: bir so'rov ichida bir_xilmi: true, lekin tugilgan belgisi har so'rovda boshqa. ⚠️ spl_object_id bilan o'lchasangiz aldanasiz: u qayta ishlatiladi.

Eslab ayting

Javobni ovoz chiqarib ayting, keyin ochib solishtiring.

Container klassni yasashda qaysi to'rt qadamni bosib o'tadi?
1) new ReflectionClass($klass) — klassdan «senga nima kerak?» deb so'rash. 2) isInstantiable() — yasab bo'ladimi (interfeys/abstract bo'lsa yo'q). 3) getConstructor() — konstruktor bormi; yo'q bo'lsa darrov new. 4) getParameters() — har bir parametrni rekursiv yasab, new ga uzatish. Bu 15-darsdagi kodingiz bilan bir xil.
Laravelning ikkita container xatosi bizning qaysi throw larimizga mos keladi?
Target [X] is not instantiable ← if (! $reflector->isInstantiable()) — interfeysdan obyekt yasab bo'lmaydi. Unresolvable dependency resolving [Parameter #0 ...] ← if ($tip === null || $tip->isBuiltin()) — string ni yasab bo'lmaydi. 🔍 Laravel qo'shimcha while building [...] zanjirini ham ko'rsatadi.
bound() nega ishonchli tekshiruv emas?
Chunki u faqat bog'langan nomlarni biladi. Autowiring bilan yasaladigan konkret klasslar ro'yxatda yo'q: bound(LogXabar::class) false, lekin app(LogXabar::class) muvaffaqiyatli yasaydi. «Bog'langan» va «yasalishi mumkin» boshqa narsa.
show(Vakansiya $vakansiya) ga model qanday keladi va nega container unga tegmaydi?
Modelni route model binding (SubstituteBindings middleware'i) parametrlar ro'yxatiga qo'yadi. ResolvesRouteDependencies::transformDependency() esa alreadyInParameters() bilan tekshiradi: ro'yxatda bor bo'lsa — tegmaydi. Request $request ro'yxatda yo'q, shuning uchun container->make() ishlaydi. 🔑 45-darsdagi «200, lekin ma'lumot null» xatosining sababi ham shu: nom mos kelmagani uchun model ro'yxatga tushmagan.
Singletonga nima qo'yish mumkin, nima mumkin emas?
✅ Holatsiz xizmatlar: ulanish, sozlama, klient, formatlovchi. ⚠️ So'rovga tegishli holat — mumkin emas. Oddiy PHP-FPM da bu ko'rinmaydi (har so'rov yangi jarayon), lekin Octane yoki navbat ishchisida bitta jarayon ko'p so'rovga xizmat qiladi va ma'lumot bir foydalanuvchidan ikkinchisiga oqib o'tadi. Bunday holatlar uchun bind yoki scoped.
Xulosa
  • app() — bu container: Illuminate\Foundation\Application extends Illuminate\Container\Container.
  • Autowiring — ReflectionClass bilan konstruktorni o'qib, parametrlarni rekursiv yasash. Siz buni 15-darsda yozgansiz.
  • Laravelning build() metodi va sizning make() ingiz — bir xil to'rt qadam.
  • Ikkita xato — ikkita throw: is not instantiable (interfeys) va Unresolvable dependency (oddiy tip).
  • bind Reflection hal qila olmaydigan yagona narsani hal qiladi: interfeys → klass.
  • bind har safar yangi · singleton bitta · instance tayyor obyekt · scoped doira tugaganda unutiladi.
  • ⚠️ singleton = bitta so'rov davomida. So'rov tugadi — ilova o'chadi.
  • ⚠️ spl_object_id bilan obyekt tengligini so'rovlar orasida o'lchab bo'lmaydi — u qayta ishlatiladi.
  • ⚠️ bound() false bo'lsa ham klass yasalishi mumkin.
  • Kontekstli bog'lash: when()->needs()->give() — bitta interfeys, har xil javob.
  • Laravelning o'zida 217 bog'lanish, 159 instance bor — app('router') shundan.
  • Metod argumentlari ham shu container'dan: alreadyInParameters() route model binding'ga tegmaydi.
  • Testda app()->instance() bilan almashtirish — DI ning asosiy foydasi.
🌱 Keyingi dars

Bugun ko'rdik: container'da 217 ta bog'lanish tayyor turibdi — router, log, db, cache… Lekin ularni u yerga kim qo'ydi?

Biz o'z bog'lanishimizni AppServiceProvider::register() ga yozdik va HOLAT 5 da register() bilan boot() farqiga tegib o'tdik — lekin sababini aytmadik.

50-darsda Service Providerlarni ochamiz: ilova ishga tushganda aynan nima sodir bo'ladi, provider'lar qanday tartibda yuklanadi, register() va boot() nega ikkiga bo'lingan, va deferred provider nima uchun kerak.

Undan keyingi darsda esa Log::info() da Log degan klass yo'q ekanini ko'rsatamiz. Javob bugungi ro'yxatda yashiringan: app('log').
