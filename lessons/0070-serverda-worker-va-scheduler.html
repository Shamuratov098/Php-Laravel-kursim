Kim ularni ishlatadi?

55-darsda navbat yozdik, 57-darsda bildirishnoma, 58-darsda rejalashtirilgan buyruq. Mahalliy ishda ularni o'zimiz ishga tushirdik:

php artisan queue:work php artisan schedule:work

Terminalni yopsangiz — ular to'xtaydi. Serverda esa terminal umuman yo'q.

Demak ikkita savol:

1) Kim ularni ishga tushiradi? 2) O'lib qolsa, kim qayta ko'taradi?

🔑 Javob: supervisor (navbat uchun) va cron (reja uchun). Ikkalasi ham operatsion tizim vositalari — Laravel'ga tegishli emas.

⚠️ Va 69-darsdagi predict'ni eslang: ilova ishlayapti, log toza, lekin xat kelmayapti. Sabab aynan shu yerda edi.

⭐ Worker eski kodni xotirasida saqlaydi

Bu — navbat bilan ishlashdagi eng ko'p chalkashlik manbai. O'lchaymiz.

Oddiy job yozamiz:

final class ZondJob implements ShouldQueue { use Queueable; public function handle(): void { Log::info('ZOND: VERSIYA-1'); } }
1) worker ni fonda ishga tushiramiz php artisan queue:work --sleep=1 --tries=1 2) job yuboramiz log: ZOND: VERSIYA-1 ✅ 3) ⚠️ KODNI o'zgartiramiz (worker ISHLAB TURIBDI) Log::info('ZOND: VERSIYA-2'); 4) yana job yuboramiz log: ZOND: VERSIYA-1 ⚠️ ESKI KOD!
⚠️ Nega bunday?

queue:work — demon. U bir marta ishga tushadi va doim ishlaydi.

PHP fayllarni bir marta yuklaydi va xotirada saqlaydi. Diskdagi fayl o'zgarsa ham, xotiradagi sinf o'zgarmaydi.

🔑 Bu odatiy HTTP so'rovdan tubdan farq qiladi: u yerda har so'rov yangi jarayon — fayllar qayta o'qiladi.

⚠️ Va oqibati jiddiy: deploy qildingiz, bug tuzatildi — lekin worker hamon eski bug bilan ishlayapti.

✅ queue:restart

php artisan queue:restart worker CHIQDI ✅ # yangi worker ko'tarilgach: log: ZOND: VERSIYA-2 ✅
🔑 queue:restart qanday ishlaydi

U worker'ni o'ldirmaydi. U keshga vaqt tamg'asini qo'yadi:

Cache::get('illuminate:queue:restart') → 1787731068

Worker har job'dan keyin shu qiymatni tekshiradi. O'zgargan bo'lsa — joriy job'ni tugatib, chiroyli chiqadi.

⚠️ Va shuning uchun uni qayta ko'tarish kerak — queue:restart buni qilmaydi. Bu supervisorning ishi.

🔑 Deploy skriptida (69-dars) shuning uchun queue:restart bor edi.

queue:work va queue:listen

queue:work → BITTA jarayon, doim ishlaydi kod XOTIRADA qoladi TEZ ✅ ishlab chiqarish uchun queue:listen → har job uchun YANGI jarayon kod HAR SAFAR qayta o'qiladi SEKIN mahalliy ish uchun

🔍 Sinadik — listen bilan kodni o'zgartirdik:

listen bilan: ZOND: VERSIYA-3 kod o'zgargach: ZOND: VERSIYA-4 ✅ restart SHART EMAS

🔑 Mahalliy ishda listen qulay: har o'zgarishdan keyin restart qilish shart emas. Serverda esa work — chunki har job uchun jarayon yaratish qimmat.

supervisor — worker'ni tirik saqlaydi

Worker o'lishi mumkin: xotira tugadi, queue:restart bo'ldi, server qayta yuklandi, kutilmagan xato.

supervisor — jarayonlarni kuzatib turadigan va o'lganini qayta ko'taradigan dastur.

sudo apt install supervisor
/etc/supervisor/conf.d/ishtop-worker.conf
[program:ishtop-worker] process_name=%(program_name)s_%(process_num)02d command=php /var/www/ishtop/artisan queue:work --sleep=3 --tries=3 --max-time=3600 directory=/var/www/ishtop autostart=true autorestart=true stopasgroup=true killasgroup=true user=www-data numprocs=2 redirect_stderr=true stdout_logfile=/var/www/ishtop/storage/logs/worker.log stopwaitsecs=3600
sudo supervisorctl reread sudo supervisorctl update sudo supervisorctl start ishtop-worker:* sudo supervisorctl status
🔑 Har sozlamaning ma'nosi
autorestart=true → o'lsa QAYTA ko'taradi ← eng muhimi numprocs=2 → ikkita worker parallel user=www-data → 69-darsdagi huquqlar bilan bir xil --max-time=3600 → har soatda O'ZINI qayta ishga tushiradi stopwaitsecs=3600 → to'xtatishda joriy job ni tugatishga vaqt beradi stopasgroup=true → bola jarayonlarni ham to'xtatadi

⚠️ --max-time nima uchun? PHP uzoq ishlaganda xotira sizishi (memory leak) bo'lishi mumkin. Soatiga bir marta qayta boshlash — eng oddiy yechim.

⚠️ stopwaitsecs juda muhim: usiz supervisor worker'ni o'rtada o'ldiradi va job yarim bajarilgan qoladi.

Ataylab yiqiladigan job yozdik:

Uch marta urindi, so'ng failed_jobs jadvaliga ko'chirdi.

To'liq tsikl: yiqildi → tuzatildi → o'tdi

1) queue:retry all d35004f5-... DONE jobs: 1 failed_jobs: 0 ← navbatga QAYTDI 2) kodni tuzatamiz 3) queue:work --stop-when-empty App\Jobs\ZondJob ..... 4.75ms DONE jobs: 0 failed_jobs: 0 ✅
🔑 --tries va --backoff
--tries=3 → 3 marta urinadi, keyin failed_jobs ga --tries=0 → CHEKSIZ urinadi ⚠️ tashqi API o'chsa — cheksiz sikl --backoff=60 → urinishlar orasida 60 soniya kutadi --backoff=10,60,300 → o'sib boruvchi kutish (eng yaxshisi)

✅ Tashqi xizmatga murojaat qiladigan job'larda o'sib boruvchi backoff ishlating: xizmat qayta ko'tarilishiga vaqt beradi.

🔑 Job ichida ham berish mumkin:

public $tries = 3; public array $backoff = [10, 60, 300];

Scheduler va cron

58-darsda reja yozdik:

Schedule::command('ishtop:vakansiyalarni-yop') ->dailyAt('03:00') ->withoutOverlapping();

Lekin uni kim ishga tushiradi? Serverda — cron. Va crontab'da bitta qator bo'ladi:

crontab -e -u www-data * * * * * cd /var/www/ishtop && php artisan schedule:run >> /dev/null 2>&1
🔑 Nega bitta qator?

Cron har daqiqada schedule:run ni chaqiradi. U esa Laravel ichidagi rejani o'qib, hozir vaqti kelganini bajaradi.

php artisan schedule:run INFO No scheduled commands are ready to run.

✅ Foydasi: yangi vazifa qo'shsangiz, crontab'ga tegmaysiz — hammasi routes/console.php da, ya'ni git'da.

⚠️ * * * * * — har daqiqada. Bu to'g'ri: schedule:run hech narsa bo'lmasa ~100 ms ishlaydi va chiqadi.

🔍 schedule:test — aniq buyruqni ko'rish

php artisan schedule:test --name="ishtop:vakansiyalarni-yop" Running ['artisan' ishtop:vakansiyalarni-yop] ....... 141.77ms DONE ⇂ '/usr/bin/php8.3' 'artisan' ishtop:vakansiyalarni-yop >> 'storage/logs/reja.log' 2>&1

Ikkinchi qator — Laravel haqiqatan bajaradigan buyruq. Bu 67-darsdagi «o'lchash» qadamining scheduler'dagi ko'rinishi.

🔑 Va u PHP ning to'liq yo'lini ishlatadi (/usr/bin/php8.3) — cron muhitida PATH bo'sh bo'lishi mumkin.

⭐ 🔍 withoutOverlapping — o'lchandi

Vazifa 8 soniya davom etadi, lekin har daqiqada ishga tushadi. Nima bo'ladi?

Ikkita schedule:run ni bir vaqtda ishga tushirdik:

Schedule::command('zond:sekin')->everyMinute()->withoutOverlapping(); 1-jarayon: 0 ta ishga tushdi 2-jarayon: Running ['artisan' zond:sekin] ..... 8s DONE fayldagi yozuvlar soni: 1 ✅ FAQAT BITTA
🔑 Bu qanday ishlaydi

withoutOverlapping() keshda qulf (mutex) qo'yadi. Ikkinchi jarayon qulfni ko'radi va o'tkazib yuboradi.

⚠️ Usiz nima bo'lardi? Vazifa 8 soniya, interval 60 soniya — bu holda muammo yo'q. Lekin vazifa 2 daqiqa davom etsa:

00:00 boshlandi 00:01 YANA boshlandi ← ikkitasi parallel 00:02 YANA boshlandi ← uchtasi parallel ...

Natija: xatlar ikki marta yuboriladi, hisobot ikki marta yoziladi.

✅ Qo'shimcha himoya:

->withoutOverlapping(10) ← qulf 10 daqiqadan keyin o'zi ochiladi ->onOneServer() ← bir NECHTA server bo'lsa (kesh umumiy bo'lsin) ->runInBackground() ← keyingi vazifani kutdirmaydi

⚠️ Jarayon qattiq o'ldirilsa qulf qolib ketishi mumkin — schedule:clear-cache uni tozalaydi.

Nazorat: qanday bilasiz ishlayotganini?

🔑 Eng muhim ko'rsatkich — navbat uzunligi

Bu buyruq navbat uzunligi chegaradan oshsa QueueBusy hodisasini yuboradi — siz uni 53-darsdagi listener bilan ushlab, ogohlantirish yuborasiz.

✅ Uni ham rejaga qo'ying:

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qing, keyin serverda qaytib qarang.

HOLAT 1

Xotira sizishi

--memory=128 → 128 MB dan oshsa chiqadi --max-jobs=1000 → 1000 job dan keyin chiqadi --max-time=3600 → 1 soatdan keyin chiqadi

Uzoq ishlaydigan PHP jarayonida xotira asta o'sadi — Eloquent modellari, statik massivlar, kutubxonalar.

✅ Uchalasidan kamida bittasini ishlating. autorestart=true bilan birga bu butunlay xavfsiz: worker chiqadi, supervisor darrov qayta ko'taradi.

🔑 60-darsdagi chunkById naqshi ham shu sababdan: butun jadvalni xotiraga olmang.

HOLAT 2

--timeout va uzoq job'lar

--timeout=60 → job 60 soniyadan oshsa TO'XTATILADI public $timeout = 120; ← job ichida

⚠️ Muhim qoida: --timeout har doim retry_after dan kichik bo'lsin (config/queue.php).

retry_after = 90 timeout = 60 ✅ retry_after = 60 timeout = 90 ⚠️ job IKKI MARTA bajariladi

Sabab: retry_after o'tgach navbat job'ni «tashlab ketilgan» deb hisoblab boshqa worker'ga beradi — birinchisi hali ishlayotgan bo'lsa ham.

🔑 Bu ham «xato yo'q, natija noto'g'ri» turkumidan: xat ikki marta ketadi.

HOLAT 3

Bir necha navbat va ustuvorlik

// yuborishda ParolniTikla::dispatch($user)->onQueue('tez'); HisobotYarat::dispatch()->onQueue('sekin'); // supervisor da command=php artisan queue:work --queue=tez,sekin

Vergul bilan ajratilgan tartib — ustuvorlik: tez bo'shamaguncha sekin ga o'tmaydi.

✅ Yoki ikkita alohida supervisor dasturi: tez uchun 4 ta worker, sekin uchun 1 ta.

⚠️ Aks holda bitta uzoq hisobot butun navbatni tiqib qo'yadi va parol tiklash xati kelmaydi.

HOLAT 4

Redis va database navbatlari

database → sozlash SHART EMAS, tayyor. Sekinroq. redis → tezroq, atomik. Alohida xizmat kerak (68-dars). sqs → AWS, cheksiz masshtab

🔍 Bizda QUEUE_CONNECTION=database — o'rganish va kichik loyihalar uchun butunlay yetarli.

⚠️ Katta yuklamada database muammo bo'ladi: har worker jadvalni qulflaydi.

✅ Redis'ga o'tish — bitta qator (.env), lekin Horizon ham ochiladi (HOLAT 7).

HOLAT 5

Job ichida model saqlash

❌ public function __construct(public Vakansiya $vakansiya) {}

Model SerializesModels orqali faqat id sifatida saqlanadi va bajarilganda qayta yuklanadi. Bu yaxshi. Lekin:

⚠️ Yozuv O'CHIRILGAN bo'lsa → ModelNotFoundException ⚠️ Yozuv O'ZGARGAN bo'lsa → job ESKI emas, YANGI holat bilan ishlaydi

✅ 64-darsdagi qoida: job ichiga DTO yoki id soling — o'sha paytdagi holat muhim bo'lsa.

🔑 Va ModelNotFoundException ni kutib oling:

public $deleteWhenMissingModels = true;
HOLAT 6

Cron muhiti — bo'sh

⚠️ Cron da PATH, .env, HOME — hammasi BOSHQACHA yoki YO'Q Ko'p uchraydigan xatolar: "php: command not found" → to'liq yo'l: /usr/bin/php8.3 "Could not open input file" → cd qilinmagan hech narsa bo'lmayapti → loglar /dev/null ga ketyapti

✅ Tuzatish uchun /dev/null ni vaqtincha faylga almashtiring:

* * * * * cd /var/www/ishtop && /usr/bin/php8.3 artisan schedule:run >> /tmp/cron.log 2>&1

🔑 Va crontab qaysi foydalanuvchida ekaniga e'tibor bering: crontab -e -u www-data — 69-darsdagi huquqlar bilan mos bo'lsin.

HOLAT 7

Laravel Horizon

composer require laravel/horizon php artisan horizon:install php artisan horizon

Redis navbatlari uchun boshqaruv paneli: real vaqtda job'lar, yiqilganlar, o'tkazuvchanlik, kutish vaqti.

✅ Supervisor sozlamasi ham soddalashadi — bitta horizon jarayoni worker'larni o'zi boshqaradi (config/horizon.php da).

⚠️ Faqat Redis bilan ishlaydi. database navbatida ishlamaydi.

⚠️ Va 66-darsdan: panelni himoyalang — Horizon::auth() yoki gate.

Sinab ko'ramiz

Natijani taxmin qiling

Onlayn do'kon. Buyurtma to'langanda job ishlaydi:

class BuyurtmaniTasdiqla implements ShouldQueue { public $tries = 3; public function handle(): void { $this->buyurtma->update(['holat' => 'tasdiqlangan']); Mail::to($this->buyurtma->email)->send(new BuyurtmaTasdigi($this->buyurtma)); $this->omborga->zaxiraKamaytir($this->buyurtma); // tashqi API } }

Sozlamalar:

config/queue.php: 'retry_after' => 60 supervisor: queue:work --timeout=90 --tries=3

Odatda hammasi yaxshi. Lekin ombor API'si sekinlashgan kunlari mijozlar shikoyat qildi: «ikkita bir xil xat keldi», va omborchi «zaxira ikki marta kamaydi» dedi.

Javobni ko'rish

retry_after (60) — --timeout (90) dan kichik.

00:00 worker A job ni oldi, ombor API ni kutyapti 00:60 retry_after o'tdi → navbat job ni "tashlab ketilgan" deb hisobladi → worker B GA BERDI ⚠️ 00:75 worker A tugatdi: xat #1, zaxira -1 00:135 worker B tugatdi: xat #2, zaxira -1 ⚠️

🔑 Job yiqilmadi — shuning uchun log toza va failed_jobs bo'sh. U shunchaki ikki marta bajarildi.

✅ Ikki qismli tuzatish:

1) SOZLAMA: timeout HAR DOIM retry_after dan KICHIK 'retry_after' => 120 timeout = 90 ✅ 2) KOD: job IDEMPOTENT bo'lsin — ikki marta ishlasa ham natija bir xil

Idempotentlik nima?

❌ $this->omborga->zaxiraKamaytir($buyurtma); // har chaqiruvda -1 ✅ if ($buyurtma->holat === 'tasdiqlangan') { return; // ALLAQACHON bajarilgan } ✅ yoki: ShouldBeUnique interfeysi public function uniqueId(): string { return $this->buyurtma->id; }

🔑 Umumiy saboq: navbat «kamida bir marta» yetkazishni kafolatlaydi — «aynan bir marta»ni emas. Bu Laravel'ning kamchiligi emas, taqsimlangan tizimlarning tabiati.

✅ Shuning uchun har job'ni yozayotganda so'rang: «bu ikki marta ishlasa nima bo'ladi?»

🔍 Va e'tibor bering: bu 62, 66 va 69-darslardagi bilan bir xil turkum — xato yo'q, natija noto'g'ri.

SAVOL 1 ⭐ queue:work ishlab turganda kodni o'zgartirsangiz nima bo'ladi?

🔍 O'lchandi: kod VERSIYA-2 ga o'zgartirilgach ham worker VERSIYA-1 ni yozdi. 🔑 queue:work — demon: PHP fayllarni bir marta yuklaydi va xotirada saqlaydi. HTTP so'rovdan tubdan farq qiladi. ✅ queue:restart keshga vaqt tamg'asini qo'yadi (illuminate:queue:restart = 1787731068), worker joriy job'ni tugatib chiqadi — qayta ko'tarish supervisorning ishi. 🔍 queue:listen esa kodni qayta yuklaydi (VERSIYA-3 → VERSIYA-4).

SAVOL 2 ⭐ withoutOverlapping() bo'lgan vazifa ikki marta bir vaqtda ishga tushsa?

🔍 O'lchandi: ikkita schedule:run bir vaqtda ishga tushirildi — 1-jarayon 0 ta, 2-jarayon 1 ta ishga tushirdi, faylda bitta yozuv. 🔑 Keshda qulf (mutex) qo'yiladi; ikkinchisi qulfni ko'radi va o'tkazib yuboradi. ⚠️ Jarayon qattiq o'ldirilsa qulf qolib ketishi mumkin → schedule:clear-cache. ✅ Bir necha server bo'lsa — onOneServer().

SAVOL 3 Rejalashtirilgan vazifalar serverda qanday ishga tushadi?

🔑 Crontab'da bitta qator: * * * * * cd /var/www/ishtop && php artisan schedule:run >> /dev/null 2>&1. schedule:run Laravel ichidagi rejani o'qib, vaqti kelganini bajaradi (INFO No scheduled commands are ready to run.). ✅ Foydasi: yangi vazifa qo'shsangiz crontab'ga tegmaysiz — hammasi routes/console.php da, ya'ni git'da. ⚠️ Cron muhitida PATH bo'sh bo'lishi mumkin — PHP ning to'liq yo'lini yozing.

⭐ Nega deploy'dan keyin queue:restart kerak?
queue:work — demon: PHP fayllarni bir marta yuklaydi va xotirada saqlaydi. 🔍 O'lchandi: kod VERSIYA-2 ga o'zgardi, worker hamon VERSIYA-1 yozdi. 🔑 queue:restart worker'ni o'ldirmaydi — keshga vaqt tamg'asini qo'yadi (illuminate:queue:restart); worker joriy job'ni tugatib chiqadi. ⚠️ Qayta ko'tarish — supervisorning ishi (autorestart=true). 🔍 queue:listen har job uchun yangi jarayon yaratadi va kodni qayta yuklaydi — mahalliy ish uchun.
supervisor sozlamasidagi muhim qatorlar
autorestart=true — eng muhimi: o'lsa qayta ko'taradi. numprocs=2 — nechta worker. user=www-data — 69-darsdagi huquqlar bilan mos. --max-time=3600 — xotira sizishiga qarshi, soatiga bir marta qayta boshlaydi. stopwaitsecs=3600 — to'xtatishda joriy job'ni tugatishga vaqt (usiz job yarim qoladi). stopasgroup=true — bola jarayonlarni ham. ✅ supervisorctl reread → update → start ishtop-worker:*.
🔍 Job yiqilganda nima bo'ladi?
🔍 O'lchandi (--tries=3): 3 ta FAIL, so'ng failed_jobs: 1. queue:failed uuid, ulanish va sinf nomini ko'rsatadi. queue:retry all → job navbatga qaytadi (jobs: 1); kod tuzatilgach DONE va ikkalasi ham 0. 🔑 --tries=0 — cheksiz urinadi ⚠️ tashqi API o'chsa cheksiz sikl. ✅ Tashqi xizmatlar uchun o'sib boruvchi backoff: public array $backoff = [10, 60, 300];
⚠️ --timeout va retry_after
🔑 --timeout har doim retry_after dan kichik bo'lsin. ⚠️ Aks holda: retry_after o'tgach navbat job'ni «tashlab ketilgan» deb hisoblab boshqa worker'ga beradi — birinchisi hali ishlayotgan bo'lsa ham. Natija: xat ikki marta, zaxira ikki marta kamayadi. Va log toza — job yiqilmadi, shunchaki ikki marta bajarildi. ✅ Navbat «kamida bir marta» kafolatlaydi. Har job uchun so'rang: «ikki marta ishlasa nima bo'ladi?» → idempotentlik yoki ShouldBeUnique.
