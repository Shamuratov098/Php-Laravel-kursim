DARS 53 · MODUL G — LARAVEL ICHKI MEXANIZMI

Events va Listeners

49-darsda store() ga xabar yuborishni qo'shdik. Ertaga statistika, indeks, adminga bildirish qo'shiladi — va metod o'sib ketadi. Bugun zanjirni uzamiz: controller «vakansiya yaratildi» deb e'lon qiladi, kim eshitishi esa uning ishi emas. Va yo'lda eng xavfli holatni o'lchaymiz: 500 qaytdi, lekin yozuv bazada.

📱 O'qish ≈ 16 daqiqa 💻 Amaliyot ≈ 26 daqiqa Kerak: Dars 52

Bu darsda nimalar bor
  1. Semiz store() muammosi Bitta metodga to'rt xil ish yig'ilganda nima bo'ladi va nega bu yomon.
  2. make:event va make:listener Hodisa — ma'lumot, tinglovchi — reaksiya. Ikkalasi ham oddiy klass.
  3. 🔍 Laravel 11+ da ro'yxatdan o'tkazish kerak emas EventServiceProvider yo'q. Tinglovchi handle() ning tip-belgisi bo'yicha topiladi — event:list bilan tasdiqlandi.
  4. Tinglovchida konstruktor injektsiyasi 49-darsdagi zanjir davom etadi: tinglovchi ham container'dan xizmat oladi.
  5. ⚠️ Hodisalar sinxron Darsning eng qimmat o'lchovi: tinglovchi xato tashladi → 500, lekin yozuv bazada qoldi.
  6. ShouldQueue — bir qatorli yechim 🔍 O'lchandi: xuddi shu buzuq tinglovchi bilan javob 201 bo'ldi.
  7. ⚠️ Testda ShouldQueue ishlamaydi phpunit.xml da QUEUE_CONNECTION=sync — navbat testda o'chirilgan. O'lchandi.
  8. Ish qayerga tushdi? jobs jadvali → queue:work → FAIL → failed_jobs. Uchala bosqich ko'rsatiladi.
  9. Event::fake() va tekshiruvlar assertDispatched · assertListening · assertNotDispatched · closure bilan shart.
  10. Model hodisalari created, updated, deleted va yana 9 tasi — Eloquent ularni o'zi e'lon qiladi.
  11. Observer — model hodisalari uchun O'nta tinglovchi o'rniga bitta klass.
  12. Har xil holatlar (7 ta) Hodisa nomlash · tartib · afterCommit · model hodisalari qachon ishlamaydi · hodisa yoki to'g'ridan-to'g'ri chaqiruv.
O'sib borayotgan metod

49-darsdan keyin store() shunday:

public function store(VakansiyaRequest $request) { $vakansiya = Vakansiya::create(...); $this->xabar->yubor($request->user()->email, "Vakansiya e'lon qilindi: ..."); return VakansiyaResource::make($vakansiya->fresh())->response()->setStatusCode(201); }

Hozircha yaxshi. Endi talablar keladi:

1) statistika keshini tozalash 2) qidiruv indeksiga qo'shish 3) adminga bildirish 4) hamkor saytga yuborish

Har biri 3–5 qator. Bir yildan keyin store() — 40 qatorli metod, va uning asosiy ishi (yozuv yaratish) bir qatorda ko'milib qoladi.

Yomoni shundaki, bu ishlarning hech biri controllerga tegishli emas. Controller HTTP bilan ishlaydi: so'rovni oladi, javob qaytaradi. Xabar yuborish esa — domen ishi.

Yechim: controller faktni e'lon qiladi, kim unga qanday javob berishi boshqa joyda hal qilinadi.

Hodisa va tinglovchi

php artisan make:event VakansiyaYaratildi php artisan make:listener XabarYubor --event=VakansiyaYaratildi

Hodisa — sodir bo'lgan fakt haqidagi ma'lumot. Unda mantiq yo'q, faqat ma'lumot:

app/Events/VakansiyaYaratildi.php
<?php namespace App\Events; use App\Models\Vakansiya; use Illuminate\Foundation\Events\Dispatchable; use Illuminate\Queue\SerializesModels; class VakansiyaYaratildi { use Dispatchable, SerializesModels; public function __construct(public Vakansiya $vakansiya) {} }

Ikkita trait bor. Dispatchable — VakansiyaYaratildi::dispatch($v) yozish uchun. SerializesModels — hodisa navbatga tushsa, model butunligicha emas, id bo'yicha saqlanadi va ishchi uni bazadan qayta oladi.

Tinglovchi — reaksiya:

app/Listeners/XabarYubor.php
<?php namespace App\Listeners; use App\Events\VakansiyaYaratildi; use App\Xizmatlar\XabarYuboruvchi; class XabarYubor { public function __construct(private XabarYuboruvchi $xabar) {} public function handle(VakansiyaYaratildi $event): void { $this->xabar->yubor( $event->vakansiya->egasi?->email ?? 'admin@ishtop.uz', "Vakansiya e'lon qilindi: {$event->vakansiya->nom}" ); } }

Konstruktorga e'tibor bering: XabarYuboruvchi — 49-darsdagi interfeys. Uni container beradi, tinglovchi esa faqat so'raydi. Zanjir davom etyapti.

Controller endi bir qator:

app/Http/Controllers/Api/VakansiyaController.php
public function store(VakansiyaRequest $request) { $vakansiya = Vakansiya::create( $request->validated() + ['user_id' => $request->user()->id] ); VakansiyaYaratildi::dispatch($vakansiya); return VakansiyaResource::make($vakansiya->fresh()) ->response()->setStatusCode(201); }

Konstruktordagi XabarYuboruvchi ham kerak emas — controller endi xabar haqida hech narsa bilmaydi.

Ro'yxatdan o'tkazish kerak emas

Eski Laravel'da EventServiceProvider bo'lgan va unda hodisa–tinglovchi juftliklari qo'lda yozilgan. Laravel 11+ da bu fayl yo'q:

ls app/Providers/ → AppServiceProvider.php XabarServiceProvider.php

Shunga qaramay tinglovchi ishlaydi. Tekshiramiz:

php artisan event:list App\Events\VakansiyaYaratildi ⇂ App\Listeners\XabarYubor@handle ⇂ App\Listeners\StatistikaniYangila@handle

Laravel app/Listeners papkasini skanerlaydi va har bir handle() metodining tip-belgisiga qaraydi. VakansiyaYaratildi deb yozilgan bo'lsa — o'sha hodisaga ulanadi.

🔑 Yana bir «sehr» — yana Reflection

49-darsdan tanish mexanizm: klassdan «senga nima kerak?» deb so'rash. Bu yerda savol boshqacha: «sen qaysi hodisani kutyapsan?»

🔍 Shuning uchun tip-belgisi majburiy: handle($event) deb yozsangiz, Laravel uni topa olmaydi va tinglovchi jimgina ishlamaydi.

✅ Tashxis: php artisan event:list — agar tinglovchingiz ro'yxatda yo'q bo'lsa, birinchi navbatda tip-belgisiga qarang.

⚠️ Hodisalar sinxron

Bu darsning eng muhim qismi. Ikkinchi tinglovchimizni ataylab buzamiz:

// StatistikaniYangila public function handle(VakansiyaYaratildi $event): void { throw new \RuntimeException('tinglovchi yiqildi'); }

Va vakansiya yaratamiz. Natija:

status: 500 javob: {"message":"Serverda kutilmagan xato yuz berdi.","xato_id":"..."} bazada yozuv bormi: TRUE ⚠️⚠️

Ikkala qatorga birga qarang. Mijoz xato oldi — demak u «vakansiya yaratilmadi» deb o'ylaydi. Vakansiya esa yaratilgan.

⚠️ Bu eng yomon holat

Mijoz qayta urinadi — ikkinchi vakansiya paydo bo'ladi. Yoki urinmaydi — va foydalanuvchi e'loni «yo'qolgan» deb o'ylaydi, aslida esa u saytda turibdi.

Sabab oddiy: dispatch() tinglovchilarni o'sha yerda, o'sha so'rovda chaqiradi. Ular xato tashlasa, xato controllerga qaytadi va butun javobni buzadi.

🔑 Ya'ni hodisa o'zi hech narsani ajratmaydi. U faqat kodni ajratadi, xatarni emas.

✅ ShouldQueue

app/Listeners/StatistikaniYangila.php
<?php namespace App\Listeners; use App\Events\VakansiyaYaratildi; use Illuminate\Contracts\Queue\ShouldQueue; use Illuminate\Support\Facades\Cache; class StatistikaniYangila implements ShouldQueue { public function handle(VakansiyaYaratildi $event): void { Cache::forget('statistika'); } }

Bitta interfeys qo'shildi — ShouldQueue. Endi o'sha buzuq tinglovchi bilan qayta o'lchaymiz:

status: 201 ✅ javob: {"data":{"id":40016,"nom":"Sinov vakansiya",...}}

Tinglovchi hamon buzuq. Lekin u endi so'rov ichida ishlamaydi — navbatga tushadi. Mijoz to'g'ri javob oladi.

Ish qayerga tushdi?

DB::table('jobs')->count() → 1 ta navbatdagi ish

Ishchini bir marta ishga tushiramiz:

php artisan queue:work --once --stop-when-empty 2026-08-25 18:17:09 App\Listeners\StatistikaniYangila .... RUNNING 2026-08-25 18:17:09 App\Listeners\StatistikaniYangila .... 9.89ms FAIL
DB::table('failed_jobs')->count() → 1 ta muvaffaqiyatsiz ish

To'liq zanjir ko'rindi:

dispatch() → jobs jadvali → queue:work → FAIL → failed_jobs

Xato yo'qolmadi — u ko'chdi. Endi u foydalanuvchining javobini emas, sizning logingizni buzadi. Va aynan shunday bo'lishi kerak.

🔑 Qaysi tinglovchi navbatga tushsin?
Sinxron qoldiring: natija javobga TA'SIR qiladi (masalan yozuvni to'ldirish, tekshirish) Navbatga bering: natija javobga ta'sir QILMAYDI (email, statistika, indeks, tashqi API)

Savol: bu ish bajarilmasa, mijozga 500 qaytarish to'g'rimi? To'g'ri bo'lmasa — ShouldQueue.

⚠️ Testda ShouldQueue ishlamaydi

Yuqoridagi tuzatishni test bilan tekshirmoqchi bo'ldik — va 500 hamon chiqdi. Sabab:

phpunit.xml: <env name="QUEUE_CONNECTION" value="sync"/>

sync — «navbat yo'q, hamma ishni darrov shu yerda bajar». Ya'ni test muhitida ShouldQueue hech nima o'zgartirmaydi.

⚠️ Bu ataylab qilingan

Sababi mantiqiy: testda navbat ishchisi yo'q, ish esa bajarilishi kerak — aks holda testlar hech narsani tekshira olmaydi.

⚠️ Lekin oqibati bor: navbatga ko'chirish to'g'ri ishlashini test tasdiqlay olmaydi. Buni curl bilan tekshirdik.

✅ Testda navbatni tekshirish uchun boshqa yo'l bor: Queue::fake() va Queue::assertPushed(...) — Modul H'da batafsil.

Model hodisalari

Eloquent har bir model uchun hodisalarni o'zi e'lon qiladi — siz hech narsa yozmaysiz:

retrieved · creating · created · updating · updated saving · saved · deleting · deleted restoring · restored · replicating

Ularni tinglashning eng toza yo'li — observer:

php artisan make:observer VakansiyaObserver --model=Vakansiya
class VakansiyaObserver { public function created(Vakansiya $vakansiya): void { ... } public function updated(Vakansiya $vakansiya): void { ... } public function deleted(Vakansiya $vakansiya): void { ... } }

Model'ga ulash Laravel 12+ da atribut bilan:

#[ObservedBy(VakansiyaObserver::class)] class Vakansiya extends Model { ... }
⚠️ Model hodisalari qachon ishlamaydi
Vakansiya::create([...]) → created ishlaydi Vakansiya::where(...)->update([...]) → updated ISHLAMAYDI ⚠️ Vakansiya::where(...)->delete() → deleted ISHLAMAYDI ⚠️ DB::table('vakansiyalar')->insert() → hech narsa ishlamaydi

Sabab: ommaviy (mass) amallar modelni yasamaydi — ular to'g'ridan-to'g'ri SQL yuboradi. Hodisa esa modelning ishi.

🔑 Shuning uchun muhim mantiqni model hodisasiga qo'ymang: kimdir ommaviy yangilash yozsa, u jimgina o'tkazib yuboriladi.

✅ Ochiq dispatch() — ko'rinadigan va ishonchli. Model hodisalari yordamchi ishlar uchun yaxshi (slug yasash, kesh tozalash).

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

HOLAT 2

Tinglovchilar tartibiga tayanish

⚠️ event:list dagi tartib — kafolat EMAS

Ikkita tinglovchi bir-biriga bog'liq bo'lsa (birinchisi ma'lumot tayyorlaydi, ikkinchisi ishlatadi) — bu xato dizayn.

✅ Bunday holatda ikkalasini bitta tinglovchiga birlashtiring, yoki birinchisi o'z hodisasini e'lon qilsin.

🔑 Hodisa tinglovchilari mustaqil bo'lishi kerak: biri o'chsa, boshqasi ishlayveradi.

HOLAT 3

Tranzaksiya ichidagi hodisa

DB::transaction(function () { $v = Vakansiya::create([...]); VakansiyaYaratildi::dispatch($v); ⚠️ // ... keyin xato chiqsa — tranzaksiya BEKOR }); → yozuv bekor qilindi, lekin email KETIB BO'LGAN

Navbatdagi tinglovchi tranzaksiya tugashini kutmaydi.

✅ Yechim: ShouldQueue yoniga ShouldHandleEventsAfterCommit qo'shing — tinglovchi faqat commit dan keyin ishlaydi.

HOLAT 4

Hodisa yoki to'g'ridan-to'g'ri chaqiruv?

✅ hodisa: bir necha mustaqil reaksiya bor (yoki kelajakda bo'ladi) ✅ to'g'ridan: bitta ish va u asosiy oqimning qismi

Bitta tinglovchi uchun hodisa — ortiqcha qatlam. Kodni o'qiganingizda «keyin nima bo'ladi?» degan savolga javob topish qiyinlashadi.

🔑 Hodisaning narxi shu: bog'lanish ko'rinmay qoladi. Foydasi ham shunda — lekin faqat reaksiyalar haqiqatan ko'p bo'lganda.

🔍 Tashxis vositasi: event:list — kim kimni tinglayotganini ko'rsatadi.

HOLAT 5

dispatchAfterResponse()

VakansiyaYaratildi::dispatchAfterResponse($vakansiya);

Navbatsiz, lekin javob yuborilgandan keyin ishlaydi. Foydalanuvchi kutmaydi, ishchi ham kerak emas.

⚠️ Lekin PHP jarayoni tugamaguncha — ya'ni server hamon band. Va xato bo'lsa hech kim bilmaydi: javob allaqachon ketgan.

🔑 Yengil va ahamiyatsiz ishlar uchun. Muhim narsa — haqiqiy navbat.

HOLAT 6

Bitta tinglovchi — ko'p hodisa

public function handle(VakansiyaYaratildi|VakansiyaYangilandi $event): void

PHP 8 ning union tipi bilan bitta tinglovchi bir necha hodisani kutishi mumkin — Laravel ikkalasiga ham ulaydi.

🔍 Yoki Event::listen ni provider'ning boot() ida qo'lda yozish (50-dars: register() emas!) — joker bilan: Event::listen('vakansiya.*', ...).

HOLAT 7

Tinglovchini to'xtatish

public function handle(VakansiyaYaratildi $event): bool { if (! $event->vakansiya->faol) { return false; // keyingi tinglovchilar ISHLAMAYDI } ... }

⚠️ Bu HOLAT 2 bilan bog'liq: tartibga tayanish demakdir. Ehtiyot bo'ling — ba'zan foydali (spam filtri), ko'pincha esa dizayn muammosi belgisi.

Sinab ko'ramiz

Natijani taxmin qiling

Dasturchi store() ni hodisaga o'tkazdi va xursand bo'ldi: controller qisqardi, testlar yashil.

Bir hafta o'tib, hamkasbi yangi tinglovchi qo'shdi — hamkor saytga vakansiyani yuborish:

app/Listeners/HamkorgaYubor.php
class HamkorgaYubor { public function handle(VakansiyaYaratildi $event): void { Http::post('https://hamkor.uz/api/vakansiyalar', [ 'nom' => $event->vakansiya->nom, ]); } }

Testlar yashil (chunki Event::fake() tinglovchilarni ishlatmaydi). Ishga tushirildi.

Ertasi kuni: «vakansiya qo'shish juda sekin, ba'zan umuman ishlamayapti». Hamkor sayti esa ta'mirda. Nima bo'lyapti?

Javobni ko'rish

Tinglovchida ShouldQueue yo'q. Demak Http::post(...) foydalanuvchining so'rovi ichida bajariladi.

Eslab ayting

Javobni ovoz chiqarib ayting, keyin ochib solishtiring.

Hodisa va tinglovchi nima va nomlari qanday bo'ladi?
Hodisa — sodir bo'lgan fakt haqidagi ma'lumot, mantiqsiz. Tinglovchi — reaksiya. Nomlash: hodisa o'tgan zamonda (VakansiyaYaratildi), tinglovchi buyruq shaklida (XabarYubor). 🔍 Laravel 11+ da ro'yxatdan o'tkazish kerak emas — handle() ning tip-belgisi yetarli.
Nega sinxron tinglovchi xavfli?
U o'sha so'rov ichida ishlaydi. Xato tashlasa, xato controllerga qaytadi. 🔍 O'lchandi: status 500, lekin yozuv bazada — mijoz qayta urinadi va ikkinchi nusxa paydo bo'ladi. 🔑 Hodisa kodni ajratadi, xatarni emas.
Qaysi tinglovchi ShouldQueue bo'lishi kerak?
Savol bering: bu ish bajarilmasa, mijozga 500 qaytarish to'g'rimi? To'g'ri bo'lmasa — navbatga. Amalda: email, statistika, indeks, tashqi API — hammasi navbatga. Javobga ta'sir qiladigan ish (tekshirish, to'ldirish) — sinxron.
Navbatdagi tinglovchi xato tashlasa ish qayerga boradi?
Zanjir: dispatch() → jobs jadvali → queue:work → FAIL → failed_jobs. 🔍 O'lchandi: ishchi RUNNING keyin FAIL chiqardi, failed_jobs da 1 ta yozuv. 🔑 Xato yo'qolmadi — u foydalanuvchining javobini emas, sizning logingizni buzadi.
Model hodisalari qachon ishlamaydi?
Ommaviy amallarda: where(...)->update(), where(...)->delete(), DB::table(...)->insert(). Sabab: ular modelni yasamaydi, to'g'ridan-to'g'ri SQL yuboradi. 🔑 Muhim mantiqni model hodisasiga qo'ymang — ochiq dispatch() ishonchliroq.
