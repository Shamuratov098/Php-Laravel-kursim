DARS 42 · MODUL F — API QATLAMI

REST, JSON va status kodlar

Shu paytgacha IshTop faqat HTML qaytardi: Blade render qilinib, brauzerga sahifa borardi. Bugun ikkinchi ko'rinish qatlami qo'shamiz — o'sha bir Eloquent ma'lumoti JSON bo'lib chiqadi. Model ham, baza ham, policy ham o'zgarmaydi: faqat javob shakli boshqacha.

📱 O'qish ≈ 16 daqiqa 💻 Amaliyot ≈ 25 daqiqa Kerak: Dars 41

Bu darsda nimalar bor
  1. Bitta ma'lumot — ikki qatlam Nega API alohida controller talab qiladi va nega model o'zgarmaydi.
  2. php artisan install:api Laravel 11+ da routes/api.php yo'q. Buyruq nima qilishi — to'rt qadam, o'lchangan.
  3. REST: resurs, fe'l, manzil Bir manzil — bir necha amal. Fe'l (GET, POST) ishni belgilaydi.
  4. Model o'zi JSON'ga aylanadi response()->json($vakansiya) — sehr yo'q: Eloquent JsonSerializable interfeysini bajaradi.
  5. Status kodlar: 200 · 201 · 404 · 422 Har biri o'lchandi va javob shakli ko'rsatildi.
  6. ⚠️ Accept: application/json Sarlavhasiz mijoz 302 redirect va HTML oladi. Ikkala holat ham o'lchandi.
  7. shouldRenderJsonWhen bootstrap/app.php da bir marta sozlansa, api/* har doim JSON qaytaradi.
  8. ⚠️ APP_DEBUG va 404 true bo'lganda javobda fayl yo'li va istisno klassi chiqadi. O'lchandi.
  9. 🔍 API'da CSRF yo'q Token yubormasdan POST qildik va 201 oldik. Nega bu to'g'ri va nima o'rniga ishlatiladi.
  10. API testlari getJson · postJson · assertJsonPath · assertJsonCount · assertJsonStructure · assertJsonValidationErrors.
  11. ⚠️ Model to'liq ochilib ketdi Javobda user_id, created_at — hammasi. Bu ataylab qoldirilgan muammo.
  12. Har xil holatlar (7 ta) api.php yo'qligi · Accept · APP_DEBUG · CSRF · model ochilishi · inglizcha xabarlar · route nomlari.
Bitta Eloquent — ikki ko'rinish qatlami

IshTop bugun brauzer uchun ishlaydi. Lekin ma'lumot boshqa joylarga ham kerak bo'ladi:

mobil ilova → vakansiyalar ro'yxati kerak, HTML emas boshqa saytdagi vidjet → «oxirgi 5 ta e'lon» hamkor kompaniya → o'z e'lonlarini avtomatik joylamoqchi

Ularning hech biriga <table> kerak emas. Ularga ma'lumot kerak — mashina o'qiy oladigan shaklda. Bu shakl — JSON.

Muhim narsa shuki, pastdagi qatlamlar o'zgarmaydi:

baza · model · bog'lanishlar · policy · validatsiya ← O'ZGARMAYDI ↓ ↓ Blade (HTML) JSON javob ← faqat SHU boshqa

Shuning uchun bugun yangi controller yozamiz, lekin Vakansiya modeliga bitta ham qator qo'shmaymiz.

install:api — API qatlamini yoqish

Loyihangizdagi routes/ papkasiga qarang:

routes/ ├── console.php └── web.php ← api.php YO'Q

Laravel 11 dan boshlab API qatlami ataylab o'chirilgan holda keladi: har loyihaga ham API kerak emas.1 Uni bitta buyruq bilan yoqamiz:

php artisan install:api INFO Published API routes file. INFO Running migrations. 2026_..._create_personal_access_tokens_table .. DONE INFO API scaffolding installed. Please add the [Laravel\Sanctum\HasApiTokens] trait to your User model.

Buyruq to'rt ish qildi:

1) Sanctum paketini o'rnatdi (token autentifikatsiyasi — shu modulda) 2) routes/api.php faylini yasadi 3) bootstrap/app.php ga bitta qator qo'shdi 4) personal_access_tokens migratsiyasini bajardi

Uchinchi qadamni o'z ko'zingiz bilan ko'ring:

bootstrap/app.php ->withRouting( web: __DIR__.'/../routes/web.php', api: __DIR__.'/../routes/api.php', // ← qo'shildi commands: __DIR__.'/../routes/console.php', health: '/up', )

Va yasalgan fayl:

routes/api.php Route::get('/user', function (Request $request) { return $request->user(); })->middleware('auth:sanctum');
php artisan route:list --path=api GET|HEAD api/user routes/api.php:6

🔍 Manzil api/user — fayl ichida /user deb yozilgan bo'lsa ham. Sehr yo'q: withRouting(api: ...) bu faylga /api prefiksini avtomatik qo'shadi.

REST — manzil emas, resurs

24-darsda Route::resource ni ko'rgan edik. API'da o'sha fikr yanada qat'iyroq: manzil narsani bildiradi, fe'l amalni.

GET /api/vakansiyalar → ro'yxatni ber POST /api/vakansiyalar → yangisini yarat GET /api/vakansiyalar/7 → 7-raqamlisini ber PUT /api/vakansiyalar/7 → 7-raqamlisini yangila DELETE /api/vakansiyalar/7 → 7-raqamlisini o'chir

Ikkita manzil, beshta amal. Fe'lni ko'rgan mijoz nima bo'lishini oldindan biladi — bu REST'ning asosiy foydasi.

⚠️ Fe'lni manzilga solmang
/api/vakansiyalar/yarat ⚠️ /api/vakansiya-ochirish/7 ⚠️ /api/getVakansiyalar ⚠️ /api/vakansiyalar + POST ✅ /api/vakansiyalar/7 + DELETE ✅

Birinchi uslubda har amal uchun yangi manzil o'ylab topiladi, va mijoz ularni yodlab olishi kerak. Ikkinchisida qoida bitta.

API controlleri

Web controllerdan alohida yozamiz — javob shakli boshqa bo'lgani uchun. Papka ham alohida:

php artisan make:controller Api/VakansiyaController INFO Controller [app/Http/Controllers/Api/VakansiyaController.php] created successfully.
app/Http/Controllers/Api/VakansiyaController.php <?php namespace App\Http\Controllers\Api; use App\Http\Controllers\Controller; use App\Models\Vakansiya; use Illuminate\Http\JsonResponse; use Illuminate\Http\Request; class VakansiyaController extends Controller { public function index(): JsonResponse { $vakansiyalar = Vakansiya::query() ->with('kompaniya') ->latest('id') ->take(10) ->get(); return response()->json($vakansiyalar); } public function show(string $id): JsonResponse { $vakansiya = Vakansiya::with('kompaniya')->findOrFail($id); return response()->json($vakansiya); } public function store(Request $request): JsonResponse { $tekshirilgan = $request->validate([ 'nom' => ['required', 'string', 'min:5', 'max:100'], 'maosh' => ['required', 'integer', 'min:1'], ]); $vakansiya = Vakansiya::create($tekshirilgan); return response()->json($vakansiya, 201); } }
routes/api.php use App\Http\Controllers\Api\VakansiyaController; Route::get('/vakansiyalar', [VakansiyaController::class, 'index']); Route::get('/vakansiyalar/{id}', [VakansiyaController::class, 'show']); Route::post('/vakansiyalar', [VakansiyaController::class, 'store']);
Sehr yo'q: model qanday JSON bo'ladi

response()->json($vakansiya) ishlaydi, chunki Eloquent modeli JsonSerializable interfeysini bajaradi. PHP'ning json_encode funksiyasi shu interfeysni ko'radi va modeldan atributlar massivini so'raydi.

Yuklangan bog'lanishlar ham qo'shiladi — shuning uchun with('kompaniya') yozganimizda javobda ichma-ich kompaniya obyekti paydo bo'ldi.

->with('kompaniya') → javobda "kompaniya": { "id": 1, "nom": "Softex Lab", ... } without with(...) → "kompaniya" kaliti UMUMAN bo'lmaydi

🔑 Ya'ni 29-darsdagi N+1 muammosi API'da ham xuddi shunday: with() ni unutsangiz ro'yxat sekinlashadi.

Status kodlar — o'lchangan

GET /api/vakansiyalar → 200 application/json, 10 ta yozuv GET /api/vakansiyalar/30 → 200 bitta obyekt GET /api/vakansiyalar/999999 → 404 {"message": "No query results ..."} POST /api/vakansiyalar (to'g'ri) → 201 yaratilgan obyekt + id POST /api/vakansiyalar (xato) → 422 {"message": ..., "errors": {...}}

Ikkitasi yangi va ular API'ga xos:

201 Created → «yaratdim». 200 emas, chunki YANGI narsa paydo bo'ldi. 422 Unprocessable → «so'rovingni tushundim, lekin ma'lumot qoidaga mos emas»

422 ni 400 bilan chalkashtirmang: 400 — so'rovning o'zi buzuq (masalan JSON sintaksisi xato). 422 — so'rov to'g'ri o'qildi, lekin mazmuni qoidalarga mos emas.3

422 javobining shakli

{ "message": "The nom field must be at least 5 characters. (and 1 more error)", "errors": { "nom": ["The nom field must be at least 5 characters."], "maosh": ["The maosh field must be an integer."] } }

Bu shakl Laravel standarti — 20-darsdagi $errors ning JSON ko'rinishi. Mijoz uni maydonlar bo'yicha ajratib, formaning tegishli joyiga chiqara oladi.

⚠️ Xabarlar inglizcha — chunki API controllerda messages() yozmadik. 35-darsdagi Form Request bu yerda ham ishlaydi va o'zbekcha xabar berish mumkin.

201 javobi

status: 201 {"nom":"API orqali qoshilgan","maosh":7000000, "updated_at":"2026-08-21T05:02:51.000000Z", "created_at":"2026-08-21T05:02:51.000000Z","id":30}

Yaratilgan obyekt qaytariladi — va eng muhimi, unda id bor. Mijoz uni saqlab qo'yadi va keyingi so'rovlarda ishlatadi.

🔍 Kalitlar tartibiga qarang: id oxirida. Chunki u bazadan qaytgandan keyin qo'shildi. JSON'da kalitlar tartibi ahamiyatsiz — mijoz nom bo'yicha o'qiydi.

⚠️ Accept — API mijozining eng muhim sarlavhasi

Bu darsning eng ko'p vaqt yeydigan tuzog'i. Xuddi shu so'rovni ikki xil yuboramiz — farq faqat bitta sarlavhada:

Accept: application/json BILAN → 422 application/json {"message": ..., "errors": {...}} ✅ Accept sarlavhasiSIZ → 302 text/html Location: http://127.0.0.1:8407/ ⚠️ <!DOCTYPE html> <meta http-equiv="refresh" ...>

Nima bo'ldi? Laravel so'rovni brauzerdan kelgan deb hisobladi va 35-darsdagi odatiy yo'lni tanladi: validatsiya xatosida back() qilish. Mijoz esa JSON kutayotgan edi.

404 da ham xuddi shunday:

Accept siz 404 → text/html <!DOCTYPE html>... (chiroyli xato sahifasi)
🔑 Ikki yechim — ikkalasi ham to'g'ri

1) Mijoz tomonda: har so'rovga sarlavha qo'shing. Bu REST qoidasi va barcha kutubxonalar shuni qiladi.

curl -H "Accept: application/json" ... fetch(url, { headers: { 'Accept': 'application/json' } })

2) Server tomonda: api/* har doim JSON qaytarsin deb bir marta sozlang:

// bootstrap/app.php ->withExceptions(function (Exceptions $exceptions): void { $exceptions->shouldRenderJsonWhen( fn (Request $request) => $request->is('api/*') || $request->expectsJson(), ); })

Shundan keyin Accept siz yuborilgan so'rov ham JSON oladi — biz buni o'lchab ko'rdik.

✅ Amalda ikkalasi qilinadi: server ehtiyot chorasi sifatida sozlanadi, mijoz esa baribir to'g'ri sarlavha yuboradi.

🔍 Tashxis: API'dan 302 yoki text/html kelsa — birinchi navbatda Accept sarlavhasini tekshiring. Bu 38-darsdagi «xato xabari boshqa tomonga olib ketadi» holatining API'dagi ko'rinishi.

⚠️ APP_DEBUG va xato javoblari

404 javobini ikki sozlamada o'lchadik:

APP_DEBUG=true { "message": "No query results for model [App\\Models\\Vakansiya] 999999", "exception": "Symfony\\Component\\HttpKernel\\Exception\\NotFoundHttpException", "file": "/home/.../vendor/laravel/framework/src/.../Handler.php", "line": 521, "trace": [ ... ] } APP_DEBUG=false { "message": "No query results for model [App\\Models\\Vakansiya] 999999" }

true bo'lganda javob serveringizning fayl yo'llarini, Laravel versiyasini va butun chaqiruvlar zanjirini oshkor qiladi. Bu ishlab chiqishda foydali, internetda esa xavfli.

🔑 .env da APP_DEBUG=false — serverga chiqarishdagi birinchi qoida. API'da uning oqibati ayniqsa yaqqol ko'rinadi: HTML sahifada xato ekranda qolardi, JSON javobda esa u mijozning kodiga matn bo'lib boradi va o'sha yerda saqlanib qolishi mumkin.
🔍 O'lchangan: true holatida javobda message, exception, file, line va 36 bosqichli trace bo'ldi.

⚠️ Diqqat: false bo'lganda ham xabar modelning to'liq nomini aytadi: App\Models\Vakansiya. Buni ham yashirish mumkin — bootstrap/app.php da ModelNotFoundException uchun o'z javobingizni berish orqali.

🔍 API'da CSRF tokeni yo'q

32-darsda CSRF ni o'rgangan edik: tokensiz POST 419 olardi. API'da esa:

curl -X POST /api/vakansiyalar (token YO'Q) → 201 Created

Bu xato emas, ataylab shunday. Sababi:

CSRF hujumi → brauzer SESSIYA cookie'sini avtomatik yuborishiga tayanadi API mijozi → sessiya ishlatmaydi, TOKEN yuboradi (shu modulda) cookie yo'q → hujum ham yo'q

routes/web.php va routes/api.php ikki xil middleware to'plamiga tushadi: birinchisida sessiya va CSRF bor, ikkinchisida yo'q.

⚠️ Lekin «himoya yo'q» degani emas: hozir bizning API ochiq — istalgan odam vakansiya qo'sha oladi. Shu modulda Sanctum tokenlari bilan yopamiz. install:api Sanctum'ni allaqachon o'rnatib qo'ygani shundan.

API testlari

Modul E'dagi hamma narsa shu yerda ham ishlaydi — faqat get/post o'rniga getJson/postJson ishlatiladi. Ular Accept: application/json sarlavhasini o'zi qo'yadi.

tests/Feature/ApiVakansiyaTest.php test('ro\'yxat JSON qaytaradi', function () { $kompaniya = Kompaniya::factory()->create(['nom' => 'Softex Lab']); Vakansiya::factory()->count(3)->for($kompaniya, 'kompaniya')->create(); $javob = $this->getJson('/api/vakansiyalar'); $javob->assertOk(); $javob->assertJsonCount(3); $javob->assertJsonStructure([ '*' => ['id', 'nom', 'maosh', 'kompaniya' => ['id', 'nom']], ]); }); test('bitta vakansiya JSON qaytaradi', function () { $vakansiya = Vakansiya::factory()->create(['nom' => 'Backend dasturchi']); $this->getJson("/api/vakansiyalar/{$vakansiya->id}") ->assertOk() ->assertJsonPath('nom', 'Backend dasturchi') ->assertJson(['id' => $vakansiya->id]); }); test('mavjud bo\'lmagan vakansiya 404 beradi', function () { $this->getJson('/api/vakansiyalar/999999') ->assertNotFound() ->assertJsonStructure(['message']); }); test('yangi vakansiya 201 bilan yaratiladi', function () { $javob = $this->postJson('/api/vakansiyalar', [ 'nom' => 'Backend dasturchi', 'maosh' => 9000000, ]); $javob->assertCreated(); $javob->assertJsonPath('nom', 'Backend dasturchi'); $this->assertDatabaseHas(Vakansiya::class, ['nom' => 'Backend dasturchi']); }); test('xato ma\'lumot 422 beradi', function () { $javob = $this->postJson('/api/vakansiyalar', [ 'nom' => 'abc', 'maosh' => 'matn', ]); $javob->assertStatus(422); $javob->assertJsonValidationErrors(['nom', 'maosh']); $this->assertDatabaseMissing(Vakansiya::class, ['nom' => 'abc']); });
✓ ro'yxat JSON qaytaradi 0.12s ✓ bitta vakansiya JSON qaytaradi 0.01s ✓ mavjud bo'lmagan vakansiya 404 beradi 0.01s ✓ yangi vakansiya 201 bilan yaratiladi 0.01s ✓ xato ma'lumot 422 beradi 0.01s Tests: 5 passed (34 assertions)

Yangi tekshiruvlar:

assertJsonCount(3) → massivda nechta element assertJsonPath('nom', '...') → aniq yo'ldagi qiymat assertJson(['id' => 5]) → javob SHU kalitlarni o'z ichiga oladimi assertJsonStructure([...]) → SHAKL to'g'rimi (qiymatlar muhim emas) assertJsonValidationErrors([...]) → 422 dagi errors kalitlari assertCreated() → 201 assertNotFound() → 404

🔑 assertJsonStructure va assertJsonPath farqi muhim: birinchisi shaklni tekshiradi (kalitlar bormi), ikkinchisi qiymatni. Mijoz uchun ikkalasi ham shartnoma — kalit nomi o'zgarsa uning kodi buziladi.

⚠️ Model to'liq ochilib ketdi

Javobga yana bir marta qarang:

{ "id": 30, "nom": "Backend dasturchi", "maosh": 9000000, "shahar": null, "faol": true, "kompaniya_id": 1, "created_at": "...", "updated_at": "...", "masofadan": false, "user_id": 2 ← ⚠️ ichki maydonlar }

Mijozga hamma narsa ketdi: ichki kalitlar (kompaniya_id, user_id), texnik vaqt belgilari, va ertaga qo'shiladigan har qanday yangi ustun.

Ikki muammo bor:

1) Xavfsizlik → ichki ma'lumot tashqariga chiqadi 2) Shartnoma → bazaga ustun qo'shsangiz, API javobi O'ZGARADI mijozning kodi esa buni kutmaydi

🔑 Ikkinchisi jiddiyroq: bazangiz ichki narsa, API esa tashqi shartnoma. Ular bir-biriga yopishib qolmasligi kerak.

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

routes/api.php yo'q

Route::get('/api/vakansiyalar', ...) → web.php ga yozilsa ISHLAYDI, lekin sessiya va CSRF bilan birga

Laravel 11+ da api.php standart holda yo'q. Ko'plab qo'llanmalar undan foydalanadi va «menda bunday fayl yo'q» degan chalkashlik tug'iladi.

✅ php artisan install:api. Faylni qo'lda yasash yetarli emas — bootstrap/app.php ga api: ... qatori ham kerak.

🔍 API marshrutini web.php ga yozish ishlaydi, lekin u sessiya va CSRF middleware'iga tushadi — tokensiz POST 419 oladi.

HOLAT 2

Accept sarlavhasi unutilishi

Accept siz: 422 o'rniga → 302 + text/html 404 o'rniga → HTML xato sahifasi

Eng ko'p vaqt yeydigan API tuzog'i, chunki xato mijoz tomonda ko'rinadi: JSON kutgan kod HTML oladi va tushunarsiz xato beradi.

✅ curl bilan sinayotganda har doim -H "Accept: application/json" qo'shing. Testda getJson/postJson buni o'zi qiladi.

✅ Serverda esa shouldRenderJsonWhen ni sozlang — o'shanda api/* har doim JSON qaytaradi.

HOLAT 3

APP_DEBUG=true serverda

{"message": "...", "exception": "...", "file": "/home/...", "trace": [...]}

Javob serveringiz haqida ko'p narsani aytadi: fayl yo'llari, kutubxona versiyalari, chaqiruvlar zanjiri. Hujumchi uchun bu xarita.

✅ Serverda APP_DEBUG=false. O'zgartirgandan keyin php artisan config:clear.

🔍 Tekshirish oson: curl bilan mavjud bo'lmagan manzilga so'rov yuboring va javobda file kaliti bor-yo'qligiga qarang.

HOLAT 4

API'da CSRF yo'qligi

POST /api/vakansiyalar (tokensiz) → 201 Created

Bu to'g'ri: CSRF hujumi brauzerning cookie'ni avtomatik yuborishiga tayanadi, API mijozi esa cookie emas, token ishlatadi.

⚠️ Lekin hozircha bizning API umuman himoyasiz — istalgan odam e'lon qo'sha oladi. Bu Sanctum darsigacha shunday qoladi.

🔍 Istisno: agar API'ni brauzerdan sessiya bilan ishlatsangiz (SPA), CSRF yana kerak bo'ladi — Sanctum buning uchun alohida rejimga ega.

HOLAT 5

Model to'g'ridan-to'g'ri qaytarilishi

return response()->json($vakansiya); → BARCHA ustunlar mijozga ketadi

Bugungi kodimiz aynan shunday. Bazaga yangi ustun qo'shsangiz — u avtomatik API javobiga tushadi, siz xohlaysizmi-yo'qmi.

⚠️ Teskarisi ham yomon: ustun nomini o'zgartirsangiz mijozning kodi buziladi, chunki u maosh kalitiga tayangan edi.

✅ Vaqtinchalik chora — modelda $hidden. To'liq yechim esa API Resource (43-dars): javob shakli alohida faylda yoziladi va bazadan mustaqil bo'ladi.

HOLAT 6

Validatsiya xabarlari inglizcha

"The nom field must be at least 5 characters."

Web tomonda 35-darsda messages() yozgan edik, API controllerda esa oddiy $request->validate([...]) ishlatildi.

✅ Form Request bu yerda ham ishlaydi — rules(), messages(), authorize() hammasi bir xil. Farqi faqat javob shaklida: web'da 302, API'da 422 JSON.

🔍 Ya'ni bitta Form Request'ni ikkala controllerda ishlatish mumkin — Laravel javob shaklini Accept ga qarab o'zi tanlaydi.

HOLAT 7

Route nomlari va prefiks

routes/api.php da: Route::get('/vakansiyalar', ...) haqiqiy manzil: /api/vakansiyalar ← prefiks avtomatik

Prefiksni qo'lda yozsangiz /api/api/vakansiyalar chiqadi — 34-darsdagi make:enum Enums/Rol tuzog'i bilan bir xil naqsh.

✅ Nomlash uchun guruh ishlatish qulay:

Route::name('api.')->group(function () { Route::get('/vakansiyalar', [...])->name('vakansiyalar.index'); }); // → route('api.vakansiyalar.index') = http://.../api/vakansiyalar

🔍 php artisan route:list --path=api — haqiqiy manzillarni ko'rishning eng tez usuli.

💻 Amaliy qism kompyuterda

Amaliyotda API qatlamini yoqasiz, uchta endpoint yozasiz va curl bilan barcha status kodlarni ko'rasiz. Yo'lda Accept sarlavhasini ataylab tashlab, JSON o'rniga HTML kelishini kuzatasiz.

Sinab ko'ramiz

Natijani taxmin qiling

Mobil ilova dasturchisi IshTop API'sidan foydalanmoqchi. U shunday kod yozdi:

mobil ilovadagi so'rov
fetch('https://ishtop.uz/api/vakansiyalar', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ nom: 'abc', maosh: 'matn' }) }) .then(r => r.json()) .then(d => console.log(d.errors));

Server tomonda shouldRenderJsonWhen sozlanmagan. Dasturchi 422 va xatolar ro'yxatini kutyapti. Nima ko'radi?

Javobni ko'rish
status: 302 Content-Type: text/html Location: https://ishtop.uz/ r.json() → SyntaxError: Unexpected token '<'

Mijoz Accept sarlavhasini yubormadi. Laravel so'rovni brauzerdan kelgan deb hisobladi va validatsiya xatosida back() qildi — HTML qaytardi.

⚠️ Va endi eng yomoni: xato xabari butunlay boshqa narsa haqida. Dasturchi SyntaxError: Unexpected token '<' ni ko'radi va JSON tahlilida muammo qidira boshlaydi — aslida muammo sarlavhada.

Content-Type qo'yilgani yordam bermaydi: u «men nima yuboryapman» degani. Accept esa «men nima kutyapman» degani. Ikki xil savol.

Content-Type: application/json → yuborayotgan ma'lumot shakli Accept: application/json → KUTILAYOTGAN javob shakli ← shu yetishmadi

🔑 Ikki tomonlama yechim:

// mijoz tomonda headers: { 'Content-Type': 'application/json', 'Accept': 'application/json' ← qo'shildi } // server tomonda (bootstrap/app.php) $exceptions->shouldRenderJsonWhen( fn (Request $request) => $request->is('api/*') || $request->expectsJson(), );

🔍 Serverdagi sozlama ehtiyot chorasi: mijozlar xato yozganda ham API o'zini API kabi tutadi. Mijoz tomondagi sarlavha esa to'g'ri usul — u boshqa serverlarda ham ishlaydi.

SAVOL 1 php artisan install:api nima qiladi?

To'rt ish: Sanctum o'rnatadi · routes/api.php yasaydi · bootstrap/app.php ga api: ... qatorini qo'shadi · personal_access_tokens migratsiyasini bajaradi. 🔍 Faylni qo'lda yasash yetarli emas — bootstrap/app.php dagi qator ham kerak.

SAVOL 2 API so'rovida Accept: application/json unutilsa nima bo'ladi?

O'lchandi: validatsiya xatosida 302 va text/html, 404 da esa HTML xato sahifasi. Mijoz SyntaxError: Unexpected token '<' ko'radi va muammoni noto'g'ri joyda qidiradi. ⚠️ Content-Type boshqa savolga javob beradi — u yuborayotgan ma'lumot shakli.

SAVOL 3 201 va 422 nimani bildiradi?

201 Created — 200 emas, chunki yangi narsa paydo bo'ldi; javobda yaratilgan obyekt va uning id si qaytariladi. 422 — so'rov to'g'ri o'qildi, lekin mazmuni qoidaga mos emas. ⚠️ 400 dan farqi: 400 — so'rovning o'zi buzuq.

Eslab ayting

Avval o'zingiz javob bering, keyin ochib tekshiring. Oxirgi ikkitasi — 41-darsni takrorlash.

Model qanday qilib JSON'ga aylanadi?

Sehr yo'q: Eloquent modeli JsonSerializable interfeysini bajaradi va json_encode undan atributlar massivini so'raydi. Yuklangan bog'lanishlar ham qo'shiladi — shuning uchun with('kompaniya') javob shaklini o'zgartiradi.

Nega API'da CSRF tokeni kerak emas?

CSRF hujumi brauzerning sessiya cookie'sini avtomatik yuborishiga tayanadi. API mijozi sessiya emas, token ishlatadi — cookie yo'q, hujum ham yo'q. ⚠️ Lekin hozircha API umuman himoyasiz.

Content-Type va Accept farqi?

Content-Type — «men nima yuboryapman». Accept — «men nima kutyapman». API'dan JSON olish uchun ikkinchisi kerak.

Metod jimgina o'tkazib yuboriladi — xato ham, ogohlantirish ham yo'q. Yangi test yozgach Tests: N passed dagi N ortdimi — shuni kuzating.
