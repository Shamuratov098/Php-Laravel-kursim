N+1 — nihoyat raqamda

29-darsdan tanish kod. 200 ta vakansiyani olib, har birining kompaniyasini so'raymiz:

So'rovlarni sanaymiz:

usul so'rov vaqt ────────────────────────────────────────────── N+1 (with YO'Q) 201 22.9 ms with() bilan 2 2.5 ms load() bilan 2 2.4 ms withCount 1 13.0 ms

Nomi shundan: 1 ta so'rov ro'yxat uchun va N ta (200) har bir element uchun.

🔑 Nega 22.9 ms «yomon» hisoblanadi?

22 millisekund kichik ko'rinadi. Lekin uchta narsa bor:

1) MASSHTAB: 200 emas, 2000 yozuv bo'lsa — 2001 so'rov 2) MASOFA: bizda baza bir faylda. Alohida serverda har so'rov ~1 ms tarmoq vaqti — 200 ms qo'shiladi 3) YUKLAMA: 100 foydalanuvchi = 20 100 so'rov

🔍 load() — with() ning kech ko'rinishi: kolleksiya allaqachon olingan bo'lsa ishlatiladi. Natija bir xil: 2 so'rov.

withCount esa 1 so'rov — u bog'liq yozuvlarni olmaydi, faqat sanaydi (SQL'ning ichida sanaladi).

EXPLAIN QUERY PLAN — baza nima qilyapti

Baza so'rovni qanday bajarishini aytib beradi:

EXPLAIN QUERY PLAN select * from vakansiyalar where shahar = ? SCAN vakansiyalar

SCAN — «hamma qatorni boshdan oxirigacha o'qidim». 50 000 yozuvda bu 50 000 tekshiruv.

Indeks qo'shamiz:

create index vakansiyalar_shahar_index on vakansiyalar (shahar); EXPLAIN QUERY PLAN select * from vakansiyalar where shahar = ? SEARCH vakansiyalar USING INDEX vakansiyalar_shahar_index (shahar=?)

SEARCH ... USING INDEX — «indeksdan topib oldim». Reja o'zgardi. Vaqt-chi?

⚠️ Indeks haqidagi eng keng tarqalgan noto'g'ri tushuncha

shahar = ? (indekssiz) 7.71 ms shahar = ? (indeksli) 7.29 ms ⚠️ deyarli bir xil

Indeks qo'shdik, reja SEARCH ga o'zgardi — tezlik esa deyarli o'zgarmadi. Nega?

Chunki bu so'rov ~7000 ta yozuv qaytaradi (50 000 ning yettidan biri). Indeks ularni tez topdi, lekin baribir hammasini o'qib berish kerak.

Endi tanlovchan so'rov — bitta yozuv qaytaradi:

nom = 'Vakansiya 49999' indekssiz: SCAN vakansiyalar 1.868 ms indeksli: SEARCH ... USING INDEX (nom=?) 0.043 ms → 43 BAROBAR tez
🔑 Qoida
Indeks TOPISHNI tezlashtiradi, O'QIB BERISHNI emas. Foyda katta: so'rov OZ yozuv qaytarsa (id, email, slug bo'yicha) Foyda kichik: so'rov KO'P yozuv qaytarsa (jadvalning yarmi)

Buni «tanlovchanlik» deyiladi: ustunda qancha har xil qiymat bo'lsa, indeks shuncha foydali.

email → har bir yozuvda boshqa → indeks ZO'R shahar → 7 xil qiymat → indeks o'rtacha faol → 2 xil qiymat (true/false) → indeks deyarli BEFOYDA

⚠️ Shuning uchun «har ustunga indeks qo'yaman» — yomon strategiya: har indeks yozishni sekinlashtiradi va joy oladi.

Yana ikkita o'lchov

count(*) where shahar = ? (indeksli) 0.170 ms select * where shahar = ? (indeksli) 7.397 ms

Bir xil shart, 43 barobar farq. Sabab: count(*) uchun baza yozuvlarga tegmaydi — javob indeksning o'zida bor.

EXPLAIN QUERY PLAN select * from vakansiyalar where nom like '%dasturchi%' SCAN vakansiyalar ⚠️

Va 46-darsdagi qidiruvimiz — whereLike('nom', "%{$matn}%") — indeksdan foydalana olmaydi. Indeks alifbo tartibida saqlanadi, «ichida» qidirish esa tartibga tayana olmaydi.

🔍 Bu haqiqiy cheklov, va yechimi boshqa vositalarda: to'liq matnli qidiruv (MySQL FULLTEXT, PostgreSQL tsvector) yoki qidiruv xizmatlari (Meilisearch, Algolia).

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Qo'shma indeks va tartib

$table->index(['shahar', 'faol']); → bitta indeks, ikki ustun where shahar = ? and faol = ? → ISHLAYDI where shahar = ? → ISHLAYDI (chapdan boshlanadi) where faol = ? → ISHLAMAYDI ⚠️

Qo'shma indeks — telefon kitobi kabi: familiya+ism bo'yicha tartiblangan. Familiya bilan topasiz, faqat ism bilan — yo'q.

🔑 Shuning uchun tartib muhim: eng ko'p ishlatiladigan (va eng tanlovchan) ustun oldinda.

HOLAT 2

Indeksning narxi

indeks TEZLASHTIRADI: select ... where indeks SEKINLASHTIRADI: insert · update · delete indeks JOY OLADI: jadval hajmining 10-30% i

Har insert da baza hamma indeksni yangilashi kerak. Beshta indeksli jadvalga yozish beshta qo'shimcha ish.

✅ Qoida: indeksni o'lchov asosida qo'shing, «ehtimol kerak bo'lar» deb emas.

🔍 Ishlatilmayotgan indekslarni topish: MySQL'da sys.schema_unused_indexes, PostgreSQL'da pg_stat_user_indexes.

HOLAT 3

Faqat kerakli ustunlarni olish

❌ Vakansiya::with('kompaniya')->get() ✅ Vakansiya::with('kompaniya:id,nom')->select('id','nom','kompaniya_id')->get()

Katta jadvalda (uzun matn ustunlari bilan) farq sezilarli: baza kamroq o'qiydi, PHP kamroq xotira oladi.

⚠️ with('kompaniya:id,nom') da id ni albatta qo'shing — usiz Laravel bog'lanishni ulay olmaydi va kompaniya null bo'ladi.

🔍 select da esa kompaniya_id kerak — aks holda with ishlamaydi.

HOLAT 4

chunkById va cursor

Vakansiya::chunk(1000, ...) → limit/offset — chuqurda SEKIN (46-dars) Vakansiya::chunkById(1000, ...) → where id > ? — har doim tez ✅ Vakansiya::cursor() → bitta so'rov, bittalab o'qish (52-dars)

⚠️ chunk bilan siklda yozuvlarni yangilasangiz yoki o'chirsangiz, offset siljiydi va ba'zi yozuvlar o'tkazib yuboriladi.

✅ Yozish bor bo'lsa — har doim chunkById.

HOLAT 5

Yashirin N+1: Resource ichida

// VakansiyaResource 'kompaniya' => $this->kompaniya->nom, ⚠️ har element uchun so'rov // to'g'risi (43-dars): 'kompaniya' => KompaniyaResource::make($this->whenLoaded('kompaniya')),

N+1 controllerda emas, Resource da yoki Blade da tug'ilishi mumkin — kod boshqa faylda bo'lgani uchun ko'zga tashlanmaydi.

✅ whenLoaded() (43-dars) va preventLazyLoading — ikkalasi birga ishlaydi: birinchisi yashiradi, ikkinchisi xato beradi.

HOLAT 6

SQLite va MySQL farqi

SQLite: EXPLAIN QUERY PLAN → SCAN / SEARCH USING INDEX MySQL: EXPLAIN → type: ALL / ref / const, rows, key PostgreSQL: EXPLAIN ANALYZE → Seq Scan / Index Scan, haqiqiy vaqt

Tushuncha bir xil, chiqish shakli boshqacha. MySQL'da eng muhim ustunlar: type (ALL — yomon), key (qaysi indeks) va rows (nechta qator ko'rildi).

⚠️ Va rejalar farq qiladi: SQLite'da tez so'rov MySQL'da sekin bo'lishi mumkin. Shuning uchun tezlikni ishlab chiqarishdagi baza bilan o'lchash kerak (61-darsda MySQL'ga o'tamiz).

HOLAT 7

Sekin so'rovlarni topish tartibi

1) O'LCHANG → Telescope yoki DB::listen bilan sanang 2) ENG SEKININI TOPING → odatda bitta so'rov 80% vaqtni oladi 3) EXPLAIN qiling → SCAN mi? nechta qator ko'rildi? 4) TUZATING → with() / indeks / select() / kesh 5) QAYTA O'LCHANG → haqiqatan yordam berdimi? 6) TEST YOZING → qaytib kelmasin

⚠️ Eng ko'p uchraydigan xato — 3-qadamni o'tkazib yuborish: «sekin ekan, indeks qo'yaman». Biz bugun ko'rdik: indeks har doim yordam bermaydi.

🔑 DB::listen() — Telescope'siz sanashning eng yengil yo'li:

DB::listen(fn ($q) => logger()->info($q->sql, ['ms' => $q->time]));

Natijani taxmin qiling

Vakansiyalar ro'yxati sahifasi sekin ishlayapti. Dasturchi Telescope'ni ochdi va ko'rdi: bitta so'rovda 153 ta SQL.

Sababni topdi — Blade shablonida:

Tuzatdi:

Telescope'da qayta tekshirdi: 153 → 3 so'rov. Sahifa tezlashdi. Commit qildi.

Ikki hafta o'tib sahifa yana sekin bo'ldi. Telescope'da yana 153 ta so'rov. Kod esa o'zgarmagan — with([...]) hamon joyida. Nima bo'lgan?

@foreach ($vakansiyalar as $v) {{ $v->kompaniya->nom }} {{ $v->konikmalar->count() }} ta ko'nikma {{ $v->egasi->name }} ← YANGI, with() da YO'Q @endforeach

Eslab ayting

Javobni ovoz chiqarib ayting, keyin ochib solishtiring.

N+1 nima va uni qanday o'lchaysiz?
1 ta so'rov ro'yxat uchun + N ta har element uchun. 🔍 O'lchandi (200 yozuv): 201 so'rov / 22.9 ms va with() bilan 2 / 2.5 ms. O'lchash: DB::enableQueryLog() + count(DB::getQueryLog()), yoki Telescope, yoki DB::listen(). withCount — 1 so'rov (yozuvlarni olmaydi, sanaydi).
Indeks nima qiladi va nima qilmaydi?
Indeks topishni tezlashtiradi, o'qib berishni emas. 🔍 O'lchandi: 7000 yozuv qaytaradigan so'rovda 7.71 → 7.29 ms (deyarli farqsiz); 1 yozuv qaytaradiganida 1.868 → 0.043 ms (43 barobar). 🔑 Tanlovchanlik: ustunda qancha har xil qiymat bo'lsa shuncha foydali (email zo'r, faol befoyda). ⚠️ Narxi: insert/update sekinlashadi va joy oladi.
EXPLAIN nimani ko'rsatadi?
Bazaning rejasini. SQLite'da: SCAN (hamma qator) yoki SEARCH ... USING INDEX. MySQL'da: type, key, rows. 🔍 O'lchandi: LIKE '%...%' hamon SCAN — indeks alifbo tartibida saqlanadi, «ichida» qidirish tartibga tayana olmaydi. ⚠️ Rejalar bazadan bazaga farq qiladi.
Telescope nima beradi va narxi nima?
Har so'rov ortidagi SQL, kesh, model, navbat, xat va xatolarni brauzerda ko'rsatadi. 🔍 O'lchandi: bitta statistika so'rovi ortida 14 ta SQL, 4 ta kesh amali, 2 ta model hodisasi. ⚠️ Narxi: ~15% sekinlashuv (~1.52s va ~1.32s) va katta joy. ✅ --dev bilan o'rnating, TELESCOPE_ENABLED=false bilan o'chiring, telescope:prune ni rejaga qo'ying (58-dars).
Sekin so'rovni tuzatish tartibi qanday?
1) O'lchang 2) Eng sekinini toping 3) EXPLAIN qiling 4) Tuzating (with() / indeks / select() / kesh) 5) Qayta o'lchang 6) Test yozing. ⚠️ Eng ko'p uchraydigan xato — 3-qadamni o'tkazib yuborish. 🔑 Oxirgisi eng muhimi: test bilan mixlanmagan tuzatish qaytib keladi.
