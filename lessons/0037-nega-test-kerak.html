Nega test kerak va birinchi test

Oxirgi yetti darsda har o'zgarishdan keyin siz brauzerni ochib, kirib, forma to'ldirib, uch xil odam bilan sinab chiqdingiz. Bu ro'yxat uzayib boradi, va bir kun kelib biror joyni tekshirishni unutasiz. Bugun o'sha ishni mashinaga topshiramiz: bitta buyruq — butun loyiha tekshiriladi.

  6. test() va it() Farqi chiqishda ko'rinadi. O'zbekcha nom uchun qaysi biri to'g'ri keladi — o'lchab ko'rsatiladi.

Qo'lda tekshirish ro'yxati qanday uzaydi

36-darsni tugatganingizda IshTop'da nimalarni sinab ko'rish kerak edi? Sanab chiqamiz:

ro'yxatdan o'tish (rol tanlab) kirish / chiqish vakansiyalar ro'yxati qidiruv va filtr vakansiya qo'shish (ish beruvchi) qo'shishga urinish (nomzod) → 403 tahrirlash (egasi) tahrirlash (begona) → 403 o'chirish validatsiya xatolari rezyume yuklash soxta PDF → xato ochiq/yopiq disk

O'n beshdan ortiq holat. Har biri uchun: brauzerni och, kir, formani to'ldir, natijani ko'r, chiqib boshqa odam bo'lib kir...

Bir marta bajarish — bir necha daqiqa. Muammo shundaki, buni har o'zgarishdan keyin qilish kerak. Amalda esa nima bo'ladi: siz o'zgartirgan joyni sinaysiz, qolganiga tegmadim-ku deb o'ylaysiz.

Va aynan shu «tegmadim-ku» degan joyda xato tug'iladi.

Dalil: ilova ishlayveradi, test tutadi

Buni gapirib emas, o'lchab ko'rsatamiz. 34-darsdagi policy'dan bitta shartni olib tashlaymiz — go'yo shoshib turib qilingan o'zgarish:

Endi saytni oching. Nima ko'rasiz?

Sayt ochiladi. Xato sahifasi YO'Q. Jurnalda xato YO'Q. Hech nima qizil emas. Ish beruvchi vakansiya qo'shadi — ishlaydi.

Hammasi joyida ko'rinadi. Aslida esa nomzodlar ham e'lon joylay oladi — 34-darsda qurilgan butun rol tizimi ochiq. Buni sezish uchun nomzod bo'lib kirib, forma yuborib ko'rish kerak. Kim buni har o'zgarishdan keyin qiladi?

Endi o'sha holatda testni ishga tushiramiz:

Test nima ekanining eng sodda ta'rifi

Test — bu yozib qo'yilgan qo'lda tekshirish. Siz baribir tekshirasiz; savol faqat shu tekshiruv xotirangizda qoladimi yoki faylda.

Xotiradagi tekshiruv: siz bor bo'lsangiz ishlaydi, esingizda bo'lsa ishlaydi, vaqtingiz bo'lsa ishlaydi.
Fayldagi tekshiruv: har safar ishlaydi.

Pest'ni o'rnatamiz

Laravel loyihasida test asbobi allaqachon bor — PHPUnit. IshTop'da ham shunday. Biz uning ustiga Pest ni qo'yamiz: u xuddi shu PHPUnit ustida ishlaydi, faqat yozilishi ancha qisqa.1

PHPUnit'cha: Pest'cha: class VakansiyaTest extends TestCase test('sahifa ochiladi', function () { { $this->get('/vakansiyalar') public function test_sahifa() ->assertStatus(200); { }); $this->get('/vakansiyalar') ->assertStatus(200); } }
composer require pestphp/pest --dev --with-all-dependencies Using version ^4.7 for pestphp/pest INFO Discovering packages.
./vendor/bin/pest --init INFO Preparing tests directory. phpunit.xml .. File already exists. tests/Pest.php .. File created.

🔍 --init yo'lda bitta savol beradi («Pest'ni GitHub'da yulduzlaysizmi?») — Enter bosib o'tib ketishingiz mumkin. Muhimi: u tests/Pest.php faylini yasaydi. Mavjud fayllarga tegmaydi — chiqishda «File already exists» deb aytadi.

tests/ — nima qayerda

tests/ ├── Pest.php ← butun to'plamning sozlamasi ├── TestCase.php ← Laravel'ni testda ishga tushiradi ├── Unit/ ← tez, sof PHP testlari (baza yo'q) └── Feature/ ← HTTP so'rov yuboradigan testlar (baza bor)

Farqi qat'iy qoida emas, kelishuv:

Unit → bitta funksiya yoki klass. Laravel ko'tarilmasa ham bo'ladi. Juda tez (millisoniyalar). Feature → «foydalanuvchi shunday qilsa, natija shunday bo'ladi». Route, controller, baza — hammasi ishlaydi.
🔍 Testlar boshqa bazada ishlaydi

phpunit.xml ni oching:

<env name="APP_ENV" value="testing"/> <env name="DB_CONNECTION" value="sqlite"/> <env name="DB_DATABASE" value=":memory:"/> <env name="BCRYPT_ROUNDS" value="4"/>

:memory: — xotiradagi baza. U test boshlanganda yaratiladi, tugagach yo'q bo'ladi. Sizning database/database.sqlite fayliga tegilmaydi.

Buni sanab tekshirdik — testdan oldin va keyin:

testdan oldin: vakansiyalar: 27 users: 5 testdan keyin: vakansiyalar: 27 users: 5

BCRYPT_ROUNDS=4 ham qasddan: 30-darsdagi parol xeshlash sekin bo'lishi kerak edi, testda esa tezlik muhimroq.

🔑 Birinchi darsdan qoladigan odat: qizil chiqishni oxirigacha o'qing. Pest sizga aynan qaysi faylda, qaysi qatorda, nima kutilgan va nima kelganini aytadi. Bu 4-darsdagi «xatoni o'qish» ko'nikmasining davomi — faqat endi xatoni siz emas, mashina topadi.

Birinchi test: expect()

Eng sodda testdan boshlaymiz — bazasiz, HTTP siz. 34-darsdagi enum'ni tekshiramiz:

tests/Unit/RolTest.php <?php use App\Enums\Rol; test('rol ko\'rinadigan nom beradi', function () { expect(Rol::IshBeruvchi->nomi())->toBe('Ish beruvchi'); expect(Rol::Nomzod->nomi())->toBe('Nomzod'); }); test('matndan rolga aylantiriladi', function () { expect(Rol::from('nomzod'))->toBe(Rol::Nomzod); expect(Rol::tryFrom('boshqa'))->toBeNull(); });

Diqqat: klass yo'q, namespace yo'q, public function yo'q. Faqat test() va ichida funksiya. Pest'ning butun g'oyasi shu.

expect($qiymat)->toBe($kutilgan) // aynan teng (===) expect($qiymat)->toBeNull() // null-mi expect($qiymat)->toBeTrue() // true-mi expect($qiymat)->toBeEmpty() // bo'sh-mi expect($ro'yxat)->toHaveCount(3) // uchta elementmi expect($matn)->toContain('dastur') // ichida bormi
php artisan test tests/Unit
PASS Tests\Unit\RolTest ✓ rol ko'rinadigan nom beradi ✓ matndan rolga aylantiriladi Tests: 2 passed (4 assertions) Duration: 0.04s

🔍 4 ta assertion, 2 ta test. Bitta testda bir necha expect() bo'lishi normal — ular bitta fikrni turli tomondan tekshiryapti.

test() yoki it() — qaysi biri

Pest ikkala nomni ham beradi va ular bir xil ishlaydi. Farq faqat chiqishda ko'rinadi — it() nom oldiga «it» qo'shadi:

it('returns the visible name', ...) → ✓ it returns the visible name test('rol ko\'rinadigan nom beradi', ...) → ✓ rol ko'rinadigan nom beradi

it() inglizcha jumla uchun o'ylab topilgan: «it returns…» — «u qaytaradi…». O'zbekcha nomda esa oldidagi «it» ortiqcha bo'lib qoladi.

🔑 Shu kursda: test() ishlatamiz va nomni o'zbekcha yozamiz. Nom — hujjat: kimdir testni ochmasdan turib ham nima tekshirilayotganini bilishi kerak.

Feature test — haqiqiy so'rov

Endi qiziqrog'i: brauzer o'rniga test so'rov yuboradi.

tests/Feature/VakansiyaTest.php <?php use App\Enums\Rol; use App\Models\User; test('vakansiyalar sahifasi ochiladi', function () { $javob = $this->get('/vakansiyalar'); $javob->assertStatus(200); });

$this->get(...) — bu haqiqiy HTTP so'rovi emas, tarmoqqa chiqmaydi. Laravel so'rovni ichkaridan o'tkazadi: route topiladi, middleware ishlaydi, controller chaqiriladi, Blade render qilinadi. Server ishga tushirish shart emas.

⚠️ Birinchi to'siq: no such table

Ishga tushiring — va shunday chiqadi:

Expected response status code [200] but received 500. PDOException: SQLSTATE[HY000]: General error: 1 no such table: vakansiyalar

Mantiqiy: test xotiradagi bazada ishlaydi, u esa bo'sh — hech qanday migratsiya bajarilmagan.

Yechim tests/Pest.php da turibdi, izohga olingan holda:

tests/Pest.php pest()->extend(TestCase::class) // ->use(RefreshDatabase::class) ← izohni oching ->in('Feature');
pest()->extend(TestCase::class) ->use(RefreshDatabase::class) ->in('Feature');

🔑 RefreshDatabase ikki ish qiladi: har test boshlanishidan oldin migratsiyalarni bajaradi va har test tugagach o'zgarishlarni bekor qiladi.

->in('Feature') — «faqat shu papkadagi testlarga». Unit testlarga baza kerak emas, ular shusiz ham tez ishlaydi.

Nega har testdan keyin tozalanadi

Tasavvur qiling, tozalanmasa: birinchi test bitta vakansiya qo'shdi, ikkinchi test «ro'yxatda nechta yozuv bor?» deb tekshiryapti. Javob testlar tartibiga bog'liq bo'lib qoladi.

Bunday to'plam eng yomon xulqni ko'rsatadi: ba'zan o'tadi, ba'zan yiqiladi. Sababini topish esa haqiqiy xatoni topishdan ham qiyin.

🔑 Har test toza dunyoda boshlanishi kerak — bu testlarning asosiy qoidalaridan biri.

34-darsni test bilan qulflaymiz

Endi eng qimmatlisi: rol tizimi haqiqatan ishlayotganini yozib qo'yamiz.

tests/Feature/VakansiyaTest.php test('ish beruvchi vakansiya qo\'sha oladi', function () { $ishBeruvchi = User::factory()->create(['rol' => Rol::IshBeruvchi]); $javob = $this->actingAs($ishBeruvchi)->post('/vakansiyalar', [ 'nom' => 'Backend dasturchi', 'maosh' => 9000000, ]); $javob->assertRedirect('/vakansiyalar'); $this->assertDatabaseHas('vakansiyalar', [ 'nom' => 'Backend dasturchi', 'user_id' => $ishBeruvchi->id, ]); }); test('nomzod vakansiya qo\'sha olmaydi', function () { $nomzod = User::factory()->create(['rol' => Rol::Nomzod]); $javob = $this->actingAs($nomzod)->post('/vakansiyalar', [ 'nom' => 'Backend dasturchi', 'maosh' => 9000000, ]); $javob->assertStatus(403); $this->assertDatabaseMissing('vakansiyalar', ['nom' => 'Backend dasturchi']); });

Uchta yangi narsa bor:

User::factory()->create([...]) → 28-darsdagi factory. Testda ayni muddao. $this->actingAs($user) → «shu odam sifatida kirgan hisobla» assertDatabaseHas / Missing → bazada yozuv bormi / yo'qmi

actingAs() — 30-darsdagi butun kirish jarayonini chetlab o'tadi: forma to'ldirish, parol tekshirish, sessiya yozish shart emas. Test sizga «bu odam kirgan» deb aytadi va davom etadi.

🔑 Ikkinchi testga alohida qarang: u ikki narsani tekshiryapti. 403 — javob to'g'ri kelganini, assertDatabaseMissing esa yozuv haqiqatan yozilmaganini. Ikkinchisisiz test to'liq emas: 403 qaytarib, ammo yozuvni saqlab qo'yish ham mumkin edi.

php artisan test
PASS Tests\Unit\RolTest ✓ rol ko'rinadigan nom beradi ✓ matndan rolga aylantiriladi PASS Tests\Feature\VakansiyaTest ✓ vakansiyalar sahifasi ochiladi 0.12s ✓ ish beruvchi vakansiya qo'sha oladi 0.02s ✓ nomzod vakansiya qo'sha olmaydi 0.01s Tests: 5 passed (10 assertions) Duration: 0.18s

Qo'lda qilganingizda bir necha daqiqa ketadigan ish — 0.18 soniya. Va endi u har safar bajariladi.

Kerakli testni tanlash

php artisan test --filter=nomzod PASS Tests\Feature\VakansiyaTest ✓ nomzod vakansiya qo'sha olmaydi Tests: 1 passed (2 assertions)
php artisan test tests/Unit

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Birinchi ishga tushirish qizil chiqadi

FAILED Tests\Feature\ExampleTest Expected response status code [200] but received 404.

Laravel qo'ygan namuna test / sahifasini so'raydi. IshTop'da bunday route yo'q. Bu sizning xatongiz emas.

✅ Ikki yechim: namuna testlarni o'chirish (biz shunday qildik) yoki ichidagi '/' ni '/vakansiyalar' ga almashtirish. Bo'sh loyihalarda esa u shunchaki o'tib ketadi — chunki u yerda / bor.

HOLAT 2

no such table

PDOException: no such table: vakansiyalar

Feature testdagi eng birinchi to'siq. Sabab: xotiradagi baza bo'sh, migratsiyalar bajarilmagan.

✅ tests/Pest.php da ->use(RefreshDatabase::class) izohini oching.

🔍 Diqqat: bu qator ->in('Feature') bilan birga yozilgan. Agar Unit testlarda ham baza kerak bo'lsa, papkani qo'shing — lekin odatda kerak emas, va shusiz ular ancha tez.

HOLAT 3

Chiqishda «it» so'zi paydo bo'ladi

✓ it rolning ko'rinadigan nomini beradi ← g'alati o'qiladi ✓ rol ko'rinadigan nom beradi ← toza

it() nom oldiga «it» qo'shadi — inglizcha jumla uchun o'ylab topilgan (it returns…).

✅ O'zbekcha nomlarda test() ishlating. Ikkalasi bir xil ishlaydi, farq faqat chiqishda.

HOLAT 4

Testlar bir-biriga bog'lanib qolsa

// ⚠️ test tashqarisida yaratilgan umumiy ma'lumot $user = User::factory()->create(); // hamma testga bitta test('birinchi', fn () => ... $user ...); test('ikkinchi', fn () => ... $user ...); ← birinchisi uni o'zgartirgan bo'lsa?

Bunday to'plam ba'zan o'tadi. Testlar tartibi o'zgarsa yoki bittasi qo'shilsa — kutilmaganda qiziradi. Sabab esa haqiqiy xatodan ham qiyinroq topiladi.

✅ Har test o'z ma'lumotini o'zi yaratsin. Takrorlanishdan qo'rqmang: testda takrorlanish — aniqlik.

HOLAT 5

Hech nima tekshirmaydigan test

test('vakansiya qo\'shiladi', function () { $this->post('/vakansiyalar', ['nom' => 'Test', 'maosh' => 100]); }); // ⚠️ birorta assert YO'Q ! vakansiya qo'shiladi → This test did not perform any assertions Tests: 1 risky (chiqish kodi: 0)

Pest buni sezadi va risky deb belgilaydi — yaxshi xabar. Yomon xabar: chiqish kodi baribir 0, ya'ni to'plam «o'tdi» hisoblanadi. CI to'xtamaydi, faqat ekranda sariq qator qoladi.

Bu test 403 kelsa ham, 500 kelsa ham bir xil xulq ko'rsatadi — u hech qanday kutish bildirmagan.

✅ Har testda kamida bitta assert* yoki expect() bo'lsin. Yaxshi odat: testni yozgach uni ataylab buzib ko'ring — qizil bo'lmasa, u hech nima tekshirmayapti.

🔍 Biz shu darsda aynan shunday qildik: policy'ni buzib, testning qizil bo'lishini ko'rdik. Bu testga bo'lgan ishonchni tekshirishning eng ishonchli usuli.

HOLAT 6

make:test — skelet yasash

php artisan make:test VakansiyaTest → tests/Feature/ php artisan make:test RolTest --unit → tests/Unit/

Pest o'rnatilgach make:test o'zi Pest uslubida yasaydi — --pest bayrog'i shart emas:

<?php test('example', function () { $response = $this->get('/'); $response->assertStatus(200); });

--unit bilan esa expect(true)->toBeTrue() li sodda skelet chiqadi.

HOLAT 7

To'plam sekinlashsa

Bugun 5 ta test — 0.18 soniya. Yuzta testda vaziyat o'zgaradi, va odatiy sabab bitta: hamma narsa Feature test qilib yozilgan.

Unit : 0.04s / 2 test ← baza yo'q, HTTP yo'q Feature : 0.15s / 3 test ← har biri migratsiya + so'rov

✅ Mantiqni tekshirish uchun Unit yetadi (enum, hisob-kitob, formatlash). Feature testni haqiqiy oqim uchun saqlang: «odam shunday qilsa, natija shunday bo'ladi».

🔍 Ishlab chiqish paytida --filter bilan bitta testni ishlating; to'liq to'plamni commit oldidan.

💻 Amaliy qism kompyuterda

    php artisan tinker --execute="echo App\Models\Vakansiya::count(), ' / ', App\Models\User::count();"

    Kutilgan natija: sonlar testdan oldingi bilan bir xil. Testlar :memory: bazasida ishladi — phpunit.xml ga qarang.

Sinab ko'ramiz

Natijani taxmin qiling

Dasturchi shunday test yozdi. U 36-darsdagi rezyume yuklashni tekshirmoqchi:

tests/Feature/RezyumeTest.php
test('nomzod rezyume yuklaydi', function () { $nomzod = User::factory()->create(['rol' => Rol::Nomzod]); $this->actingAs($nomzod)->post('/rezyume', [ 'rezyume' => UploadedFile::fake()->create('rezyume.pdf'), ]); });

Ishga tushirdi — yashil. U xursand bo'lib commit qildi. Test haqiqatan biror narsani tekshiryaptimi?

Javobni ko'rish
WARN Tests\Feature\RezyumeTest ! nomzod rezyume yuklaydi → This test did not perform any assertions Tests: 1 risky (chiqish kodi: 0 — to'plam baribir MUVAFFAQIYATLI hisoblanadi)

Yashil ✓ emas, sariq ! — Pest buni risky («shubhali») deb belgiladi. Testda birorta assert* yoki expect() yo'q: so'rov yuborildi, javob esa qaralmadi.

⚠️ Eng muhim nozik joy: chiqish kodi baribir 0. Ya'ni to'plam «o'tdi» hisoblanadi va CI hech nimani to'xtatmaydi. Ogohlantirish faqat ekranda — kim uni o'qimasa, sezmaydi ham.

Va bu test 403 kelsa ham, 500 kelsa ham, rezyume umuman saqlanmasa ham xuddi shunday xulq ko'rsatadi. U «kod ishga tushdi» deganini bildiradi, «to'g'ri ishladi» deganini emas.

To'g'ri variant kamida ikki narsani so'raydi — javob va natija:

$javob = $this->actingAs($nomzod)->post('/rezyume', [ 'rezyume' => UploadedFile::fake()->create('rezyume.pdf'), ]); $javob->assertRedirect('/rezyume'); // javob to'g'rimi expect($nomzod->fresh()->rezyume)->not->toBeNull(); // bazaga yozildimi

🔑 Qoida: testni yozgach uni ataylab buzib ko'ring. Kodni buzasiz, testni ishlatasiz — qizil bo'lmasa, test hech nima tekshirmayapti.

🔍 Biz bugun shu usulni policy'da qo'lladik: shartni olib tashladik, test qizil bo'ldi. Demak unga ishonish mumkin.

Va yana bir nozik joy: $nomzod->fresh() — $nomzod o'zgaruvchisi test boshida olingan eski nusxa. So'rov bazani o'zgartirdi, lekin PHP'dagi obyekt buni bilmaydi. fresh() uni bazadan qayta o'qiydi.

SAVOL 1 Testlar qaysi bazada ishlaydi?

phpunit.xml da DB_DATABASE=:memory: — test boshlanganda yaratiladi, tugagach yo'qoladi. Testdan oldin va keyin sanadik: 27 / 5 → 27 / 5. RefreshDatabase esa o'sha bo'sh bazaga migratsiyalarni quyadi.

SAVOL 2 Feature testda no such table chiqsa sabab nima?

tests/Pest.php da ->use(RefreshDatabase::class) qatori standart holda izohga olingan. Xotira bazasi bo'sh bo'lgani uchun birinchi so'rov PDOException beradi. Bitta izohni ochish — masala hal.

SAVOL 3 Testda birorta assert bo'lmasa nima bo'ladi?

Pest sariq ! bilan This test did not perform any assertions deb ogohlantiradi. ⚠️ Lekin chiqish kodi 0 — to'plam muvaffaqiyatli hisoblanadi va CI to'xtamaydi. Ogohlantirishni faqat o'qigan odam ko'radi. 🔑 Yozgan testingizni ataylab buzib ko'ring: qizil bo'lmasa, u hech nima tekshirmayapti.

Eslab ayting

Avval o'zingiz javob bering, keyin ochib tekshiring. Oxirgi ikkitasi — 36-darsni takrorlash.

test() va it() farqi nimada?

Ishlashida farq yo'q. it() chiqishda nom oldiga «it» qo'shadi — inglizcha jumla uchun. O'zbekcha nomda test() toza o'qiladi.

RefreshDatabase nima qiladi?

Har test oldidan migratsiyalarni bajaradi, har test keyin o'zgarishlarni bekor qiladi. Shunda har test toza dunyoda boshlanadi va testlar bir-biriga bog'lanmaydi.

Testga ishonish mumkinligini qanday tekshirasiz?

Kodni ataylab buzib, testni ishlatasiz. Qizil bo'lsa — test ishlayapti. Yashil qolsa — u hech nima tekshirmayapti (masalan assert yo'q).

↩︎ Takrorlash: rezyume qaysi diskka saqlanadi va nega?

'local' — storage/app/private. Uning URL i yo'q, faylni faqat controller bera oladi va o'shanda huquq tekshiriladi. Ochiq diskdagi faylni mehmon 200 bilan olgan edi.

↩︎ Takrorlash: mimes:pdf nimaga qaraydi?

Faylning ichiga, nomiga emas. Nomi .pdf bo'lgan matn fayl tutilgan edi. getClientOriginalExtension() esa yolg'on gapiradi — u foydalanuvchidan keladi.

Cho'ntak xulosasi
  • Test — yozib qo'yilgan qo'lda tekshirish. Siz baribir tekshirasiz; savol — u xotirangizda qoladimi yoki faylda.
  • Dalil o'lchandi: policy'dan bitta shart olib tashlanganda sayt bemalol ishladi, xato chiqmadi — test esa 0.18 soniyada qizil bo'ldi.
  • O'rnatish: composer require pestphp/pest --dev --with-all-dependencies, keyin ./vendor/bin/pest --init.
  • Pest PHPUnit ustida ishlaydi — klass, namespace, public function yozilmaydi.
  • tests/Unit — tez, bazasiz. tests/Feature — HTTP so'rov, route, controller, baza. tests/Pest.php — butun to'plamning sozlamasi.
  • 🔍 phpunit.xml: DB_DATABASE=:memory: — testlar haqiqiy bazangizga tegmaydi (sanab tekshirildi). BCRYPT_ROUNDS=4 — testda tezlik uchun.
  • expect($x)->toBe(...) · toBeNull() · toBeTrue() · toHaveCount() · toContain().
  • test() va it() — bir xil ishlaydi. it() chiqishda «it» qo'shadi, shuning uchun o'zbekcha nomda test().
  • ⚠️ Birinchi php artisan test qizil chiqadi: namuna test / ni so'raydi, IshTop'da u yo'q → 404.
  • ⚠️ Feature testdagi birinchi to'siq — no such table. Sabab: tests/Pest.php da ->use(RefreshDatabase::class) izohga olingan.
  • $this->get(...) / ->post(...) — tarmoqqa chiqmaydi, server ishga tushirish shart emas.
  • actingAs($user) — kirish jarayonini chetlab o'tadi. User::factory()->create([...]) — 28-darsdagi factory.
  • assertStatus · assertRedirect · assertDatabaseHas · assertDatabaseMissing. Taqiqni tekshirganda ikkalasi: javob va bazaning holati.
  • ⚠️ assert siz test risky deb belgilanadi (sariq !), lekin chiqish kodi 0 — to'plam baribir o'tadi va CI to'xtamaydi. 🔑 Yozgan testingizni ataylab buzib ko'ring.
  • Har test o'z ma'lumotini o'zi yaratsin — umumiy holat «ba'zan yiqiladigan» testlar tug'diradi.
  • php artisan test · --filter=nomzod · php artisan test tests/Unit. Commit oldidan — to'liq to'plam.
🌱 Keyingi dars

Bugun test asbobini qo'ldan o'tkazdik va uchta testni yozdik. Lekin HTTP javobidan biz atigi ikki narsa so'radik: status va redirect.

Aslida javobda ancha ko'p narsa bor: sahifada qaysi matn chiqdi, qaysi xato xabari ko'rindi, sessiyada nima yozildi, qaysi ma'lumot ko'rinmasligi kerak edi.

38-darsda Feature testlarga chuqurroq kiramiz: assertSee, assertDontSee, assertSessionHasErrors va validatsiya xatolarini test qilish. O'shanda 35-darsdagi Form Request qoidalarini bittalab qulflaymiz.
