DARS 35 · MODUL D — FOYDALANUVCHI VA HUQUQLAR

Form Request: validatsiya o'z uyiga ko'chdi

store() metodiga qarang: huquq tekshiruvi, qoidalar ro'yxati, xato xabarlari va saqlash — hammasi bitta joyda. Bugun ularni alohida klassga ko'chiramiz, controller uch qatorga tushadi. Va darhol foydasini ko'ramiz: tahrirlash amalini qo'shamiz — bitta ham yangi validatsiya qatorisiz.

📱 O'qish ≈ 16 daqiqa 💻 Amaliyot ≈ 25 daqiqa Kerak: Dars 34

Bu darsda nimalar bor
  1. Nega controller shishib ketadi Bitta metodda to'rt xil ish. Ikkinchi amal qo'shilganda ro'yxat ko'chiriladi — va ikkitasi asta ajralib ketadi.
  2. make:request Yasalgan skelet: authorize() va rules(). ⚠️ authorize() false qaytaradi — birinchi tuzoq shu.
  3. Type-hint — ulash usuli Controllerda Request o'rniga VakansiyaRequest yozish kifoya. Sehr yo'q: Laravel argument tipini ko'rib, metod tanasidan oldin tekshiradi.
  4. rules() massiv shaklida 'required|string' emas, ['required', 'string'] — nega shu ko'proq ishlatiladi.
  5. messages() va attributes() To'liq xabar yozish yoki faqat maydon nomini o'zbekchalash. Ikkinchisi ancha kam yozuv.
  6. To'siqlar tartibi — o'lchangan CSRF 419 → auth 302 → authorize() 403 → rules() 302 → controller. Har biri alohida sinaldi.
  7. authorize() policy'ni chaqiradi 33- va 34-darsdagi qoidalar shu yerdan ishlatiladi: yaratishda create, tahrirlashda update.
  8. ⚠️ Mehmon holati $this->user() null bo'lishi mumkin. Tekshirmasangiz 403 emas, 500 olasiz.
  9. validated() va all() 🔒 Xavfsizlik farqi o'lchandi: user_id=999 yuborilganda e'lon boshqa odamga yozilib qolishi mumkin edi.
  10. prepareForValidation() Tekshiruvdan oldin ma'lumotni tozalash — probellarni kesish, formatni to'g'rilash.
  11. Foydasi: tahrirlash amali Yangi route, metod va forma qo'shiladi — validatsiya kodi umuman yozilmaydi. Xabarlar o'zi chiqadi.
  12. Har xil holatlar (7 ta) Stub false · all() xavfi · failedAuthorization · attributes qachon ishlaydi · mehmon · @method unutilishi · bitta yoki ikkita klass.
Nega controller shishib ketadi

34-darsdan keyin store() shunday ko'rinadi:

public function store(Request $request): RedirectResponse { $this->authorize('create', Vakansiya::class); ← 1) huquq $tekshirilgan = $request->validate([ ← 2) qoidalar 'nom' => 'required|string|min:5|max:100', 'maosh' => 'required|integer|min:1', ], [ 'nom.required' => 'Vakansiya nomi kiritilishi shart.', ← 3) xabarlar 'nom.min' => 'Vakansiya nomi kamida :min belgidan iborat bo\'lsin.', 'maosh.required' => 'Maosh kiritilishi shart.', 'maosh.integer' => 'Maosh butun son bo\'lishi kerak.', ]); Vakansiya::create(...); ← 4) asl ish return redirect()...; }

To'rt xil ish bitta metodda, va asl ish — saqlash — eng oxirida, ko'rinmay qolgan. Lekin haqiqiy muammo bugun emas, ertaga boshlanadi.

Ertaga tahrirlash amali kerak bo'ladi. Qoidalar bir xil. Nima qilasiz? Ro'yxatni ko'chirasiz. Keyin bir kun kelib max:100 ni max:150 ga o'zgartirasiz — bitta joyda. Ikkinchisi eski holida qoladi va hech kim sezmaydi.

bir xil qoida ikki joyda → bir kun ajraladi → xato tug'iladi

Form Request — validatsiyaning uyi

Laravel'da bu ish uchun alohida klass turi bor:1

php artisan make:request VakansiyaRequest INFO Request [app/Http/Requests/VakansiyaRequest.php] created successfully.

Yasalgan skeletda ikkita metod bor:

app/Http/Requests/VakansiyaRequest.php — yasalgan holicha class VakansiyaRequest extends FormRequest { public function authorize(): bool { return false; // ← ⚠️ DIQQAT } public function rules(): array { return [ // ]; } }
⚠️ Birinchi tuzoq: return false

Skelet hammaga taqiq qo'yib turadi. Agar buni o'zgartirmasdan controllerga ulasangiz, ruxsati bor odam ham 403 oladi.

O'lchandi: Ali — ish beruvchi va policy unga ruxsat beradi. Baribir:

Ali (ish beruvchi) vakansiya qo'shmoqchi → 403

Va sahifada hech qanday tushuntirish yo'q. Siz policy'ni, rolni, hatto bazani tekshirib chiqasiz — muammo esa yangi faylning ikkinchi qatorida.

🔑 Yodda tuting: make:request dan keyin birinchi ish — authorize() ga qarash.

Klassni to'ldiramiz

app/Http/Requests/VakansiyaRequest.php use App\Models\Vakansiya; use Illuminate\Foundation\Http\FormRequest; class VakansiyaRequest extends FormRequest { public function authorize(): bool { $user = $this->user(); if ($user === null) { // ← mehmon holati, pastda tushuntiriladi return false; } $vakansiya = $this->route('vakansiya'); return $vakansiya ? $user->can('update', $vakansiya) // tahrirlash : $user->can('create', Vakansiya::class); // yaratish } public function rules(): array { return [ 'nom' => ['required', 'string', 'min:5', 'max:100'], 'maosh' => ['required', 'integer', 'min:1'], ]; } public function messages(): array { return [ 'nom.required' => 'Vakansiya nomi kiritilishi shart.', 'nom.min' => 'Vakansiya nomi kamida :min belgidan iborat bo\'lsin.', 'maosh.required' => 'Maosh kiritilishi shart.', 'maosh.integer' => 'Maosh butun son bo\'lishi kerak.', ]; } }

Uchta narsaga alohida to'xtalamiz.

1. rules() — massiv shakli

'nom' => 'required|string|min:5|max:100' // vertikal chiziq bilan 'nom' => ['required', 'string', 'min:5', 'max:100'] // massiv bilan ✅

Ikkalasi bir xil ishlaydi. Lekin massiv shakli afzal, chunki qoidalar orasida obyektlar ham bo'lishi mumkin — 34-darsdagi Rule::enum(Rol::class) ni vertikal chiziq bilan yozib bo'lmaydi.

2. authorize() policy'ni chaqiradi

Bu yerda yangi qoida yozilmadi — 33- va 34-darsda yozilgan policy ishlatildi. $this->route('vakansiya') — route'dagi {vakansiya} parametri:

POST /vakansiyalar → {vakansiya} yo'q → create tekshiriladi PUT /vakansiyalar/27 → {vakansiya} bor → update tekshiriladi

Shu bir metod ikkala amalga ham xizmat qiladi.

3. attributes() — arzon o'zbekchalashtirish

Har bir qoidaga xabar yozish uzoq. Ko'pincha faqat maydon nomi o'zbekcha bo'lsa yetadi:

app/Http/Requests/VakansiyaRequest.php public function attributes(): array { return [ 'nom' => 'vakansiya nomi', 'maosh' => 'maosh', ]; }

Natija — max:100 qoidasining o'z xabari yo'q, shuning uchun Laravel standart xabarni ishlatadi, lekin bizning nom bilan:

The vakansiya nomi field must not be greater than 100 characters.

🔍 E'tibor bering: messages() da xabari bor qoidalarga attributes() ta'sir qilmaydi — u yerda butun jumla siznikida.

Controllerga ulash — bitta so'z

Ulash uchun hech qanday ro'yxatdan o'tkazish kerak emas. Argument tipini almashtirasiz, xolos:

app/Http/Controllers/VakansiyaController.php public function store(VakansiyaRequest $request): RedirectResponse { $tekshirilgan = $request->validated(); Vakansiya::create($tekshirilgan + ['user_id' => $request->user()->id]); return redirect()->route('vakansiyalar.index') ->with('xabar', "Qo'shildi: {$tekshirilgan['nom']}"); }

17 qator edi — 8 qator bo'ldi. Va qolgan qatorlarning hammasi asl ish haqida.

Sehr yo'q — mexanizm shu

15-darsdagi service container yodingizdami? Laravel controller metodini chaqirishdan oldin uning argumentlarini ko'radi va har birini tipiga qarab yasab beradi.

VakansiyaRequest — FormRequest avlodi. Container uni yasab bo'lgach, tanani chaqirishdan oldin ikki ishni bajaradi:

1) authorize() → false bo'lsa → 403, metod ISHLAMAYDI 2) rules() → xato bo'lsa → 302 orqaga, metod ISHLAMAYDI 3) metod tanasi ishga tushadi

Shuning uchun controller ichida «tekshirdimmi?» deb o'ylash shart emas: u yerga faqat tekshiruvdan o'tgan so'rov yetib keladi.

To'siqlar tartibi — o'lchangan

Bitta so'rov yo'lda to'rtta to'siqdan o'tadi. Har birini alohida sinadik:4

1) CSRF _token yo'q → 419 2) auth mehmon (kirmagan) → 302 → /kirish 3) authorize() nomzod qo'shmoqchi → 403 4) rules() nom qisqa, maosh matn → 302 orqaga + xatolar 5) controller hammasi joyida → 302 → /vakansiyalar

🔑 Muhim natija: nomzod bo'sh formani yuborganda ham 403 keladi, validatsiya xatosi emas. Chunki authorize() rules() dan oldin ishlaydi — huquqi yo'q odamga «maosh kiritilishi shart» deb javob berish mantiqsiz bo'lardi.

validated() — nega all() emas

Controllerda $request->validated() yozildi. $request->all() ham bor. Farqi katta.

Formaga qo'shimcha maydon qo'lda qo'shib yuboramiz — brauzer konsolidan buni qilish oson:

yuborilgan: nom · maosh · user_id=999 · shahar=Buxoro · _token all() → nom · maosh · user_id · shahar · _token ← HAMMASI validated() → {"nom": "...", "maosh": "5000000"} ← faqat rules() dagilar

Endi nima bo'lishini ko'ring. Controller shunday yozilgan:

Vakansiya::create($tekshirilgan + ['user_id' => $request->user()->id]);

PHP'dagi + massivlar uchun — chap tomon ustun. Agar $tekshirilgan ichida allaqachon user_id bo'lsa, o'ngdagi haqiqiy egasi e'tiborga olinmaydi.

validated() bilan: user_id = 2 (kirgan odam) ✅ shahar = NULL all() bilan: user_id = 999 ← hujumchi yuborgan 💥 shahar = 'Buxoro'

O'lchangan: user_id=999 mavjud emas, shuning uchun baza to'sib qoldi: SQLSTATE[23000]: Integrity constraint violation: 19 FOREIGN KEY constraint failed — ya'ni 500.
⚠️ Lekin mavjud odamning raqamini yuborsa (masalan 3), xato chiqmaydi — e'lon jimgina boshqa odamga yozib qo'yiladi. Buni ham sinab ko'rdik.

🔒 $fillable yetarli emas edi

«Menda $fillable bor-ku» degan javob bu yerda ishlamaydi: Vakansiya modelining $fillable ro'yxatida user_id va shahar bor — ular haqiqatan ham to'ldirilishi kerak bo'lgan maydonlar.

$fillable: nom · maosh · shahar · faol · kompaniya_id · user_id

validated() boshqa savolga javob beradi: «bu so'rovda qaysi maydonlar kutilgan edi?» Javob — rules() da yozilganlari. Qolgani tashlanadi.

🔑 Bu qatlamli himoya: $fillable — model darajasida, validated() — so'rov darajasida.

Yaqin qarindoshlari

$request->validated() → hammasi (tekshirilganlari) $request->safe()->only(['nom']) → {"nom": "..."} $request->safe()->except(['maosh']) → {"nom": "..."} $request->safe()->collect() → Illuminate\Support\Collection

⚠️ Bir narsani kutmang: validatsiya tipni o'zgartirmaydi. 'maosh' => ['integer'] qoidasidan o'tgandan keyin ham qiymat string bo'lib qoladi — "5000000". Tekshiruv «bu son bo'la oladimi?» deb so'raydi, «uni songa aylantir» demaydi. Tip kerak bo'lsa model casts() ida ayting — 34-darsdagi kabi.

prepareForValidation() — tekshiruvdan oldin tozalash

Odam formaga " Devops muhandis " deb yozdi — boshida va oxirida probel. Qoidalar buni o'tkazadi (uzunligi yetarli), va bazaga probellari bilan tushadi.

app/Http/Requests/VakansiyaRequest.php protected function prepareForValidation(): void { $this->merge([ 'nom' => trim((string) $this->input('nom')), ]); }

O'lchangan: " Devops muhandis " yuborilgandan keyin bazada [Devops muhandis], uzunligi 15 — probellar yo'q.

Bu metod rules() dan oldin ishlaydi, shuning uchun qoidalar allaqachon tozalangan qiymatni ko'radi. Foydali holatlar: probel kesish, telefon raqamdan chiziqcha olib tashlash, bo'sh matnni null ga aylantirish.

protected ekaniga e'tibor bering — bu metod tashqaridan chaqirilmaydi, uni faqat Laravel'ning o'zi chaqiradi.

Foydasi: tahrirlash amali

Bu darsning haqiqiy javobi shu yerda. Endi IshTop'ga tahrirlash qo'shamiz va nechta qator validatsiya yozishimizga qarang.

routes/web.php Route::get('/vakansiyalar/{vakansiya}/tahrirlash', [VakansiyaController::class, 'tahrirlash']) ->name('vakansiyalar.tahrirlash')->middleware('auth'); Route::put('/vakansiyalar/{vakansiya}', [VakansiyaController::class, 'yangilash']) ->name('vakansiyalar.yangilash')->middleware('auth');
app/Http/Controllers/VakansiyaController.php public function tahrirlash(Vakansiya $vakansiya): View { $this->authorize('update', $vakansiya); return view('vakansiyalar.tahrirlash', ['v' => $vakansiya]); } public function yangilash(VakansiyaRequest $request, Vakansiya $vakansiya): RedirectResponse { $vakansiya->update($request->validated()); return redirect()->route('vakansiyalar.index') ->with('xabar', "Yangilandi: {$vakansiya->nom}"); }

yangilash() — uch qator. Validatsiya yo'q, xabarlar yo'q, huquq tekshiruvi yo'q. Hammasi VakansiyaRequest ichida turibdi va o'zi ishlaydi.

O'lchangan — xato ma'lumot yuborilganda:

Vakansiya nomi kamida 5 belgidan iborat bo'lsin. Maosh butun son bo'lishi kerak.

Bu — store uchun yozilgan xabarlar. Update da o'zi chiqdi. Bitta ham yangi qator yozilmadi.

Huquq — ikkala amalda ham

authorize() ichidagi $this->route('vakansiya') o'z ishini qildi. Uchta odam bilan sinaldi:

tahrirlash sahifasi PUT Ali (egasi, ish beruvchi) 200 302 ✅ Sardor (ish beruvchi, EGASI EMAS) 403 403 🔒 Vali (nomzod) 403 403 🔒 Mehmon (kirmagan) 302 → /kirish

34-darsdagi «rol va egalik — ikki xil savol» qoidasi shu yerda ish berdi: Sardor ish beruvchi, lekin egasi emas — va to'sildi.

resources/views/vakansiyalar/tahrirlash.blade.php @extends('layouts.asosiy') @section('mazmun') <h1>Vakansiyani tahrirlash</h1> @if ($errors->any()) <ul style="color:crimson"> @foreach ($errors->all() as $xato) <li>{{ $xato }}</li> @endforeach </ul> @endif <form method="POST" action="{{ route('vakansiyalar.yangilash', $v) }}"> @csrf @method('PUT') <p><input type="text" name="nom" value="{{ old('nom', $v->nom) }}"></p> <p><input type="number" name="maosh" value="{{ old('maosh', $v->maosh) }}"></p> <button type="submit">Saqlash</button> </form> @endsection

old('nom', $v->nom) — ikkinchi argument standart qiymat: sahifa birinchi ochilganda bazadagi qiymat, validatsiya xatosidan keyin esa odam yozgan qiymat. 20-darsdagi old() shu yerda to'liq shaklda ko'rinadi.

@method('PUT') — brauzer formalari faqat GET va POST biladi. Bu direktiva yashirin _method maydonini qo'shadi, Laravel esa uni ko'rib so'rovni PUT deb hisoblaydi.

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Stub'dagi return false qolib ketsa

Ali (ish beruvchi, policy ruxsat beradi) → 403

Eng ko'p vaqt yeydigan xato, chunki qidiruv noto'g'ri joyda boshlanadi: policy, rol, baza. Yangi fayl esa hech kimga shubhali tuyulmaydi.

✅ Tashxis: 403 chiqdi-yu, policy to'g'ri ishlayotganiga ishonchingiz komil bo'lsa — Form Request'ning authorize() iga qarang. Vaqtincha return true; qilib ko'ring: xato yo'qolsa, sabab topildi.

HOLAT 2

all() ishlatish

Vakansiya::create($request->all() + ['user_id' => $user->id]);

Ishlaydi — sinovda hammasi joyida ko'rinadi. Chunki oddiy forma ortiqcha maydon yubormaydi. Hujumchi esa yuboradi.

PHP'da + chap tomonni ustun qo'yadi, shuning uchun all() ichidagi user_id haqiqiy egasini bosib ketadi.

✅ Qoida: controllerga faqat validated() yoki safe()->only([...]) kirsin. all() — faqat tuzatish (debug) paytida.

HOLAT 3

Taqiq sababini aytish

use Illuminate\Auth\Access\AuthorizationException; protected function failedAuthorization(): void { throw new AuthorizationException( 'Vakansiya joylash uchun ish beruvchi bo\'lishingiz kerak.' ); }

O'lchandi: 403 sahifasida standart matn o'rniga shu jumla chiqdi.

33-darsdagi Response::deny('sabab') bilan bir maqsad, faqat boshqa joyda: u policy ichida, bu Form Request ichida. Qaysi biri ishlashi qaysi biri taqiqlaganiga bog'liq.

HOLAT 4

attributes() qachon ko'rinadi

nom.min → messages() da BOR → 'Vakansiya nomi kamida 5 belgidan...' nom.max → messages() da YO'Q → 'The vakansiya nomi field must not be...'

Ya'ni attributes() — zaxira mexanizm. U faqat standart xabar ishlatilganda ko'rinadi.

Amalda foydali strategiya: eng muhim ikki-uch qoidaga messages() yozing, qolganiga attributes() yetadi. Butun ilovani o'zbekchalash uchun esa boshqa yo'l bor — lang/ papkasidagi til fayllari. U yerda barcha standart xabarlar bir joyda turadi va bu Form Request mavzusidan alohida ish.

HOLAT 5

Mehmon: $this->user() — null

// null tekshiruvisiz: return $this->user()->can('create', Vakansiya::class); mehmon so'rov yuborsa → 500 Call to a member function can() on null

Hozir bu ko'rinmaydi, chunki route'da middleware('auth') turibdi va mehmonni oldinroq to'sib qoladi (302 → /kirish).

⚠️ Lekin bir kun route ko'chiriladi yoki middleware tushib qoladi — va 403 o'rniga 500 olasiz. O'lchab ko'rdik: middleware olib tashlanganda aynan shunday bo'ldi.

✅ $user === null tekshiruvi qo'shilgach, xuddi shu holat 403 berdi. Har bir qatlam o'zicha to'g'ri ishlashi kerak — qo'shnisiga ishonib qolmasin.

HOLAT 6

@method('PUT') unutilsa

405 MethodNotAllowedHttpException The POST method is not supported for route vakansiyalar/27

Forma POST yuboradi, route esa PUT kutadi — mos kelmadi. 405 — «bu manzil bor, lekin bu usul bilan emas».

✅ Xato xabarini oxirigacha o'qing: u qaysi usul kelganini va qaysi route haqida gap ketayotganini aniq aytadi. Ko'pincha yechim — formaga @method('PUT') qo'shish yoki route'ni Route::post qilish.

HOLAT 7

Bitta klass yoki ikkita

VakansiyaRequest ← bitta, ikkala amalga StoreVakansiyaRequest + UpdateVakansiyaRequest ← ikkita

Biz bittasini tanladik, chunki qoidalar aynan bir xil — va takrorlamaslik bugungi darsning butun maqsadi.

Qoidalar ajrala boshlaganda ikkitaga bo'ling. Odatiy misol: yaratishda 'email' => 'unique:users', tahrirlashda esa o'zining emailiga ruxsat berish kerak. O'shanda bitta klassdagi if lar ko'payib ketadi — bu bo'lish vaqti kelganining belgisi.

🔑 Qoida: bir xil bo'lsa — birlashtiring, ajrasa — bo'ling. Oldindan bo'lib qo'yish ham, oxirigacha birga saqlash ham xato.

💻 Amaliy qism kompyuterda

Amaliyotda VakansiyaRequest yasaysiz, controllerni ingichkalashtirasiz va tahrirlash amalini qo'shasiz. Yo'lda stub'dagi return false tuzog'ini ataylab ko'rasiz va all() nima uchun xavfli ekanini o'z ko'zingiz bilan tekshirasiz.

Sinab ko'ramiz

Natijani taxmin qiling

Vali — nomzod. U vakansiya qo'sha olmaydi (34-darsdagi policy). Vali formani butunlay bo'sh yuboradi: nom ham, maosh ham yo'q.

app/Http/Requests/VakansiyaRequest.php
public function authorize(): bool { return $this->user()->can('create', Vakansiya::class); } public function rules(): array { return [ 'nom' => ['required', 'string', 'min:5'], 'maosh' => ['required', 'integer'], ]; }

Vali nima ko'radi — «Vakansiya nomi kiritilishi shart» degan xato ro'yxatimi, yoki boshqa narsami?

Javobni ko'rish
status: 403 Xato ro'yxati YO'Q. «nom kiritilishi shart» xabari CHIQMAYDI.

Chunki tartib qat'iy: authorize() avval ishlaydi. false qaytardi — va rules() ga umuman yetib borilmadi.

🔑 Bu to'g'ri xatti-harakat. Huquqi yo'q odamga «maosh maydonini to'ldiring» deb aytish — unga formaning tuzilishi haqida keraksiz ma'lumot berish demak. 30-darsdagi user enumeration mavzusi bilan bir oiladan.

Endi qiyinrog'i: aynan shu kod bilan mehmon (umuman kirmagan odam) so'rov yuborsa-chi?

middleware('auth') BOR → 302 → /kirish (bu yergacha yetmaydi) middleware('auth') YO'Q → 500 Call to a member function can() on null

Mehmon uchun $this->user() — null. Yuqoridagi kodda tekshiruv yo'q, shuning uchun 403 emas, 500 keladi. O'lchab ko'rdik.

🔑 Qoida: har bir qatlam o'zicha to'g'ri ishlashi kerak. «Middleware baribir to'sadi-ku» deb hisoblash — bir kun kelib middleware ko'chirilganda ochiladigan qarz.

SAVOL 1 make:request yasagan authorize() boshida nima qaytaradi?

Skelet hammaga taqiq qo'yib turadi — bu xavfsiz standart, lekin kutilmagan. Ruxsati bor odam ham 403 oladi va sahifada hech qanday tushuntirish bo'lmaydi. 🔑 make:request dan keyin birinchi ish — authorize() ga qarash.

SAVOL 2 validated() metodi nimani qaytaradi?

user_id=999 yuborilganda validated() uni tashladi — e'lon kirgan odamga yozildi. all() bilan esa hujumchining raqami o'tib ketardi. 🔒 $fillable bu yerda qutqarmaydi: user_id unda bor — u haqiqatan to'ldiriladigan maydon.

SAVOL 3 Huquqi yo'q odam xato ma'lumot yuborsa nima bo'ladi?

Tartib qat'iy: authorize() → rules() → controller tanasi. Nomzod bo'sh forma yuborganda ham 403 oldi — validatsiya xatosi emas. Bu to'g'ri: huquqi yo'q odamga forma tuzilishi haqida ma'lumot berilmaydi.

Eslab ayting

Avval o'zingiz javob bering, keyin ochib tekshiring. Oxirgi ikkitasi — 34-darsni takrorlash.

Form Request controllerga qanday ulanadi?

Argument tipi orqali: store(VakansiyaRequest $request). Ro'yxatdan o'tkazish shart emas — container tipni ko'rib obyektni yasaydi va metod tanasidan oldin authorize() hamda rules() ni ishlatadi.

validated() nega all() dan xavfsiz?

U faqat rules() da nomi yozilgan maydonlarni qaytaradi. Formaga qo'lda qo'shilgan user_id yoki shahar tashlanadi. $fillable bu yerda yordam bermaydi — ular unda bor.

Bitta Form Request ikkala amalni qanday ajratadi?

$this->route('vakansiya') orqali: route'da {vakansiya} bo'lsa — tahrirlash (update), bo'lmasa — yaratish (create).

↩︎ Takrorlash: enum cast bazada nimani saqlaydi?

Oddiy matn — backing value ('ish_beruvchi'). PHP tomonda obyekt, o'rtada from() va ->value. Sehr yo'q.

↩︎ Takrorlash: rol va egalik farqi nimada?

Rol — toifa savoli («umuman shunday ish qila olasanmi?»), egalik — yozuv savoli («bu aynan seningmi?»). Yozuv ustidagi amallarda ikkalasi ham kerak. Bugun buni Sardor misolida ko'rdik: ish beruvchi, lekin egasi emas — 403.

Cho'ntak xulosasi
  • php artisan make:request VakansiyaRequest → app/Http/Requests/.
  • ⚠️ Birinchi tuzoq: yasalgan authorize() false qaytaradi — ruxsati bor odam ham 403 oladi.
  • Ulash — type-hint: store(VakansiyaRequest $request). Boshqa hech nima kerak emas.
  • Sehr yo'q: container obyektni yasaydi, keyin metod tanasidan oldin authorize() → rules() ishlaydi.
  • To'siqlar tartibi: 419 CSRF → 302 auth → 403 authorize() → 302 rules() → controller.
  • rules() da massiv shakli afzal: ['required', 'string'] — ichiga Rule::enum(...) kabi obyektlar ham sig'adi.
  • messages() — to'liq jumla. attributes() — faqat maydon nomi, va u zaxira: o'z xabari bor qoidaga ta'sir qilmaydi.
  • authorize() policy'ni chaqiradi: $this->route('vakansiya') bor bo'lsa update, yo'q bo'lsa create.
  • ⚠️ $this->user() mehmon uchun null — tekshirmasangiz 403 emas, 500. Har qatlam o'zicha to'g'ri ishlasin.
  • 🔒 validated() ishlating, all() emas: user_id=999 yuborilganda birinchisi tashladi, ikkinchisi o'tkazib yubordi. $fillable bu yerda qutqarmaydi.
  • Yaqinlari: safe()->only([...]), safe()->except([...]), safe()->collect().
  • ⚠️ Validatsiya tipni o'zgartirmaydi: integer qoidasidan o'tgan qiymat baribir string. Tip kerak bo'lsa — casts().
  • prepareForValidation() — tekshiruvdan oldin tozalash (trim, format). protected, uni Laravel chaqiradi.
  • failedAuthorization() — 403 sahifasida o'z sababingiz.
  • Foydasi o'lchandi: tahrirlash amali qo'shildi — validatsiyadan bitta ham qator yozilmadi, xabarlar o'zi chiqdi.
  • Bitta klass yoki ikkita: qoidalar bir xil bo'lsa birlashtiring, ajrasa bo'ling.
