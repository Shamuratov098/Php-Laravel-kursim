DARS 41 · MODUL E — TEST (PEST)

PHPUnit ko'rinishi va red → green → refactor

Modul E'da Pest bilan ishladik. Ammo dunyodagi Laravel loyihalarining katta qismi hali ham PHPUnit uslubida yozilgan — ochilgan har bir eski loyihada shu ko'rinishni uchratasiz. Bugun ikkalasini yonma-yon qo'yamiz, keyin test-birinchi yozishni sinab ko'ramiz: yiqiladigan test → eng sodda kod → tozalash.

📱 O'qish ≈ 16 daqiqa 💻 Amaliyot ≈ 25 daqiqa Kerak: Dars 40

Bu darsda nimalar bor
  1. Nega PHPUnit uslubi kerak Yozmasangiz ham o'qiy olishingiz shart: eski loyihalar, qo'llanmalar va StackOverflow javoblari shu uslubda.
  2. Bitta test — ikki ko'rinish Xuddi shu tekshiruv Pest'da va PHPUnit'da. Nima o'zgaradi, nima o'zgarmaydi.
  3. ⚠️ PHPUnit klassiga tests/Pest.php ta'sir qilmaydi Birinchi ishga tushirish no such table: users beradi. Sabab va bir qatorli yechim.
  4. Nomlash: test_ prefiksi Metod nomi test_ bilan boshlanishi shart. Pest uni chiqishda o'qiladigan jumlaga aylantiradi.
  5. setUp() va beforeEach() Har testdan oldingi tayyorgarlik — ikki uslubda. ⚠️ parent::setUp() unutilmasin.
  6. Tekshiruvlar lug'ati assertSame ↔ toBe, assertEquals ↔ toEqual va boshqalar — jadval bilan.
  7. ⚠️ Argument tartibi teskari PHPUnit: kutilgan birinchi. Pest: haqiqiy birinchi. Adashsangiz xato xabari teskari chiqadi — o'lchandi.
  8. Data provider ↔ with() Bitta testdan bir nechta holat. PHPUnit'da nomlangan to'plamlar chiroyliroq chiqadi.
  9. make:test --phpunit 🔍 --unit bilan birga PHPUnit\Framework\TestCase chiqadi — Laravel umuman yo'q.
  10. 🔴 RED — yiqiladigan test Kod yozilmasdan turib test yoziladi va ataylab yiqitiladi. Nega bu qadam tashlab ketilmaydi.
  11. 🟢 GREEN → 🔵 REFACTOR Eng sodda kod, keyin tozalash. Ikkinchi aylanada null holati qo'shiladi va birinchi test yashil qoladi.
  12. Har xil holatlar (7 ta) RefreshDatabase · --unit · assertEquals · argument tartibi · test_ prefiksi · «keyin yozaman» · refaktoring xavfsizligi.
O'qish — yozishdan muhimroq

Pest 2021-yilda chiqdi. Undan oldingi o'n yillik Laravel kodi — va bugungi ko'p loyihalar — PHPUnit uslubida yozilgan:

class VakansiyaTest extends TestCase { public function test_nomzod_vakansiya_qosha_olmaydi(): void { // ... } }

Siz yangi loyihada Pest yozishingiz mumkin. Lekin:

eski loyihaga qo'shilsangiz → PHPUnit testlarini o'qiysiz paket kodini ochsangiz → PHPUnit testlari StackOverflow javobi → odatda PHPUnit Laravel'ning o'z manba kodi → PHPUnit

Shuning uchun maqsad — ikkalasini o'qiy olish va kerak bo'lganda birini ikkinchisiga o'girish. Yaxshi xabar: ular bir xil asosda ishlaydi. Pest — PHPUnit ustidagi qobiq, 37-darsda aytilgandek.

Bitta test — ikki ko'rinish

38-darsdagi testni PHPUnit uslubida qayta yozamiz:

Pest uslubi — tests/Feature/VakansiyaTest.php <?php use App\Enums\Rol; use App\Models\User; test('nomzod vakansiya qo\'sha olmaydi', function () { $nomzod = User::factory()->create(['rol' => Rol::Nomzod]); $this->actingAs($nomzod) ->post('/vakansiyalar', ['nom' => 'Backend dasturchi', 'maosh' => 9000000]) ->assertForbidden(); $this->assertDatabaseMissing('vakansiyalar', ['nom' => 'Backend dasturchi']); });
PHPUnit uslubi — tests/Feature/PhpunitUslubTest.php <?php namespace Tests\Feature; // ← namespace kerak use App\Enums\Rol; use App\Models\User; use Illuminate\Foundation\Testing\RefreshDatabase; // ← qo'lda use Tests\TestCase; class PhpunitUslubTest extends TestCase // ← klass { use RefreshDatabase; // ← qo'lda public function test_nomzod_vakansiya_qosha_olmaydi(): void { $nomzod = User::factory()->create(['rol' => Rol::Nomzod]); $this->actingAs($nomzod) ->post('/vakansiyalar', ['nom' => 'Backend dasturchi', 'maosh' => 9000000]) ->assertForbidden(); $this->assertDatabaseMissing('vakansiyalar', ['nom' => 'Backend dasturchi']); } }

O'zgarmagan qismga qarang: actingAs, post, assertForbidden, assertDatabaseMissing, User::factory() — hammasi aynan bir xil. Chunki bu metodlar Laravel'niki, Pest'niki emas.

O'zgargani: namespace · class · use RefreshDatabase · public function test_... O'zgarmagani: TEKSHIRUVLARNING O'ZI
⚠️ Birinchi ishga tushirish yiqiladi

use RefreshDatabase; ni yozmasdan ishlatsangiz:

SQLSTATE[HY000]: General error: 1 no such table: users (Connection: sqlite, Database: :memory:)

37-darsdagi tests/Pest.php ni eslang:

pest()->extend(TestCase::class) ->use(RefreshDatabase::class) ->in('Feature');

Bu sozlama Pest fayllariga qo'llanadi — qo'lda yozilgan PHPUnit klasslariga emas. Klass o'zi nimani ishlatishini o'zi e'lon qilishi kerak.

🔍 Shuning uchun make:test --phpunit yasagan skelet RefreshDatabase ni import qilib beradi — ishlatilmagan holda ham. Bu eslatma.

Nomlash va chiqish

PHPUnit metodning nomi test_ bilan boshlanishi shart — aks holda u test deb hisoblanmaydi va jimgina o'tkazib yuboriladi.

Pest esa uni chiqishda o'qiladigan jumlaga aylantiradi:

kodda: public function test_nomzod_vakansiya_qosha_olmaydi() chiqishda: ✓ nomzod vakansiya qosha olmaydi

🔍 Diqqat: qosha — apostrofsiz. Metod nomida ' yozib bo'lmaydi, shuning uchun PHPUnit uslubida o'zbekcha nomlar biroz g'aliz chiqadi. Pest'dagi test('...') esa istalgan matnni oladi — 37-darsda shuning uchun test() ni tanlagan edik.

Tayyorgarlik: setUp() ↔ beforeEach()

// PHPUnit // Pest protected function setUp(): void beforeEach(function () { { $this->tayyorgarlik = '...'; parent::setUp(); ← ⚠️ }); $this->tayyorgarlik = '...'; }

⚠️ PHPUnit'da parent::setUp() ni unutmang: Laravel'ni ishga tushiradigan kod aynan o'sha yerda. Unutsangiz ilova ko'tarilmaydi.

Pest'da bu muammo yo'q — beforeEach() ichida ota-metod chaqirilmaydi.

Tekshiruvlar lug'ati

PHPUnit Pest ───────────────────────────────────────────────────────────────── $this->assertSame($k, $h) expect($h)->toBe($k) $this->assertEquals($k, $h) expect($h)->toEqual($k) $this->assertTrue($h) expect($h)->toBeTrue() $this->assertFalse($h) expect($h)->toBeFalse() $this->assertNull($h) expect($h)->toBeNull() $this->assertCount(3, $h) expect($h)->toHaveCount(3) $this->assertStringContainsString expect($h)->toContain(...) $this->assertNotSame($k, $h) expect($h)->not->toBe($k)

Laravel qo'shgan tekshiruvlar — assertDatabaseHas, assertForbidden, assertGuest — ikkala uslubda ham $this-> orqali chaqiriladi. Ular Pest'niki emas, Laravel'niki.

assertSame va assertEquals

$this->assertEquals('5', 5); // ✅ o'tadi — qiymat teng $this->assertSame('5', 5); // ⨯ yiqiladi — tip boshqa expect('5')->toEqual(5); // ✅ expect('5')->toBe(5); // ⨯

assertSame/toBe — === bilan bir xil: qiymat va tip. 35-darsdagi «validatsiya tipni o'zgartirmaydi» qoidasini eslang: integer qoidasidan o'tgan maosh baribir string. O'shanday joyda toBe ni tanlasangiz test sizga haqiqatni aytadi.

⚠️ Argument tartibi teskari
PHPUnit: assertSame($KUTILGAN, $haqiqiy) ← kutilgan BIRINCHI Pest: expect($haqiqiy)->toBe($KUTILGAN) ← haqiqiy BIRINCHI

Adashsangiz test baribir to'g'ri ishlaydi (tenglik ikki tomonlama), lekin xato xabari teskari chiqadi:

$this->assertSame('haqiqiy natija', 'kutilgan natija'); // ⚠️ teskari Failed asserting that two strings are identical. -'haqiqiy natija' ← minus = KUTILGAN deb ko'rsatilyapti +'kutilgan natija' ← plyus = HAQIQIY deb ko'rsatilyapti

Ya'ni siz «kutgan narsam haqiqiy natija edi» degan xabarni o'qiysiz — va tashxis butunlay noto'g'ri yo'nalishga ketadi.

🔑 Yodda tuting: - qatori — kutilgan, + qatori — haqiqiy. Diff shu tartibda o'qiladi.

Bir nechta holat: data provider ↔ with()

Pest — tests/Unit/MaoshTest.php test('maosh o\'qiladigan ko\'rinishda chiqadi', function (?int $miqdor, string $kutilgan) { expect(Maosh::format($miqdor))->toBe($kutilgan); })->with([ [9000000, "9 000 000 so'm"], [500, "500 so'm"], [0, "0 so'm"], [null, 'Kelishuv asosida'], ]);
PHPUnit — tests/Unit/MaoshPhpunitTest.php use PHPUnit\Framework\Attributes\DataProvider; #[DataProvider('maoshHolatlari')] public function test_maosh_oqiladigan_korinishda_chiqadi(?int $miqdor, string $kutilgan): void { $this->assertSame($kutilgan, Maosh::format($miqdor)); } public static function maoshHolatlari(): array { return [ 'katta son' => [9000000, "9 000 000 so'm"], 'kichik son' => [500, "500 so'm"], 'nol' => [0, "0 so'm"], 'ko\'rsatilmagan' => [null, 'Kelishuv asosida'], ]; }

Ikkalasi ham bitta test tanasidan to'rtta test yasaydi:

✓ maosh oqiladigan korinishda chiqadi with data set "katta son" ✓ maosh oqiladigan korinishda chiqadi with data set "kichik son" ✓ maosh oqiladigan korinishda chiqadi with data set "nol" ✓ maosh oqiladigan korinishda chiqadi with data set "ko'rsatilmagan" ✓ maosh o'qiladigan ko'rinishda chiqadi with (9000000, '9 000 000 so'm') ✓ maosh o'qiladigan ko'rinishda chiqadi with (500, '500 so'm') ✓ maosh o'qiladigan ko'rinishda chiqadi with (0, '0 so'm') ✓ maosh o'qiladigan ko'rinishda chiqadi with (null, 'Kelishuv asosida')

🔍 Bu yerda PHPUnit ustunroq: nomlangan to'plamlar ('katta son' => [...]) chiqishda o'qiladigan bo'lib turadi. Pest esa qiymatlarni o'zini ko'rsatadi. Pest'da ham nom berish mumkin, lekin yozilishi biroz uzunroq.

🔑 Muhimi: to'rtta alohida test. Bittasi yiqilsa, qaysi biri ekani darhol ko'rinadi — foreach bilan yozilgan bitta testda esa bu ma'lumot yo'qoladi.

Generator bayroqlari

php artisan make:test XTest → Pest (standart) php artisan make:test XTest --phpunit → class ... extends Tests\TestCase php artisan make:test XTest --phpunit --unit → class ... extends PHPUnit\Framework\TestCase

TDD har doim kerakmi?

Yo'q. U bir asbob, dogma emas. Amalda yaxshi ishlaydigan joylar:

✅ sof mantiq (formatlash, hisob-kitob, qoidalar) — tez aylana ✅ xato tuzatish: avval xatoni ko'rsatuvchi test — «qaytmasin» ✅ talab aniq bo'lganda — kutilgan natija ma'lum ⚠️ interfeys izlayotganda (dizayn hali noaniq) ⚠️ tashqi tizim bilan tanishayotganda

🔑 Xato tuzatishdagi qo'llanishi eng qimmatlisi: xatoni ko'rgach, avval uni ko'rsatuvchi test yozing (qizil), keyin tuzating (yashil). Shunda o'sha xato hech qachon jimgina qaytmaydi.

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

PHPUnit klassida RefreshDatabase yo'q

no such table: users (Connection: sqlite, Database: :memory:)

tests/Pest.php dagi sozlama Pest fayllariga qo'llanadi. Qo'lda yozilgan klass o'zi e'lon qilishi kerak.

✅ Klass ichiga use RefreshDatabase; qo'ying (import ham kerak).

🔍 Teskari holat ham bor: Pest faylida uses(RefreshDatabase::class) deb ikkinchi marta yozish zarar qilmaydi, lekin ortiqcha — u allaqachon tests/Pest.php da ulangan.

HOLAT 2

--phpunit --unit — Laravel yo'q

class XTest extends PHPUnit\Framework\TestCase ← Laravel'niki EMAS RuntimeException: A facade root has not been set.

Bu skelet ataylab shunday: sof PHP mantiqni Laravel'siz sinash uchun. Lekin unda User::factory(), config(), route() — hech biri ishlamaydi.

✅ Laravel kerak bo'lsa Tests\TestCase dan meros oling (--phpunit siz --unit). Yoki testni Feature ga ko'chiring.

HOLAT 3

assertEquals jimgina o'tkazadi

$this->assertEquals('5', 5); // ✅ o'tadi $this->assertSame('5', 5); // ⨯ yiqiladi

assertEquals tipni e'tiborsiz qoldiradi. Ko'pincha bu qulay, lekin ba'zan haqiqiy xatoni yashiradi — masalan API javobida son o'rniga matn qaytayotganini.

✅ Shubha bo'lsa assertSame / toBe dan boshlang. Kerak bo'lsa keyin bo'shatasiz — teskarisi qiyinroq.

HOLAT 4

Argument tartibi almashib ketsa

assertSame($haqiqiy, $kutilgan) // ⚠️ teskari Failed asserting that two strings are identical. -'haqiqiy natija' ← «kutilgan» deb ko'rsatilyapti +'kutilgan natija'

Test baribir to'g'ri ishlaydi, lekin tashxis buziladi: siz xato xabarini teskari o'qiysiz va muammoni noto'g'ri joyda qidirasiz.

✅ Yodda tuting: PHPUnit'da kutilgan birinchi, Pest'da haqiqiy birinchi. Diffda - — kutilgan, + — haqiqiy.

HOLAT 5

test_ prefiksi unutilsa

public function nomzod_qosha_olmaydi(): void // ⚠️ test_ yo'q → test UMUMAN ishga tushmaydi, xato ham chiqmaydi

Eng xavfli tur: to'plam yashil, chunki test mavjud emas deb hisoblanadi. 37-darsdagi risky holatidan ham yomonroq — u hech bo'lmasa sariq belgi berardi.

✅ Test sonini kuzating: yangi test yozgach Tests: N passed dagi N ortdimi? Ortmagan bo'lsa — prefiksni tekshiring.

🔍 Muqobil: metod ustiga #[Test] atributi qo'yish (PHPUnit\Framework\Attributes\Test). O'shanda nom test_ bilan boshlanishi shart emas.

HOLAT 6

«Testni keyin yozaman»

Kod yozilib bo'lgach test yozish — mumkin, va biz 37–40-darslarda aynan shunday qildik. Lekin bitta xavf bor: kod tayyor bo'lgani uchun test uni tasdiqlashga moslashib qoladi.

// kod shunday yozilgan bo'lsa: return $miqdor . ' som'; // apostrofsiz, xato // keyin yozilgan test ham shunga moslashadi: expect(...)->toBe('9000000 som'); // ⚠️ xatoni QULFLAB qo'ydi

✅ Test-birinchi yozilganda kutilgan natijani talabdan olasiz, koddan emas. Shuning uchun TDD ayniqsa aniq talab bo'lgan joylarda kuchli.

🔑 Keyin yozayotgan bo'lsangiz ham qoidani saqlang: testni yozgach kodni ataylab buzib, qizilni ko'ring (37-dars).

HOLAT 7

Refaktoring — testlar ruxsat beradi

ko'rinish fayli o'zgartirildi → 38 test yashil qoldi

Testsiz refaktoring — umid. Testlar bilan — tekshirilgan o'zgarish.

✅ Refaktoring qoidasi: bitta vaqtda bitta narsa. Yo xulqni o'zgartirasiz (yangi test bilan), yo shaklni tozalaysiz (testlar o'zgarmaydi). Ikkalasini birga qilsangiz, test qizarganda sababini ajratib bo'lmaydi.

🔍 Shu darsda ikkalasi ham ko'rindi: ?int ga o'tish — xulq (yangi test), dataset'ga yig'ish — shakl (xulq o'zgarmadi).

💻 Amaliy qism kompyuterda

Amaliyotda bitta testni ikki uslubda yozasiz, keyin test-birinchi usulida yangi funksiya qurasiz — qizil, yashil, tozalash. Yo'lda test_ prefiksi unutilganda test jimgina yo'qolib qolishini ham ko'rasiz.

Sinab ko'ramiz

Natijani taxmin qiling

Dasturchi eski loyihaga qo'shildi va u yerda shunday testni topdi:

tests/Feature/VakansiyaTest.php
class VakansiyaTest extends TestCase { use RefreshDatabase; public function test_ish_beruvchi_vakansiya_qosha_oladi(): void { $u = User::factory()->create(['rol' => Rol::IshBeruvchi]); $this->actingAs($u)->post('/vakansiyalar', [ 'nom' => 'Backend dasturchi', 'maosh' => 9000000, ]); $this->assertDatabaseHas('vakansiyalar', ['nom' => 'Backend dasturchi']); } public function nomzod_qosha_olmasligi_kerak(): void { $u = User::factory()->create(['rol' => Rol::Nomzod]); $this->actingAs($u)->post('/vakansiyalar', [ 'nom' => 'Backend dasturchi', 'maosh' => 9000000, ])->assertForbidden(); } }

Javobni ko'rish
✓ ish beruvchi vakansiya qosha oladi Tests: 1 passed ← BITTA, ikkita emas

Ikkinchi metod test_ bilan boshlanmaydi — u umuman ishga tushmagan. Xato ham, ogohlantirish ham yo'q: PHPUnit uni oddiy metod deb hisoblaydi.

⚠️ Ya'ni «nomzod qo'sha olmaydi» qoidasi umuman tekshirilmayapti. Policy'ni buzsangiz to'plam yashil qolaveradi — 37-darsdagi eng xavfli holat.

🔑 Tashxis usuli: fayldagi test metodlarini sanang va chiqishdagi Tests: N passed bilan solishtiring. Ikkitasi bo'lishi kerak edi — bittasi chiqdi.

Ikki yechim:

public function test_nomzod_qosha_olmasligi_kerak(): void // prefiks #[Test] // yoki atribut public function nomzod_qosha_olmasligi_kerak(): void

🔍 Va shu yerda Pest'ning ustunligi ko'rinadi: test('nomzod qo\'sha olmaydi', ...) da bunday tuzoq yo'q — funksiya nomi emas, test() chaqiruvining o'zi testni ro'yxatga oladi.

Umumiy saboq: «to'plam yashil» — «hamma narsa tekshirilgan» degani emas. Nechta test bo'lishi kerak edi, degan savolni ham bering.

SAVOL 1 PHPUnit klassida no such table chiqsa sabab nima?

tests/Pest.php dagi ->use(RefreshDatabase::class)->in('Feature') faqat Pest fayllariga qo'llanadi. Qo'lda yozilgan klass ichiga use RefreshDatabase; qo'yish kerak — shuning uchun --phpunit skeleti uni import qilib beradi.

SAVOL 2 Argument tartibi ikki uslubda qanday?

assertSame($kutilgan, $haqiqiy) va expect($haqiqiy)->toBe($kutilgan). Adashsangiz test baribir ishlaydi, lekin xato xabari teskari chiqadi va tashxis noto'g'ri yo'nalishga ketadi. Diffda - — kutilgan, + — haqiqiy.

SAVOL 3 Nega 🔴 qadamni tashlab ketmaslik kerak?

Qizilni ko'rish ikki narsani tasdiqlaydi: test ishga tushyapti va aynan kutgan sababdan yiqilyapti. Hech qachon qizil bo'lmagan test — 37-darsdagi risky yoki bugungi test_ siz metod kabi yolg'on xotirjamlik berishi mumkin.

Eslab ayting

Avval o'zingiz javob bering, keyin ochib tekshiring. Oxirgi ikkitasi — 40-darsni takrorlash.

Ikki uslubda nima o'zgaradi, nima o'zgarmaydi?

O'zgaradi: namespace, klass, use RefreshDatabase, test_ prefiksi. O'zgarmaydi: tekshiruvlarning o'zi — actingAs, assertForbidden, assertDatabaseHas. Ular Laravel'niki.

Red → Green → Refactor nima beradi?

🔴 test ishlayotganini isbotlaydi · 🟢 eng sodda yechim · 🔵 shaklni tozalash, xulq o'zgarmasdan. Har aylanada eski testlar yashil qolishi — ishonchning manbai.

assertSame va assertEquals farqi?

assertSame — === (qiymat va tip), assertEquals — faqat qiymat. assertEquals('5', 5) o'tadi, assertSame yiqiladi. Shubha bo'lsa assertSame/toBe dan boshlang.

↩︎ Takrorlash: assertAuthenticated nega yetarli emas?

U «kimdir kirgan» deydi — «har doim birinchi foydalanuvchini kiritadigan» buzuq koddan ham o'tadi. Kirish testida assertAuthenticatedAs($user).

↩︎ Takrorlash: policy testi nega Feature da?

tests/Pest.php Laravel'ni faqat Feature da ko'taradi. Unit'da A facade root has not been set. chiqadi. «Feature» — HTTP emas, Laravel kerak degani.

Cho'ntak xulosasi
  • Pest — PHPUnit ustidagi qobiq. Tekshiruvlarning o'zi (actingAs, assertDatabaseHas…) ikkala uslubda bir xil — ular Laravel'niki.
  • PHPUnit uslubi: namespace · class ... extends Tests\TestCase · public function test_...().
  • ⚠️ tests/Pest.php sozlamasi PHPUnit klasslariga qo'llanmaydi → no such table: users. Yechim: klass ichiga use RefreshDatabase;.
  • ⚠️ test_ prefiksi yo'q metod jimgina o'tkazib yuboriladi — xato ham, ogohlantirish ham yo'q. Muqobil: #[Test] atributi.
  • 🔑 Yangi test yozgach Tests: N passed dagi N ortdimi — shuni kuzating.
  • setUp() ↔ beforeEach(). ⚠️ PHPUnit'da parent::setUp() majburiy.
  • Lug'at: assertSame ↔ toBe · assertEquals ↔ toEqual · assertTrue ↔ toBeTrue · assertCount ↔ toHaveCount.
  • ⚠️ Argument tartibi teskari: assertSame($kutilgan, $haqiqiy) va expect($haqiqiy)->toBe($kutilgan). Adashsangiz xato xabari teskari o'qiladi. Diffda - kutilgan, + haqiqiy.
  • #[DataProvider] ↔ ->with([...]) — bitta test tanasidan bir nechta test. PHPUnit'da nomlangan to'plamlar o'qilishi qulayroq.
  • make:test X --phpunit → Tests\TestCase. ⚠️ --phpunit --unit → PHPUnit\Framework\TestCase, Laravel umuman yo'q.
  • 🔴 RED: kod yozilmasdan test. Qizilni ko'rish test ishlayotganini va aynan kutgan sababdan yiqilayotganini isbotlaydi.
  • 🟢 GREEN: eng sodda yechim. 🔵 REFACTOR: shaklni tozalash, xulq o'zgarmaydi.
  • 🔑 Ikkinchi aylanada eski test yashil qoldi — yangi talab eskisini buzmagani shundan bilinadi.
  • TDD tez aylana talab qiladi: Unit test 0.04 s. Brauzerda qo'lda tekshirish bilan TDD ishlamaydi.
  • TDD eng foydali joylar: sof mantiq, xato tuzatish (avval xatoni ko'rsatuvchi test), talab aniq bo'lganda.
  • Natija: 38 test, 94 tekshiruv. Ko'rinish o'zgartirildi — qolgan 37 tasi yashil qoldi.
