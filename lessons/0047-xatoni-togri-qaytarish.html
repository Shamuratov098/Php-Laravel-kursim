withExceptions — boshqaruv joyi

Fayl allaqachon tanish: bootstrap/app.php. Uning uchinchi bloki hozir shunday:

bootstrap/app.php — hozirgi holat
->withExceptions(function (Exceptions $exceptions): void { $exceptions->shouldRenderJsonWhen( fn (Request $request) => $request->is('api/*') || $request->expectsJson(), ); })->create();
🔍 Buni biz yozmaganmiz

Tekshirdim: toza laravel/laravel skeletini yonma-yon ochib solishtirdim — bu blok Laravel 13'da standart holda bor.

Ya'ni 42-darsdan beri API xatolarimiz JSON bo'lib kelayotgani tasodif emas: api/* bilan boshlanadigan yoki Accept: application/json yuborgan so'rovga Laravel HTML sahifa emas, JSON qaytaradi.

🔑 Demak -H "Accept: application/json" ni curl ga qo'shib yurganimiz shu sababdan edi.

Bu blokda ishlatadigan to'rtta metod bor:

render(...) → ma'lum bir xato uchun javobni o'zim yozaman respond(...) → tayyor javobni oxirida ko'rib chiqaman context(...) → har bir log yozuviga qo'shimcha ma'lumot dontReport(...) → bu xatoni logga yozma

Hech qachon ishlamaydigan kod

404 xabarini tuzatish uchun tabiiy qadam shunday ko'rinadi — va internetdagi ko'p maqolada aynan shunday yozilgan:

❌ bu ishlamaydi
$exceptions->render(function (ModelNotFoundException $e, Request $request) { return response()->json(['message' => 'Yozuv topilmadi.'], 404); });

Yozamiz, saqlaymiz, so'rov yuboramiz:

GET /api/vakansiyalar/999999 → 404 { "message": "No query results for model [App\\Models\\Vakansiya] 999999" } ⚠️ o'zgarmadi

Xato chiqmadi. Sintaksis to'g'ri. Klass nomi to'g'ri. Kod shunchaki hech qachon chaqirilmaydi.

Sababni topish uchun framework kodiga qaraymiz — Handler.php:

// Illuminate/Foundation/Exceptions/Handler.php $e = $this->prepareException($e); ← 710-qator: AVVAL if ($response = $this->renderViaCallbacks($request, $e)) { ← KEYIN return ...; (bizning render'imiz) }

Va prepareException() ichida:

match (true) { $e instanceof ModelNotFoundException => new NotFoundHttpException($e->getMessage(), $e), $e instanceof AuthorizationException => new AccessDeniedHttpException($e->getMessage(), $e), ... }

Ya'ni bizning handler chaqirilguncha ModelNotFoundException boshqa klassga aylantirilgan bo'ladi. Biz esa eski nomni kutib turibmiz.

Qaysi biri aylantiriladi?

To'rtta handler yozib, har birini alohida sinab ko'rdim:

render(ModelNotFoundException ...) → ISHLAMADI ⚠️ render(AuthorizationException ...) → ISHLAMADI ⚠️ render(AuthenticationException ...) → ishladi ✅ render(ValidationException ...) → ishladi ✅ render(NotFoundHttpException ...) → ishladi ✅ render(AccessDeniedHttpException ...) → ishladi ✅

Naqsh aniq: prepareException ro'yxatidagilar ishlamaydi, qolganlari ishlaydi.

Siz kutgan nom Aslida keladigan nom ──────────────────────────────────────────────────────── ModelNotFoundException → NotFoundHttpException AuthorizationException → AccessDeniedHttpException TokenMismatchException → HttpException (419) AuthenticationException → o'zi (401 alohida yo'l bilan) ValidationException → o'zi (422 alohida yo'l bilan)
⚠️ Nega bu xato juda xavfli

Chunki u jimgina. Kod bor, u to'g'ri ko'rinadi, code review'dan o'tadi, testda ham ko'rinmaydi — chunki natija baribir 404. Faqat xabar boshqacha.

🔑 Bu 46-darsdagi ?sort=moash bilan bir oiladan: status to'g'ri, mazmun noto'g'ri. Bunday xatolarni faqat javob tanasini tekshiradigan test tutadi.

getPrevious() — asl sabab

To'g'ri nomni yozdik — endi yangi savol tug'iladi. NotFoundHttpException ikki xil holatda keladi:

GET /api/vakansiyalar/999999 → yozuv topilmadi GET /api/yolgon-manzil → bunday marshrut yo'q

Mijoz uchun bular butunlay boshqa narsa. Birinchisida manzil to'g'ri, ma'lumot yo'q. Ikkinchisida mijoz noto'g'ri manzilga murojaat qilyapti — bu mijozning kodidagi xato.

Ajratish uchun getPrevious() ishlatiladi. prepareException eski xatoni yangisining ichiga qo'yadi (new NotFoundHttpException($e->getMessage(), $e) — ikkinchi argument aynan shu). O'lchandi:

/api/vakansiyalar/999999 → getPrevious(): ModelNotFoundException /api/yolgon-manzil → getPrevious(): null // 403 uchun ham xuddi shunday: begona yozuvni o'chirish → getPrevious(): AuthorizationException

Endi handlerni yozish mumkin:

bootstrap/app.php
$exceptions->render(function (NotFoundHttpException $e, Request $request) { if (! $request->is('api/*')) { return null; } return response()->json([ 'message' => match (true) { $e->getPrevious() instanceof ModelNotFoundException => 'So\'ralgan yozuv topilmadi.', $request->route() === null => 'Bunday manzil yo\'q.', default => $e->getMessage(), }, ], 404); });

Natija:

/api/vakansiyalar/999999 → { "message": "So'ralgan yozuv topilmadi." } /api/yolgon-manzil → { "message": "Bunday manzil yo'q." }

return null nima qiladi?

Handler null qaytarsa, Laravel «bu xatoni sen bilmagansan» deb tushunadi va standart yo'lga tushadi. Bizga aynan shu kerak: API JSON oladi, web esa o'zining HTML 404 sahifasida qoladi. O'lchandi:

GET /api/yolgon → 404, application/json ← bizning xabar GET /yolgon → 404, text/html ← Laravel sahifasi

Uchinchi qator — default => $e->getMessage() — nima uchun kerakligini «Har xil holatlar» bo'limida ko'ramiz (HOLAT 3).

O'z xatoyingiz

Endi domen tomoniga o'tamiz. Ish beruvchi vakansiyani yopadi (faol = false). Mijoz esa eski havolani ochadi. Hozir nima bo'ladi?

GET /api/vakansiyalar/3 → 200, hamma ma'lumot bilan

Bu noto'g'ri: mobil ilova «Ariza yuborish» tugmasini chiqaradi, foydalanuvchi bosadi — va ariza hech qayerga bormaydi.

Bu holat uchun HTTP'da aniq status bor — 410 Gone: «bu resurs bor edi, endi yo'q, va bu doimiy». 404 dan farqi shunda: 404 «bunday narsa bo'lganini bilmayman», 410 esa «bo'lgan, ataylab yopilgan».1

Buning uchun o'z xato klassimizni yozamiz:

app/Exceptions/VakansiyaYopilgan.php
<?php namespace App\Exceptions; use App\Models\Vakansiya; use Exception; use Illuminate\Http\Request; class VakansiyaYopilgan extends Exception { public function __construct(public Vakansiya $vakansiya) { parent::__construct("Vakansiya yopilgan: {$vakansiya->id}"); } public function render(Request $request) { return response()->json([ 'message' => 'Bu vakansiya endi qabul qilmayapti.', 'kod' => 'vakansiya_yopilgan', 'yopilgan_sana' => $this->vakansiya->updated_at->toDateString(), ], 410); } }

Ikkita yangi narsa bor.

Birinchisi — render() metodi. Agar xato klassida shunday metod bo'lsa, Laravel uni o'zi topadi: bootstrap/app.php ga hech narsa yozish kerak emas. Xato o'z javobini o'zi bilan olib yuradi.

Ikkinchisi — public Vakansiya $vakansiya konstruktorda. Bu 12-darsdagi konstruktor bo'yicha xossa (constructor property promotion): argument bir vaqtning o'zida xossa bo'lib qoladi. Shu tufayli render() ichida $this->vakansiya mavjud — ya'ni javobga kontekst qo'sha olamiz.

Controllerda ishlatish bir qator:

app/Http/Controllers/Api/VakansiyaController.php
public function show(Vakansiya $vakansiya) { if (! $vakansiya->faol) { throw new VakansiyaYopilgan($vakansiya); } return VakansiyaResource::make($vakansiya->load('kompaniya')); }
GET /api/vakansiyalar/1 (faol) → 200, ma'lumot GET /api/vakansiyalar/3 (yopiq) → 410 { "message": "Bu vakansiya endi qabul qilmayapti.", "kod": "vakansiya_yopilgan", "yopilgan_sana": "2026-08-25" }
🔍 kod maydoni nima uchun?

message — odam uchun, va u o'zgarishi mumkin (tarjima, tahrir). kod — dastur uchun, va u hech qachon o'zgarmaydi.

Mobil ilova if (kod === 'vakansiya_yopilgan') deb yozadi. Agar u message matnini solishtirsa, siz xabardagi bitta harfni tuzatishingiz bilan uning kodi buziladi.

Log: shovqin va foyda

Xatoni yozgach, storage/logs/laravel.log ga qaraymiz. Kutilmagan narsa bor:

[2026-08-25 07:22:46] local.ERROR: Vakansiya yopilgan: 3

Yopilgan vakansiyani ochish — xato emas. Bu normal ish jarayoni. Lekin har safar ERROR darajasida loglanmoqda. Kuniga ming marta bo'lsa, logingiz shu bilan to'ladi va haqiqiy xatolar ko'rinmay qoladi.

Laravel'ning o'zida bunday ro'yxat bor — 12 ta klass hech qachon loglanmaydi (ValidationException, AuthenticationException, ModelNotFoundException va boshqalar). Shuning uchun 422 va 404 logda ko'rinmaydi. O'z klassimizni ham qo'shamiz:

bootstrap/app.php
$exceptions->dontReport([ VakansiyaYopilgan::class, ]);

Teskarisi ham bor: stopIgnoring(ModelNotFoundException::class) — «404'larni menga ko'rsat» degani. Ba'zan foydali: mijoz qayerlarni noto'g'ri so'rayotganini bilish uchun.

Logga kontekst qo'shish

Endi haqiqiy xato — 500 — logda qanday ko'rinadi? Standart holda faqat xabar va stack trace. «Kim?» va «qaysi manzil?» yo'q. Buni context() hal qiladi:

bootstrap/app.php
$exceptions->context(fn () => [ 'manzil' => request()->fullUrl(), 'user_id' => request()->user()?->id, ]);
[2026-08-25 07:22:45] local.ERROR: Baza yiqildi {"manzil":"http://127.0.0.1:8000/api/x/500","user_id":null,"exception":"[object] ..."}

Bu funksiya har bir log yozuvida chaqiriladi — shuning uchun uni yengil tuting.

500 uchun xato raqami

Endi darsning boshidagi ikkinchi muammoga qaytamiz. {"message": "Server Error"} — mijoz bunga qarab hech narsa qila olmaydi, siz ham unga qarab logdan hech narsa topa olmaysiz.

Yechim oddiy: har bir 500 ga raqam beramiz. O'sha raqam javobda ham, logda ham bo'ladi. Mijoz shikoyat qilganda raqamni aytadi, siz logdan bir soniyada topasiz.

Buning uchun respond() ishlatiladi — u tayyor javobni oxirgi marta ko'rib chiqadi:

bootstrap/app.php
$exceptions->respond(function ($javob, Throwable $e, Request $request) { if (! $request->is('api/*') || $javob->getStatusCode() !== 500) { return $javob; } $id = (string) Str::uuid(); Log::error('API 500', [ 'xato_id' => $id, 'manzil' => $request->fullUrl(), 'sabab' => $e->getMessage(), ]); return response()->json([ 'message' => 'Serverda kutilmagan xato yuz berdi.', 'xato_id' => $id, ], 500); });
// mijozga: { "message": "Serverda kutilmagan xato yuz berdi.", "xato_id": "6a72b6d9-e53a-4856-9c9e-845aeec7c3ca" } // logda: local.ERROR: API 500 {"xato_id":"6a72b6d9-e53a-4856-9c9e-845aeec7c3ca", ...}

Bir xil raqam ikki joyda. Endi «sizda 500 chiqdi» degan shikoyat manzilga aylandi.

⚠️ Metod nomi respondUsing emas

Avval $exceptions->respondUsing(...) deb yozdim va butun ilova qulab tushdi — 404 ham, 410 ham, hammasi 500 Server Error bo'lib qoldi.

Call to undefined method Illuminate\Foundation\Configuration\Exceptions::respondUsing()

Sababi: respondUsing() Handler klassida bor, bootstrap/app.php dagi $exceptions esa boshqa klass — Configuration\Exceptions. Undagi nom — respond().

🔑 Va bu xatoni topish oson bo'lmadi: APP_DEBUG=false bo'lgani uchun javob shunchaki «Server Error» edi. Sabab faqat APP_DEBUG=true qo'yilgach ko'rindi.
🔍 Tashxis: hamma narsa 500 bo'lib qolsa — birinchi ish APP_DEBUG=true.

Yakuniy withExceptions

bootstrap/app.php
use App\Exceptions\VakansiyaYopilgan; use Illuminate\Database\Eloquent\ModelNotFoundException; use Illuminate\Http\Request; use Illuminate\Support\Facades\Log; use Illuminate\Support\Str; use Symfony\Component\HttpKernel\Exception\NotFoundHttpException; // ... ->withExceptions(function (Exceptions $exceptions): void { $exceptions->shouldRenderJsonWhen( fn (Request $request) => $request->is('api/*') || $request->expectsJson(), ); $exceptions->context(fn () => [ 'manzil' => request()->fullUrl(), 'user_id' => request()->user()?->id, ]); $exceptions->dontReport([ VakansiyaYopilgan::class, ]); $exceptions->render(function (NotFoundHttpException $e, Request $request) { if (! $request->is('api/*')) { return null; } return response()->json([ 'message' => match (true) { $e->getPrevious() instanceof ModelNotFoundException => 'So\'ralgan yozuv topilmadi.', $request->route() === null => 'Bunday manzil yo\'q.', default => $e->getMessage(), }, ], 404); }); $exceptions->respond(function ($javob, Throwable $e, Request $request) { if (! $request->is('api/*') || $javob->getStatusCode() !== 500) { return $javob; } $id = (string) Str::uuid(); Log::error('API 500', [ 'xato_id' => $id, 'manzil' => $request->fullUrl(), 'sabab' => $e->getMessage(), ]); return response()->json([ 'message' => 'Serverda kutilmagan xato yuz berdi.', 'xato_id' => $id, ], 500); }); })->create();

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

API xatolar jadvali

400 so'rov o'zi buzuq (JSON sintaksisi xato) 401 { "message": "Unauthenticated." } tokensiz / yolg'on token 403 { "message": "This action is unauthorized." } policy ruxsat bermadi 404 { "message": "So'ralgan yozuv topilmadi." } yozuv yo'q 405 { "message": "The DELETE method is not supported for route api/vakansiyalar. Supported methods: GET, HEAD, POST." } 410 { "message": "...", "kod": "vakansiya_yopilgan" } yopilgan 422 { "message": "...", "errors": { "nom": [...] } } ma'lumot xato 429 (48-darsda) juda ko'p so'rov 500 { "message": "...", "xato_id": "..." } bizning xatomiz

🔑 Chegara: 4xx — mijozning xatosi, 5xx — sizniki. Agar 5xx qaytarayotgan bo'lsangiz, kimdir kodni tuzatishi kerak.

🔍 405 javobi qaysi metodlar ruxsat etilganini o'zi aytadi — bu foydali, sizdirish emas: mijoz baribir manzilni biladi.

HOLAT 2

APP_DEBUG ishlab chiqarishda yoqilgan

APP_DEBUG=true → 500 javobi 14911 bayt file, line, 38 kadrli trace

Bu eng ko'p uchraydigan haqiqiy xavfsizlik xatosi: .env ni serverga ko'chirishda unutiladi.

✅ APP_DEBUG=false va APP_ENV=production.
🔍 Tashxis: php artisan about — «Debug Mode» qatoriga qarang.

⚠️ Lekin false qilish yetarli emas: 404 xabari baribir model nomini aytadi (yuqorida ko'rdik). Shuning uchun render() yozamiz.

HOLAT 3

Keng handler abort() xabarini yutib yuboradi

// controllerda: abort(404, 'Bu kompaniya arxivlangan'); // mijozga (bizning render'imiz bilan): { "message": "Bunday manzil yo'q." } ⚠️ xabar yo'qoldi

Sabab: abort(404, ...) ham NotFoundHttpException tashlaydi, va bizning handler hammasini ushlaydi.

✅ Shuning uchun yakuniy kodda uchinchi tarmoq bor:

$request->route() === null => 'Bunday manzil yo\'q.' ← marshrut topilmadi default => $e->getMessage() ← abort() xabari

$request->route() — marshrut topilmagan bo'lsa null. Shu bilan «manzil yo'q» va «kod ataylab 404 tashladi» ajraladi. O'lchandi — uchala holat ham to'g'ri xabar beradi.

🔑 Umumiy saboq: keng handler yozsangiz, u nimalarni ushlashini sanab chiqing.

HOLAT 4

JSON'da — ko'rinishi

json_encode(['x' => 'salom — dunyo']) → {"x":"salom — dunyo"} json_encode([...], JSON_UNESCAPED_UNICODE) → {"x":"salom — dunyo"}

PHP standart holda ASCII bo'lmagan belgilarni qochiradi. Bu xato emas — mijoz JSON'ni ochganda to'g'ri matn oladi.

🔍 Bizning xabarlarimizda muammo yo'q, chunki o' va g' oddiy ASCII apostrof bilan yozilgan. Lekin —, «» yoki emoji ishlatsangiz javob shunday ko'rinadi.

HOLAT 5

Xatoni testda ko'rish

$this->withoutExceptionHandling(); ← xatoni O'ZI ni ko'rsatadi

Test 500 qaytardi, sababi noma'lum. Shu qatorni testning boshiga qo'ying — Laravel xatoni ushlamaydi va Pest sizga haqiqiy xato bilan stack trace'ni ko'rsatadi.

⚠️ Tekshirgandan keyin o'chiring: bu qator turgan testda xato javoblarini (404, 422) tekshirib bo'lmaydi — ular endi exception bo'lib chiqadi.

HOLAT 6

Log darajasini boshqarish

$exceptions->level(ValidationException::class, LogLevel::INFO); $exceptions->dontReport([VakansiyaYopilgan::class]); $exceptions->stopIgnoring(ModelNotFoundException::class); $exceptions->dontReportDuplicates();

level() — «logla, lekin ERROR emas». dontReport() — «umuman loglama». stopIgnoring() — «Laravel yashirganini menga ko'rsat».

🔑 Maqsad bitta: logda faqat siz harakat qiladigan narsalar qolsin. Logga qaramaydigan dasturchi yo'q emas — logi shovqinli dasturchi bor.

Sinab ko'ramiz

Natijani taxmin qiling

Dasturchi 404 xabarini tuzatmoqchi bo'ldi. U bootstrap/app.php ga shuni yozdi:

bootstrap/app.php
$exceptions->render(function (ModelNotFoundException $e, Request $request) { return response()->json(['message' => 'Yozuv topilmadi.'], 404); });

Testni ishga tushirdi:

it('mavjud bo\'lmagan yozuv uchun 404 beradi', function () { $this->getJson('/api/vakansiyalar/999999')->assertNotFound(); }); Tests: 1 passed ← YASHIL

Test yashil, kod bor, xato yo'q. Lekin mijoz hamon App\Models\Vakansiya ni ko'ryapti. Nima bo'lyapti?

Javobni ko'rish

Handler hech qachon chaqirilmaydi. Laravel ModelNotFoundException ni NotFoundHttpException ga aylantirib bo'lgan.

Handler.php:710 $e = $this->prepareException($e); ← AVVAL aylantiradi Handler.php:712 $this->renderViaCallbacks($request, $e) ← KEYIN bizni chaqiradi

⚠️ Test yashil bo'lgani chalg'itdi: u faqat statusni tekshirgan. Status esa ikkala holatda ham 404 — handler ishlagan-ishlamaganidan qat'i nazar.

🔑 Bu 46-darsdagi ?sort=moash bilan bir xil naqsh: status to'g'ri, mazmun noto'g'ri. Bunday xatolar faqat tanani tekshiradigan test bilan tutiladi:

->assertExactJson(['message' => 'So\'ralgan yozuv topilmadi.']); expect($javob->json('message'))->not->toContain('App\\Models');

✅ To'g'ri klass — NotFoundHttpException, va yozuv/manzilni ajratish uchun getPrevious().

🔍 Umumiy saboq: assertNotFound() — zaif tekshiruv. «Status to'g'rimi?» degan savol «javob to'g'rimi?» degani emas.

SAVOL 1 render(ModelNotFoundException …) nega ishlamaydi?

prepareException() ModelNotFoundException ni NotFoundHttpException ga aylantiradi — va bu bizning handler chaqirilishidan oldin bo'ladi. ⚠️ Eng yomoni: xato chiqmaydi, kod shunchaki o'lik. ✅ Asl sababni getPrevious() beradi.

SAVOL 2 APP_DEBUG=false qilish yetarlimi?

O'lchandi: 500 javobi 14911 baytdan 33 baytga tushdi — bu katta yutuq. Lekin 404 hamon No query results for model [App\Models\Vakansiya] deydi. ✅ Shuning uchun render() bilan xabarni o'zingiz yozasiz.

SAVOL 3 Xato javobida kod maydoni nima uchun kerak?

message — odam uchun va o'zgaradi (tarjima, tahrir). kod — dastur uchun va o'zgarmaydi. ⚠️ Mijoz message matnini solishtirsa, xabardagi bitta harf tuzatilishi bilan uning kodi buziladi. 🔑 43-darsdagi Resource g'oyasi — xatolar tomonida.

Eslab ayting

Javobni ovoz chiqarib ayting, keyin ochib solishtiring.

APP_DEBUG ikki holatida 500 javobi qanday farq qiladi?
true: 14911 bayt — message, exception, file (to'liq fayl yo'li), line va 38 kadrli trace. false: 33 bayt — {"message": "Server Error"}. Birinchisi xavfli, ikkinchisi foydasiz — shuning uchun xato_id qo'shamiz.
Nega render(ModelNotFoundException …) hech qachon chaqirilmaydi?
Handler::prepareException() uni NotFoundHttpException ga aylantiradi, va bu renderViaCallbacks() dan oldin bo'ladi. Xuddi shu narsa AuthorizationException → AccessDeniedHttpException uchun ham to'g'ri. AuthenticationException va ValidationException esa aylantirilmaydi — ular uchun handler ishlaydi.
Bitta NotFoundHttpException ichidagi ikki xil holatni qanday ajratasiz?
$e->getPrevious() bilan. Yozuv topilmasa u ModelNotFoundException qaytaradi; marshrut topilmasa null. Uchinchi holat — abort(404, 'xabar'): unda getPrevious() null, lekin $request->route() bor, ya'ni xabarni saqlab qolish kerak.
Xato klassidagi render() metodi nima qiladi va u qanday topiladi?
Xato o'z HTTP javobini o'zi bilan olib yuradi: status, xabar, qo'shimcha maydonlar. bootstrap/app.php ga hech narsa yozish kerak emas — Laravel klassda render() borligini o'zi ko'radi. Konstruktor bo'yicha xossa (public Vakansiya $vakansiya) tufayli javobga kontekst qo'shish mumkin.
dontReport nega kerak va nima uchun respond() (respondUsing() emas)?
dontReport: normal ish jarayoni (masalan yopilgan vakansiya) standart holda ERROR darajasida loglanadi — bu shovqin, haqiqiy xatolarni ko'mib yuboradi. Laravel'ning o'zida shunday 12 ta klass bor. respondUsing() — Handler klassining metodi; bootstrap/app.php dagi $exceptions esa Configuration\Exceptions, undagi nom — respond().
Xulosa
  • Mijozga kerakli miqdorda, logga hamma narsani. Xato javobining maqsadi — «nima bo'ldi» va «endi nima qilay».
  • APP_DEBUG=true → 14911 bayt, fayl yo'li va 38 kadrli trace. Ishlab chiqarishda faqat false.
  • ⚠️ false yetarli emas: 404 hamon App\Models\Vakansiya deydi.
  • ⚠️ render(ModelNotFoundException …) — o'lik kod. prepareException() uni NotFoundHttpException ga aylantirib bo'lgan.
  • Xuddi shu narsa AuthorizationException → AccessDeniedHttpException uchun ham. AuthenticationException va ValidationException esa aylantirilmaydi.
  • getPrevious() asl sababni beradi: yozuv yo'q · manzil yo'q · abort().
  • return null — standart yo'lga qaytish. Shu tufayli web tomon HTML'da qoladi.
  • Xato klassidagi render() metodi javobni xato bilan birga olib yuradi. 410 Gone — «bor edi, ataylab yopildi».
  • message odam uchun, kod dastur uchun. Mijoz matnni emas, kodni solishtirsin.
  • ⚠️ O'z xatoyingiz standart holda ERROR bo'lib loglanadi → dontReport.
  • respond() (emas respondUsing()) — 500 uchun xato_id: javobda ham, logda ham bir xil.
  • ⚠️ assertNotFound() zaif tekshiruv — tanani ham tekshiring (assertExactJson, not->toContain).
  • Autentifikatsiya xatolari doim bir xil gapirsin.
🌱 Keyingi dars

API endi to'liq, himoyalangan, qidiriladigan va xatolari tartibli. Bitta bo'shliq qoldi: hozir istalgan kishi /api/token ga soniyasiga ming marta so'rov yubora oladi — parolni taxmin qilish uchun ham, serverni band qilish uchun ham.

48-darsda rate limiting qo'shamiz: throttle, RateLimiter va yangi status — 429 Too Many Requests. Yonida versiyalash ham bor: /api/v1 nima uchun kerak va uni qachon qo'shish kerak (javob: kech emas).
