⭐ 1-zaiflik: hujumchi o'zini admin qiladi

Laravel 13 da User modeli shunday yozilgan:

#[Fillable(['name', 'email', 'password', 'rol'])] #[Hidden(['password', 'remember_token'])] class User extends Authenticatable

rol — fillable ro'yxatida. Ya'ni uni ommaviy tayinlash orqali yozish mumkin.

Endi tasavvur qiling, ro'yxatdan o'tish kodi shunday:

User::create($request->all());

Hujumchi oddiy formaga yashirin maydon qo'shadi:

yuborilgan: {"name":"Hujumchi","email":"h@x.uz","password":"parol123","rol":"admin"} User::create($request->all()) -> rol = 'admin' ⚠️ rol siz -> rol = NULL
⚠️ Nima bo'ldi?

Hujumchi admin bo'ldi. Bir qator qo'shib.

Xato yo'q. Ogohlantirish yo'q. Log toza. Ro'yxatdan o'tish muvaffaqiyatli.

🔑 Bu ommaviy tayinlash (mass assignment) zaifligi. Nomi shundan: bir marta ommaviy ravishda hamma maydonni tayinlaysiz — va ular orasida tayinlanmasligi kerak bo'lgani ham bor.

✅ Tuzatish — ikki qatlam

1-QATLAM: modelda #[Fillable(['name', 'email', 'password'])] ← rol OLIB TASHLANDI 2-QATLAM: so'rovda $request->validate([...]) ← rol qoidalarda YO'Q User::create($request->validated()) ← faqat tekshirilgani o'tadi

🔑 Ikkalasi ham kerak. Birinchisi — «hech qachon», ikkinchisi — «bu yerda». Biri unutilsa, ikkinchisi ushlab qoladi.

⚠️ Va $request->all() ni hech qachon to'g'ridan-to'g'ri create() ga bermang. Har doim validated().

2-zaiflik: user_id

O'z modelimizga qaraymiz:

protected $fillable = ['nom', 'maosh', 'shahar', 'faol', 'kompaniya_id', 'user_id', 'muddat']; ↑ XAVF

user_id — vakansiyaning egasi. Uni foydalanuvchi yozmasligi kerak — server o'zi qo'yadi.

Vakansiya::create(['user_id' => $qurbon->id, ...]) -> user_id = QURBON <-- yozildi

🔍 Hozircha bizni tekshiruv qutqaradi: VakansiyaRequest qoidalarida user_id yo'q, demak validated() uni chiqarib tashlaydi.

Lekin bu — bitta qatlam. Kimdir ertaga yangi controller yozsa va $request->all() ishlatsa — zaiflik ochiladi.

⚠️ Tuzatishning tuzog'i

Yechim ravshan: user_id ni fillable dan olib tashlaymiz.

protected $fillable = ['nom', 'maosh', 'shahar', 'faol', 'kompaniya_id', 'muddat'];

Testlarni ishga tushiramiz:

Tests: 3 failed, 1 skipped, 112 passed (229 assertions) FAILED Tests\Feature\AmalTest > it vakansiya yaratadi va egasini biriktiradi Failed asserting that null is identical to 1.
⚠️ null — bu eng muhim so'z

fillable da bo'lmagan maydon xato bermaydi — u jimgina tashlab yuboriladi.

Vakansiya::create([... 'user_id' => 5]) user_id fillable da BOR -> user_id = 5 user_id fillable da YO'Q -> user_id = null ⚠️ xato YO'Q

Ya'ni «himoya qo'ydim» deb o'ylab, aslida egasi yo'q vakansiyalar yaratgan bo'lardingiz.

🔑 Bizni test qutqardi. Testsiz bu ishlab chiqarishga chiqib ketardi — va faqat «nega mening vakansiyalarim ko'rinmayapti?» degan shikoyatdan keyin bilinardi.

✅ To'g'ri tuzatish

public function bajar(VakansiyaMalumoti $malumot, User $egasi): Vakansiya { $vakansiya = new Vakansiya($malumot->jadvalGa()); $vakansiya->user_id = $egasi->id; // ← ALOHIDA, ommaviy emas $vakansiya->save(); VakansiyaYaratildi::dispatch($vakansiya); return $vakansiya->fresh(); }

SQL inyeksiya

Klassik hujum. Bazada 5 ta kompaniya bor. Hujumchi qidiruvga shuni yozadi:

' OR '1'='1

Ikki xil yozilgan kodni solishtiramiz:

where('nom', $yovuz) -> 0 ta ✅ DB::select("select * from kompaniyalar where nom = '$yovuz'") -> 5 ta ⚠️

Ikkinchisi hamma yozuvni qaytardi. Agar bu kirish tekshiruvi bo'lganida — hujumchi parolsiz kirgan bo'lardi.

🔑 Nega birinchisi xavfsiz?

Laravel qiymatni SQL'ga qo'shmaydi. U alohida yuboriladi:

SQL: select * from "kompaniyalar" where "nom" = ? bog'lash: ["' OR '1'='1"]

Baza ? o'rniga qiymatni ma'lumot sifatida qo'yadi — hech qachon buyruq sifatida emas.

🔑 Bu «bog'langan parametr» (prepared statement) deb ataladi va u eng ishonchli himoya.

orderBy va orderByRaw

Ustun nomlarini bog'lab bo'lmaydi — ular SQL'ning bir qismi. Laravel nima qiladi?

Vakansiya::orderBy('nom; drop table vakansiyalar') -> order by "nom; drop table vakansiyalar" asc ✅ qo'shtirnoqda Vakansiya::orderByRaw('nom; drop table vakansiyalar') -> order by nom; drop table vakansiyalar ⚠️ XOM

orderBy() butun matnni bitta ustun nomi deb qo'shtirnoqqa oladi. Natijada so'rov xato beradi — lekin inyeksiya bo'lmaydi.

⚠️ orderByRaw() esa — hech narsa qilmaydi. Foydalanuvchi kiritmasi u yerga hech qachon tushmasin.

✅ Bizda 62-darsdagi TARTIBLAR qat'iy ro'yxati bor — foydalanuvchi faqat beshta qiymatdan birini tanlay oladi, boshqasi 422 beradi.

XSS — brauzerdagi hujum

Foydalanuvchi vakansiya nomiga shuni yozadi:

<script>alert(1)</script>

Blade ikki usulni beradi:

{{ $x }} -> &lt;script&gt;alert(1)&lt;/script&gt; ✅ qochirildi {!! $x !!} -> <script>alert(1)</script> ⚠️ XOM

Birinchisi — standart. Ya'ni Blade sizni o'zi himoya qiladi.

⚠️ {!! !!} qachon ishlatiladi?

Faqat siz yozgan HTML uchun. Masalan Markdown'dan yaratilgan matn yoki tarjima fayli.

❌ Hech qachon foydalanuvchi kiritmasi uchun — hatto «tozalab olganman» desangiz ham.

🔑 Qidirish oson: grep -rn '{!!' resources/views. Har topilganini tekshiring.

🔍 JSON API — kim qochiradi?

Bizning ilovamiz JSON qaytaradi. Tekshiramiz:

response()->json(['nom' => '<script>alert(1)</script>']) -> {"nom":"<script>alert(1)<\/script>"}

<script> saqlanib qoldi (faqat / qochirildi — bu JSON qoidasi, xavfsizlik emas).

🔑 Va bu — TO'G'RI

JSON — ma'lumot, HTML emas. API qochirmasligi kerak, chunki:

API qochirsa -> mobil ilova "&lt;script&gt;" ko'rsatadi ❌ API qochirmasa -> har mijoz O'ZIGA kerakligicha ishlatadi ✅

⚠️ Demak mas'uliyat mijozda: React, Vue, mobil ilova — hammasi o'z tomonida qochirishi kerak.

🔑 Zamonaviy freymvorklar buni o'zi qiladi (React {x} qochiradi), lekin dangerouslySetInnerHTML yoki v-html — o'sha {!! !!} ning o'zi.

CSRF

Hujum shunday ishlaydi: siz saytimizga kirgansiz. Keyin boshqa saytga borasiz, va o'sha yerda yashirin forma bizning saytimizga POST yuboradi. Brauzer cookie'ni o'zi qo'shadi — server sizni tanidi.

Himoya: har formada maxfiy token.

Haqiqiy serverda sinadik:

curl -X POST http://127.0.0.1:8077/zond-web -d 'a=1' -> 419 ✅ CSRF token mismatch curl -X POST http://127.0.0.1:8077/api/v1/vakansiyalar -d 'nom=x' -> 401 ← CSRF emas, autentifikatsiya

419 — Laravel'ning maxsus kodi: «token yo'q yoki eskirgan».

🔑 Nega API'da CSRF yo'q?

CSRF hujumi cookie ga tayanadi. API esa cookie emas, token ishlatadi (44-dars) — va brauzer Authorization sarlavhasini o'zi qo'shmaydi.

Shuning uchun routes/api.php da CSRF kerak emas va Laravel uni qo'ymaydi ham.

⚠️ CSRF ni testda tekshirib bo'lmaydi

Test yozmoqchi bo'ldik — 200 qaytdi, 419 emas. Sabab freymvork kodida:

// Illuminate\Foundation\Http\Middleware\PreventRequestForgery public function handle($request, Closure $next) { if ( $this->isReading($request) || $this->runningUnitTests() || // ← MANA ...

Testda CSRF butunlay o'chiriladi — aks holda har testda token olish kerak bo'lardi.

✅ Demak CSRF ni faqat haqiqiy server bilan tekshirasiz (yuqoridagi curl kabi).

🔍 Yon eslatma: Laravel 13 da sinf nomi PreventRequestForgery. ValidateCsrfToken hamon ishlaydi, lekin eskirgan deb belgilangan.

⭐ APP_DEBUG — eng qimmat bir harf

Bitta marshrut yozdik. U ataylab xato tashlaydi va xato matnida sir bor:

⚠️ 877 560 bayt ichida nima bor?

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

IDOR — begona yozuvni ko'rish

❌ GET /api/v1/buyurtmalar/1042 public function show(Buyurtma $buyurtma) { return BuyurtmaResource::make($buyurtma); // KIMNIKI ekani tekshirilmadi }

Hujumchi shunchaki id ni o'zgartiradi: 1042, 1043, 1044... va begonalarning ma'lumotini o'qiydi.

Nomi: IDOR — Insecure Direct Object Reference.

✅ Yechim — 38-darsdagi Policy:

$this->authorize('view', $buyurtma);

🔑 Sinov: «bu endpointda id ni o'zgartirsam nima bo'ladi?» Har endpoint uchun so'rang.

HOLAT 2

Fayl yuklash

❌ $request->file('rasm')->storeAs('public', $request->file('rasm')->getClientOriginalName());

Uchta muammo: 1) nomi hujumchidan (../../.env), 2) turi tekshirilmagan (.php yuklash mumkin), 3) hajmi cheklanmagan.

✅ 'rasm' => ['required', 'image', 'mimes:jpg,png', 'max:2048'], $yol = $request->file('rasm')->store('rasmlar'); // nomni Laravel o'zi beradi

⚠️ mimes: fayl mazmunini tekshiradi, kengaytmasini emas — zararli.php ni rasm.jpg deb nomlash yordam bermaydi.

🔑 Va yuklangan fayllarni bajariladigan papkada saqlamang.

HOLAT 3

Parol qoidalari

'password' => ['required', Password::min(8)->letters()->numbers()->uncompromised()],

uncompromised() — parol ommaviy sizib chiqqan ro'yxatda bormi, shuni tekshiradi.

🔑 U parolni yubormaydi: SHA-1 hashning faqat birinchi 5 belgisi jo'natiladi (k-anonymity).

✅ 'password' => 'hashed' casti (bizda bor) parolni o'zi hash qiladi — Hash::make() yozish shart emas.

⚠️ Ikki marta hash qilmang: cast va Hash::make() birga ishlatilsa, parol buziladi.

HOLAT 4

Model::unguard()

❌ Model::unguard(); // fillable BUTUNLAY o'chadi User::create($request->all());

Ba'zan seederlarda uchraydi. Agar u AppServiceProvider ga tushib qolsa — butun ilova himoyasiz qoladi.

✅ Faqat vaqtincha va aniq chegarada:

Model::unguarded(function () { // faqat shu ichida });

🔑 Qidiring: grep -rn 'unguard' app/ database/.

Sinab ko'ramiz

Natijani taxmin qiling

Jamoa profil tahrirlash sahifasini yozdi:

// UserController public function update(Request $request) { $malumot = $request->validate([ 'name' => ['required', 'string', 'max:120'], 'email' => ['required', 'email'], ]); $request->user()->update($malumot); return back()->with('holat', 'Saqlandi'); }

Ko'rib chiqishda hammasi joyida ko'rindi: validate() ishlatilgan, $request->all() yo'q, $request->user() — o'z profili.

Uch oydan keyin qo'llab-quvvatlash xizmatiga savol keldi: «nega mening emailim boshqa odamniki bilan bir xil?»

Bazada ikkita foydalanuvchi bir xil email bilan turibdi. Nima bo'lgan?

Javobni ko'rish

Tekshiruvda unique yo'q.

'email' => ['required', 'email'], // ↑ formati to'g'rimi — TEKSHIRILDI // band emasmi — TEKSHIRILMADI ⚠️

Ro'yxatdan o'tishda unique bor edi. Tahrirlashda — ko'chirilmagan.

🔑 Va bu xavfsizlik muammosi, shunchaki ma'lumot xatosi emas:

1) hujumchi qurbonning emailiga o'z profilini o'zgartiradi 2) "parolni unutdim" ni bosadi 3) tiklash havolasi... QAY BIRIGA ketadi? -> User::where('email', $email)->first() ← BIRINCHISI

Ya'ni hujumchi qurbonning hisobini egallashi mumkin.

✅ To'g'ri qoida:

'email' => [ 'required', 'email', Rule::unique('users')->ignore($request->user()->id), ],

ignore() shart — usiz foydalanuvchi o'z emailini saqlay olmaydi («band» deydi).

⚠️ Va baza darajasida ham:

$table->string('email')->unique(); ← migratsiyada

SAVOL 1 ' OR '1'='1 kiritmasini ikki xil kodga berdik. Natija?

🔍 O'lchandi: where('nom', $yovuz) → 0; DB::select("... nom = '$yovuz'") → 5 (hammasi). 🔑 Laravel qiymatni SQL'ga qo'shmaydi: where "nom" = ? + ["' OR '1'='1"]. Baza uni ma'lumot deb qabul qiladi, buyruq emas. ⚠️ orderByRaw ham xavfli: order by nom; drop table vakansiyalar — orderBy esa qo'shtirnoqqa oladi.

Eslab ayting

Javobni ovoz chiqarib ayting, keyin ochib solishtiring.

⭐ Ommaviy tayinlash zaifligi nima?
create() yoki update() ga foydalanuvchi kiritmasini to'g'ridan-to'g'ri berish. 🔍 O'lchandi: rol #[Fillable] da bo'lgani uchun User::create([... 'rol' => 'admin']) → foydalanuvchi admin bo'ldi. Xato yo'q, log toza. ✅ Ikki qatlam: 1) modeldan olib tashlash, 2) validated() ishlatish (all() emas). 🔑 Ikkalasi ham kerak: biri «hech qachon», ikkinchisi «bu yerda». ⚠️ Tuzoq: fillable dan olib tashlansa, maydon jimgina null bo'ladi — alohida yozing.
SQL inyeksiyadan nima himoya qiladi?
Bog'langan parametrlar (prepared statements). Laravel qiymatni SQL'ga qo'shmaydi: where "nom" = ? + ["' OR '1'='1"]. 🔍 O'lchandi: bog'lash bilan 0 yozuv, xom birlashtirish bilan 5 — hammasi. ⚠️ Xavfli joylar: whereRaw · orderByRaw · DB::select("...$x...") · selectRaw. 🔍 orderBy() esa xavfsiz — u butun matnni qo'shtirnoqqa oladi (so'rov xato beradi, lekin inyeksiya yo'q). ✅ Ustun nomlarini qat'iy ro'yxatdan tanlang (62-darsdagi TARTIBLAR).
XSS va JSON API — kim qochiradi?
Blade'da {{ }} o'zi qochiradi (&lt;script&gt;), {!! !!} — yo'q. 🔍 JSON'da esa <script> saqlanadi — va bu to'g'ri: JSON ma'lumot, HTML emas. 🔑 Mas'uliyat mijozda: React, Vue, mobil ilova o'z tomonida qochiradi. ⚠️ dangerouslySetInnerHTML va v-html — o'sha {!! !!} ning o'zi. ✅ Qidiring: grep -rn '{!!' resources/views.
CSRF nima va nega uni testda tekshirib bo'lmaydi?
Boshqa sayt sizning nomingizdan so'rov yuboradi — brauzer cookie'ni o'zi qo'shadi. Himoya: har formada maxfiy token. 🔍 O'lchandi (haqiqiy serverda): web POST → 419, API POST → 401. API'da CSRF kerak emas — u cookie emas, token ishlatadi. ⚠️ Testda CSRF butunlay o'chirilgan: PreventRequestForgery::handle() da $this->runningUnitTests() sharti bor. ✅ Shuning uchun uni faqat curl bilan tekshirasiz.

1) APP_DEBUG=false, APP_ENV=production — eng muhimi (🔍 877 560 bayt / 4 marta sir). 2) .env git'da yo'qmi, .env.example toza mi. 3) grep -rn '$request->all()' app/ 4) grep -rn '{!!' resources/views 5) grep -rn 'Raw(' app/ 6) grep -rn 'unguard' 7) fillable da rol/user_id/is_admin bormi 8) har endpoint: «id ni o'zgartirsam?» (IDOR) 9) composer audit. 🔑 10 daqiqada bajariladi.
