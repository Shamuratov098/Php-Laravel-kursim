DARS 40 · MODUL E — TEST (PEST)

Auth oqimi va policy testi

IshTop'ning ma'lumot qatlami test bilan qoplandi. Ammo 30–32-darsdagi auth oqimi — ro'yxatdan o'tish, kirish, chiqish va so'rov cheklovi — hali yozib qo'yilmagan. Bugun shularni yozamiz, va policy'ni HTTP so'rovsiz, to'g'ridan-to'g'ri sinashni o'rganamiz.

📱 O'qish ≈ 15 daqiqa 💻 Amaliyot ≈ 24 daqiqa Kerak: Dars 39

Bu darsda nimalar bor
  1. Kim kirgan — uchta savol assertGuest() · assertAuthenticated() · assertAuthenticatedAs($user). Farqi va qachon qaysi biri.
  2. Ro'yxatdan o'tish oqimi 34-darsdagi rol tanlash ham shu yerda qulflanadi: rol saqlandimi va odam darhol kirdimi.
  3. Rad etilgan holatlar Rolsiz yuborish va band email — ikkalasida ham foydalanuvchi yaratilmasligi tekshiriladi.
  4. Kirish: to'g'ri va xato parol assertAuthenticatedAs va assertGuest — bitta oqimning ikki tomoni.
  5. 🔍 Xato xabarini aniq tekshirish assertSessionHasErrors(['email' => 'Email yoki parol xato.']) — kalit emas, matn bo'yicha.
  6. ⚠️ session('errors') tuzog'i U massiv bo'lib turadi. 38-darsdagi sirli Call to a member function all() on array xatosining ildizi shu — o'lchab ko'rsatiladi.
  7. Chiqish post('/chiqish') dan keyin assertGuest().
  8. So'rov cheklovini test qilish 31-darsdagi RateLimiter: beshta xato urinish, oltinchisida boshqa xabar.
  9. 🔍 Cheklov keyingi testga o'tmaydi phpunit.xml dagi CACHE_STORE=array tufayli — bu ham o'lchandi.
  10. Policy — HTTP'siz $user->can('update', $vakansiya). Route ham, controller ham, forma ham kerak emas.
  11. Gate::forUser() Boshqa odam nomidan tekshirish: allows() va denies().
  12. Har xil holatlar (7 ta) session('errors') · assertAuthenticated vs As · sekin auth testlari · cheklov qoldig'i · policy testi qayerda yashaydi · actingAs chegarasi · faqat taqiqni tekshirish.
Auth — eng qimmat oqim

37-darsda «eng qimmat joylardan boshlang» degan edik: pul, huquq va ma'lumot yo'qolishi bilan bog'liq oqimlar. IshTop'da eng qimmatlisi — auth.

Chunki bu yerda buzilish jimgina bo'ladi:

parol tekshiruvi buzilsa → hamma hammaning hisobiga kiradi rol saqlanmasa → hamma nomzod bo'lib qoladi chiqish ishlamasa → umumiy kompyuterda sessiya ochiq qoladi cheklov ishlamasa → parolni bittalab tanlash mumkin

Bularning hech biri xato sahifasi ko'rsatmaydi. Sayt ishlayveradi — 37-darsdagi policy misolidagidek.

Va yana bir sabab bor: auth oqimini qo'lda tekshirish eng zerikarli ish. Ro'yxatdan o'tish, chiqish, boshqa odam bo'lib kirish, xato parol kiritish, besh marta xato kiritish... Buni bir marta yozib qo'yish — bir umrga yetadi.

Kim kirgan: uchta savol

$this->assertGuest(); // hech kim kirmagan $this->assertAuthenticated(); // kimdir kirgan (kimligi muhim emas) $this->assertAuthenticatedAs($user); // AYNAN shu odam kirgan

Uchtasi uch xil savolga javob beradi va ularni chalkashtirmaslik muhim:

ro'yxatdan o'tish → assertAuthenticated() («odam kirdimi?») kirish → assertAuthenticatedAs($u) («aynan Ali kirdimi?») xato parol → assertGuest() («kirmaganmi?») chiqish → assertGuest()

🔑 assertAuthenticated() zaifroq: u «kimdir kirgan» deydi. Kirish testida aynan kim kirganini tekshirish kerak — aks holda «har doim birinchi foydalanuvchini kiritadigan» buzuq kod ham o'tib ketardi.

Ro'yxatdan o'tish oqimi

tests/Feature/AuthTest.php test('nomzod ro\'yxatdan o\'tadi va darhol kiradi', function () { $javob = $this->post('/royxatdan-otish', [ 'name' => 'Nodira', 'email' => 'nodira@example.uz', 'password' => 'parol1234', 'password_confirmation' => 'parol1234', 'rol' => 'nomzod', ]); $javob->assertRedirect('/vakansiyalar'); $this->assertDatabaseHas(User::class, ['email' => 'nodira@example.uz']); $this->assertAuthenticated(); expect(User::where('email', 'nodira@example.uz')->first()->rol) ->toBe(Rol::Nomzod); });

To'rtta narsa bir joyda tekshirildi: qayerga qaytdi, foydalanuvchi yaratildimi, u darhol kirdimi, va 34-darsdagi rol to'g'ri saqlandimi.

Oxirgi expect() ga alohida qarang: ->toBe(Rol::Nomzod) — matn emas, enum bilan solishtiryapmiz. Agar cast qo'shilmagan bo'lsa (34-dars), bu tekshiruv yiqiladi.

Rad etilishi kerak bo'lgan holatlar

tests/Feature/AuthTest.php test('rol tanlanmasa ro\'yxatdan o\'tkazilmaydi', function () { $this->from('/royxatdan-otish')->post('/royxatdan-otish', [ 'name' => 'Nodira', 'email' => 'nodira@example.uz', 'password' => 'parol1234', 'password_confirmation' => 'parol1234', ])->assertSessionHasErrors(['rol' => 'Rolni tanlang.']); $this->assertGuest(); $this->assertDatabaseMissing(User::class, ['email' => 'nodira@example.uz']); });

🔑 Uchta qatlam yana: xato xabari chiqdimi, odam kirmadimi, va bazaga yozilmadimi. Uchinchisisiz test to'liq emas — foydalanuvchi yaratib, keyin xato ko'rsatadigan kod ham bo'lishi mumkin.

🔍 Xato xabarini matn bilan tekshirish

38-darsda assertSessionHasErrors(['rol']) yozgan edik — «shu maydonda xato bor». Endi kuchliroq shakl:

assertSessionHasErrors(['rol']) // maydon bo'yicha assertSessionHasErrors(['rol' => 'Rolni tanlang.']) // MATN bo'yicha ✅

Ikkinchisi 34-darsda yozgan o'zbekcha xabaringizni ham qulflaydi. Kimdir uni ingliz tiliga qaytarsa yoki o'chirsa — test aytadi.

Kirish: ikki tomon

tests/Feature/AuthTest.php test('to\'g\'ri parol bilan kiriladi', function () { $user = User::factory()->create(['email' => 'ali@example.uz']); $this->post('/kirish', [ 'email' => 'ali@example.uz', 'password' => 'password', ])->assertRedirect('/vakansiyalar'); $this->assertAuthenticatedAs($user); }); test('xato parol bilan kirib bo\'lmaydi', function () { User::factory()->create(['email' => 'ali@example.uz']); $this->from('/kirish')->post('/kirish', [ 'email' => 'ali@example.uz', 'password' => 'xato-parol', ])->assertSessionHasErrors(['email' => 'Email yoki parol xato.']); $this->assertGuest(); });

🔍 'password' => 'password' — bu UserFactory dagi standart parol. Fabrika har foydalanuvchiga shu parolni qo'yadi, shuning uchun testda uni bilib turasiz.

Ikkinchi testdagi xabar 30-darsdagi qoidani ham qulflaydi: xato «Email yoki parol xato» deyiladi, «bunday email yo'q» emas. Bu user enumeration dan himoya, va endi u yozib qo'yilgan.

Chiqish

$this->actingAs($user)->post('/chiqish')->assertRedirect('/vakansiyalar'); $this->assertGuest();

actingAs() bilan kirdik, so'rov yubordik, keyin mehmon bo'lganini tasdiqladik — uch qator.

So'rov cheklovini test qilish

31-darsda RateLimiter qo'shgan edik: beshta xato urinishdan keyin kirish vaqtincha to'xtatiladi. Uni ham yozib qo'yamiz.

tests/Feature/AuthTest.php test('besh urinishdan keyin so\'rov cheklanadi', function () { User::factory()->create(['email' => 'ali@example.uz']); foreach (range(1, 5) as $urinish) { $this->from('/kirish')->post('/kirish', [ 'email' => 'ali@example.uz', 'password' => 'xato-parol', ]); } // oltinchi urinish — endi PAROL TO'G'RI $javob = $this->from('/kirish')->post('/kirish', [ 'email' => 'ali@example.uz', 'password' => 'password', ]); $javob->assertSessionHasErrors(['email']); expect(session('errors')->get('email')[0])->toContain("Juda ko'p urinish"); $this->assertGuest(); });

🔑 Oltinchi urinishda parol to'g'ri — va baribir kiritilmadi. Aynan shu narsa cheklov ishlayotganini isbotlaydi. Agar parolni xato qoldirsak, test cheklovni emas, oddiy xatoni tekshirgan bo'lardi.

O'lchangan xabar:

Juda ko'p urinish. 59 soniyadan keyin qayta urining.

Shuning uchun toContain ishlatildi, toBe emas: soniyalar soni har safar boshqacha bo'ladi.

🔍 Cheklov keyingi testga o'tmaydi

Tabiiy savol: birinchi test besh urinish sarfladi — ikkinchi test allaqachon cheklangan holatda boshlanmaydimi?

Yo'q. 37-darsdagi phpunit.xml ga qayting:

<env name="CACHE_STORE" value="array"/>

RateLimiter hisoblagichni keshda saqlaydi, kesh esa testda array — ya'ni oddiy PHP massivi, har test uchun yangi.

Buni sinab ko'rdik: cheklov testidan keyin turgan test odatdagi Email yoki parol xato. xabarini oldi — cheklov xabarini emas.

⚠️ session('errors') — 38-darsdagi sirning yechimi

Yuqoridagi testda session('errors')->get('email') yozdik va u ishladi. Lekin bitta qatorni olib tashlasangiz — buziladi:

// assertSessionHasErrors CHAQIRILMASDAN: session('errors') → turi: array // assertSessionHasErrors dan KEYIN: session('errors') → ViewErrorBag (->get() ishlaydi)

Ya'ni session('errors') boshida oddiy massiv bo'lib turadi va faqat tekshiruvdan keyin obyektga aylanadi.

🔑 Va mana 38-darsdagi sirning javobi. U yerda redirect tekshiruvi yiqilganda tushunarsiz xato chiqqan edi:

Call to a member function all() on array

Endi sabab aniq: xato xabarini yasashda Laravel session('errors')->all() ni chaqiradi, u esa o'sha paytda hali massiv. Xato sizning kodingizda emas edi.

✅ Amaliy qoida: sessiyaga qo'lda tegmang. Iloji boricha assertSessionHasErrors(['email' => 'matn']) ishlating — u ham qisqaroq, ham bu tuzoqqa tushmaydi. Faqat matnning bir qismini tekshirish kerak bo'lgandagina sessiyani o'qing, va o'shanda ham assertSessionHasErrors dan keyin.

Policy'ni HTTP'siz sinash

38-darsda policy'ni so'rov orqali tekshirdik: begona odam tahrirlash sahifasini ochib 403 oldi. Bu to'g'ri va kerakli test.

Lekin policy'ning o'zi — oddiy PHP klassi. Uni to'g'ridan-to'g'ri sinash mumkin, va bu ancha tez hamda aniqroq:

tests/Feature/VakansiyaPolicyTest.php test('vakansiyani faqat egasi tahrirlay oladi', function () { $egasi = User::factory()->create(['rol' => Rol::IshBeruvchi]); $begona = User::factory()->create(['rol' => Rol::IshBeruvchi]); $nomzod = User::factory()->create(['rol' => Rol::Nomzod]); $vakansiya = Vakansiya::factory()->for($egasi, 'egasi')->create(); expect($egasi->can('update', $vakansiya))->toBeTrue(); expect($begona->can('update', $vakansiya))->toBeFalse(); expect($nomzod->can('update', $vakansiya))->toBeFalse(); });

Route yo'q, controller yo'q, forma yo'q, HTML yo'q. Faqat qoida.

HTTP orqali: «begona odam tahrirlash sahifasini ocholmaydi» To'g'ridan: «begona odam update qila olmaydi»

🔑 Ikkalasi ham kerak, chunki ikki xil narsani himoya qiladi. Policy testi qoidani qulflaydi; HTTP testi esa o'sha qoida controllerga ulanganini qulflaydi. Policy to'g'ri bo'lib, authorize() chaqirilmasa — faqat ikkinchisi tutadi.

Gate::forUser()

expect(Gate::forUser($egasi)->allows('delete', $vakansiya))->toBeTrue(); expect(Gate::forUser($begona)->denies('delete', $vakansiya))->toBeTrue();

33-darsdagi Gate::forUser() testda ayni muddao: kimning nomidan tekshirayotganingizni aniq yozasiz. $user->can(...) bilan farqi yo'q — qaysi biri o'qilishi qulay bo'lsa, o'shani tanlang.

Policy testi qayerda yashaydi

«Bu Unit test-ku?» degan savol tug'iladi. Mantiqan — ha, u bitta klassni tekshiryapti. Lekin unga baza kerak: User::factory() va Vakansiya::factory() yozuv yaratadi.

37-darsdagi tests/Pest.php ni eslang:

pest()->extend(TestCase::class) ->use(RefreshDatabase::class) ->in('Feature'); ← faqat Feature papkasiga

Shuning uchun policy testini tests/Feature/ ga qo'yamiz. 🔑 Xulosa: «Feature» papkasi albatta HTTP degani emas — u baza kerak degani.

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

session('errors') ga erta murojaat

$this->post('/kirish', [...]); session('errors')->get('email') → Error: Call to a member function get() on array

Sessiyadagi xatolar assertSessionHasErrors chaqirilmaguncha oddiy massiv bo'lib turadi.

✅ Ikki yechim: matnni to'g'ridan-to'g'ri tekshiring (assertSessionHasErrors(['email' => 'matn'])) yoki sessiyani assertion'dan keyin o'qing.

🔍 38-darsdagi Call to a member function all() on array ham aynan shu sabab edi — faqat u yerda ->all() ni Laravel'ning o'zi chaqirgan.

HOLAT 2

assertAuthenticated() yetarli deb o'ylash

$this->post('/kirish', ['email' => 'ali@example.uz', 'password' => 'password']); $this->assertAuthenticated(); // ⚠️ «kimdir kirdi»

Bu test har doim birinchi foydalanuvchini kiritadigan buzuq kodda ham o'tadi. «Kimdir kirdi» — kirish tizimi uchun juda past talab.

✅ Kirish testida assertAuthenticatedAs($user) ishlating. assertAuthenticated() ni esa ro'yxatdan o'tish kabi «foydalanuvchi hozirgina yaratilgan» holatlarda qoldiring.

HOLAT 3

Auth testlari sekinroq

✓ to'g'ri parol bilan kiriladi 0.01s ✓ xato parol bilan kirib bo'lmaydi 0.21s ← xeshlash ✓ besh urinishdan keyin cheklanadi 1.04s ← olti marta xeshlash

Sabab — parol xeshlash ataylab sekin (30-dars). Har xato urinish to'liq xeshlashni talab qiladi.

✅ 37-darsdagi phpunit.xml buni allaqachon yumshatgan: BCRYPT_ROUNDS=4 (odatda 12). Shusiz cheklov testi bir necha soniya ketardi.

🔍 Cheklov testini bittadan ortiq yozmang — u eng qimmat test turi. Bitta yaxshi yozilgani yetadi.

HOLAT 4

Cheklov qoldig'i — bu yerda muammo yo'q

<env name="CACHE_STORE" value="array"/> ← phpunit.xml

Haqiqiy saytda RateLimiter hisoblagichi keshda qoladi va 31-darsda men sinov paytida o'zimni qamab qo'yganman (php artisan cache:clear kerak bo'lgan).

Testda esa kesh array — har test uchun yangi massiv. O'lchandi: cheklov testidan keyingi test odatdagi Email yoki parol xato. xabarini oldi.

🔑 Umumiy naqsh: testdagi tashqi holat (kesh, sessiya, fayl, pochta) — phpunit.xml da soxta variantga almashtiriladi.

HOLAT 5

Policy testi Unit'da ishlamaydi

tests/Unit/VakansiyaPolicyTest.php RuntimeException: A facade root has not been set. at vendor/laravel/framework/.../Support/Facades/Facade.php:361

Xato kutilganidan ham chuqurroq: gap bazada emas — Unit papkasida Laravel umuman ko'tarilmagan.

tests/Pest.php ga qayting:

pest()->extend(TestCase::class) ← Laravel'ni ishga tushiradi ->use(RefreshDatabase::class) ← bazani tayyorlaydi ->in('Feature'); ← FAQAT shu papkaga

Ikkala qator ham Feature ga bog'langan. Unit testlar esa oddiy PHP muhitida ishlaydi — User::factory() ichida ishlatilgan facade'lar u yerda mavjud emas.

✅ Policy testini tests/Feature/ ga qo'ying. Unit — Laravel'siz ishlay oladigan mantiq uchun: enum, hisob-kitob, formatlash (37-darsdagi RolTest shunday).

🔍 Yoki ->in('Feature', 'Unit') deb yozib bo'lardi — lekin unda barcha Unit testlar sekinlashadi. Papkaning ma'nosi shunda: tez va sekin testlarni ajratish.

HOLAT 6

actingAs() nimani tekshirmaydi

$this->actingAs($user)->get('/vakansiyalar'); // ✅ qulay // LEKIN bu test kirish FORMASI ishlashini tekshirmaydi: // parol xeshi to'g'ri solishtiriladimi? // sessiya yoziladimi? // redirect qayerga?

actingAs() butun kirish jarayonini chetlab o'tadi — aynan shuning uchun qulay. Ammo shu sababdan u kirish tizimini sinamaydi.

✅ Naqsh oddiy: kirish oqimini bir marta haqiqiy post('/kirish') bilan tekshiring; qolgan barcha testlarda actingAs() ishlating.

HOLAT 7

Faqat taqiqni tekshirish

expect($begona->can('update', $vakansiya))->toBeFalse(); // ⚠️ yolg'iz

Bu test update() metodi doim false qaytaradigan buzuq policy'da ham o'tadi — va o'shanda egasi ham o'z e'lonini tahrirlay olmaydi.

✅ Har doim ikkala tomonni yozing:

expect($egasi->can('update', $vakansiya))->toBeTrue(); // ruxsat expect($begona->can('update', $vakansiya))->toBeFalse(); // taqiq

🔑 Bu 38-darsdagi assertDontSee qoidasining aynan o'zi: «yo'q»ni tekshirish yolg'iz o'zi kam narsa isbotlaydi.

💻 Amaliy qism kompyuterda

Amaliyotda auth oqimini to'liq qoplaysiz va policy'ni HTTP'siz sinaysiz. Yo'lda session('errors') tuzog'ini ataylab ko'rasiz — o'sha 38-darsda javobsiz qolgan xatoning ildizini.

Sinab ko'ramiz

Natijani taxmin qiling

Dasturchi kirish testini shunday yozdi:

tests/Feature/AuthTest.php
test('kirish ishlaydi', function () { User::factory()->create(['email' => 'ali@example.uz']); User::factory()->create(['email' => 'vali@example.uz']); $this->post('/kirish', [ 'email' => 'vali@example.uz', 'password' => 'password', ])->assertRedirect('/vakansiyalar'); $this->assertAuthenticated(); });

Test yashil. Endi tasavvur qiling: kimdir kirish() metodini buzdi va u emaildan qat'i nazar birinchi foydalanuvchini kiritadigan bo'lib qoldi. Test buni tutadimi?

Javobni ko'rish
✓ kirish ishlaydi Yashil. Holbuki Vali o'rniga ALI kirgan.

assertAuthenticated() faqat «kimdir kirgan» deydi. Ali ham kimdir — demak tekshiruv bajarildi.

⚠️ Bu 38-darsdagi assertDontSee muammosining boshqa ko'rinishi: tekshiruv juda bo'sh, shuning uchun buzuq kod ham undan o'tib ketadi.

To'g'ri variant — kimligini aniq ayting:

$vali = User::factory()->create(['email' => 'vali@example.uz']); ... $this->assertAuthenticatedAs($vali); // ✅ AYNAN Vali

🔑 Qoida: assertAuthenticated() ni faqat foydalanuvchi hozirgina yaratilgan joyda ishlating (ro'yxatdan o'tish). Kirish testida har doim assertAuthenticatedAs($user).

🔍 Va yana bir daraja chuqurroq: yuqoridagi testda ikkita foydalanuvchi ataylab yaratilgan. Agar bitta bo'lsa, «birinchi foydalanuvchini kiritadigan» xato umuman ko'rinmaydi — chunki birinchi va kerakli odam bitta.

Umumiy saboq: test ma'lumoti xatoni ko'rsata oladigan bo'lishi kerak. Bitta yozuv bilan tartib, tanlov va filtr xatolarini tutib bo'lmaydi.

SAVOL 1 Kirish testida qaysi tekshiruv to'g'ri?

assertAuthenticated() «kimdir kirgan» deydi — «har doim birinchi foydalanuvchini kiritadigan» buzuq kod ham undan o'tadi. Kirish testida assertAuthenticatedAs($user) ishlating. assertAuthenticated() esa ro'yxatdan o'tish kabi «foydalanuvchi hozirgina yaratilgan» holatlarga qoladi.

SAVOL 2 Nega cheklov testi keyingi testga ta'sir qilmaydi?

phpunit.xml da CACHE_STORE=array — hisoblagich oddiy PHP massivida yashaydi va har test uchun yangi. Haqiqiy saytda esa u keshda qoladi; 31-darsda php artisan cache:clear aynan shuning uchun kerak bo'lgan.

SAVOL 3 Policy testi nega Feature papkasida turadi?

tests/Pest.php da ->extend(TestCase::class) ham, ->use(RefreshDatabase::class) ham ->in('Feature') ga bog'langan. Unit'da esa A facade root has not been set. chiqadi. 🔑 «Feature» papkasi albatta HTTP degani emas — Laravel kerak degani.

Eslab ayting

Avval o'zingiz javob bering, keyin ochib tekshiring. Oxirgi ikkitasi — 39-darsni takrorlash.

Uchta auth tekshiruvi qanday farq qiladi?

assertGuest() — hech kim kirmagan. assertAuthenticated() — kimdir kirgan. assertAuthenticatedAs($user) — aynan shu odam. Kirish testida uchinchisi.

Nega session('errors') ga tegmaslik kerak?

U assertSessionHasErrors chaqirilmaguncha oddiy massiv bo'lib turadi. 38-darsdagi Call to a member function all() on array xatosining ildizi ham shu. Yaxshisi: assertSessionHasErrors(['email' => 'matn']).

Policy testi va HTTP testi nimasi bilan farq qiladi?

Policy testi qoidani qulflaydi ($user->can(...)), HTTP testi esa o'sha qoida controllerga ulanganini. Policy to'g'ri bo'lib authorize() chaqirilmasa — faqat ikkinchisi tutadi.

↩︎ Takrorlash: nega has() da nom majburiy?

Taxmin avval ko'plik (Konikma → konikmas), keyin birlik (konikma) qidiradi. O'zbekcha konikmalar() ikkalasiga ham mos emas.

↩︎ Takrorlash: factory zanjirini nima to'xtatadi?

->for($model, 'nom') yoki ->recycle($model). Aks holda Vakansiya::factory()->count(3) uchta kompaniya ham yasaydi.

  • Rad etilishi kerak bo'lgan holatlarda uchinchi qatlam majburiy: assertDatabaseMissing(User::class, [...]).
