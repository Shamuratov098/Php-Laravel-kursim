SOLID — qoida emas, og'riqning nomi

SOLID — beshta tamoyilning bosh harflaridan tuzilgan so'z. Ular ko'pincha «qoida» sifatida o'rgatiladi va yodlanadi. Bu — eng foydasiz yo'l.

Aslida har bir tamoyil — oldin ko'p marta uchragan og'riqning nomi:

S → "bu faylni o'zgartirsam, aloqasiz narsa buzilyapti" O → "yangi turini qo'shish uchun eski kodni ochishga to'g'ri kelyapti" L → "interfeys bir xil, lekin xulqi boshqacha chiqdi" I → "bu metod menga kerak emas, lekin yozishga majburman" D → "test yozolmayapman, chunki ichida aniq sinf qotib qolgan"

🔑 Shuning uchun bugun ta'riflardan emas, kodimizdan boshlaymiz. Har tamoyil uchun: bizda qanday ko'rinadi?

Va oxirida — eng muhim savol: qachon SOLID ga e'tibor bermaslik kerak?

S — Single Responsibility (bitta mas'uliyat)

Ko'p aytiladigan ta'rif: «sinf faqat bitta ish qilsin». Bu noaniq — Vakansiya modeli o'nlab ish qiladi.

Aniqroq ta'rif (Robert Martin'ning o'zi keyinroq shunday aytgan):

Sinfning o'zgarishiga BITTA sabab bo'lsin.

62-darsdagi index() ni eslang. Uni o'zgartirishga to'rtta sabab bor edi:

1) tekshirish qoidasi o'zgardi 2) yangi tartib qo'shildi 3) yangi filtr qo'shildi 4) javob shakli o'zgardi

Ajratgandan keyin har sabab o'z fayliga tegadi:

tekshirish → VakansiyaQidiruvRequest tartib/filtr → VakansiyaQidiruvi javob → VakansiyaResource HTTP → VakansiyaController (6 qator)
🔑 Amaliy sinov

Faylni ochishdan oldin savol bering: «buni kim o'zgartirishni so'raydi?»

tekshirish qoidasi → biznes egasi tartib xaritasi → mahsulot menejeri javob shakli → mobil dasturchi status kodi → backend dasturchi

Bir faylda bir necha odamning talabi yashasa — u fayl bo'linishga tayyor.

O — Open/Closed (kengaytirishga ochiq, o'zgarishga yopiq)

50-darsda XabarYuboruvchi interfeysini yozgandik:

interface XabarYuboruvchi { public function yubor(string $kimga, string $matn): string; }

Keyin LogXabar, EmailXabar va SmsXabar paydo bo'ldi. Savol: ular qo'shilganda interfeys yoki listener o'zgardimi?

interfeys metodlari: yubor LogXabar implements XabarYuboruvchi? HA EmailXabar implements XabarYuboruvchi? HA SmsXabar implements XabarYuboruvchi? HA

Interfeysda hamon bitta metod. XabarYubor listeneri esa uch amalga oshirishning hech birini bilmaydi:

class XabarYubor { public function __construct(private XabarYuboruvchi $xabar) {} public function handle(VakansiyaYaratildi $event): void { $this->xabar->yubor(..., ...); } }

Bu — OCP. Yangi kanal qo'shish uchun yangi fayl yoziladi, eskilari ochilmaydi.

Ikkinchi misol — 62-darsdagi TARTIBLAR:

public const TARTIBLAR = [ 'nom' => ['nom', 'asc'], ... 'yangi' => ['created_at', 'desc'], ];

Yangi tartib qo'shish uchun massivga bitta qator qo'shiladi. soRov() metodi tegilmaydi — va tekshirish qoidasi ham o'zi yangilanadi (Rule::in(array_keys(...))).

⭐ L — Liskov Substitution (o'rnini bosish)

Ta'rif: interfeysni amalga oshirgan har sinf boshqasining o'rnini bosa olishi kerak — chaqiruvchi farqni sezmasin.

Bizda uchta amalga oshirish bor va ular bir xil interfeysni bajaradi. Demak hammasi joyida? Tekshiramiz.

Uchalasiga bir xil matn beramiz:

$y->yubor('a@b.uz', 'SALOM-MATNIM'); LogXabar qaytardi: log ✅ SmsXabar qaytardi: sms ✅ EmailXabar qaytardi: email ✅

Uchalasi ham ishladi. Xato yo'q. Endi natijani tekshiramiz:

yuborilgan xat: 1 ta xat ichida 'SALOM-MATNIM' bormi? YO'Q ⚠️ MATN YO'QOLDI xat ichida vakansiya nomi bormi? HA
⚠️ Sababi kodda
class EmailXabar implements XabarYuboruvchi { public function yubor(string $kimga, string $matn): string { $vakansiya = Vakansiya::latest('id')->first(); // ← qayerdan? Mail::to($kimga)->send(new VakansiyaEloni($vakansiya)); return 'email'; // ← $matn QAYERDA? } }

$matn parametri qabul qilinadi va hech qayerda ishlatilmaydi. Uning o'rniga sinf bazadan oxirgi vakansiyani olib, o'sha haqida xat yuboradi.

Ya'ni: kimdir «Salom, parolingiz tiklandi» deb yuborsa, foydalanuvchi butunlay boshqa xat oladi.

🔑 Va PHP buni tutmaydi: parametr ishlatilmasa ham tip to'g'ri, imzo to'g'ri, interfeys bajarilgan.

Ikkinchi buzilish: kutilmagan xato

Endi bazada vakansiya bo'lmasa nima bo'ladi?

LogXabar (bo'sh jadval) -> 'log' ✅ SmsXabar (bo'sh jadval) -> 'sms' ✅ EmailXabar (bo'sh jadval) -> TypeError ⚠️ TypeError: App\Mail\VakansiyaEloni::__construct(): Argument #1 ($vakansiya) must be of type App\Models\Vakansiya, null given

Bu ikkinchi LSP buzilishi va u birinchisidan ham jiddiyroq: EmailXabar chaqiruvchidan qo'shimcha shart talab qiladi — «bazada kamida bitta vakansiya bo'lsin». Interfeysda bunday shart yozilmagan.

🔑 LSP buzilishining ikki turi
1) SHART QATTIQLASHDI → "menga qo'shimcha narsa kerak" (EmailXabar: bazada vakansiya bo'lsin) 2) VA'DA KUCHSIZLASHDI → "so'raganingizni qilmadim" ($matn ni tashlab yubordi)

Ikkalasi ham tipda ko'rinmaydi. Ularni faqat test tutadi.

✅ Tuzatish

class EmailXabar implements XabarYuboruvchi { public function yubor(string $kimga, string $matn): string { Mail::to($kimga)->send(new XabarMaktubi($matn)); // $matn ISHLATILDI return 'email'; } }

Tuzatgandan keyin qayta o'lchadik:

LogXabar -> log SmsXabar -> sms EmailXabar -> email yuborilgan xat: 1 ta matn saqlandimi? HA ✅ bo'sh jadvalda EmailXabar: email ✅ (xato yo'q)

I — Interface Segregation (interfeysni ajratish)

Ta'rif: hech kim ishlatmaydigan metodni yozishga majbur bo'lmasin.

Bizning interfeysda bitta metod bor. Uni «boyitib» ko'ramiz — jadvalga qo'yish va bekor qilish qo'shamiz:

interface XabarYuboruvchi { public function yubor(string $kimga, string $matn): string; public function jadvalga(string $kimga, string $matn, DateTimeInterface $qachon): string; public function bekorQil(string $id): bool; }

Natija:

PHP Fatal error: Class App\Xizmatlar\LogXabar contains 2 abstract methods and must therefore be declared abstract or implement the remaining methods (App\Xizmatlar\XabarYuboruvchi::jadvalga, App\Xizmatlar\XabarYuboruvchi::bekorQil)
⚠️ Interfeysni kengaytirish — buzuvchi o'zgarish

Bitta faylga ikki qator qo'shdik — uchala sinf ham buzildi. Va ilova umuman ishga tushmaydi.

Endi tanlov: har uchalasiga jadvalga() yozish kerak. Lekin LogXabar logga yozadi — u qanday «jadvalga qo'yadi»? Odatda shunday bo'ladi:

public function jadvalga(...): string { throw new BadMethodCallException('Qo\'llab-quvvatlanmaydi'); ⚠️ LSP BUZILDI }

Ya'ni ISP buzilishi LSP buzilishiga olib keladi — tamoyillar bir-biriga bog'liq.

✅ To'g'ri yechim — ikkinchi interfeys:

interface XabarYuboruvchi { public function yubor(...): string; } interface JadvalliYuboruvchi { public function jadvalga(...): string; } class EmailXabar implements XabarYuboruvchi, JadvalliYuboruvchi { } class LogXabar implements XabarYuboruvchi { } ✅ tegilmadi

🔑 Amaliy qoida: agar amalga oshirishlardan birortasi metodni «qo'llab-quvvatlamaydi» desa — u metod noto'g'ri interfeysda.

D — Dependency Inversion (bog'liqlikni ag'darish)

Ta'rif: yuqori qatlam pastki qatlamga emas, ikkalasi ham abstraksiyaga tayansin.

Bizda: listener EmailXabar ni emas, XabarYuboruvchi ni so'raydi. Qaysi amalga oshirish kelishini provayder hal qiladi (50-dars):

$this->app->singleton( XabarYuboruvchi::class, fn () => match (config('ishtop.xabar_drayveri')) { 'email' => new EmailXabar(), default => new LogXabar(), } );

Sinab ko'rdik — faqat sozlamani o'zgartirib:

config('ishtop.xabar_drayveri') = 'log' app(XabarYuboruvchi::class) = App\Xizmatlar\LogXabar drayver 'email' bo'lgach = App\Xizmatlar\EmailXabar

Listener kodi bir harf ham o'zgarmadi.

🔑 «Ag'darish» nimasi ag'darilgan?
ODATIY (ag'darilmagan): Listener ──tayanadi──> EmailXabar (yuqori qatlam pastkisini BILADI) AG'DARILGAN: Listener ──tayanadi──> XabarYuboruvchi <──bajaradi── EmailXabar (ikkalasi ham O'RTADAGI abstraksiyaga tayanadi)

E'tibor bering: interfeys kimga tegishli? U App\Xizmatlar da — ya'ni ilovaga tegishli, email kutubxonasiga emas. Shuning uchun ham «ag'darilgan».

🔍 Yon topilma: konteyner nimani yasay olmaydi

app(SmsXabar::class) BindingResolutionException: Unresolvable dependency resolving [Parameter #0 [ string $kalit ]] in class App\Xizmatlar\SmsXabar

62-darsdagi qoida shu yerda ko'rindi: konstruktorda oddiy qiymat (matn, son) bo'lsa — konteyner uni o'zi topa olmaydi, provayderda bog'lash kerak.

🔍 Testlash qiyinligi — dizayn signali

Buzilishni tuzatishda birinchi urinishimiz Mail::raw() edi — eng qisqa yo'l:

Mail::raw($matn, fn (Message $xat) => $xat->to($kimga)->subject('IshTop xabari'));

Ishladi. Lekin testni yozmoqchi bo'lganimizda:

Mail::fake(); (new EmailXabar)->yubor('a@b.uz', 'ANIQ-MATN-123'); MailFake ichida: mailables: 0 ta ⚠️ queuedMailables: 0 ta ⚠️

Mail::fake() Mailable obyektlarini yozib oladi. Mail::raw() esa hech qanday Mailable yaratmaydi — demak tekshirib bo'lmaydi.

🔑 Bu — foydali signal

«Testlash qiyin» degani ko'pincha «dizayn noto'g'ri» degani.

Yechim testni majburlash emas edi — to'g'ri obyekt yaratish (XabarMaktubi mailable'i). Va natijada kod ham yaxshilandi: xatning mavzusi va ko'rinishi endi bitta joyda.

✅ Test yozolmayotgan bo'lsangiz, avval kodga qarang, testga emas.

⚠️ Eng muhim bo'lim: qachon e'tibor bermaslik

SOLID o'rganganlar ko'pincha bir xil xatoga tushadi — hamma joyga qo'llash.

❌ interface VakansiyaYaratuvchiInterface { } class VakansiyaYarat implements VakansiyaYaratuvchiInterface { } // bitta amalga oshirish. Hech qachon ikkinchisi bo'lmaydi.

Bu — foyda emas, soliq. Endi har o'zgarishda ikki fayl ochiladi, «bu metod qayerda?» degan savolga javob bir qadam uzoqlashdi.

🔑 Interfeys qachon kerak?
✅ KERAK: 1) HAQIQATAN ikki yoki undan ko'p amalga oshirish bor (XabarYuboruvchi: log, email, sms) 2) testda o'rnini bosuvchi kerak (tashqi API, to'lov tizimi) 3) chegara — boshqa jamoa/paket bilan kelishuv ❌ KERAK EMAS: 1) "kelajakda kerak bo'lar" 2) bitta amalga oshirish bor va bo'ladi 3) "SOLID shunday deydi"

🔍 Bizning ilovamizda bitta interfeys bor — XabarYuboruvchi. Uchta amalga oshirish bilan. Qolgan barcha sinflar interfeyssiz — va bu to'g'ri.

🔑 Eng foydali fikr: SOLID ni oldindan emas, og'riq paydo bo'lganda qo'llang. Og'riq — bu «yana o'sha faylni ochyapman», «testni yozolmayapman», «ikkinchi turini qo'shish uchun uchta joyni o'zgartirdim».

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Merosda LSP buzilishi

class Kvadrat extends Turtburchak { public function enBer(int $en): void { $this->en = $this->boy = $en; } public function boyBer(int $boy): void { $this->en = $this->boy = $boy; } } $t->enBer(5); $t->boyBer(4); echo $t->yuza(); // Turtburchak: 20 Kvadrat: 16 ⚠️

Klassik misol. Matematikada kvadrat — to'rtburchakning turi. Kodda esa emas: u ota-sinfning va'dasini buzadi.

✅ Shuning uchun Laravel'da meros kam ishlatiladi: interfeys va trait afzal.

🔑 Sinov: «ota-sinf o'rniga bolani qo'ysam, hech kim sezmaydimi?»

HOLAT 2

Enum — OCP ning eng oddiy shakli

enum Rol: string { case Admin = 'admin'; case Ishberuvchi = 'ishberuvchi'; public function tahrirlashiMumkinmi(): bool { return match ($this) { self::Admin => true, self::Ishberuvchi => false, }; } }

Yangi rol qo'shsangiz, PHP match da xato beradi — «UnhandledMatchError». Ya'ni til o'zi eslatadi: «bu yerni ham yangila».

✅ Bu if/else zanjiridan yaxshiroq: u indamay false qaytaradi.

🔑 default => yozmaslik — ataylab qilingan tanlov.

HOLAT 3

Shartnomani hujjatlash

interface XabarYuboruvchi { /** * Xabarni yuboradi. * * @param string $kimga Qabul qiluvchi manzili * @param string $matn Yuboriladigan matn — O'ZGARTIRILMASDAN yetkaziladi * @return string Ishlatilgan kanal nomi ('log', 'email', 'sms') * * Bazaga yoki tashqi holatga TAYANMASLIGI kerak. * Yuborilmasa istisno tashlaydi, jimgina qaytmaydi. */ public function yubor(string $kimga, string $matn): string; }

✅ Tipda ko'rinmaydigan va'dalarni yozib qo'ying: nima kafolatlanadi, nimaga tayanilmaydi, xato qanday beriladi.

⚠️ Lekin kommentariya tekshirilmaydi. Shuning uchun eng muhim va'dalar shartnoma testida bo'lsin.

HOLAT 4

final va readonly

final class VakansiyaYarat { } // meros olinmasin final class XabarMaktubi extends Mailable { } readonly class Filtr // yaratilgach o'zgarmasin { public function __construct( public ?string $q, public ?string $shahar, ) {} }

final — «bu sinfdan meros olmang». LSP buzilishining eng ko'p manbasini oldindan yopadi.

readonly — 62-darsdagi holatsizlik qoidasini til darajasida majburlaydi.

🔑 Laravel o'zi final ni kam ishlatadi (kengaytirish qulay bo'lsin deb), lekin sizning ilova kodingizda u foydali.

HOLAT 5

Yashirin bog'liqlik: fasad va new

❌ class HisobXizmati { public function hisobla(): int { $kurs = new ValyutaKursi(); // qotib qolgan return Cache::get('x') * $kurs->ol(); // fasad — yashirin } }

Bu sinfning konstruktori bo'sh — «hech narsaga tayanmaydi» degan taassurot beradi. Aslida esa ikkita bog'liqligi bor, ikkalasi ham ichida yashiringan.

✅ Konstruktorga chiqaring:

public function __construct(private ValyutaKursi $kurs) {}

🔑 51-darsdan eslang: fasadlar testda almashtiriladi (Cache::fake()), shuning uchun ular chidasa bo'ladi. new esa — yo'q.

HOLAT 6

SOLID va Laravel'ning o'zi

Illuminate\Contracts\* → o'nlab interfeys (DIP) Cache::store('redis') → drayverlar bir-birini almashtiradi (LSP) Mailable, Notification → kengaytirasiz, o'zgartirmaysiz (OCP) FormRequest / Resource / Job → har biri bitta sabab (SRP)

🔍 Ya'ni siz SOLID ni o'rganmasdan oldin ham ishlatib kelgansiz — Laravel uni tuzilishga singdirgan.

✅ Shuning uchun «Laravel usuli»da yozish ko'pincha yetarli. Tamoyillar freymvork chegarasidan tashqarida — o'z biznes mantiqingizda kerak bo'ladi.

HOLAT 7

Kod ko'rikda beriladigan savollar

S → "bu faylni o'zgartirishga nechta sabab bor?" O → "yangi turini qo'shsam, nechta faylni ochaman?" L → "bu sinfni birodari bilan almashtirsam, kim sezadi?" I → "bu metod hamma amalga oshirishga kerakmi?" D → "buni testda almashtira olamanmi?"

✅ Beshta savol — beshta tamoyil. Ta'rifni eslash shart emas.

🔑 Va oltinchi savol, eng muhimi: «hozir bu muammo bormi?» Yo'q bo'lsa — tegmang.

Og'riq hali yo'q bo'lganda. ⚠️ Bitta amalga oshirish uchun interfeys — foyda emas, soliq: har o'zgarishda ikki fayl ochiladi. ✅ Interfeys kerak: haqiqatan 2+ amalga oshirish bor · testda o'rnini bosuvchi kerak · boshqa jamoa bilan chegara. ❌ Kerak emas: «kelajakda kerak bo'lar» · «SOLID shunday deydi». 🔍 Bizning ilovamizda bitta interfeys bor — va bu to'g'ri. 🔑 SOLID ni oldindan emas, og'riq paydo bo'lganda qo'llang.
