Service Provider

49-darsda container'da 217 ta bog'lanish turganini ko'rdik. Bugungi savol oddiy: ularni u yerga kim qo'ydi? Javob — service provider'lar. Va yo'lda register() bilan boot() nega ikkiga bo'linganini buzib ko'rsatib tushuntiramiz.

📱 O'qish ≈ 17 daqiqa 💻 Amaliyot ≈ 28 daqiqa Kerak: Dars 49

Bu darsda nimalar bor
  1. bootstrap/providers.php Laravel 11+ dagi ro'yxat. Unda atigi bitta qator bor — qolgan 40+ provider qayerdan keladi?
  2. Provider'lar uch manbadan keladi Yadro · paket avtomatik topilishi (auto-discovery) · sizning ro'yxatingiz. 🔍 O'lchandi: 8 ta paket topilgan.
  3. register() va boot() tartibi 🔍 O'lchandi: hamma register() avval, keyin hamma boot(). Log fayl bilan ko'rsatiladi.
  4. ⚠️ Tartibni buzib ko'ramiz register() ichida boshqa provider xizmatini ishlatsak — 500. Va xato xabari 49-darsdan tanish.
  5. make:provider 🔍 U bootstrap/providers.php ga o'zi qo'shadi — alifbo tartibida.
  6. Kechiktirilgan (deferred) provider DeferrableProvider + provides(). Ishlatilmaguncha yuklanmaydi.
  7. 🔍 Laravelning o'zi shunday ishlaydi Manifestda 18 ta eager, 161 ta kechiktirilgan xizmat. Ya'ni Laravelning ko'p qismi yuklanmaydi.
  8. HTTP va konsol farqi ⚠️ O'lchandi: so'rovda 28 provider, konsolda 45. Bu testda tuzoq yasaydi.
  9. Kechiktirish uyg'onishi 🔍 28 → 29: bitta xizmatni so'rash provider'ni uyg'otadi.
  10. ⚠️ Kechiktirilgan provider'ning boot() i U ham faqat xizmat so'ralganda ishlaydi. Jimgina buziladigan joy — o'lchandi.
  11. Provider testlari provides() ro'yxatidagi har bir nom haqiqatan yasaladimi — buni test tekshiradi.
  12. Har xil holatlar (7 ta) Nima qaysi metodga · konfiguratsiya birlashtirish · booted() · optimize · paketni o'chirish.
217 ta bog'lanish qayerdan keldi?

49-darsda sanadik:

bindings 217 ta instances 159 ta qisqa nomlar: events, log, router, url, path, app, auth ...

Va o'z bog'lanishimizni AppServiceProvider::register() ga yozdik. Ya'ni bitta qatorni biz qo'shdik. Qolgan 216 tasini kim qo'ydi?

Javob: service provider'lar. Har bir Laravel qismi — router, log, baza, kesh, sessiya — o'z provider'iga ega va ishga tushganda o'zini container'ga yozib qo'yadi.

49-darsning HOLAT 5 ida register() bilan boot() farqiga tegib o'tgandik, lekin sababini aytmagandik. Bugun aytamiz — va aytish o'rniga buzib ko'rsatamiz.

Ro'yxat qayerda?

Laravel 11 dan boshlab provider ro'yxati alohida faylda:

bootstrap/providers.php
<?php return [ App\Providers\AppServiceProvider::class, ];

Bitta qator. Lekin ilova ishga tushganda:

count(app()->getLoadedProviders()) → 28 (HTTP so'rovda)

28 ta provider yuklangan, ro'yxatda esa bittasi. Qolganlari uch manbadan keladi:

1) YADRO — Application klassining o'zida qattiq yozilgan (Events, Log, Routing — eng birinchi kerak bo'ladiganlar) 2) PAKETLAR — composer.json dagi "extra.laravel.providers" bootstrap/cache/packages.php ga yig'iladi 3) SIZNIKI — bootstrap/providers.php

Ikkinchisini ko'rish mumkin:

bootstrap/cache/packages.php → 8 ta paket topildi: laravel/pail laravel/pao laravel/sanctum laravel/tinker nesbot/carbon nunomaduro/collision nunomaduro/termwind pestphp/pest-plugin-laravel
🔑 Auto-discovery — «sehr» emas

44-darsda composer require laravel/sanctum dedik va Sanctum o'zi ishlay boshladi. Sababi shu: paketning composer.json ida extra.laravel.providers bo'limi bor, Composer o'rnatgandan keyin Laravel uni bootstrap/cache/packages.php ga yig'ib qo'yadi.

🔍 Bu fayl — kesh. Uni php artisan package:discover qayta yasaydi (composer install uni avtomatik chaqiradi).

Tartib: hamma register, keyin hamma boot

Buni aytish oson, ko'rish esa foydaliroq. Ikkita provider yasaymiz va har bir metodda fayl ga yozamiz:

app/Providers/XabarServiceProvider.php (vaqtinchalik)
public function register(): void { file_put_contents(storage_path('tartib.log'), "XABAR register\n", FILE_APPEND); } public function boot(): void { file_put_contents(storage_path('tartib.log'), "XABAR boot\n", FILE_APPEND); }

Bitta so'rov yuborib, faylni o'qiymiz:

APP register SINOV register XABAR register ← hamma register TUGADI APP boot SINOV boot XABAR boot

Qoida aniq: barcha provider'lar avval register() dan o'tadi, keyin barchasi boot() dan.

Ro'yxat tartibi esa bootstrap/providers.php dagi tartib — va make:provider yangi provider'ni alifbo bo'yicha qo'yadi.

⚠️ Tartibni buzib ko'ramiz

Endi eng muhim qismi. Bog'lanishni XabarServiceProvider::register() ga ko'chiramiz:

// XabarServiceProvider public function register(): void { $this->app->singleton(XabarYuboruvchi::class, LogXabar::class); }

Va SinovServiceProvider::register() ichida uni ishlatib ko'ramiz:

// SinovServiceProvider public function register(): void { $x = $this->app->make(XabarYuboruvchi::class); ❌ }

Natija:

GET /api/v1/vakansiyalar → 500 // logda: "sabab":"Target [App\\Xizmatlar\\XabarYuboruvchi] is not instantiable." // tartib.log da: APP register SINOV register ← shu yerda o'ldi
⚠️ Tanish xato, yangi sabab

Target [...] is not instantiable — 49-darsdan tanish. U yerda sabab bind yozilmagan edi. Bu yerda bind bor, lekin u hali ishlamagan: Sinov alifboda Xabar dan oldin, demak uning register() i ham oldin ishlaydi.

🔑 Ya'ni bir xil xato ikki xil sababdan chiqadi: bind yo'q yoki bind hali ishlamagan. Ikkinchisi yomonroq: u provider tartibiga bog'liq bo'lib qoladi va ertaga yangi provider qo'shsangiz o'zgarishi mumkin.

Yechim — boot() ga ko'chirish:

// SinovServiceProvider public function boot(): void { $x = $this->app->make(XabarYuboruvchi::class); ✅ }
GET /api/v1/vakansiyalar → 200 APP register SINOV register XABAR register APP boot SINOV boot SINOV oldi: App\Xizmatlar\LogXabar ← ishladi XABAR boot

E'tibor bering: SINOV boot hamon XABAR boot dan oldin. Lekin endi ishlaydi — chunki hamma register() tugagan. Aynan shu narsa uchun ikki bosqich bor.

🔑 Qoida bir jumlada
register() → faqat container'ga YOZING. Hech narsani O'QIMANG. boot() → o'qish, ishlatish, sozlash — bu yerda.

«O'qish» deganda make(), fasadlar (Route::, Log::, Config::), event tinglovchilari — hammasi kiradi.

O'z provider'imiz

49-darsda XabarYuboruvchi bog'lanishini AppServiceProvider ga yozgandik. Bu vaqtinchalik yechim edi: AppServiceProvider tez orada «hamma narsa aralashgan» faylga aylanadi.

php artisan make:provider XabarServiceProvider INFO Provider [app/Providers/XabarServiceProvider.php] created successfully.

Va bootstrap/providers.php ni ochib ko'ramiz:

return [ App\Providers\AppServiceProvider::class, App\Providers\XabarServiceProvider::class, ← O'ZI qo'shildi ];

Laravel 11+ da make:provider ro'yxatga o'zi yozadi — qo'lda qo'shish kerak emas.

Kechiktirilgan provider

Bir savol tug'iladi: XabarYuboruvchi faqat vakansiya yaratilganda kerak. Nega u har so'rovda ro'yxatdan o'tsin?

Laravelning javobi — DeferrableProvider:

app/Providers/XabarServiceProvider.php
<?php namespace App\Providers; use App\Xizmatlar\LogXabar; use App\Xizmatlar\XabarYuboruvchi; use Illuminate\Contracts\Support\DeferrableProvider; use Illuminate\Support\ServiceProvider; class XabarServiceProvider extends ServiceProvider implements DeferrableProvider { public function register(): void { $this->app->singleton( XabarYuboruvchi::class, LogXabar::class ); } /** * @return array<int, string> */ public function provides(): array { return [XabarYuboruvchi::class]; } }

Ikki narsa qo'shildi: implements DeferrableProvider va provides() metodi. provides() — «men shu nomlarni bera olaman» degan e'lon.

Endi o'lchaymiz. Xizmatni ishlatmaydigan so'rov:

GET /api/x/deferred { "yuklangan_oldin": 28, "XabarServiceProvider yuklanganmi": false, ← YUKLANMAGAN "kechiktirilganlar_ichida": true ← navbatda turibdi }

Endi xizmatni so'raydigan so'rov:

GET /api/x/deferred-keyin { "oldin": 28, "keyin": 29, ← +1 "endi_yuklanganmi": true }

Mexanizm shunday: Laravel provides() ro'yxatini eslab qoladi va XabarYuboruvchi birinchi marta so'ralganda provider'ni o'sha payt ro'yxatdan o'tkazadi.

⚠️ Kechiktirilgan provider'ning boot() i

Bu jimgina buziladigan joy. Sinab ko'rdik: boot() ga log yozuvi qo'shdik.

xizmat ishlatilmagan so'rov → log BO'SH ⚠️ xizmat ishlatilgan so'rov → "XABAR boot"

Ya'ni boot() ham faqat xizmat so'ralganda ishlaydi.

🔑 Shuning uchun boot() da har doim bajarilishi kerak bo'lgan narsa bo'lsa (marshrutlar, view'lar, event tinglovchilari, validatsiya qoidalari) — provider'ni kechiktirmang. Xato chiqmaydi, narsa shunchaki ishlamay qoladi.

Laravelning o'zi ham shunday qiladi

bootstrap/cache/services.php — provider manifesti. Ichida:

providers: 33 ta eager: 18 ta ← har so'rovda yuklanadi deferred: 161 ta ← so'ralganda yuklanadi deferred namunalari: Illuminate\Bus\Dispatcher -> BusServiceProvider Illuminate\Broadcasting\BroadcastManager -> BroadcastServiceProvider Illuminate\Contracts\Bus\Dispatcher -> BusServiceProvider

Ya'ni Laravelning ko'p qismi odatiy so'rovda yuklanmaydi. Navbatlar, translyatsiya, pochta — hammasi navbatda turadi.

Buni HTTP so'rovda ham ko'rish mumkin:

yuklangan: 28 ta provider kechiktirilgan: 159 ta xizmat navbatda

Bittasini so'rasak — bittasi uyg'onadi:

app(\Illuminate\Bus\Dispatcher::class); yuklangan: 28 → 29 kechiktirilgan: 159 → 158
⚠️ Konsolda boshqacha

O'lchandi:

HTTP so'rovda: yuklangan 28, kechiktirilgan 159 konsolda: yuklangan 45, kechiktirilgan 0 ⚠️

Konsol (va test) hamma narsani yuklaydi — komanda qaysi xizmatni so'rashini oldindan bilib bo'lmaydi.

🔑 Amaliy oqibati: kechiktirishni test bilan tekshirib bo'lmaydi. Testda hamma provider yuklangan bo'ladi va getDeferredServices() bo'sh qaytaradi. Buni brauzer yoki curl bilan tekshiring.

Testlar

Yuqoridagi cheklovni bilgan holda, provider'ni nimasini test qilish mumkin? Uch narsani: bog'lanish ishlashini, ro'yxatda borligini, va provides() rost gapirayotganini.

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Nima qaysi metodga

register() boot() ────────────────────────────── ────────────────────────────── bind, singleton, scoped Route::, View::, Gate:: instance RateLimiter::for() (48-dars) mergeConfigFrom() Model::observe() Blade::directive() loadRoutesFrom(), loadViewsFrom() event tinglovchilari

Oddiy tekshiruv: «bu qator boshqa xizmatga tegadimi?» Tegsa — boot().

🔑 48-darsdagi RateLimiter::for() boot() da edi — endi sababi ma'lum: RateLimiter fasadi container'dan xizmat oladi.

HOLAT 2

Konfiguratsiyani birlashtirish

public function register(): void { $this->mergeConfigFrom(__DIR__.'/../../config/xabar.php', 'xabar'); } // endi: config('xabar.drayver')

mergeConfigFrom — register() da ruxsat etilgan kam sonli «o'qish» amallaridan biri: konfiguratsiya juda erta yuklanadi.

🔑 Foydasi: foydalanuvchi config/xabar.php ni o'zi yozsa, sizning standart qiymatlaringiz bilan birlashadi — u faqat kerakli kalitni yozadi.

HOLAT 3

booting() va booted()

$this->app->booting(fn () => ...); // hamma boot() dan OLDIN $this->app->booted(fn () => ...); // hamma boot() dan KEYIN

booted() kerak bo'ladigan holat: sizga boshqa provider'ning boot() i tugagan bo'lishi kerak.

⚠️ Ilova allaqachon yuklangan bo'lsa (masalan testda), booting() ga bergan callback umuman ishlamaydi — bu payt allaqachon o'tib ketgan.

HOLAT 4

provides() yolg'on gapirsa

public function provides(): array { return [EskiNom::class]; ⚠️ bind YangiNom::class ga o'zgargan }

Xato chiqmaydi. Provider ro'yxatdan o'tmaydi, chunki hech kim EskiNom ni so'ramaydi. Va YangiNom ham topilmaydi — natijada Target [...] is not instantiable.

✅ Yuqoridagi to'rtinchi test aynan shuni tutadi: provides() dagi har bir nomni yasab ko'radi.

🔍 Tashxis: «bind yozganman, lekin topilmayapti» degan holatda birinchi navbatda provides() ga qarang.

HOLAT 5

Kesh va optimize

php artisan optimize → config, routes, events keshlanadi php artisan optimize:clear → hammasini tozalaydi php artisan package:discover → packages.php ni qayta yasaydi

⚠️ bootstrap/cache/services.php — provider manifesti. Yangi provider qo'shsangiz u o'zi yangilanadi, lekin g'alati xatti-harakat ko'rsangiz optimize:clear birinchi urinish bo'lsin.

🔑 Ishlab chiqarishda optimize ishlating — provider ro'yxatini har so'rovda qayta hisoblash kerak emas.

HOLAT 6

Paket provider'ini o'chirish

// composer.json "extra": { "laravel": { "dont-discover": ["laravel/telescope"] } }

Paket avtomatik topilishini o'chirib, provider'ni bootstrap/providers.php ga o'zingiz qo'shasiz — masalan faqat local muhitda.

🔍 Bu kamdan-kam kerak bo'ladi, lekin packages.php nima ekanini bilsangiz, sozlash oson.

HOLAT 7

Provider'da og'ir ish

public function boot(): void { $sozlamalar = Sozlama::all(); ⚠️ HAR so'rovda baza so'rovi }

boot() har so'rovda ishlaydi (kechiktirilmagan bo'lsa). Undagi baza so'rovi yoki HTTP chaqiruvi — butun ilovaning sekinlashuvi.

✅ Yechimlar: provider'ni kechiktirish, singleton ichida yalqov (fn () => ...) yasash, yoki keshlash.

🔑 Qoida: boot() da sozlash qiling, ish qilmang.

💻 Quyida amaliyot bor. Hozir o'qish rejimidasiz — kompyuter yoningizda bo'lganda 💻 Amaliyot rejimiga o'ting va shu bo'limdan davom eting.

Eslab ayting

Javobni ovoz chiqarib ayting, keyin ochib solishtiring.

Provider'lar qaysi uch manbadan keladi?
1) Yadro — Application klassida qattiq yozilgan (Events, Log, Routing). 2) Paketlar — composer.json dagi extra.laravel.providers, bootstrap/cache/packages.php ga yig'iladi (o'lchandi: 8 ta paket). 3) Sizniki — bootstrap/providers.php. 🔍 Natijada HTTP so'rovda 28 provider yuklanadi.
register() ichida boshqa xizmatni ishlatsak nega xato bo'ladi?
Chunki o'sha xizmatning bog'lanishi keyingi provider'da yozilgan bo'lishi mumkin — va u hali ishlamagan. 🔍 O'lchandi: 500, Target [...] is not instantiable. 🔑 Xato xabari 49-darsdagi bilan bir xil, lekin sabab boshqa: u yerda bind yo'q edi, bu yerda bind hali ishlamagan. Qoida: register() da faqat yozing, boot() da ishlating.
Kechiktirilgan provider nima va u nimani talab qiladi?
Ishlatilmaguncha ro'yxatdan o'tmaydigan provider. Ikki narsa kerak: implements DeferrableProvider va provides() metodi — «men shu nomlarni bera olaman» degan ro'yxat. 🔍 O'lchandi: ishlatilmagan so'rovda 28 provider, xizmat so'ralganda 29. Laravelning o'zida 161 ta kechiktirilgan xizmat bor.
Kechiktirishning eng xavfli tomoni nima?
boot() ham faqat xizmat so'ralganda ishlaydi. Agar unda marshrut, view, event tinglovchi yoki Blade direktivasi ro'yxatdan o'tayotgan bo'lsa — ular jimgina yo'qoladi. ⚠️ Va testlar buni tutmaydi: konsolda hamma provider yuklanadi (o'lchandi: HTTP 28, konsol 45, kechiktirilgan 0).
provides() yolg'on gapirsa nima bo'ladi va buni qanday tutasiz?
Provider hech qachon ro'yxatdan o'tmaydi (hech kim eski nomni so'ramaydi), va yangi nom ham topilmaydi → Target [...] is not instantiable. ✅ Test: provides() dagi har bir nomni app($nom) bilan yasab ko'ring — ro'yxat kengaysa test o'zi kengayadi.
