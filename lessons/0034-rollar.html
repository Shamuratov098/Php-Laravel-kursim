DARS 34 · MODUL D — FOYDALANUVCHI VA HUQUQLAR

Rollar: ish beruvchi va nomzod

33-darsda policy yozdik — lekin create(User $user) metodi hech kimga ruxsat bermay false qaytardi. Sababi: «kim vakansiya yarata oladi?» degan savolga javob beradigan ma'lumot yo'q edi. Bugun users jadvaliga rol qo'shamiz. Yo'lda PHP'ning enum turini o'rganamiz — cheklangan qiymatlar to'plamini himoyalashning eng ishonchli usuli.

📱 O'qish ≈ 15 daqiqa 💻 Amaliyot ≈ 24 daqiqa Kerak: Dars 33

Bu darsda nimalar bor
  1. Nega rol kerak 33-darsdan qolgan bo'shliq: create() da yozuv yo'q, demak javob foydalanuvchining o'zida bo'lishi kerak.
  2. Enum — cheklangan to'plam Oddiy matn ustuni 'ish_beruvhi' xatosini ham qabul qiladi. Enum qabul qilmaydi. PHP 8.1 dan.
  3. make:enum Rol --string case nomi va backing value — ikki tomon: ->name kodda, ->value bazada.
  4. from() va tryFrom() Birinchisi noto'g'ri qiymatda otiladi, ikkinchisi null qaytaradi. Qaysi biri qayerda.
  5. ⚠️ Migration'da default() Jadvalda allaqachon qatorlar bor — default yozmasangiz baza aniq xato bilan rad etadi. O'lchandi.
  6. Cast: 'rol' => Rol::class Bazada oddiy matn, PHP'da obyekt. Sehr yo'q — ichida nima bo'layotgani xom SQL bilan ko'rsatiladi.
  7. Enum'ga metod qo'shish nomi() va match. To'liq bo'lmagan match — foyda, zarar emas.
  8. Policy'da roldan foydalanish create() endi true qaytara oladi. === nega ishlaydi — enum case yagona nusxa.
  9. ⚠️ Rol yetarli emas update/delete da rol va egalik — ikkalasi ham. Faqat rolni tekshirsangiz ochiq zaiflik.
  10. Ro'yxatdan o'tishda rol tanlash Rule::enum() bilan tekshirish, Rol::cases() bilan formani enum'ning o'zidan yasash.
  11. Blade: @can klass bilan Obyekt yo'q — Vakansiya::class beriladi. Nomzod formani ko'rmaydi, POST qilsa 403.
  12. Har xil holatlar (7 ta) Begona qiymat → ValueError · defaultsiz migration · Rule::enum vs in: · klass vs obyekt · faqat rol tekshirish · cases() · where() va JSON.
33-darsdan qolgan bo'shliq

Policy'dagi beshta metodni eslang. To'rttasida yozuv bor, bittasida yo'q:

public function view(User $user, Vakansiya $vakansiya) ← yozuv bor public function update(User $user, Vakansiya $vakansiya) ← yozuv bor public function delete(User $user, Vakansiya $vakansiya) ← yozuv bor public function create(User $user) ← yozuv YO'Q

Sababi oddiy: create chaqirilganda vakansiya hali yaratilmagan. Tekshirishga yozuv yo'q. Demak javob faqat bitta joydan kelishi mumkin — foydalanuvchining o'zidan.

IshTop'da ikki xil odam bor:

ish beruvchi → vakansiya joylaydi nomzod → vakansiyalarni ko'radi, ariza beradi

Hozir esa hamma bir xil. users jadvalida bu farqni saqlaydigan hech nima yo'q — shuning uchun create() false dan boshqa hech nima qaytara olmasdi.

Nega oddiy matn ustuni yetmaydi

Eng sodda yechim — rol nomli matn ustuni. Ishlaydi... to birinchi xatogacha:

oddiy matn ustuni bo'lganda $user->rol = 'ish_beruvhi'; // ← harf tushib qolgan, baza QABUL QILADI $user->rol = 'employer'; // ← boshqa til, baza QABUL QILADI $user->rol = 'Nomzod'; // ← katta harf, baza QABUL QILADI $user->rol = 'nomzod '; // ← oxirida probel, baza QABUL QILADI

To'rttasi ham bazaga tushadi va hech qanday xato bermaydi. Xato keyin, boshqa joyda chiqadi: $user->rol === 'ish_beruvchi' tekshiruvi jimgina false qaytaradi va odam o'z e'lonini qo'sha olmay qoladi. Bunday xatoni topish qiyin — chunki u xato bo'lib ko'rinmaydi.

PHP 8.1 dan boshlab bunga tayyor tur bor: enum. Enum — «faqat shu qiymatlar bo'lishi mumkin» degan ro'yxat.1

app/Enums/Rol.php <?php namespace App\Enums; enum Rol: string // ← «: string» — backing (tayanch) turi { case Nomzod = 'nomzod'; case IshBeruvchi = 'ish_beruvchi'; }

Bu yerda ikki tomon bor va ularni chalkashtirmaslik muhim:

Rol::IshBeruvchi ← case NOMI — kodda shu ishlatiladi 'ish_beruvchi' ← backing VALUE — bazada shu yotadi $rol->name → 'IshBeruvchi' (matn, kamdan-kam kerak) $rol->value → 'ish_beruvchi' (matn, bazaga shu boradi)

Endi yuqoridagi to'rtta xatoning hech biri yozilmaydi — chunki Rol::IshBeruvhi deb yozsangiz PHP darhol to'xtaydi: bunday case yo'q.

Matndan enum'ga: from va tryFrom

Bazadan yoki formadan kelgan narsa — matn. Uni enum'ga aylantirish kerak. Ikkita usul bor va farqi jiddiy:

Rol::from('nomzod') → Rol::Nomzod ✅ Rol::from('boshqa') → ValueError OTILADI 💥 Rol::tryFrom('nomzod') → Rol::Nomzod ✅ Rol::tryFrom('boshqa') → null ⚠️ jimgina

O'lchangan: Rol::tryFrom('boshqa') → NULL, Rol::tryFrom('nomzod')->name → Nomzod.4

Qaysi birini qachon

from() — o'zingiz ishonadigan manbada (baza). Xato bo'lsa darhol bilish yaxshi.

tryFrom() — tashqaridan kelgan ma'lumotda (forma, API). U yerda noto'g'ri qiymat kutilgan narsa, dastur qulamasligi kerak.

Bazaga rol ustuni

Enum — PHP tomonidagi tur. Bazada esa oddiy ustun kerak. 23-darsdagi migration mexanizmi bilan qo'shamiz:

database/migrations/..._add_rol_to_users_table.php public function up(): void { Schema::table('users', function (Blueprint $table) { $table->string('rol')->default('nomzod'); }); } public function down(): void { Schema::table('users', function (Blueprint $table) { $table->dropColumn('rol'); }); }
⚠️ default('nomzod') — bezak emas, majburiy

Jadvalda allaqachon foydalanuvchilar bor (30-darsda ro'yxatdan o'tgan). Yangi ustun ularda qanday qiymat oladi? Javob yo'q — shuning uchun baza rad etadi:

SQLSTATE[HY000]: General error: 1 Cannot add a NOT NULL column with default value NULL

Ikki yechim bor: ->default('nomzod') (mavjud odamlarning hammasi nomzod bo'ladi) yoki ->nullable() (bo'sh qoladi, keyin to'ldirasiz). Biz birinchisini tanlaymiz — IshTop'da nomzod mantiqiy boshlang'ich holat.

🔍 Bu qoida faqat SQLite'da emas: MySQL va PostgreSQL ham xuddi shu savolni beradi. Mavjud qatorlarga qiymat kerak.

Cast — bazadagi matnni enum'ga aylantirish

Ustun tayyor, lekin $user->rol hozir oddiy matn qaytaradi. Modelga bitta qator qo'shamiz:

app/Models/User.php use App\Enums\Rol; protected $fillable = ['name', 'email', 'password', 'rol']; // ← 'rol' qo'shildi protected function casts(): array { return [ 'email_verified_at' => 'datetime', 'password' => 'hashed', 'rol' => Rol::class, // ← shu qator ]; }

Endi ikkala tomonga ham qaraymiz — sehr yo'q, faqat aylantirish:

── PHP tomonda: obyekt tipi : App\Enums\Rol value : ish_beruvchi name : IshBeruvchi ── 🔍 Bazada nima yotibdi (xom SQL bilan tekshirildi) Dostonbek 'nomzod' Ali 'ish_beruvchi' Vali 'nomzod'

Bazada — oddiy matn, boshqa hech nima. Cast shunchaki ikki yo'nalishda ishlaydi:

bazadan o'qiyotganda: 'ish_beruvchi' → Rol::from('ish_beruvchi') bazaga yozayotganda: Rol::IshBeruvchi → ->value → 'ish_beruvchi'

Shuning uchun boshqa dasturlar (masalan hisobot yozadigan skript) bu ustunni bemalol o'qiy oladi — u yerda hech qanday maxsus format yo'q.

Enum'ga metod qo'shish

Enum — klassga o'xshaydi: unga metod yozish mumkin. Ekranda ish_beruvchi emas, «Ish beruvchi» ko'rinishi kerak:

app/Enums/Rol.php — to'ldirilgan enum Rol: string { case Nomzod = 'nomzod'; case IshBeruvchi = 'ish_beruvchi'; public function nomi(): string { return match ($this) { self::Nomzod => 'Nomzod', self::IshBeruvchi => 'Ish beruvchi', }; } }

Bu yerda match ishlatilgan — switchning qat'iy ukasi. Va uning bir xususiyati bor, u dastlab kamchilikka o'xshaydi:

// match'da IshBeruvchi unutilsa: $f(Rol::Nomzod) → 'Nomzod' ✅ $f(Rol::IshBeruvchi) → UnhandledMatchError 💥 "Unhandled match case of type App\Enums\Rol"
Bu xato — foyda

Ertaga uchinchi rol qo'shsangiz (masalan Admin), match darhol xato beradi va sizni o'sha joyga olib boradi. Agar match jim turganda edi, saytda bo'sh nom chiqib qolardi va siz buni bilmasdingiz.

Bu «zanjir uzilmaydi» qoidasining kod ichidagi ko'rinishi: yangi holat qo'shilsa, unga bog'liq hamma joy eslatib turadi.

Policy'ga rol kiradi

Endi create() nihoyat mazmunli javob bera oladi:

app/Policies/VakansiyaPolicy.php use App\Enums\Rol; public function create(User $user): bool { return $user->rol === Rol::IshBeruvchi; }

Diqqat: === ishlatilgan — == emas, matn solishtiruvi emas. Bu ishlaydi, chunki enum case yagona nusxada mavjud: butun dastur davomida Rol::IshBeruvchi — bitta va o'sha obyekt. Shu sababli === (aynan bir xil obyektmi?) to'g'ri javob beradi.1

$u->rol === Rol::IshBeruvchi : true

⚠️ Rol yetarli emas — egalik ham kerak

Endi eng muhim joy. update va delete uchun faqat rolni tekshirsangiz, mana bu bo'ladi: har qanday ish beruvchi boshqa ish beruvchining e'lonini o'chira oladi. Bu 33-darsda yopgan teshikni qayta ochish bilan barobar.

To'g'ri variant — ikkalasi ham:

app/Policies/VakansiyaPolicy.php public function update(User $user, Vakansiya $vakansiya): bool { return $user->rol === Rol::IshBeruvchi // ← kim && $vakansiya->user_id === $user->id; // ← kimniki } public function delete(User $user, Vakansiya $vakansiya): bool { return $this->update($user, $vakansiya); // ← qoida bir xil }

Ikki savol, ikki shart:

rol → «sen umuman shunday ish qila olasanmi?» egalik → «bu aynan sening yozuvingmi?»

O'lchangan natija:

create: Ali (ish beruvchi) true Vali (nomzod) false delete: Ali (egasi + ish beruvchi) true Vali (nomzod) false Vali ish beruvchi, lekin EGASI EMAS: create → true (yarata oladi) delete → false (begonasini yo'q)

Oxirgi qatorga qarang: bitta odam bir vaqtning o'zida yarata oladi, lekin begonasini o'chira olmaydi. Ikki shart mustaqil ishlayapti.

Controllerda: yaratishni himoyalash

33-darsdagi naqsh o'zgarmaydi — faqat endi create uchun ham qo'yamiz. Yozuv yo'q, shuning uchun ikkinchi argument klass nomi:

app/Http/Controllers/VakansiyaController.php public function store(Request $request) { $this->authorize('create', Vakansiya::class); // ← obyekt emas, KLASS $tekshirilgan = $request->validate([ /* ... */ ]); Vakansiya::create($tekshirilgan + ['user_id' => $request->user()->id]); return redirect()->route('vakansiyalar.index') ->with('xabar', 'Qo\'shildi: ' . $tekshirilgan['nom']); }

Nega klass? Chunki Laravel policy'ni topishi kerak, lekin uzatishga yozuv yo'q. Klass nomi — «shu model uchun policy'ni top, keyin create($user) ni chaqir» degani.

O'lchangan: nomzod POST yuborsa — 403. Ish beruvchi yuborsa — 302 va «Qo'shildi: Rolli vakansiya».4

Blade'da: formani kimga ko'rsatamiz

@can ham xuddi shunday — klass nomi bilan:

resources/views/vakansiyalar/index.blade.php @can('create', App\Models\Vakansiya::class) <h2>Yangi vakansiya</h2> <form method="POST" action="{{ route('vakansiyalar.store') }}"> @csrf {{-- ... maydonlar ... --}} </form> @else <p>Vakansiya joylash uchun <b>ish beruvchi</b> sifatida kirishingiz kerak.</p> @endcan

@else — bu yerda muhim. Formani shunchaki yashirsangiz, nomzod nima uchun ko'rmayotganini bilmaydi va sayt buzuq deb o'ylaydi. Sabab ko'rsatish — interfeys sifati.

O'lchangan:

Ali (ish beruvchi): forma bor 1 Vali (nomzod) : forma yo'q 0 Vali ko'radi: «... ish beruvchi sifatida kirishingiz kerak.»
🔒 Yashirish — himoya emas (to'rtinchi marta)

@can formani yashirdi. Lekin nomzod POST so'rovini qo'lda yuborishi mumkin — 33-darsda buni sinab ko'rgan edik.

Shuning uchun store() ichidagi $this->authorize('create', ...) ham turibdi. Biz uni sinadik: nomzodning qo'lda yuborgan so'rovi 403 oldi.

@can → ko'rinish uchun (nima ko'rsatamiz) authorize() → himoya uchun (nimaga ruxsat beramiz)

Ro'yxatdan o'tishda rol tanlash

Yangi odam kelganda unga rol berish kerak. 30-darsdagi royxat() metodiga qo'shamiz:

app/Http/Controllers/AuthController.php use App\Enums\Rol; use Illuminate\Validation\Rule; $tekshirilgan = $request->validate([ 'name' => ['required', 'string', 'max:255'], 'email' => ['required', 'email', 'unique:users,email'], 'password' => ['required', 'confirmed', 'min:8'], 'rol' => ['required', Rule::enum(Rol::class)], // ← shu qator ], [ 'rol.required' => 'Rolni tanlang.', ]); $user = User::create([ 'name' => $tekshirilgan['name'], 'email' => $tekshirilgan['email'], 'password' => $tekshirilgan['password'], 'rol' => $tekshirilgan['rol'], // ← cast o'zi enum'ga aylantiradi ]);

Rule::enum(Rol::class) — «bu qiymat shu enum'ning case'laridan biri bo'lsin».2 Qo'lda 'in:nomzod,ish_beruvchi' deb yozish ham mumkin edi, lekin unda ro'yxat ikki joyda yotadi va bir kun kelib ajralib ketadi.

Formani enum'ning o'zidan yasash

resources/views/auth/royxat.blade.php <p> Kim sifatida: @foreach (\App\Enums\Rol::cases() as $rol) <label> <input type="radio" name="rol" value="{{ $rol->value }}" @checked(old('rol') === $rol->value)> {{ $rol->nomi() }} </label> @endforeach </p>

Rol::cases() — barcha case'lar ro'yxati. Formani qo'lda yozmaganimiz uchun, ertaga Admin qo'shsangiz forma o'zi yangilanadi.

@checked(...) — 30-darsdagi old() naqshining radio uchun ko'rinishi: validatsiya xatosidan keyin tanlov saqlanib qoladi.

O'lchangan:

rolsiz yuborilsa → <li>Rolni tanlang.</li> rol=ish_beruvchi bilan → 302 → /vakansiyalar forma darhol ko'rinadi (1) bazadagi rol: ish_beruvchi (Ish beruvchi) rol=nomzod bilan → forma ko'rinmaydi (0) «... ish beruvchi sifatida kirishingiz kerak.»

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Bazaga begona qiymat tushib qolsa

Enum PHP tomonini himoyalaydi, lekin bazani emas. Kimdir xom SQL bilan (yoki eski migration bilan) noto'g'ri qiymat yozsa, o'qishda portlaydi:

UPDATE users SET rol = 'boshqa' WHERE id = 1; $user->rol → ValueError "boshqa" is not a valid backing value for enum App\Enums\Rol

Bu yomon emas, aslida yaxshi: yashirin buzuq ma'lumot jimgina yurgandan ko'ra, darhol ko'rinib qolgani afzal. Lekin bilib turish kerak — xato User modelini o'qigan har qanday joyda chiqadi, hatto ro'yxat sahifasida ham.

✅ Oldini olish: bazada ham cheklov qo'ying. MySQL'da enum ustun turi bor; barcha bazalarda check cheklovi ishlaydi.

HOLAT 2

defaultsiz migration

$table->string('rol'); // default yo'q SQLSTATE[HY000]: General error: 1 Cannot add a NOT NULL column with default value NULL

Jadval bo'sh bo'lsa bu xato chiqmaydi — shuning uchun ba'zan kompyuteringizda ishlaydi, serverda esa ishlamaydi. Farq: sizda baza yangi, serverda ming dona foydalanuvchi bor.

✅ Qoida: mavjud jadvalga ustun qo'shayotganda har doim default() yoki nullable() bering. Bu 23-darsdagi «migration oldinga ham, orqaga ham ishlashi kerak» qoidasining davomi.

HOLAT 3

Rule::enum() vs qo'lda in:

'rol' => ['required', 'in:nomzod,ish_beruvchi'] // ishlaydi, lekin... 'rol' => ['required', Rule::enum(Rol::class)] // ✅ afzal

Ikkalasi ham bugun bir xil natija beradi. Farq ertaga ko'rinadi: yangi rol qo'shsangiz birinchi variantda in: ro'yxatini qo'lda yangilash kerak — va uni unutish oson, chunki hech qanday xato chiqmaydi.

Bu bir manba qoidasi: ro'yxat bitta joyda — enum'da — yashasin.

HOLAT 4

Klass nomi bilan yoki obyekt bilan

$this->authorize('create', Vakansiya::class); // yozuv YO'Q → klass $this->authorize('update', $vakansiya); // yozuv BOR → obyekt @can('create', App\Models\Vakansiya::class) // Blade'da ham xuddi shunday @can('update', $vakansiya)

Qoidasi oddiy: policy metodi ikkinchi argument oladimi? create(User $user) olmaydi — klass beriladi. update(User $user, Vakansiya $v) oladi — obyekt beriladi.

⚠️ Blade'da to'liq yo'lni yozish kerak (App\Models\Vakansiya::class) — Blade fayllarida use yo'q.

HOLAT 5

Faqat rolni tekshirish

public function delete(User $user, Vakansiya $vakansiya): bool { return $user->rol === Rol::IshBeruvchi; // ⚠️ egalik unutilgan }

Natija: har qanday ish beruvchi boshqa ish beruvchining e'lonini o'chira oladi. Bu 33-darsda yopilgan teshikning aynan o'zi — faqat endi «kirgan har kim» o'rniga «ish beruvchi bo'lgan har kim».

✅ Yodda tuting: rol — toifa savoli, egalik — yozuv savoli. Yozuv ustidagi amallarda ikkalasi ham kerak.

🔍 Buni sinash oson: ikkinchi ish beruvchi yasang va birinchisining e'lonini o'chirib ko'ring. false chiqishi shart.

HOLAT 6

cases() — ro'yxatni takrorlamaslik

@foreach (\App\Enums\Rol::cases() as $rol) // ✅ enum'dan ... {{ $rol->nomi() }} @endforeach <input type="radio" value="nomzod"> Nomzod // ⚠️ qo'lda <input type="radio" value="ish_beruvchi"> Ish beruvchi

Qo'lda yozilgan variantda uchta joy bir-biriga qarab turadi: enum, validatsiya ro'yxati va forma. Ulardan bittasi o'zgarsa, qolgani jimgina eskirib qoladi.

cases() + Rule::enum() bilan enum yagona manba bo'ladi — o'zgartirish bir joyda.

HOLAT 7

Enum qidiruvda va JSON'da

User::where('rol', Rol::IshBeruvchi)->count() → 2 User::where('rol', Rol::Nomzod)->count() → 3 $user->only(['name', 'rol']) → {"name":"Ali","rol":"ish_beruvchi"}

Ikkala joyda ham enum o'zi ->value ga aylanadi — qo'lda Rol::IshBeruvchi->value deb yozish shart emas (yozsangiz ham ishlaydi).

JSON'da esa 'ish_beruvchi' chiqadi, 'Ish beruvchi' emas. Ekranga chiqarish uchun nomi() ni aniq chaqirish kerak: {{ $user->rol->nomi() }}.

💻 Amaliy qism kompyuterda

Amaliyotda enum yasaysiz, users ga rol ustuni qo'shasiz va ikkita foydalanuvchi bilan sinaysiz: ish beruvchi formani ko'radi va qo'sha oladi, nomzod formani ko'rmaydi va qo'lda yuborsa 403 oladi.

Amaliyot

  1. Enum yasang

    cd ~/Projects/Learn/ishtop php artisan cache:clear php artisan make:enum Rol --string INFO Enum [app/Enums/Rol.php] created successfully.

    ⚠️ Rol deb yozildi, Enums/Rol emas — generator app/Enums/ papkasini o'zi biladi. Enums/Rol desangiz app/Enums/Enums/Rol.php yasaladi (papka ikki marta!) va keyin «klass topilmadi» xatosi bilan ovora bo'lasiz. Yasalgan faylning yo'liga qarang — chiqishda aniq yozilgan.

    🔍 --string — enum Rol: string yozadi, yani backing value beradi. Bayroqsiz oddiy (tayanchsiz) enum chiqadi va uni bazaga saqlab bo'lmaydi.

    🔍 cache:clear — 31-darsda qo'shilgan so'rov cheklovi (rate limit) sinovlar paytida sizni qamab qo'ymasligi uchun.

  2. Enum'ni to'ldiring

    # app/Enums/Rol.php — to'liq fayl: <?php namespace App\Enums; enum Rol: string { case Nomzod = 'nomzod'; case IshBeruvchi = 'ish_beruvchi'; public function nomi(): string { return match ($this) { self::Nomzod => 'Nomzod', self::IshBeruvchi => 'Ish beruvchi', }; } }
    php -l app/Enums/Rol.php No syntax errors detected in app/Enums/Rol.php

    Kutilgan natija: sintaksis xatosi yo'q. Faylni qo'lda tahrirlagandan keyin php -l — arzon va tez tekshiruv, odat qiling.

  3. rol ustunini qo'shing

    php artisan make:migration add_rol_to_users_table

    Yasalgan faylni to'ldiring:

    public function up(): void { Schema::table('users', function (Blueprint $table) { $table->string('rol')->default('nomzod'); }); } public function down(): void { Schema::table('users', function (Blueprint $table) { $table->dropColumn('rol'); }); }
    php artisan migrate

    Kutilgan natija: migration bajariladi.
    ⚠️ Diqqat: default('nomzod') tufayli mavjud hamma foydalanuvchi — shu jumladan sizning o'z hisobingiz — nomzod bo'ldi. Shuning uchun 9-qadamda yangi hisob yasaysiz. Eski hisobingizni ish beruvchi qilmoqchi bo'lsangiz: php artisan tinker --execute="App\Models\User::first()->update(['rol' => 'ish_beruvchi']);"
    🔍 Sinab ko'ring: default('nomzod') ni o'chirib php artisan migrate:rollback va yana migrate qiling — Cannot add a NOT NULL column xatosini o'z ko'zingiz bilan ko'rasiz. Keyin qaytarib qo'ying.

  4. Modelga cast qo'shing

    # app/Models/User.php da uchta o'zgarish: # 1) yuqoriga: use App\Enums\Rol; # 2) $fillable ga 'rol' qo'shing: protected $fillable = ['name', 'email', 'password', 'rol']; # 3) casts() ichiga: 'rol' => Rol::class,
    php artisan tinker --execute="dump(App\Models\User::first()->rol);" App\Enums\Rol {#6414 +name: "Nomzod" +value: "nomzod" }

    Kutilgan natija: matn emas, obyekt chiqadi — va ichida ikkala tomon ham ko'rinadi: name va value. Agar faqat "nomzod" (oddiy matn) chiqsa — cast qo'shilmagan.
    🔍 {#6414 — obyektning xotiradagi raqami, har safar boshqacha bo'ladi. Unga e'tibor bermang.

  5. Policy'ga rolni kiriting

    # app/Policies/VakansiyaPolicy.php use App\Enums\Rol; public function create(User $user): bool { return $user->rol === Rol::IshBeruvchi; } public function update(User $user, Vakansiya $vakansiya): bool { return $user->rol === Rol::IshBeruvchi && $vakansiya->user_id === $user->id; } public function delete(User $user, Vakansiya $vakansiya): bool { return $this->update($user, $vakansiya); }
    php -l app/Policies/VakansiyaPolicy.php

Sinab ko'ramiz

Natijani taxmin qiling

Vali — ish beruvchi. Uning o'z vakansiyasi bor. Ali ham ish beruvchi, uning ham vakansiyasi bor. Policy shunday:

app/Policies/VakansiyaPolicy.php
public function create(User $user): bool { return $user->rol === Rol::IshBeruvchi; } public function delete(User $user, Vakansiya $vakansiya): bool { return $user->rol === Rol::IshBeruvchi; }

Vali Alining vakansiyasi sahifasini ochdi. «O'chirish» tugmasi ko'rinadimi? Va bossa nima bo'ladi?

Javobni ko'rish
Tugma: KO'RINADI. Bossa: vakansiya O'CHADI. Ali e'lonidan ayrildi. Gate::forUser($vali)->allows('delete', $alining_vakansiyasi) → true

Chunki delete() faqat rolni so'radi: «ish beruvchimisan?» — ha. $vakansiya argumenti qabul qilingan, lekin ishlatilmagan.

⚠️ Bu 33-darsda yopilgan teshikning qaytishi. Faqat endi u kamroq ko'zga tashlanadi: kod «rol tekshirilyapti» deb ishonarli ko'rinadi, hech qanday xato chiqmaydi va sinovda ham o'tib ketishi mumkin — agar sinovda bitta ish beruvchi bo'lsa.

🔑 Tashxis usuli: policy metodini o'qiyotganda argumentlarni sanang. $vakansiya qabul qilingan-u, tanada ishlatilmagan bo'lsa — deyarli har doim xato.

// to'g'risi return $user->rol === Rol::IshBeruvchi && $vakansiya->user_id === $user->id;

Va yana bir nozik joy: create() da $vakansiya yo'q — u yerda faqat rol tekshirilishi to'g'ri. Ikkita metod bir-biriga o'xshaydi, lekin qoidasi boshqa.

SAVOL 1 'rol' => Rol::class cast qo'yilganda bazaga nima yoziladi?

Bazada 'ish_beruvchi' — oddiy matn. Xom SQL bilan tekshirdik. Cast faqat aylantiradi: o'qishda Rol::from(...), yozishda ->value. Shuning uchun ustunni boshqa dasturlar ham o'qiy oladi.

SAVOL 2 Foydalanuvchilari bor jadvalga yangi ustun qo'shayotganda nima kerak?

Mavjud qatorlarda yangi ustun qanday qiymat oladi? Javob bo'lmasa baza rad etadi: Cannot add a NOT NULL column with default value NULL. Yechim — default() yoki nullable(). ⚠️ Bo'sh jadvalda bu xato chiqmaydi — shuning uchun serverdagina ko'rinishi mumkin.

SAVOL 3 delete() policy'sida faqat rol tekshirilsa nima bo'ladi?

Rol — toifa savoli («umuman shunday ish qila olasanmi?»), egalik — yozuv savoli («bu seningmi?»). Yozuv ustidagi amallarda ikkalasi ham kerak: $user->rol === Rol::IshBeruvchi && $vakansiya->user_id === $user->id.

Eslab ayting

Avval o'zingiz javob bering, keyin ochib tekshiring. Oxirgi ikkitasi — 33-darsni takrorlash.

from() va tryFrom() farqi nimada?

from('boshqa') — ValueError otadi. tryFrom('boshqa') — null qaytaradi. Ishonchli manbada (baza) birinchisi, tashqi ma'lumotda (forma, API) ikkinchisi.

Cast ichida qanday sehr bor?

Hech qanday. O'qishda Rol::from($matn), yozishda $rol->value. Bazada oddiy matn yotadi — xom SQL bilan tekshirdik.

create() policy metodida nega yozuv yo'q?

Chunki tekshirish paytida vakansiya hali yaratilmagan. Shuning uchun javob foydalanuvchining o'zidan — rolidan — kelishi kerak. Chaqirishda ham obyekt emas, Vakansiya::class beriladi.

↩︎ Takrorlash: policy qanday topiladi?

Nom bo'yicha: App\Models\X → App\Policies\XPolicy. Ro'yxatdan o'tkazish shart emas. Tekshirish — Gate::getPolicyFor(...).

↩︎ Takrorlash: $this->authorize() ishlashi uchun nima kerak?

Laravel 11+ da bazaviy Controller bo'sh — unga use AuthorizesRequests; qo'shish kerak. Aks holda Call to undefined method ...::authorize().

Cho'ntak xulosasi
  • Enum — cheklangan qiymatlar to'plami (PHP 8.1+). Oddiy matn ustuni 'ish_beruvhi' xatosini jimgina qabul qiladi, enum qabul qilmaydi.
  • php artisan make:enum Rol --string → app/Enums/Rol.php.
  • Ikki tomon: Rol::IshBeruvchi — case nomi (kodda), 'ish_beruvchi' — backing value (bazada). ->name va ->value.
  • from() noto'g'ri qiymatda otadi, tryFrom() null qaytaradi.
  • ⚠️ Mavjud qatorlar bor jadvalga ustun qo'shishda ->default(...) yoki ->nullable() majburiy: Cannot add a NOT NULL column with default value NULL.
  • Cast: 'rol' => Rol::class. Sehr yo'q — bazada matn, PHP'da obyekt, o'rtada from()/->value.
  • Enum'ga metod yozish mumkin: nomi() + match ($this). To'liq bo'lmagan match → UnhandledMatchError — bu foyda, yangi case qo'shganda eslatib turadi.
  • === enum bilan ishlaydi — case yagona nusxada mavjud.
  • ⚠️ Rol va egalik — boshqa-boshqa savol. Yozuv ustidagi amallarda ikkalasi ham: $user->rol === Rol::IshBeruvchi && $vakansiya->user_id === $user->id.
  • Yozuv yo'q bo'lganda klass beriladi: authorize('create', Vakansiya::class), @can('create', App\Models\Vakansiya::class).
  • Rule::enum(Rol::class) — validatsiya. Rol::cases() — formani enum'dan yasash. Ro'yxat bitta joyda yashaydi.
  • 🔒 Yashirish — himoya emas (to'rtinchi marta): forma yashirilgan bo'lsa ham nomzodning qo'lda yuborgan so'rovi 403 oldi.
  • Statuslar aralashmasin: 419 CSRF (so'rov qayerdan kelgani noma'lum) · 403 huquq yo'q · 302→login kirmagan.
  • Enum where() da va JSON'da o'zi ->value ga aylanadi. Ekranga chiroyli nom kerak bo'lsa — {{ $user->rol->nomi() }}.
🌱 Keyingi dars

IshTop'da endi ikki xil odam bor va har biri o'z narsasini ko'radi. Lekin store() metodiga qarang: authorize(), keyin uzun validate() ro'yxati, keyin xato xabarlari, keyin saqlash — hammasi bitta metodda. Va update() da xuddi shu ro'yxat yana bir marta takrorlanadi.
