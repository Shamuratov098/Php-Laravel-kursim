DARS 44 · MODUL F — API QATLAMI

Sanctum: token autentifikatsiyasi

API tartibli, javob shakli boshqariladi — lekin u butunlay ochiq. Istalgan odam POST /api/vakansiyalar yuborib e'lon qo'sha oladi. Web tomonda buni sessiya hal qilgan edi, API'da esa sessiya yo'q. Bugun uning o'rnini token egallaydi.

📱 O'qish ≈ 16 daqiqa 💻 Amaliyot ≈ 26 daqiqa Kerak: Dars 43

Bu darsda nimalar bor
  1. Sessiya yo'q — nima o'rniga Cookie brauzerniki. API mijozi har so'rovda token yuboradi.
  2. ⚠️ HasApiTokens traiti 42-darsdagi install:api shundan ogohlantirgan edi. Usiz: Call to undefined method ...::createToken().
  3. createToken() nima qaytaradi NewAccessToken obyekti va uning plainTextToken maydoni: id|sirli-qism.
  4. 🔍 Bazada token saqlanmaydi Faqat SHA-256 xeshi. 30-darsdagi parol naqshi — o'lchab isbotlandi.
  5. Bearer sarlavhasi Authorization: Bearer 2|zwa1Xr... — har so'rovda.
  6. auth:sanctum middleware Tokensiz so'rov 401 {"message":"Unauthenticated."}.
  7. Token berish endpoint'i Email va parol → token. Xato parolda 422, 30-darsdagi user enumeration qoidasi bilan birga.
  8. abilities — token huquqi Token nima qila olishini chegaralash. Yetmasa 403 Invalid ability provided.
  9. 🔑 Uch qatlam: 401 · 403 · 403 Token yo'q · huquq yetmaydi · policy taqiqlaydi. Uchalasi mustaqil — o'lchandi.
  10. Rolni tokenga bog'lash 34-darsdagi rol tokenning huquqlarini belgilaydi: ish beruvchi yozadi, nomzod faqat o'qiydi.
  11. Tokenni bekor qilish currentAccessToken()->delete() — «chiqish»ning API'dagi ko'rinishi. Va Sanctum::actingAs() testda.
  12. Har xil holatlar (7 ta) Trait · token bir marta ko'rsatiladi · Bearer · alias · * huquqi · 401 va 403 farqi · eski testlar.
Sessiya yo'q — o'rniga nima

30-darsda web tomonda kirish shunday ishlagan edi:

forma → parol tekshirildi → sessiyaga yozildi → cookie brauzerga berildi keyingi so'rovlarda brauzer cookie'ni AVTOMATIK yuboradi

Mobil ilova yoki boshqa server uchun bu ishlamaydi: ularda brauzer ham, cookie mexanizmi ham yo'q. Va 42-darsda ko'rganimizdek, api/* marshrutlari sessiya middleware'iga umuman tushmaydi.

O'rniga token: bir marta olinadi va har so'rovda qo'lda yuboriladi.

web: cookie → brauzer avtomatik yuboradi → sessiya api: token → mijoz QO'LDA yuboradi → sessiya YO'Q

Laravel'da buning uchun Sanctum paketi bor — va u sizda allaqachon o'rnatilgan: 42-darsdagi install:api uni keltirgan edi.1

⚠️ Birinchi qadam: HasApiTokens

install:api oxirida shunday degan edi:

30-darsdagi naqsh qaytdi

Parollar kabi, tokenlar ham xeshlangan holda saqlanadi. Baza o'g'irlansa, undagi qiymatlar bilan hech nima qilib bo'lmaydi — ular tokenning o'zi emas.

Farqi bor: parol uchun bcrypt (ataylab sekin) ishlatiladi, token uchun sha256 (tez). Nega?

parol → odam o'ylab topadi, qisqa, taxmin qilish mumkin → SEKIN xesh kerak token → server yasaydi, 48 belgi tasodifiy → taxmin mumkin emas

🔑 Va shundan muhim oqibat: token bir marta ko'rsatiladi. Yo'qotsangiz — qaytarib bo'lmaydi, chunki serverda ham u yo'q. Yangi token olasiz.

Ro'yxatni o'qish ochiq qoldi — vakansiyalar baribir ommaviy. Yozish esa token talab qiladi.

O'lchangan:

tokensiz POST /api/vakansiyalar → 401 {"message":"Unauthenticated."} Bearer token bilan → 201 {"data":{"id":32,"nom":"Token bilan qoshildi", ...}} noto'g'ri token bilan → 401

401 Unauthorized — «kim ekaningni bilmayman». Buni 33-darsdagi 403 bilan chalkashtirmang: 403 «kimligingni bilaman, huquqing yo'q» degani.

Token berish endpoint'i

app/Http/Controllers/Api/TokenController.php public function yarat(Request $request): JsonResponse { $tekshirilgan = $request->validate([ 'email' => ['required', 'email'], 'password' => ['required'], 'qurilma' => ['required', 'string'], ]); $user = User::where('email', $tekshirilgan['email'])->first(); if (! $user || ! Hash::check($tekshirilgan['password'], $user->password)) { throw ValidationException::withMessages([ 'email' => 'Email yoki parol xato.', ]); } $huquqlar = $user->rol === Rol::IshBeruvchi ? ['vakansiya:oqish', 'vakansiya:yozish'] : ['vakansiya:oqish']; $token = $user->createToken($tekshirilgan['qurilma'], $huquqlar); return response()->json(['token' => $token->plainTextToken], 201); }

Uch narsaga e'tibor bering:

1) 'qurilma' majburiy → «mobil», «planshet» — keyin qaysi birini o'chirishni bilish uchun 2) xabar «Email yoki parol xato» → 30-darsdagi user enumeration qoidasi: qaysi biri xato ekanini AYTMAYMIZ 3) huquqlar rolga qarab → 34-darsdagi rol tokenga ko'chdi

🔍 ValidationException::withMessages() ishlatilgani bejiz emas: u API'da 422 beradi va 42-darsdagi {"message":..., "errors":{...}} shaklini o'zi yasaydi.

abilities — token nima qila oladi

Token kim ekanini aytadi. Lekin bitta odamning bir nechta tokeni bo'lishi mumkin va ularning huquqi har xil bo'lishi kerak:

mobil ilova → o'qish va yozish hisobot skripti → faqat o'qish vidjet → faqat o'qish

Skript o'g'irlansa, u bilan e'lon qo'sha olmaydi — token huquqi yetmaydi.

$user->createToken('mobil', ['vakansiya:oqish', 'vakansiya:yozish']); $user->createToken('hisobot', ['vakansiya:oqish']); $user->createToken('hammasi'); // ← huquq berilmasa: ["*"]

O'lchangan:

token: ['vakansiya:oqish'] can('vakansiya:oqish') → true can('vakansiya:yozish') → false can('*') → false ← ⚠️ yulduzcha «hammasi» EMAS token: huquqsiz yaratilgan (abilities = ["*"]) can('vakansiya:oqish') → true can('vakansiya:yozish') → true

🔑 * — bu maxsus qiymat: «cheklov yo'q». Uni can('*') deb so'ramang — u shunchaki ro'yxatda bormi degan savol bo'ladi.

Marshrutda tekshirish

Sanctum ikkita middleware beradi, lekin Laravel 11+ da ularni alias qilib ro'yxatdan o'tkazish kerak — 32-darsdagi kabi:

bootstrap/app.php $middleware->alias([ 'abilities' => \Laravel\Sanctum\Http\Middleware\CheckAbilities::class, 'ability' => \Laravel\Sanctum\Http\Middleware\CheckForAnyAbility::class, 'olchash' => \App\Http\Middleware\SoravniOlchash::class, // ... ]);
routes/api.php Route::post('/vakansiyalar', [VakansiyaController::class, 'store']) ->middleware('abilities:vakansiya:yozish');
abilities:a,b → HAMMA huquq bo'lishi kerak ability:a,b → BITTASI yetadi

Farqni o'lchadik — token faqat vakansiya:oqish huquqiga ega:

'abilities:vakansiya:oqish,vakansiya:yozish' → 403 (yozish yo'q) 'ability:vakansiya:oqish,vakansiya:yozish' → 200 (o'qish yetdi)

O'lchangan: faqat vakansiya:oqish huquqli token bilan POST →

403 {"message": "Invalid ability provided."}

🔑 Uch qatlam va ularning tartibi

Endi API'da uchta mustaqil to'siq bor. Ularni alohida-alohida sinab ko'rdik:

1) auth:sanctum token yo'q yoki noto'g'ri → 401 {"message": "Unauthenticated."} 2) abilities:... token bor, lekin huquqi yetmaydi → 403 {"message": "Invalid ability provided."} 3) policy (33/34-dars) huquq bor, lekin ROL mos emas → 403 {"message": "This action is unauthorized."}

Uchinchisini isbotlash uchun nomzodga qo'lda yozish huquqli token berdik — ya'ni ikkinchi to'siqdan o'tkazdik:

Vali roli: nomzod token: ['vakansiya:oqish', 'vakansiya:yozish'] ← huquq BOR POST /api/vakansiyalar → 403 {"message": "This action is unauthorized."} AccessDeniedHttpException

🔑 Ikkala 403 ham bir xil status, lekin xabari boshqa — va bu tashxis uchun muhim:

"Invalid ability provided." → TOKEN huquqi yetmaydi → yangi token kerak "This action is unauthorized." → ODAM huquqi yetmaydi → rol kerak
Nega ikkalasi ham kerak

Ular boshqa savollarga javob beradi:

abilities → «bu TOKEN nima qila oladi?» (qurilma darajasida) policy → «bu ODAM nima qila oladi?» (foydalanuvchi darajasida)

Ish beruvchining hisobot skripti o'g'irlansa, u o'qish tokeniga ega — policy ruxsat bersa ham, token yozishga yo'l bermaydi. Teskarisi: nomzodga qandaydir yo'l bilan yozish tokeni tegsa, policy to'sadi.

🔑 Bu 32-darsdagi «qatlamli himoya» fikrining API'dagi ko'rinishi: har qatlam o'zicha to'g'ri ishlashi kerak.

app/Http/Controllers/Api/TokenController.php public function ochir(Request $request): JsonResponse { $request->user()->currentAccessToken()->delete(); return response()->json(['xabar' => 'Token o\'chirildi.']); }
$request->user()->currentAccessToken()->delete(); // shu qurilma $request->user()->tokens()->delete(); // HAMMA qurilma

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

HasApiTokens traiti unutilishi

BadMethodCallException Call to undefined method App\Models\User::createToken()

install:api buni aytgan edi, lekin chiqishning oxirgi qatorida — va o'qilmasdan o'tib ketishi oson.

✅ use Laravel\Sanctum\HasApiTokens; import qiling va klass ichida use HasApiTokens, HasFactory, Notifiable;.

🔍 33-darsdagi AuthorizesRequests bilan bir xil naqsh: paket keladi, modelga siz ulaysiz.

HOLAT 2

Token bir marta ko'rsatiladi

$token->plainTextToken → faqat SHU javobda mavjud bazadagi qiymat → sha256 xeshi, tokenning O'ZI emas

Yo'qotsangiz qaytarib bo'lmaydi — serverda ham u yo'q. Bu kamchilik emas, xavfsizlik xususiyati.

✅ Mijoz tokenni xavfsiz saqlashi kerak: mobil ilovada keychain/keystore, serverda muhit o'zgaruvchisi. Kodga yozmang — git'ga tushib ketadi.

🔍 Yo'qolgan token muammo emas: yangisini oling, eskisini o'chiring.

HOLAT 3

Bearer so'zi unutilishi

Authorization: 2|zwa1Xr... ⚠️ → 401 Authorization: Bearer 2|zwa1Xr... ✅ → 200

Sarlavha ikki qismdan iborat: turi va qiymati. Bearer — «ko'taruvchi», ya'ni «bu tokenni ko'targan odam o'zini tanitgan hisoblanadi».

✅ Tashxis: 401 kelsa, birinchi navbatda sarlavhani to'liq chop eting. Ko'pincha muammo Bearer yoki ortiqcha probelda.

🔍 42-darsdagi Accept tuzog'i bilan birga: API'da sarlavhalar — eng ko'p vaqt yeydigan joy.

HOLAT 4

abilities middleware alias'siz

Route::middleware('abilities:vakansiya:yozish') Target class [abilities] does not exist.

Laravel 11+ da Sanctum middleware'lari avtomatik ro'yxatdan o'tmaydi.

✅ bootstrap/app.php dagi alias() ga qo'shing — 32-darsdagi olchash va til bilan bir qatorda.

🔍 Muqobil: to'liq klass nomini yozish (CheckAbilities::class.':vakansiya:yozish') — lekin o'qilishi yomon.

HOLAT 5

* huquqi va can('*')

createToken('nom') → abilities = ["*"] can('vakansiya:yozish') → true ← cheklov yo'q can('*') → false ← ⚠️ kutilmagan

* — «cheklov yo'q» degan maxsus belgi, oddiy huquq nomi emas. Uni can() ga bermang.

⚠️ Va diqqat: huquq ko'rsatilmasa token hamma narsani qila oladi. Ya'ni createToken('nom') — eng keng huquqli token.

✅ Har doim huquqlarni aniq yozing. «Keyin qo'sharman» degan token ko'pincha shundayligicha qolib ketadi.

HOLAT 6

401 va 403 ni ajratish

401 {"message": "Unauthenticated."} → token YO'Q yoki noto'g'ri 403 {"message": "Invalid ability provided."} → TOKEN huquqi yetmaydi 403 {"message": "This action is unauthorized."} → ODAM huquqi yetmaydi

Uchalasi ham «ruxsat yo'q» deydi, lekin yechimi boshqa:

401 → qayta kiring, yangi token oling 403 (ability) → kengroq huquqli token so'rang 403 (policy) → rolingiz mos emas — token yordam bermaydi

✅ Mijoz kodida shu uch holatni alohida ishlang: 401 da kirish oynasini ko'rsating, 403 da esa xabarni ko'rsating.

HOLAT 7

Auth qo'shilishi eski testlarni buzadi

Failed asserting that 401 is identical to 201.

Bu yaxshi holat: himoya qo'shdingiz va testlar buni darhol tasdiqladi. Agar ular yashil qolganda — himoya ishlamayotgan bo'lardi.

✅ Tuzatish: Sanctum::actingAs($user, [huquqlar]) qo'shing. ⚠️ Faqat ataylab ochiq qolishi kerak bo'lgan endpoint'larda testni o'zgartirmang.

🔑 Modul F'da bu naqsh uchinchi marta takrorlandi: data o'rami (43) · auth (44) · va har safar test mijoz nomidan e'tiroz bildirdi.

Sinab ko'ramiz

Natijani taxmin qiling

Dasturchi hisobot skripti uchun cheklangan token yasamoqchi. U huquqlarni «keyin qo'sharman» deb qoldirdi:

token yaratish
$token = $user->createToken('hisobot-skripti'); // keyin tekshirmoqchi bo'ldi: $token->accessToken->can('*'); // ? $token->accessToken->can('vakansiya:yozish'); // ?

Ikkala tekshiruv nima qaytaradi? Va bu token nima qila oladi?

Javobni ko'rish
bazada: abilities = ["*"] can('*') → false ⚠️ kutilmagan can('vakansiya:yozish') → true ⚠️ yanada kutilmagan

Ikkala natija ham dastlab g'alati ko'rinadi, lekin mantiq oddiy:

huquq KO'RSATILMASA → abilities = ["*"] → «cheklov yo'q» → can('istalgan-narsa') → har doim TRUE can('*') → «ro'yxatda '*' degan HUQUQ bormi?» degan savol → '*' huquq emas, maxsus belgi → FALSE

⚠️ Amaliy oqibat: dasturchi eng keng huquqli token yasadi — hisobot skripti uchun. U skript o'g'irlansa, hujumchi e'lon qo'sha, tahrirlay va o'chira oladi.

🔑 «Keyin qo'sharman» degan token ko'pincha shundayligicha qolib ketadi. Huquqni darhol yozing:

$user->createToken('hisobot-skripti', ['vakansiya:oqish']); ✅

Va tekshirishni ham to'g'ri yozing:

can('*') ⚠️ hech qachon to'g'ri ishlamaydi can('vakansiya:yozish') ✅ aniq huquqni so'rang

🔍 Ikkinchi saboq: abilities — token darajasidagi chegara, u policy'ning o'rnini bosmaydi. Ish beruvchining to'liq huquqli tokeni ham begona vakansiyani tahrirlay olmaydi — u yerda policy turadi (33-dars).

SAVOL 1 Token bazada qanday saqlanadi?

O'lchandi: ochiq token 2Mkb3Yc..., bazadagi qiymat esa 0aae20f0... — va hash('sha256', $ochiq) unga teng. 30-darsdagi parol naqshi. 🔑 Shuning uchun token bir marta ko'rsatiladi: yo'qotsangiz serverda ham u yo'q.

SAVOL 2 401 va 403 qachon qaytadi?

401 «kim ekaningni bilmayman» — {"message":"Unauthenticated."}. 403 «kimligingni bilaman, huquqing yo'q». 🔑 Va 403 ikki xil bo'ladi: Invalid ability provided. (token huquqi) va This action is unauthorized. (policy) — yechimlari ham boshqa.

SAVOL 3 createToken('nom') — huquq ko'rsatilmasa nima bo'ladi?

Huquq berilmasa abilities = ["*"] — «cheklov yo'q». Ya'ni bu eng keng huquqli token. ⚠️ Va can('*') baribir false qaytaradi, chunki * — huquq nomi emas, maxsus belgi. ✅ Huquqni darhol yozing.

Eslab ayting

Avval o'zingiz javob bering, keyin ochib tekshiring. Oxirgi ikkitasi — 43-darsni takrorlash.

Nega API'da sessiya emas, token ishlatiladi?

Sessiya cookiega tayanadi, cookie esa brauzerniki. Mobil ilova yoki boshqa server uchun bu ishlamaydi. Va api/* marshrutlari sessiya middleware'iga umuman tushmaydi.

Uchta 401/403 qatlami nima bilan farq qiladi?

401 — token yo'q yoki noto'g'ri. 403 «Invalid ability provided» — token huquqi yetmaydi (yangi token kerak). 403 «This action is unauthorized» — odamning roli mos emas (token yordam bermaydi).

abilities va ability farqi?

abilities:a,b — hamma huquq bo'lishi kerak. ability:a,b — bittasi yetadi. O'lchandi: faqat oqish huquqli token birinchisida 403, ikkinchisida 200 oldi.

↩︎ Takrorlash: whenLoaded nima qiladi?

Bog'lanish yuklanmagan bo'lsa kalitni javobdan butunlay olib tashlaydi (null emas) va so'rov yubormaydi — N+1 dan himoya.

↩︎ Takrorlash: data o'rami nimaga kerak?

Sahifalashda links va meta ga joy kerak. Shuning uchun withoutWrapping() sahifalashda ishlamaydi va API nomuvofiq bo'lib qoladi.
