paginate() API'da: uchta yuqori kalit

43-darsda data o'ramini ko'rgandik. Paginator bilan birga yana ikkitasi qo'shiladi. Mana to'liq javob (qisqartirilgan data bilan):

GET /api/vakansiyalar { "data": [ { "id": 1, "nom": "Backend dasturchi", ... }, ... ], "links": { "first": "http://127.0.0.1:8000/api/vakansiyalar?page=1", "last": "http://127.0.0.1:8000/api/vakansiyalar?page=2", "prev": null, "next": "http://127.0.0.1:8000/api/vakansiyalar?page=2" }, "meta": { "current_page": 1, "from": 1, "last_page": 2, "links": [ ... ], "path": "http://127.0.0.1:8000/api/vakansiyalar", "per_page": 5, "to": 5, "total": 7 } }

Uchta kalitning vazifasi aniq ajratilgan:

data → so'ralgan narsa links → qayerga borish mumkin (mijoz bosadigan havolalar) meta → qayerdasiz va jami qancha (mijoz ko'rsatadigan raqamlar)

Shu uchtasi bo'lgani uchun mobil ilova «7 tadan 1–5» deb yoza oladi va «Keyingi» tugmasiga links.next ni bog'lay oladi. meta bo'lmasa — jami sonni bilib bo'lmaydi.

🔍 Bu qayerdan keldi?

Siz hech narsa yozmadingiz. VakansiyaResource::collection() ichiga paginator tushsa, Laravel javobni avtomatik ResourceCollection ga o'raydi va links/meta ni o'zi qo'shadi.2 Oddiy get() bersangiz — faqat data bo'ladi. Ya'ni sahifalash JSON shaklini o'zgartiradi. Buni mijozga aytmasangiz, uning kodi buziladi.

Filtr: when() va uning tuzog'i

29-darsda shunday yozgandik:

29-darsdagi shakl
Vakansiya::query() ->when($request->input('q'), fn ($so_rov, $matn) => $so_rov->whereLike('nom', "%{$matn}%")) ->when($request->input('shahar'), fn ($so_rov, $shahar) => $so_rov->where('shahar', $shahar))

when($shart, $closure) — $shart rost bo'lsa closure ishlaydi, aks holda zanjir o'zgarmaydi. Shu bilan if larsiz shartli filtr yoziladi.

Endi bazaga bitta vakansiya qo'shamiz: «0 dan boshlovchi». Va uni qidiramiz:

GET /api/vakansiyalar?q=0 meta.total: 8 ⚠️ HAMMASI qaytdi kutilgan: 1 («0 dan boshlovchi»)

Filtr umuman qo'llanmadi. Xato ham chiqmadi. Sabab PHP'da:

$request->input('q') → "0" (satr) if ("0") → FALSE ← PHP'da "0" yolg'on when(FALSE, ...) → closure ISHLAMAYDI

PHP'da yolg'on hisoblanadigan qiymatlar: false, 0, "0", "", null, []. "0" shular orasida — va aynan shu qidiruvni buzdi.

⚠️ Bu xato 29-darsdan beri kodimizda edi

Web tomonda u ko'rinmadi, chunki hech kim 0 deb qidirmaydi. API'da esa mijoz — dastur. U foydalanuvchi yozgan har qanday satrni yuboradi: 0, false, bo'sh satr. Sizning xatoyingiz mijoz uchun «qidiruv ba'zan ishlamaydi» bo'lib ko'rinadi — va u buni hech qachon ayta olmaydi.

✅ Yechim — shartni qiymatdan ajratish:

to'g'ri shakl
->when($request->filled('q'), fn ($so_rov) => $so_rov->whereLike('nom', '%'.$request->input('q').'%')) ->when($request->filled('shahar'), fn ($so_rov) => $so_rov->where('shahar', $request->input('shahar')))

filled('q') — «q bor va bo'sh emas» degani. U qiymatni rostlik bo'yicha emas, mavjudlik bo'yicha tekshiradi. "0" uchun filled() rost qaytaradi.

?q=0 → filled: true → 1 ta topildi ✅ ?q=dasturchi → filled: true → 4 ta topildi ✅ ?q= → filled: false → filtr yo'q ✅ (q yo'q) → filled: false → filtr yo'q ✅

E'tibor bering: closure endi bir argumentli. Chunki when() closure'ga $shart ning o'zini uzatadi — endi u true, matn emas. Qiymatni $request dan olamiz.

🔍 ?q= nega null?

O'lchandi: ?q= yuborilsa $request->input('q') NULL qaytaradi, bo'sh satr emas. Buni Laravel'ning ConvertEmptyStringsToNull middleware'i qiladi — u har bir so'rovda bo'sh satrlarni null ga aylantiradi.3

Shuning uchun 'nullable' qoidasi bo'sh formalar bilan ishlaydi. Bu 30-darsdagi nullable ning ichki sababi.

Saralash: eng jimgina xato

Eng oddiy yechim shunday ko'rinadi:

❌ shunday YOZMANG
->orderBy($request->input('sort', 'id'))

Uchta so'rov yuboramiz va natijani o'lchaymiz:

?sort=maosh → 200 ✅ to'g'ri saralandi ?sort=moash → 200 ⚠️ SARALANMADI, lekin xato ham yo'q ?sort=kompaniyalar.nom → 500 ⚠️ mijoz ilovani yiqita oladi

Ikkinchi qator — darsning eng muhim joyi. Foydalanuvchi «maosh bo'yicha» tugmasini bosdi, mijoz ?sort=moash yubordi (dasturchi harf xato yozgan), server 200 OK qaytardi va ro'yxat tartibsiz keldi. Hech kim hech narsani sezmaydi.

Nega 500 emas, 200?

SQL'ga qaraymiz:

orderBy('moash') → order by "moash" asc

SQLite'da qo'shtirnoq ichidagi noma'lum nom xato emas — u satr deb qabul qilinadi. O'lchandi:

select "moash" as x → 'moash' ← satr! select "nom" as x from ... → 'Backend dasturchi' ← ustun

Ya'ni order by 'moash' — hamma qatorda bir xil qiymat. Saralash bo'sh ish bo'lib qoladi.4

⚠️ Bazani almashtirsangiz — xato paydo bo'ladi

MySQL va PostgreSQL bu kelishuvni qabul qilmaydi: ular yo'q ustun uchun xato beradi. Ya'ni bir xil kod SQLite'da 200, MySQL'da 500 qaytaradi.

🔑 Bu 22-darsdagi «SQLite tayyorlov uchun» degan gapning narxi: u sizni ba'zi xatolardan himoya qilmaydi, faqat yashiradi.

Bu SQL inyeksiyami? — Yo'q

Bu savol albatta tug'iladi, shuning uchun uni o'lchadik:

kiritilgan: maosh", (select password from users) -- hosil bo'lgan SQL: order by "maosh"", (select password from users) --" asc ↑↑ qo'shtirnoq IKKILANTIRILDI → bittalik nom bo'lib qoldi

orderBy() ustun nomini o'raydi va ichidagi qo'shtirnoqni ikkilantiradi. Demak qo'shimcha SQL ijro etilmaydi — bu inyeksiya emas.

Lekin xavf boshqa shaklda bor:

1) Jimgina noto'g'ri natija → 200, tartib yo'q (yuqorida) 2) Mijoz yiqitadigan 500 → "kompaniyalar.nom" nuqta bo'yicha bo'linadi va JOIN'siz ustun izlanadi 3) Yashirin ustun bo'yicha tartib → bazangizdagi HAR QANDAY ustun

Uchinchisi eng nozigi. Agar jadvalda ichki_ball yoki tekshiruv_izohi kabi ustun bo'lsa, mijoz uni ko'ra olmaydi (Resource yashirgan), lekin o'sha bo'yicha saralay oladi — va tartibdan qiymatni taxmin qilishi mumkin.

✅ Oq ro'yxat

Qoida oddiy: mijozning satri hech qachon to'g'ridan-to'g'ri ustun nomi bo'lmasin. U faqat kalit bo'lsin, ustunni siz tanlang:

app/Http/Controllers/Api/VakansiyaController.php
$tartib = [ 'nom' => ['nom', 'asc'], '-nom' => ['nom', 'desc'], 'maosh' => ['maosh', 'asc'], '-maosh' => ['maosh', 'desc'], 'yangi' => ['created_at', 'desc'], ][$malumot['sort'] ?? 'yangi']; // ... ->orderBy(...$tartib)

Endi sort — ustun nomi emas, sizning API'ingizning so'zi. Bazadagi ustunlarni o'zgartirsangiz ham mijozning kodi buzilmaydi — bu 43-darsdagi Resource g'oyasining aynan o'zi, faqat kirish tomonida.

-maosh shakli — REST olamidagi keng tarqalgan kelishuv: minus «teskari tartib» degani.5 ?sort=maosh&yonalish=desc deb ikkita parametr qilsangiz ham bo'ladi — muhimi, bittasini tanlab hujjatda yozish.

...$tartib — bu yoyish (spread): massiv ['maosh', 'desc'] ikkita argumentga aylanadi, ya'ni orderBy('maosh', 'desc').

Query parametr ham tekshiriladi

35-darsda tekshiruvni «o'z uyiga» — FormRequest ga ko'chirgandik. Query parametr ham ma'lumot — u ham tekshirilishi kerak. Va $request->validate() GET so'rovda ham xuddi shunday ishlaydi:

app/Http/Controllers/Api/VakansiyaController.php
$malumot = $request->validate([ 'q' => ['nullable', 'string', 'max:60'], 'shahar' => ['nullable', 'string', 'max:60'], 'faqat_faol' => ['nullable', 'boolean'], 'sort' => ['nullable', 'in:nom,-nom,maosh,-maosh,yangi'], 'per_page' => ['nullable', 'integer', 'min:1', 'max:50'], ]);

Endi noto'g'ri saralash 422 bilan qaytadi — jimgina noto'g'ri javob emas:

?sort=moash 422 { "message": "The selected sort is invalid.", "errors": { "sort": ["The selected sort is invalid."] } }

Bu mijoz uchun ancha yaxshi: xato dasturchining ekranida darrov ko'rinadi, foydalanuvchining ma'lumotida yashirinib qolmaydi.

per_page: nega chegara kerak

per_page ni mijozga berish qulay — mobil ilovaga 10 ta, veb panelga 50 ta kerak bo'lishi mumkin. Lekin chegarasiz:

?per_page=1000000 → bitta so'rov bilan butun jadval xotiraga o'qiladi → har bir yozuv uchun Resource ishlaydi → javob JSON o'nlab megabayt bo'ladi

Buni bir necha marta yuborish — bepul va oson. Shuning uchun max:50:

?per_page=3 → 200, meta.per_page: 3 ?per_page=9999 → 422, "The per page field must not be greater than 50."

✅ Umumiy qoida: mijoz boshqaradigan har bir raqamning yuqori chegarasi bo'lsin.

withQueryString() — API'da yanada muhim

29-darsda buni «filtrlab, 2-sahifaga o'tsangiz filtr yo'qoladi» deb ko'rgandik. API'da oqibati og'irroq. A/B o'lchov:

GET /api/vakansiyalar?shahar=Toshkent ❌ withQueryString() YO'Q: meta.total : 4 links.next : .../api/vakansiyalar?page=2 ← shahar YO'Q ✅ withQueryString() BOR: links.next : .../api/vakansiyalar?shahar=Toshkent&page=2

Endi mijozning ko'zi bilan qaraymiz. U links.next ni o'qimaydi — shunchaki ochadi. Birinchi javobda meta.total: 4 yozilgan edi, ikkinchi sahifada esa:

GET .../api/vakansiyalar?page=2 data : [DevOps muhandis (Samarqand), QA mutaxassis (Buxoro)] meta.total : 7 ⚠️ birinchi javobda 4 edi

Foydalanuvchi «Toshkent» filtri yoqilgan holda Samarqand va Buxoro vakansiyalarini ko'radi. Jami son ham o'zgarib ketadi. Va hech qayerda xato yo'q — status 200.

⚠️ Web'da bu bug, API'da bu shartnoma buzilishi

Web'da foydalanuvchi filtr tushib qolganini ko'radi va qaytadan bosadi. API'da mijoz-dastur hech narsani ko'rmaydi — u o'sha ma'lumotni to'g'ri deb foydalanuvchisiga chiqaradi.

🔑 Shuning uchun withQueryString() API'da tanlov emas.

Yakuniy index()

app/Http/Controllers/Api/VakansiyaController.php
public function index(Request $request) { $malumot = $request->validate([ 'q' => ['nullable', 'string', 'max:60'], 'shahar' => ['nullable', 'string', 'max:60'], 'faqat_faol' => ['nullable', 'boolean'], 'sort' => ['nullable', 'in:nom,-nom,maosh,-maosh,yangi'], 'per_page' => ['nullable', 'integer', 'min:1', 'max:50'], ]); $tartib = [ 'nom' => ['nom', 'asc'], '-nom' => ['nom', 'desc'], 'maosh' => ['maosh', 'asc'], '-maosh' => ['maosh', 'desc'], 'yangi' => ['created_at', 'desc'], ][$malumot['sort'] ?? 'yangi']; $vakansiyalar = Vakansiya::with('kompaniya') ->when($request->filled('q'), fn ($so_rov) => $so_rov->whereLike('nom', '%'.$request->input('q').'%')) ->when($request->filled('shahar'), fn ($so_rov) => $so_rov->where('shahar', $request->input('shahar'))) ->when($request->boolean('faqat_faol'), fn ($so_rov) => $so_rov->faol()) ->orderBy(...$tartib) ->paginate($request->integer('per_page', 10)) ->withQueryString(); return VakansiyaResource::collection($vakansiyalar); }

Zanjirni yuqoridan pastga o'qing — u gap kabi: kompaniyani birga yukla, agar qidiruv bo'lsa qidir, agar shahar bo'lsa filtrla, agar faqat faol so'ralsa scope'ni qo'sh, saralab ber, sahifala, filtrni havolalarga ko'chir.

🔍 faol() — 29-darsdagi scope

->faol() — modeldagi #[Scope] metodi. Uni bitta qator ham o'zgartirmadik: web'da ham, API'da ham bir xil ishlaydi.

🔑 Nima uchun bu muhim: agar ertaga «faol» ta'rifi o'zgarsa (masalan «faol va muddati o'tmagan»), siz uni bitta joyda tuzatasiz — web ham, API ham darrov to'g'ri bo'ladi. Shart controllerlarga tarqalib ketganda bunday bo'lmaydi.

Har xil holatlar

Yetti holat. Bu bo'lim ma'lumotnoma — hozir bir marta o'qib chiqing, keyin kerak bo'lganda qaytib qarang.

HOLAT 1

Hech narsa topilmadi

?q=yolgonsoz status : 200 ← 404 EMAS data : [] meta.total : 0 meta.from : null links.next : null

«Topilmadi» — xato emas. So'rov to'g'ri bajarildi, javob esa bo'sh to'plam. 42-darsdagi qoida: 404 — resurs yo'q, ro'yxat esa bor, u shunchaki bo'sh.

⚠️ meta.from va meta.to bunday holatda null bo'ladi. Mijoz «from–to dan total» deb yozsa, ekranda null–null chiqadi. Buni hujjatda aytib qo'ying.

HOLAT 2

Filtr qo'shildi — N+1 qaytib keldi

with('kompaniya') BOR → 3 so'rov 1) select count(*) from "vakansiyalar" 2) select * from "vakansiyalar" limit 2 offset 0 3) select * from "kompaniyalar" where id in (1) with('kompaniya') YO'Q → 4 so'rov (sahifada 2 ta yozuv uchun) 3) select * from "kompaniyalar" where id = ? limit 1 4) select * from "kompaniyalar" where id = ? limit 1

Filtrlarni qo'shayotganda zanjirni qayta yozish oson — va with() tushib qolishi ham oson. Sahifada 50 ta yozuv bo'lsa, 3 emas 52 so'rov bo'ladi.

✅ 29-darsdagi Model::preventLazyLoading() buni testda xatoga aylantiradi.

HOLAT 3

Katta-kichik harf

?q=backend → 1 ta «Backend dasturchi» ?q=BACKEND → 1 ta «Backend dasturchi» ?q=bAcKeNd → 1 ta «Backend dasturchi»

whereLike() standart holda katta-kichik harfga sezgir emas — qidiruv uchun aynan shu kerak.

⚠️ Lekin bu bazaga bog'liq: PostgreSQL'da LIKE sezgir. Laravel'ning whereLike() uchinchi argument sifatida caseSensitive ni oladi — sezgirlik kerak bo'lsa aniq yozing, taxmin qilmang.

HOLAT 4

meta.links ichida HTML

"meta": { "links": [ { "url": null, "label": "&laquo; Previous", "page": null, "active": false }, { "url": ".../?page=1", "label": "1", "page": 1, "active": true }, ... ] }

Bu massiv Blade sahifalash tugmalari uchun yasalgan — shuning uchun label ichida HTML mohiyati (&laquo;) turibdi. JSON API uchun bu g'alati: mobil ilova buni ekranda «&laquo; Previous» deb ko'rsatib qo'yishi mumkin.

✅ Mijozga links.prev / links.next va meta.current_page / meta.last_page ni ishlatishni ayting — meta.links ni emas.

HOLAT 5

paginate va simplePaginate

paginate(2) → 3 so'rov (COUNT bor) meta: current_page, from, last_page, links, path, per_page, to, TOTAL simplePaginate(2) → 2 so'rov (limit 3 hiylasi — bittasini ortiq oladi) meta: current_page, current_page_url, from, path, per_page, to links.last: null ⚠️ total va last_page YO'Q

Farq bitta COUNT so'rovi. Katta jadvalda COUNT qimmat bo'lishi mumkin.

⚠️ Lekin narxi bor: mijoz «40 tadan 5» deb yoza olmaydi va sahifa raqamlarini ko'rsata olmaydi — faqat «Keyingi». Tanlov mijozning ekraniga bog'liq.

HOLAT 6

Mavjud bo'lmagan sahifa

?page=999 → 200 data: [] meta.current_page: 999 meta.last_page: 1

Laravel oxirgi sahifaga qaytarmaydi va xato ham bermaydi — bo'sh ro'yxat beradi.

✅ Mijoz uchun tekshiruv oddiy: meta.current_page > meta.last_page bo'lsa, «bunday sahifa yo'q» deb ko'rsating.

HOLAT 7

Chuqur sahifa sekin bo'ladi

?page=2 → limit 10 offset 10 tez ?page=50000 → limit 10 offset 499990 ⚠️ sekin

OFFSET — baza 499990 qatorni o'qib, tashlab yuborishi kerak degani. Yozuv soni o'sgan sari sekinlashadi.

🔍 Sanoat yechimi — kursor bilan sahifalash: cursorPaginate(). U offset o'rniga «oxirgi ko'rilgan yozuvdan keyin» deydi. Buni hozir kiritmaymiz — bilib qo'yish yetarli, chunki u page o'rniga cursor beradi va sakrab sahifaga o'tishga imkon bermaydi.

💻 Quyida amaliyot bor. Hozir o'qish rejimidasiz — kompyuter yoningizda bo'lganda 💻 Amaliyot rejimiga o'ting va shu bo'limdan davom eting.

Sinab ko'ramiz

Natijani taxmin qiling

Mobil ilova dasturchisi shikoyat qildi: «ro'yxat sahifasida jami son o'zgarib turadi». U shunday ketma-ketlikni ko'rsatdi:

Serverda esa hech qanday xato yo'q — ikkala so'rov ham 200. Nima bo'ldi va nima uchun buni testlar tutmagan?

Javobni ko'rish

paginate() dan keyin withQueryString() yo'q. Shuning uchun havolalar faqat page ni saqlaydi:

links.next → .../api/vakansiyalar?page=2 ← shahar YO'Q

⚠️ Mijoz o'sha havolani ochadi — va endi filtrsiz so'rov yuborgan bo'ladi. Shuning uchun total 4 dan 7 ga «o'zgardi»: bular ikki xil so'rov edi.

Foydalanuvchi buni yanada g'alati ko'radi: «Toshkent» filtri yoqilgan holda ikkinchi sahifada Samarqand vakansiyalari chiqadi.

🔑 Nega testlar tutmadi? Chunki odatdagi filtr testi birinchi sahifani tekshiradi:

$this->getJson('/api/vakansiyalar?shahar=Toshkent') ->assertJsonPath('meta.total', 1); ← YASHIL, muammo ko'rinmaydi

Muammo havolada, ma'lumotda emas. Shuning uchun alohida test kerak:

expect($javob->json('links.next'))->toContain('shahar=Toshkent');

✅ Yechim bitta qator:

->paginate($request->integer('per_page', 10)) ->withQueryString();

🔍 Umumiy saboq: API'da javobning ma'lumoti to'g'ri bo'lishi yetarli emas — havolalari ham to'g'ri bo'lishi kerak. Mijoz ularni o'qimaydi, ochadi.

SAVOL 1 ?q=0 yuborilsa, when($request->input('q'), ...) nima qiladi?

PHP'da "0" — yolg'on qiymat, shuning uchun when() closure'ni umuman ishlatmaydi. ⚠️ Xato chiqmaydi, status 200 — faqat javob noto'g'ri. ✅ Yechim: $request->filled('q'), u mavjudlikni tekshiradi.

SAVOL 2 Nima uchun sort ni to'g'ridan-to'g'ri orderBy ga berish yaramaydi?

Inyeksiya emas — o'lchandi: orderBy qo'shtirnoqni ikkilantiradi. Xavf boshqa: harf xatosi jimgina 200 beradi (SQLite'da), nuqtali nom 500 beradi, va mijoz Resource yashirgan ustun bo'yicha ham saralay oladi. ✅ Kalitdan ustunga o'zingiz o'giring.

SAVOL 3 withQueryString() nima beradi?

U links.first/last/prev/next ichiga joriy query parametrlarni ko'chiradi. ⚠️ Bo'lmasa mijoz links.next ni ochib filtrsiz ma'lumot oladi — va buni sezmaydi, chunki status 200. 🔑 API'da bu tanlov emas.

Eslab ayting

Javobni ovoz chiqarib ayting, keyin ochib solishtiring.

Sahifalangan javobdagi uchta yuqori kalit qaysilar va har biri nima uchun?
data — so'ralgan narsa. links — mijoz ochadigan havolalar (first, last, prev, next). meta — mijoz ko'rsatadigan raqamlar (current_page, last_page, per_page, from, to, total).
?q=0 nega qidiruvni buzadi va yechimi nima?
PHP'da "0" yolg'on qiymat, shuning uchun when($request->input('q'), ...) closure'ni umuman ishlatmaydi — filtr yo'qoladi, status esa 200. Yechim: shartni $request->filled('q') qilish va qiymatni closure ichida olish.
?sort=moash (harf xato) SQLite'da nega 500 emas, 200 qaytaradi?
SQLite qo'shtirnoq ichidagi noma'lum nomni satr deb qabul qiladi: order by "moash" — hamma qatorda bir xil qiymat, ya'ni saralash bo'sh ish. MySQL va PostgreSQL bunda xato beradi. Shuning uchun SQLite bu xatoni yashiradi.
Oq ro'yxat naqshi nima va nega u Resource g'oyasiga o'xshaydi?
Mijozning satri ustun nomi emas, kalit bo'ladi; kalitdan ustun va yo'nalishga o'girishni siz qilasiz. Resource javobda bazani yashirgani kabi, oq ro'yxat kirishda bazani yashiradi — ustun nomlarini o'zgartirsangiz mijozning kodi buzilmaydi.
paginate va simplePaginate farqi nimada — so'rovda ham, javobda ham?
So'rovda: 3 va 2 (simplePaginate da COUNT yo'q, o'rniga limit bittaga ortiq olinadi). Javobda: simplePaginate da meta.total, meta.last_page va links.last yo'q — mijoz «40 tadan 5» deb yoza olmaydi.
Xulosa
  • Query parametr — resursning qaysi qismini so'rayotganingiz. Manzil resursni ko'rsatadi, query esa savolni.
  • Sahifalangan javob uchta kalitli: data · links · meta. Ularni paginate() ning o'zi qo'shadi.
  • ⚠️ when($request->input('q'), ...) — ?q=0 da jimgina buziladi. Shart uchun filled() ishlating.
  • ⚠️ orderBy($request->input('sort')) — harf xatosi 200 beradi (SQLite), nuqtali nom 500 beradi. Oq ro'yxat — yagona to'g'ri yechim.
  • Bu inyeksiya emas: orderBy qo'shtirnoqni ikkilantiradi. Xavf — noto'g'ri natija va yashirin ustun bo'yicha tartib.
  • Query parametr ham tekshiriladi: in: ro'yxati va per_page uchun max:.
  • Mijoz boshqaradigan har bir raqamning yuqori chegarasi bo'lsin.
  • ⚠️ withQueryString() — API'da tanlov emas. Mijoz links.next ni ochadi, o'qimaydi.
  • Scope (faol()) web va API'da bir xil ishlaydi — shart bitta joyda turadi.
  • Filtr qo'shganda with() tushib qolmasin — N+1 shu yerda qaytadi.
  • «Topilmadi» — 200 va bo'sh data, 404 emas.
🌱 Keyingi dars

API endi haqiqiy: to'liq CRUD, himoya, boshqariladigan javob, filtr va saralash. Lekin bugun ikki marta 500 ko'rdik — ?sort=kompaniyalar.nom va binding buzilgan update.

500 — mijoz uchun eng yomon javob: unda na sabab bor, na nima qilish kerakligi. Yomoni shundaki, APP_DEBUG=true bo'lsa u butun stack trace'ni qaytaradi — fayl yo'llari bilan birga.

47-darsda xatolarni to'g'ri qaytarish bilan shug'ullanamiz: ModelNotFound qayerda 404 ga aylanadi, 403 va 422 javoblarining shaklini qanday bir xil qilamiz, va kutilmagan xato mijozga nima ko'rsatishi kerak.
